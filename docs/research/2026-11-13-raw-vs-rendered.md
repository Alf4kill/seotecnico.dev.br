## 1. What the sources say

### 1.1 Three phases, and the rendered HTML is what Google indexes **[documented]** — G1

Google crawls, renders and indexes. Every page that answers 200 goes to the
render queue, unless a robots meta tag or header says not to index it. The
page "may stay on this queue for a few seconds", and it can take longer;
no ceiling is published. After rendering, Google "also uses the rendered
HTML to index the page". A page that answers non-200 may skip rendering.

**[inference]** For Google, the rendered DOM is the version that counts,
and the raw HTML is what decides whether rendering happens at all (status,
`noindex`).

### 1.2 Field by field **[documented]** — G1, G3, G4

| Field | What the documentation says |
|---|---|
| `noindex` | In the raw HTML it stops the page before rendering; removing it with JavaScript may not work, because Google may skip rendering when it sees it |
| canonical | JavaScript can set it, but should not change it; if it must, set the same value as the raw HTML |
| title, description | JavaScript can set or change both |
| structured data | JSON-LD generated by JavaScript works if it is in the rendered DOM; test it (G1, G3). For Product markup, dynamically generated markup "can make Shopping crawls less frequent and less reliable" (G3) |
| links | Google finds links only in `<a>` elements with `href` |
| lazy images and content | load everything relevant when it is visible in the viewport; Google Search does not interact with the page (G4) |
| client routing and errors | in an app with client-side routing, avoid soft 404s by redirecting to a URL that answers 404 or adding `noindex` with JavaScript |

### 1.3 Other bots, and what Google recommends **[documented]** — G1, G2

G1 notes that "not all bots can run JavaScript" and calls server-side or
pre-rendering "still a great idea" for users and crawlers. G2 calls dynamic
rendering (one version for bots, another for people) a workaround, not a
recommended solution, and points to server-side rendering, static rendering
or hydration instead.

### 1.4 The AI assistants this site measured **[observation, published]** — L1

In this site's controlled rounds, ChatGPT, Claude and Gemini read only the
HTML the server sent; Grok and DeepSeek ran the page's JavaScript (58
rounds, `quais-ias-executam-javascript`). Those are fetches made when a
person asks the assistant to read a URL, not a crawl.

### 1.5 What Google's own tool shows **[documented]** — G5, G6, L2

G5 lists, under "View crawled page" and "View tested page", "the raw HTML
returned", the headers, console output and resources, and the screenshot
only in the live test. Elsewhere on the same page it tells the reader to
check that a video is "in the rendered HTML" with the same tool. The page
does not say plainly which of the two the HTML tab shows. G6 settles it:
the Rich Results Test and URL Inspection show the "rendered DOM", and G6
tells the reader to use either to check that the rendered HTML has the
content expected. So `javascript-seo-google-vs-ia` ("Como conferir", step 5)
is right that the live test shows the HTML Google rendered; no change
(owner asked for the check, 2026-11-13).

L2 found a second reason not to treat the tool as the crawler: on Next.js
16, `notFound()` called only in `generateMetadata` answers 200 to a browser,
Googlebot and curl, and 404 to Google-InspectionTool.

## 3. Observations — the run of 2026-11-13 **[observation]**

**Script:** `scripts/raw-vs-rendered.mjs`. Real targets in the gitignored
`audits/case-studies/raw-vs-rendered.local.json`; the shape is
`raw-vs-rendered.example.json`. Output:
`audits/case-studies/raw-vs-rendered-2026-11-13/summary.json` (codes, page
kinds, words to the nearest 10, raw size in KB); `raw.json` stays local.

**How it measures.** Per page: the raw HTML by GET with `node:https`
(declared user agent `seotecnico-render-compare/1.0`, robots.txt read
first, 1.5 s between requests); the signals of that HTML extracted in a
Chromium with JavaScript off and every subresource aborted; then the same
URL in a Chromium with JavaScript, a phone viewport (Playwright "Pixel 7"),
`load` plus 5 s, and the same extraction on the DOM. The same function
reads both sides. "Head" = title, meta description, canonical, meta
robots, `lang`, H1 text and the set of JSON-LD `@type`s. Requests to
analytics and ad hosts are aborted in the render, so the visit does not
reach the sites' metrics; anything only such a script would inject (JSON-LD
through a tag manager, for example) would not show.

**Sample.** Home plus the main templates of each site, taken from its
sitemap (S2–S4) or its HTML site map (S1, whose XML sitemap is empty), two
pages per template where there were two: 8, 8, 8 and 7 pages. The two
client-rendered satellites: 4 routes of S1's sibling site, the home of S3's
app subdomain. Control: 6 pages of this site. 49 pages in all.

**A correction during the run.** The first run (same day, started 22:26 UTC)
counted images and links inside `<noscript>` on the raw side: with
JavaScript off, the parser turns a `<noscript>` into elements. That made
S3's posts look as if JavaScript removed images. The extractor now ignores
`<noscript>` descendants on both sides and reports their images apart; the
summary is the second run (started 2026-11-13T22:35Z).

### 3.1 Head: same on every server-rendered page

| Target | Stack (as far as the HTML shows) | Head equal |
|---|---|---|
| SITE (control) | Next.js, static | 6 of 6 |
| S1 main site | server-rendered PHP | 8 of 8 |
| S2 | WordPress with a page builder | 8 of 8 |
| S3 main site | WordPress | 8 of 8 |
| S4 | Next.js, blog from a headless WordPress | 7 of 7 |
| S1 sibling site | client-rendered SPA | 0 of 4 |
| S3 app subdomain | client-rendered SPA | 0 of 1 |

On 37 of 37 server-rendered pages, the seven head fields matched. On the
5 satellite pages, the field that differed was the H1, which exists only
after JavaScript; title, description, canonical, robots and `lang` were the
same on both sides, because the shell sets them once for every route.

### 3.2 What JavaScript did change on server-rendered pages

| Change | Where | Size |
|---|---|---|
| A carousel clones cards | S2 home and listings | home about 2,250 → 3,040 words; listings about +330 |
| The same carousel removes links from the DOM | S2 home | 25 of 98 internal links only in the raw HTML |
| Images move from a placeholder to the real file | S2, every template | home 4 → 111 images with a real `src`; the real file was in `data-src` in the raw HTML, with no `<noscript>` fallback |
| A cookie banner adds text and one link | S3, every page | about +40 words, +1 internal link |
| A script builds the list of links | S4, one standalone page outside the main stack | 1 → 11 internal links, about 190 → 630 words |
| Small additions (widgets, images) | S4 | about +50 words and +4 images per page |
| Nothing | S1 main site, SITE | words, links and images identical; SITE +1 word on articles |

H2 counts and JSON-LD block counts matched on all 37 pages.

**API calls are not content.** This site's pages made 9 to 25 same-origin
fetches after load: Next.js prefetching the payloads of linked routes. S4
made 9 to 12. Neither changed the page. A count of XHR/fetch requests says
nothing without the DOM comparison.

### 3.3 The client-rendered satellites

- Raw HTML of about 3 KB on every route, with no text in the body.
- S1's sibling site: the same title on all 4 routes, `lang="en"` on a
  Portuguese site, no canonical. After JavaScript, each route has its own
  H1 (4 distinct) and 20 to 720 words, with 0 to 27 images.
- S3's app subdomain: no description, no H1 in the raw HTML; about 50 words
  after JavaScript. Its robots.txt answered 406, which RFC 9309 treats as
  no restriction.

**[inference]** For Google, which renders (G1), the satellites have
content, but every route shares one title and the S1 one declares the
wrong language. For a reader that does not run JavaScript, such as three of
the five assistants in L1, each route is an empty page with a title.
