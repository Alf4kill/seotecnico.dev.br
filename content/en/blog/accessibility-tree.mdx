The accessibility tree is the version of a page the browser builds for
assistive technology: every relevant element becomes a node with a role (link,
button, region), an accessible name and a state. Some of the AI agents that
browse read that tree instead of an image of the screen. Playwright MCP hands
the model an accessibility snapshot, and Chrome DevTools MCP has a snapshot
tool "based on the a11y tree". For those agents, a control with no name, or
with a name different from the text on screen, is a control that cannot be
found by what is written on it. That is what an axe-core audit found on this
site, in the header of every page.

This article shows this site's tree before and after the fixes, with the
script that captured it, and separates what was measured from what is
mechanism. No agent success rate was measured here.

## What the tree is, in an example from this site

The browser reads the DOM, drops what is only layout and builds a tree of what
matters to someone who cannot see the screen. This is the brand link in the
header, as Playwright describes it after the fix:

```yaml
- link "SEO Técnico .DEV.BR — home":
  - /url: /en
```

A role (`link`), a name in quotes and the destination. Two `span` elements with
font and colour classes, and a third one hidden on screen, became one line.
That line is what an agent such as Playwright MCP receives, with a reference
next to it (`[ref=e5]`, for example) that it uses to click.

Note that the screen shows "SEO TÉCNICO", in capitals, and the tree keeps
"SEO Técnico". The capitals come from CSS (`text-transform`), and the tree
carries the HTML text. An agent that reads pixels and one that reads the tree
get the same brand spelled two ways.

## Who reads the tree and who reads the screen

| Agent | What it gets from the page | How it points at an element |
|---|---|---|
| Playwright MCP | Accessibility snapshot, "instead of screenshots" | Node reference (`ref`) |
| Chrome DevTools MCP | Text snapshot "based on the a11y tree" | Node identifier (`uid`) |
| Computer use (Anthropic) | Screenshot | Pixel coordinates |

The three descriptions come from each one's documentation, read on
2026-10-23. A site does not choose which of them visits it, and one agent can
combine both modes. That is why this article's argument is conditional: **if**
the agent reads the tree, **then** what is in it is what the agent has.

## What the audit found

The suite runs axe-core with Playwright on every sitemap route, in both
themes, with the WCAG 2.0 and 2.1 rules, levels A and AA. That is 148 audits.
On the code that was in production, it found 266 nodes with a violation, all
of *serious* impact:

| axe rule | Nodes | What it is |
|---|---|---|
| `label-content-name-mismatch` | 224 | Accessible name that does not contain the visible text (WCAG 2.5.3) |
| `scrollable-region-focusable` | 16 | Table or code block that scrolls but cannot receive keyboard focus |
| `color-contrast` | 14 | Text below the minimum contrast |
| `listitem` | 8 | List item with no list around it, in the tree |
| `link-in-text-block` | 4 | Link told apart from the text by colour alone |

The first 224 are one component repeated: the brand link, on every page, in
both themes. Contrast does not change the tree, and keyboard focus changes
little for anyone not using a keyboard. Two findings change what an agent
finds, and those are the two I measured.

## Before and after: the brand link

The link had an `aria-label` reading "SEO Técnico — home". An `aria-label`
replaces the element's content as the accessible name, so the name did not
contain ".DEV.BR", which is on screen. The fix removed the `aria-label` and
added a hint for screen readers only.

To measure the "before" without reverting the code, the script opens the
served page, snapshots the tree, puts the `aria-label` back and removes the
hint in the DOM itself, which is the fix's diff applied backwards, and
snapshots again:

```yaml
# before (aria-label restored)
- link "SEO Técnico — home":
  - /url: /en
  - text: SEO Técnico .DEV.BR

# after (served page)
- link "SEO Técnico .DEV.BR — home":
  - /url: /en
```

Both names describe the link. An agent reading the whole tree would, before,
have seen the name and the text. The difference shows when someone looks for
the link by what is written on it, which is how an agent receives an
instruction from a human ("click SEO Técnico .DEV.BR") and how a voice-control
user speaks:

| Search by role + visible text | Before | After |
|---|---|---|
| `getByRole('link', { name: 'SEO Técnico .DEV.BR' })` on `/en` | 0 links | 1 link |
| The same search on `/` (Portuguese home) | 0 links | 1 link |

Playwright matches the name as a substring, ignoring case. Before,
"SEO Técnico .DEV.BR" was not a substring of "SEO Técnico — home", and the
search found nothing. WCAG 2.5.3 (Label in Name, level A) asks for exactly
this: the name must contain the visible text, preferably at the start.

The header's search button had the same defect in Portuguese: it showed
"buscar…" and was named "Abrir busca". The English one already matched.

## Before and after: the JSON-LD generator's output

In the [JSON-LD generator](/en/tools/json-ld-generator), the result appears in
a `<pre>` after clicking "Generate JSON-LD". A `<pre>` has no role of its own in the
tree. The generated code was there as text, but with no named node saying
"this is the result". The component test found it, looking for the result the
way a screen reader would:

```ts
screen.getByRole('region', { name: /resultado/i })
```

It found nothing. The fix gave the `<pre>` a region role, a name and focus:

```yaml
# after, with the form filled in and "Gerar" clicked (Portuguese page)
- region "Resultado (JSON-LD)":
  - code: "{ \"@context\": \"https://schema.org\", \"@type\": \"Article\", ... }"
```

With the three attributes removed again in the DOM, the same search by role
and name finds 0 regions. An agent told "copy the generated JSON-LD" has,
after the fix, a node named "Result" to read. Before, it had one block of text
among others.

The same component had `role="alert"` on the error `<ul>`. The alert role on
the list itself erases the list role, and each `<li>` is left orphaned in the
tree: that is the `listitem` row of the table. The alert moved to a wrapper
around the list.

## What this changes, and what it does not

What can be stated from what was measured:

- **Measured:** the tree of the brand link and of the generator's output,
  before and after; the search by visible text, from 0 to 1; the axe
  violations, from 266 nodes to 4, all contrast warnings on decorative text
  kept on purpose.
- **Mechanism:** an agent that reads the tree only has what is in it. A name
  that does not contain the visible text breaks a search by the visible text;
  an element with no role and no name cannot be found by role and name.
- **Not measured:** whether any real agent failed or succeeded more because of
  this. No agent was tested against the "before" and the "after", and an
  agent that works from screenshots sees no difference at all in these fixes.

In another experiment, this site measures [which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript) when they fetch a
page. That is about what arrives in the HTML. The accessibility tree is the
next step: what an agent with a browser can point at once the page has
rendered.

None of this touches search SEO directly. Googlebot reads the HTML and the
text. The same day's crawler audit is in the
[Screaming Frog free version case](/en/blog/screaming-frog-free-version), and
neither report saw what the other saw.

## In Next.js: the name comes from the visible text

In the [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) the
App Router is the reference implementation, and both fixes are plain JSX. In
the brand link, the name comes from the content, with a hint hidden on
screen:

```tsx
// src/components/layout/Header.tsx
<Link href={copy.home} className="flex shrink-0 items-baseline gap-2.5" title={copy.homeLabel}>
  {/* No aria-label: the accessible name comes from the visible text plus
      this hint (WCAG 2.5.3). */}
  <span className="font-display ... uppercase ...">SEO Técnico</span>
  <span className="font-mono ...">.DEV.BR</span>
  <span className="sr-only"> — {copy.homeHint}</span>
</Link>
```

In the generator's output, role, name and focus go on the `<pre>` itself,
which scrolls horizontally and has to be reachable by keyboard:

```tsx
// src/components/tools/JsonLdGenerator.tsx
<pre
  role="region"
  aria-label={`${copy.result} (${tab === 'json' ? 'JSON-LD' : copy.nextComponent})`}
  tabIndex={0}
  className="theme-dark-island mt-4 overflow-x-auto ..."
>
```

And the script that snapshots the tree before and after, to repeat the
measurement on another site:

```js
// audits/scripts/aria-snapshot.mjs (excerpt)
const brand = page.locator('header a').first()
console.log(await brand.ariaSnapshot())
await brand.evaluate((a, l) => {
  a.setAttribute('aria-label', l)
  a.querySelector('.sr-only')?.remove()
}, 'SEO Técnico — home')
console.log(await brand.ariaSnapshot())
```

`ariaSnapshot()` returns the same YAML that Playwright MCP hands to the
model, without the references. You do not need an MCP server to see what it
would see.
