An accessibility tree is the version of a web page that the browser builds
for assistive technology. Each element that matters becomes a node with a
role (link, button, region), an accessible name, and a state. Some AI agents
that browse the web read this tree instead of the screen image. Playwright
MCP hands the model an accessibility snapshot, and Chrome DevTools MCP has a
snapshot tool that its docs describe as "based on the a11y tree". For those
agents, a control with no name, or with a name that differs from its
on-screen text, can't be found by the words written on it. An axe-core audit
found exactly that in the header of every page on this site.

Below, you'll see the site's tree before and after the fixes, and the script
that captured it. I keep what I measured separate from what follows from the
mechanism. I didn't measure any agent's success rate.

## What the tree looks like, with an example from this site

A browser reads the DOM, drops whatever exists only for layout, and builds a
tree of what matters to someone who can't see the screen. Here's the brand
link in this site's header, as Playwright describes it after the fix:

```yaml
- link "SEO Técnico .DEV.BR — home":
  - /url: /en
```

Read it as a role (`link`), a name in quotes, and a destination. In the HTML,
two `span` elements with font and color classes, plus a third one that's
visually hidden, collapse into that single line. An agent like Playwright MCP
receives exactly this line, plus a reference (`[ref=e5]`, for example) that
the agent uses to click.

Look at the casing, too. On screen, the brand reads "SEO TÉCNICO" in capitals,
while the tree holds "SEO Técnico" as it's written in the HTML. CSS applies
the capitals (`text-transform`), and the tree carries the HTML text. So an
agent that reads pixels and one that reads the tree get the same brand written
two ways.

## Which agents read the tree and which read the screen

Here's what three agents get from a page and how each one targets an element:

| Agent | What it gets from the page | How it targets an element |
|---|---|---|
| Playwright MCP | An accessibility snapshot, "instead of screenshots" | A node reference (`ref`) |
| Chrome DevTools MCP | A text snapshot "based on the a11y tree" | A node identifier (`uid`) |
| Computer use (Anthropic) | A screenshot | Pixel coordinates |

All three descriptions come from each agent's own documentation, which I read on
October 23, 2026. A site doesn't get to choose which of them visits it, and
one agent can combine both modes. So this article makes a conditional argument.
**If** an agent reads the tree, **then** what's in the tree is all it has.

## What the audit found

My test suite runs axe-core with Playwright on every route in the sitemap, in
both the dark and light themes, against WCAG 2.0 and 2.1 rules at levels A
and AA. That's 148 audits in total. When I ran them against the code that was
in production at the time, they found 266 nodes with violations, all of them
with *serious* impact:

| axe rule | Nodes | What it is |
|---|---|---|
| `label-content-name-mismatch` | 224 | Accessible name doesn't contain the visible text (WCAG 2.5.3) |
| `scrollable-region-focusable` | 16 | Table or code block that scrolls but can't receive keyboard focus |
| `color-contrast` | 14 | Text below the minimum contrast |
| `listitem` | 8 | List item with no list around it in the tree |
| `link-in-text-block` | 4 | Link that only its color sets apart from the text around it |

All 224 mismatches come from one component, the brand link, repeated on every
page in both themes. Contrast doesn't change the tree, and keyboard focus
changes little for anyone who isn't using a keyboard. Two findings do change
what an agent can find, and I measured those two.

## Before and after: the brand link

Before the fix, the brand link carried an `aria-label` of
"SEO Técnico — home". An `aria-label` replaces the element's content as its
accessible name, so the name left out ".DEV.BR", even though that text is on
screen. To fix it, I removed the `aria-label` and added a hint that only
screen readers get.

To capture the "before" state without reverting any code, a script opens the
live page and snapshots the tree. It then reverses the fix's diff in the DOM
itself, putting the `aria-label` back and removing the hint, and snapshots the
tree again:

```yaml
# before (aria-label restored)
- link "SEO Técnico — home":
  - /url: /en
  - text: SEO Técnico .DEV.BR

# after (served page)
- link "SEO Técnico .DEV.BR — home":
  - /url: /en
```

Both names describe the link, and before the fix, an agent reading the whole
tree would have seen both the name and the text. The difference shows up when
you look for the link by the words written on it. That's how a person phrases
an instruction to an agent ("click SEO Técnico .DEV.BR"), and it's what
someone using voice control says.

| Search by role + visible text | Before | After |
|---|---|---|
| `getByRole('link', { name: 'SEO Técnico .DEV.BR' })` on `/en` | 0 links | 1 link |
| The same search on `/` (Portuguese home) | 0 links | 1 link |

Playwright matches the name as a case-insensitive substring. Before the fix,
"SEO Técnico .DEV.BR" wasn't a substring of "SEO Técnico — home", so the
search found nothing. WCAG 2.5.3 (Label in Name, level A) covers exactly this
case. A control's name must contain its visible text, preferably at the start.

In the Portuguese interface, the header's search button had the same problem.
It showed "buscar…" ("search…") but was named "Abrir busca" ("Open search").
Its Portuguese name is now "Buscar no site" ("Search the site"). In English,
the button's name already matched its visible text.

## Before and after: the JSON-LD generator's output

When you click "Generate JSON-LD" in the
[JSON-LD generator](/en/tools/json-ld-generator), the result goes into a
`<pre>`, which has no role of its own in the tree. So the generated code was
there as text, but no named node marked it as the result.

A component test caught this. It looked for the result the way a screen
reader would:

```ts
screen.getByRole('region', { name: /resultado/i })
```

It came up empty. To fix it, I gave the `<pre>` a region role, a name, and
keyboard focus. Here's the tree after the fix. I took it from the Portuguese
page, which is why it shows "Resultado" and "Gerar":

```yaml
# after, with the form filled in and "Gerar" clicked (Portuguese page)
- region "Resultado (JSON-LD)":
  - code: "{ \"@context\": \"https://schema.org\", \"@type\": \"Article\", ... }"
```

With those three attributes removed again in the DOM, the same search by role
and name finds 0 regions. Now an agent told to "copy the generated JSON-LD"
has a node named "Result" to read. Before the fix, it had just another block
of text.

This component also had `role="alert"` on the `<ul>` that lists errors. An
alert role on the list itself overrides its list role, which leaves every
`<li>` orphaned in the tree. That's the `listitem` row in the audit
table. The alert now sits on a wrapper around the list.

## What this changes, and what it doesn't

Here's what the measurements support:

- **Measured:** the brand link's tree and the generator output's tree, before
  and after. A search by visible text went from 0 links to 1. Axe violations
  dropped from 266 nodes to 4, all of them contrast warnings on a piece of
  decorative text I kept on purpose.
- **Mechanism:** an agent that reads the tree only has what's in it. A name
  that doesn't contain the visible text breaks a search by visible text, and
  an element with no role and no name can't be found by role and name.
- **Not measured:** whether any real agent failed more, or succeeded more,
  because of this. I didn't test any agent against the "before" and "after"
  versions, and an agent that works from screenshots sees no difference at all
  from these fixes.

In another experiment, I measure [which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript) when they fetch a
page. That experiment is about what reaches the HTML. This
article covers the next stage: what an agent with a browser can target once
the page has rendered.

None of this affects SEO for search engines directly, since Googlebot reads
the HTML and its text. This audit round also included a crawler run, which I
wrote up in my article on the
[Screaming Frog free version](/en/blog/screaming-frog-free-version). Each
report caught what the other one missed.

## In Next.js: the name comes from the visible text

My [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) uses the
App Router as the reference implementation. Both fixes here are plain JSX. For
the brand link, the name comes from the content plus a visually hidden hint:

```tsx
// src/components/layout/Header.tsx
<Link href={copy.home} className="flex shrink-0 items-baseline gap-2.5" title={copy.homeLabel}>
  {/* No aria-label: the accessible name comes from the visible text plus
      this hint (WCAG 2.5.3). */}
  <span className="font-display ... uppercase ...">SEO Técnico</span>
  <span className="font-mono ...">.DEV.BR</span>
  <span className="sr-only"> — {copy.homeHint}</span>
</Link>
```

For the generator output, the role, name, and focus go on the `<pre>` itself.
Because it scrolls horizontally, it has to be reachable by keyboard:

```tsx
// src/components/tools/JsonLdGenerator.tsx
<pre
  role="region"
  aria-label={`${copy.result} (${tab === 'json' ? 'JSON-LD' : copy.nextComponent})`}
  tabIndex={0}
  className="theme-dark-island mt-4 overflow-x-auto ..."
>
```

To repeat the measurement on another site, use the script that snapshots the
tree before and after:

```js
// audits/scripts/aria-snapshot.mjs (excerpt)
const brand = page.locator('header a').first()
console.log(await brand.ariaSnapshot())
await brand.evaluate((a, l) => {
  a.setAttribute('aria-label', l)
  a.querySelector('.sr-only')?.remove()
}, 'SEO Técnico — home')
console.log(await brand.ariaSnapshot())
```

`ariaSnapshot()` returns the same YAML that Playwright MCP gives the model,
minus the references. You don't need an MCP server to see what the model
would get.
