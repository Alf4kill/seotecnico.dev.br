The accessibility tree is the version of a page the browser builds for
assistive technology. Every relevant element becomes a node with a role
(link, button, region), an accessible name and a state. Some AI agents that
browse the web read this tree instead of an image of the screen: Playwright
MCP gives the model an accessibility snapshot, and Chrome DevTools MCP has a
snapshot tool "based on the a11y tree". For those agents, a control with no
name, or with a name that doesn't match the text on screen, can't be found by
the words written on it. An axe-core audit found exactly that on this site, in
the header of every page.

This article shows this site's tree before and after the fixes, along with
the script that captured it, and keeps what was measured separate from what
follows from the mechanism. No agent success rate was measured here.

## What the tree looks like, with an example from this site

The browser reads the DOM, drops anything that exists only for layout, and
builds a tree of what matters to someone who can't see the screen. Here is
the brand link in the header, as Playwright describes it after the fix:

```yaml
- link "SEO Técnico .DEV.BR — home":
  - /url: /en
```

A role (`link`), a name in quotes and a destination. Two `span` elements with
font and color classes, plus a third that is visually hidden, collapse into a
single line. That line is what an agent like Playwright MCP receives, along
with a reference (`[ref=e5]`, for example) it uses to click.

Notice that the screen shows "SEO TÉCNICO" in capitals while the tree keeps
"SEO Técnico". The capitals come from CSS (`text-transform`); the tree carries
the HTML text. An agent that reads pixels and one that reads the tree see the
same brand spelled two different ways.

## Which agents read the tree and which read the screen

| Agent | What it gets from the page | How it targets an element |
|---|---|---|
| Playwright MCP | Accessibility snapshot, "instead of screenshots" | Node reference (`ref`) |
| Chrome DevTools MCP | Text snapshot "based on the a11y tree" | Node identifier (`uid`) |
| Computer use (Anthropic) | Screenshot | Pixel coordinates |

The three descriptions come from each tool's documentation, read on
2026-10-23. A site doesn't get to choose which of them visits, and a single
agent can combine both approaches. So the argument in this article is
conditional: **if** the agent reads the tree, **then** what's in the tree is
all the agent has.

## What the audit found

The test suite runs axe-core through Playwright on every route in the
sitemap, in both themes, against the WCAG 2.0 and 2.1 rules at levels A and
AA. That adds up to 148 audits. Against the code in production at the time,
it flagged 266 nodes, every one rated *serious*:

| axe rule | Nodes | What it means |
|---|---|---|
| `label-content-name-mismatch` | 224 | Accessible name doesn't contain the visible text (WCAG 2.5.3) |
| `scrollable-region-focusable` | 16 | Table or code block that scrolls but can't receive keyboard focus |
| `color-contrast` | 14 | Text below the minimum contrast |
| `listitem` | 8 | List item with no parent list in the tree |
| `link-in-text-block` | 4 | Link distinguished from surrounding text by color alone |

The first 224 are a single component repeated: the brand link, on every page,
in both themes. Contrast doesn't change the tree, and keyboard focus makes
little difference to anyone not using a keyboard. Two findings change what an
agent can find, and those are the two I measured.

## Before and after: the brand link

The link had an `aria-label` of "SEO Técnico — home". An `aria-label`
replaces the element's content as its accessible name, so the name left out
".DEV.BR", which is right there on screen. The fix removed the `aria-label`
and added a hint visible only to screen readers.

To capture the "before" state without reverting the code, the script opens
the live page, snapshots the tree, then puts the `aria-label` back and
removes the hint directly in the DOM (the fix's diff applied in reverse) and
snapshots again:

```yaml
# before (aria-label restored)
- link "SEO Técnico — home":
  - /url: /en
  - text: SEO Técnico .DEV.BR

# after (served page)
- link "SEO Técnico .DEV.BR — home":
  - /url: /en
```

Both names describe the link, and an agent reading the whole tree would have
seen both the name and the text even before the fix. The difference shows up
when something looks for the link by the words written on it. That's how an
agent gets instructions from a human ("click SEO Técnico .DEV.BR"), and it's
how voice-control users speak:

| Search by role + visible text | Before | After |
|---|---|---|
| `getByRole('link', { name: 'SEO Técnico .DEV.BR' })` on `/en` | 0 links | 1 link |
| The same search on `/` (Portuguese home) | 0 links | 1 link |

Playwright matches the name as a case-insensitive substring. Before the fix,
"SEO Técnico .DEV.BR" wasn't a substring of "SEO Técnico — home", so the
search came back empty. WCAG 2.5.3 (Label in Name, level A) asks for exactly
this: the name must contain the visible text, ideally at the start.

The search button in the header had the same problem in Portuguese: it showed
"buscar…" but was named "Abrir busca". The English button already matched.

## Before and after: the JSON-LD generator's output

In the [JSON-LD generator](/en/tools/json-ld-generator), the result appears
in a `<pre>` once you click "Generate JSON-LD". A `<pre>` has no role of its
own in the tree. The generated code was there as text, but no named node said
"this is the result". The component test caught it by looking for the result
the way a screen reader would:

```ts
screen.getByRole('region', { name: /resultado/i })
```

It found nothing. The fix gave the `<pre>` a region role, a name and keyboard
focus:

```yaml
# after, with the form filled in and "Gerar" clicked (Portuguese page)
- region "Resultado (JSON-LD)":
  - code: "{ \"@context\": \"https://schema.org\", \"@type\": \"Article\", ... }"
```

With those three attributes stripped out again in the DOM, the same search by
role and name finds 0 regions. After the fix, an agent told to "copy the
generated JSON-LD" has a node named "Result" to read. Before, it had just one
block of text among many.

The same component had `role="alert"` on the error `<ul>`. Putting the alert
role on the list itself wipes out its list role and leaves every `<li>`
orphaned in the tree; that's the `listitem` row in the table above. The alert
role now sits on a wrapper around the list.

## What this changes, and what it doesn't

Here is what the measurements support:

- **Measured:** the tree for the brand link and for the generator's output,
  before and after; the search by visible text going from 0 to 1; axe
  violations going from 266 nodes to 4, all of them contrast warnings on
  decorative text that was left as-is on purpose.
- **Mechanism:** an agent that reads the tree only has what's in it. A name
  that doesn't contain the visible text breaks any search by that text, and an
  element with no role and no name can't be found by role and name.
- **Not measured:** whether any real agent succeeded or failed more often
  because of this. No agent was tested against the "before" and "after"
  versions, and an agent that works from screenshots wouldn't see any
  difference at all.

In a separate experiment, this site measures [which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript) when they fetch a
page. That's about what arrives in the HTML. The accessibility tree is the
next layer: what an agent with a browser can actually target once the page
has rendered.

None of this affects search SEO directly. Googlebot reads the HTML and its
text. The crawler audit run the same day is written up in the
[Screaming Frog free version case](/en/blog/screaming-frog-free-version), and
each report caught things the other missed.

## In Next.js: the name comes from the visible text

The [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) uses
the App Router as its reference implementation, and both fixes are plain JSX.
In the brand link, the name comes from the content, plus a visually hidden
hint:

```tsx
// src/components/layout/Header.tsx
<Link href={copy.home} className="flex shrink-0 items-baseline gap-2.5" title={copy.homeLabel}>
  {/* No aria-label: the accessible name comes from the visible text plus
      this hint (WCAG 2.5.3). */}
  <span className="font-display ... uppercase ...">SEO Técnico</span>
  <span className="font-mono ...">.DEV.BR</span>
  <span className="sr-only"> — {copy.homeHint}</span>
</Link>
```

In the generator's output, the role, name and focus go directly on the
`<pre>`, which scrolls horizontally and therefore has to be reachable by
keyboard:

```tsx
// src/components/tools/JsonLdGenerator.tsx
<pre
  role="region"
  aria-label={`${copy.result} (${tab === 'json' ? 'JSON-LD' : copy.nextComponent})`}
  tabIndex={0}
  className="theme-dark-island mt-4 overflow-x-auto ..."
>
```

And here is the script that snapshots the tree before and after, if you want
to repeat the measurement on another site:

```js
// audits/scripts/aria-snapshot.mjs (excerpt)
const brand = page.locator('header a').first()
console.log(await brand.ariaSnapshot())
await brand.evaluate((a, l) => {
  a.setAttribute('aria-label', l)
  a.querySelector('.sr-only')?.remove()
}, 'SEO Técnico — home')
console.log(await brand.ariaSnapshot())
```

`ariaSnapshot()` returns the same YAML Playwright MCP gives the model, minus
the references. You don't need an MCP server to see what the agent would see.
