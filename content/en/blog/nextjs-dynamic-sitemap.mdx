A dynamic sitemap in Next.js is an `app/sitemap.ts` file whose default export
is a function that returns an array. Next.js serves that array at
`/sitemap.xml` on its own. What makes it dynamic isn't the routing, which
Next.js already handles. It's that the array is *derived* from your content
source instead of typed by hand. Here's a quick test. If publishing a post
isn't enough to make your sitemap grow, it isn't dynamic in your project.
It's a `.ts` file with a hardcoded list inside.

Creating the file takes three lines, shown right below. After that, this
article answers a question most Portuguese-language tutorials leave open. Of
the four fields `sitemap.ts` lets you declare per URL, how many does Google
really read? And what should you do with the others, which get copied from
tutorial to tutorial without any effect?

```ts
// app/sitemap.ts
import type { MetadataRoute } from 'next'

export default function sitemap(): MetadataRoute.Sitemap {
  return [{ url: 'https://yoursite.com', lastModified: new Date() }]
}
```

That's already a valid sitemap. Trouble starts when the array doesn't change
by itself as the site grows, and that's where most tutorials stop. This
article is the sitemap and robots chapter of the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs). Each
section below covers a decision I made on this site, with code that's running
in production now.

## What Next.js generates and what Google actually reads

Practically every tutorial uses this format, including the official example
in the Next.js documentation:

```ts
{ url: '...', lastModified: new Date(), changeFrequency: 'weekly', priority: 0.8 }
```

That's four fields. Google's documentation on building a sitemap says it
ignores `<priority>` and `<changefreq>`. Of the metadata, Google actually uses
only `<lastmod>`, and only when its value is consistent and verifiable, for
example when you can compare it with the page's real last modification. So
two of the four fields do nothing, and a third works only if it's accurate.
This isn't an SEO blog's opinion. It's in the documentation.

Tutorials keep repeating the pattern for a simple reason. Next.js's own
official example also sets `lastModified: new Date()` on every entry, which is
exactly the pattern that teaches Google to distrust the field. I cover that
two sections down.

| Field | Does Google use it? | Worth declaring? |
|---|---|---|
| `url` | Yes, as the list of URLs that exist | Always |
| `lastModified` | Yes, if verifiable | Only when a real date can be derived from the content |
| `changeFrequency` | No | Never, since it affects nothing |
| `priority` | No | Never, since it affects neither crawl order nor ranking |

You type that array as `MetadataRoute.Sitemap`, which `next` exports.
Next.js serializes it to XML and serves it at `/sitemap.xml` with no extra
step.

What separates a dynamic sitemap from a list of URLs with a `.ts` extension
comes down to one function, `getAllPosts()`. On this site, `sitemap.ts`
doesn't list posts. It reads `/content/blog`, maps each MDX file to an entry,
and uses the frontmatter's `dateModified` as `lastModified`. Publishing a file
is the only step. There's no second list to remember to update.

```ts
import { getAllPosts } from '@/lib/content'

// Data local, não UTC: `new Date('2026-07-20')` seria interpretada como
// meia-noite UTC e poderia voltar um dia no fuso de quem lê.
const toDate = (d: string) => new Date(`${d}T00:00:00`)

export default function sitemap(): MetadataRoute.Sitemap {
  return getAllPosts().map(({ frontmatter }) => ({
    url: `https://seotecnico.dev.br/blog/${frontmatter.slug}`,
    lastModified: toDate(frontmatter.dateModified),
  }))
}
```

(Its Portuguese comment says the date is local time, since
`new Date('2026-07-20')` would parse as midnight UTC and could slip back a day
in the reader's time zone.)

`getAllPosts()` nests the frontmatter inside each object it returns, as
`frontmatter.slug` and `frontmatter.dateModified`, because it keeps
validated frontmatter apart from the MDX body. Validation runs at build time,
so a `title` over 60 characters or a missing required field breaks the build
before anything reaches the sitemap.

Here's the same logic as the diagram above, as a table:

| Source | Derivation | Sitemap output | When the content changes |
|---|---|---|---|
| `content/blog/*.mdx`, frontmatter | `getAllPosts()` reads each file's frontmatter | `<loc>` and `<lastmod>`, the latter from `dateModified` | Editing the post updates `lastmod` by itself, because the date lives in the file |
| Diagrams exported from the post | `postImages` maps a slug to its files | `<image:loc>` | Declaring a new diagram adds it to the sitemap with no extra edit |
| *(Alternative not used here)* hand-maintained list | None, since the list is typed in | `<loc>` with no reliable `lastmod` | Nothing changes by itself, and the list goes stale until someone remembers it |

That last row is what most Next.js projects end up with by default. It's a
literal array that works until someone forgets to add a new URL, or removes a
page without taking it off the list. Deriving from content removes that whole
class of error, because a derived sitemap never falls out of sync. It *is* a
projection of the content.

Some pages stay outside the derivation. Static pages with no content date,
such as `/ferramentas`, `/sobre`, and `/politica-de-privacidade` (the site's
Portuguese routes for tools, about, and privacy policy), have no
`dateModified` to derive from. Leaving their date out is deliberate, not a
gap, and the next section explains why.

## Getting `lastmod` right

Google is specific about when it uses `<lastmod>`. The value has to be
consistent and verifiable, for example comparable with the page's real last
modification. In practice, that rules out the pattern in almost every sitemap
example out there, including the Next.js documentation's own:

```ts
// o padrão que ensina o Google a ignorar o lastmod
{ url: '...', lastModified: new Date() }
```

Its Portuguese comment calls this the pattern that teaches Google to ignore
`lastmod`. `new Date()` runs at build time. Every time you deploy the site,
each URL declares that it changed just now, whether or not that page's content
did. A Monday redeploy with no change at all produces the same `lastmod` as a
Tuesday redeploy with the article rewritten from scratch. Google has nothing
to check that date against, because it never matches a real change. That's
the practical reason Google recommends that the value reflect only
significant updates, such as main content, structured data, or links, and not
a build date or a copyright date.

This site inverts that logic. A comment at the top of the production file
sets the rule, which in short says to emit `lastmod` only when the
frontmatter can supply it:

```ts
// lastmod só é emitido quando derivável do frontmatter: um lastmod que muda a
// cada build sem mudança real de conteúdo ensina o Google a ignorá-lo.
```

In practice, one `sitemap.ts` behaves in three different ways:

- **Blog posts.** `lastModified` comes from the frontmatter's `dateModified`.
  If the post doesn't change, neither does the field, even if the site is
  redeployed ten times in a week.
- **Home and `/blog`.** `lastModified` is derived from the most recent
  `dateModified` across the guide and all posts, because those pages do change
  when the content they list changes. It's still verifiable, since the date
  reflects a real change in what they display.
- **Static pages with no content date.** They carry no `lastModified` at all.
  Omitting it is the decision. Inventing a date would be worse than declaring
  nothing, because it would bring back exactly the unverifiable pattern
  described above.

It's the third item that usually raises a question. Why not use the deploy
date here too? Because the deploy date isn't when that page's *content*
changed. It's when the *code* changed, which happens for reasons unrelated to
content, like an updated dependency or a style tweak in another component.
Declaring that as `lastmod` would be technically easy and editorially false.

## `robots.ts`: the default is not to index

`robots.ts` solves a different problem from `sitemap.ts`, but the two go
together because `robots.txt` is what announces the sitemap. I designed it so
the default is *not* to index. Anything off the production happy path falls
into that default automatically.

This excerpt is the July 2026 version. The file now also declares groups for
individual AI agents, but the fail-safe hasn't changed:

```ts
// src/app/robots.ts (julho de 2026)
export default function robots(): MetadataRoute.Robots {
  if (!indexable) {
    return { rules: [{ userAgent: '*', disallow: '/' }] }
  }

  return {
    rules: [{ userAgent: '*', allow: '/', disallow: ['/api/'] }],
    sitemap: `${site.url}/sitemap.xml`,
  }
}
```

`indexable` comes from an environment variable, in `src/lib/site.ts`:

```ts
export const indexable = process.env.SITE_INDEXABLE === 'true'
```

What matters is which way the fail-safe fails. `indexable` is `true` only if
the variable exists *and* equals exactly `'true'`. A missing variable, a
Vercel preview deployment, and a local build all fail *closed*. Missing
configuration produces `Disallow: /`, not the opposite. Indexing is opt-in,
and the opt-in is a variable that exists only in production.

This prevents an accident that's both common and costly. A staging URL gets
indexed, shows up in search, and competes with the equivalent production
page, and you end up with two URLs splitting signals for the same content.
With the default inverted, that accident would require someone to *set* the
wrong variable in an environment that shouldn't index, instead of simply
forgetting to set it. Forgetting is by far the more common failure mode.

An audit of this site's own crawl baseline, run on July 20, 2026, turned up a
real bug. On `/busca`, the site's search page, the `robots` meta tag said
`noindex, follow` **and** `robots.txt` blocked it with `Disallow: /busca`,
both at once. It looks redundant, like two ways of saying "I don't want this
in search." But the two rules don't add up. They cancel out.

`Disallow` prevents crawling. Googlebot never downloads the page, so it never
reads the `noindex` in its HTML. If Google discovers the URL some other way,
such as an external link, it can still index it. In that case it shows up as
a URL-only result, with no title or description taken from the content,
because Google was never allowed to look at the content.

| Goal | Use | Don't use |
|---|---|---|
| Take the URL out of the index | `noindex` on the page | `Disallow` for the same URL, which stops the `noindex` from being read |
| Stop the URL from being crawled | `Disallow` in `robots.txt` | `noindex`, expecting it to handle crawling by itself |
| Both on the same URL | n/a | Never, because `Disallow` wins by keeping the other directive from being read |

Here's the rule, with no exceptions. Use `noindex` when you want a URL out of
the index, and `Disallow` only when you want to prevent crawling entirely.
Never use both on the same URL.

To fix it, I removed `Disallow: /busca` from `robots.ts` and kept only the
page's `noindex`. Googlebot can now crawl `/busca`, read the directive, and
actually honor it. That's also why the previous section's code block lists
only `/api/` under `disallow`.

## Images, languages and large sitemaps

An entry's `images` field emits `<image:image><image:loc>` in the sitemap
protocol's image namespace. On this site it declares each post's diagrams, so
you don't need a separate image sitemap file. The `images` line sits inside
the map over posts:

```ts
const postImages: Record<string, string[]> = {
  'melhorar-lcp-nextjs': ['/images/blog/melhorar-lcp-nextjs/lcp-subpartes-timeline.webp'],
}

// dentro do map dos posts:
images: postImages[frontmatter.slug]?.map((path) => `${base}${path}`),
```

Two details aren't explicit in the documentation's example. First, the URLs
must be absolute, which is why `${base}` comes before the path. Second,
optional chaining returns `undefined` for posts with no declared image, and
Next.js simply omits the field. That's what you want, rather than an empty
list.

For languages, `alternates.languages` emits
`<xhtml:link rel="alternate" hreflang="…">` per entry. This site has had
pt-BR/en pairs since September 2026, but it declares hreflang in each page's
`<head>`, generated from a single map in `src/lib/hreflang.ts`, so no sitemap
entry uses the field. Google accepts either approach. My article on
[hreflang in Next.js](/en/blog/nextjs-hreflang) shows how that map works.

On large sites, `generateSitemaps` splits the output into several files,
staying within the limit of 50,000 URLs or 50 MB uncompressed per file,
whichever comes first. Files land at paths like `/product/sitemap/1.xml`.
**You probably don't need this.** It's a limit for sites in the tens of
thousands of URLs. Below that, splitting the sitemap adds complexity with no
measurable benefit.

## Using the sitemap as the test suite's source of truth

Most articles on Next.js sitemaps don't cover this inversion, because it
means treating `sitemap.ts` as an input to something else, not as an output.
This site's SEO suite, written in Playwright, imports the sitemap function
directly and builds its route list from it:

```ts
// tests/seo/seo.spec.ts
import sitemap from '../../src/app/sitemap'

const sitemapPaths = sitemap().map((entry) => new URL(entry.url).pathname)
const routes = [...sitemapPaths, ...noindexPaths]
```

As a result, every route in the sitemap runs through the whole set of
assertions automatically: exactly one `<h1>`, title and description within
limits, a self-referencing canonical, JSON-LD that parses, and a `robots` meta
tag with the right value. Publishing an MDX file doesn't just add the URL to
the sitemap. It adds the URL to *every SEO test that exists*, without a line
of configuration.

A dedicated test also confirms that the served `/sitemap.xml` actually
contains every URL the function enumerates. It covers a specific failure mode,
where the function is correct but what reaches the visitor is stale (a CDN
cache, a revalidation that didn't fire, a partial deploy). Without that test,
`sitemap.ts` can be perfect in code and still lie in production.

`src/app/feed.xml/route.ts` uses the same derive-from-content pattern to
produce `feed.xml`, which the metadata declares for autodiscovery through
`alternates.types`. It's not this article's subject, but it's the same
principle applied to another format.

## How to check that it's working

None of this is worth anything until you confirm it against real behavior,
rather than what the code should do. Here are four ways to check it:

1. **Check the Sitemaps report in Search Console.** Submit the sitemap URL,
   or confirm Google already discovered it through `robots.txt`, then watch
   the count of discovered URLs. That number reflects what Google read from
   the file.
2. **Open `/sitemap.xml` and `/robots.txt` directly in the browser.** This
   confirms what production is serving. It's the manual version of the
   dedicated test from the previous section.
3. **Run the repository's baseline crawl.** It's what found the `/busca` bug.
   Running it after any change to `robots.ts` or `sitemap.ts` catches this
   kind of error before it reaches production.
4. **Don't confuse discovery with indexing.** A URL showing as discovered
   guarantees that Google knows it exists, not that Google will index it.
   Indexing depends on content, the canonical, and the other signals that the
   rest of this guide's articles cover.
