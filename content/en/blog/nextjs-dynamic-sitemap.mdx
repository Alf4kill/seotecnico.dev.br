A dynamic sitemap in Next.js is an `app/sitemap.ts` file whose default
export returns an array; Next.js serves that array at `/sitemap.xml`
automatically. The "dynamic" part isn't the routing, which Next.js already
takes care of. It's the array itself being *derived* from your content source
instead of typed by hand. Publishing a post should be all it takes for the
sitemap to grow; if that's not what happens in your project, your sitemap
isn't dynamic. It's a `.ts` file with a hardcoded list inside.

The rest of this article isn't about creating the file, which takes three
lines (just below). It's about the question most Portuguese-language
tutorials don't answer: of the four fields `sitemap.ts` lets you set per URL,
how many does Google actually read? And what should you do about the others,
which keep getting copied from tutorial to tutorial without doing anything?

```ts
// app/sitemap.ts
import type { MetadataRoute } from 'next'

export default function sitemap(): MetadataRoute.Sitemap {
  return [{ url: 'https://yoursite.com', lastModified: new Date() }]
}
```

That's already a valid sitemap. The trouble starts when that array doesn't
update itself as the site grows, and that's where most tutorials stop. This
is the third track of the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs), and each section below is a decision
made on this site, with the code that's running in production right now.

## What Next.js generates and what Google actually reads

The format that shows up in nearly every tutorial, including the official
example in the Next.js docs, looks like this:

```ts
{ url: '...', lastModified: new Date(), changeFrequency: 'weekly', priority: 0.8 }
```

Four fields. According to Google's documentation on building a sitemap,
`<priority>` and `<changefreq>` are ignored. The only metadata Google actually
uses is `<lastmod>`, and only when the value is consistent and verifiable, for
example when it matches the page's real last modification. So of the four
fields, two do nothing and the third only works if it's accurate.

That's not an SEO blog's opinion; it's in the documentation. And the reason
the pattern lives on in so many tutorials is simple: Next.js's own official
example also uses `lastModified: new Date()` on every entry, which is exactly
the pattern that teaches Google to distrust the field. More on that two
sections down.

| Field | Does Google use it? | Worth including? |
|---|---|---|
| `url` | yes, it's the list of URLs that exist | always |
| `lastModified` | yes, if it's verifiable | only when there's a real date you can derive from the content |
| `changeFrequency` | no | never; it doesn't affect anything |
| `priority` | no | never; it affects neither crawl order nor rankings |

The `MetadataRoute.Sitemap` type, exported by `next`, types that array. It's
what Next.js serializes to XML and serves at `/sitemap.xml` with no extra
steps.

The difference between a dynamic sitemap and a list of URLs with a `.ts`
extension comes down to one function: `getAllPosts()`. On this site,
`sitemap.ts` doesn't list posts. It reads `/content/blog`, maps each MDX file
to an entry and uses the frontmatter's `dateModified` as `lastModified`.
Adding a file is the only step; there's no second list to remember to update.

```ts
import { getAllPosts } from '@/lib/content'

// Data local, não UTC: `new Date('2026-07-20')` seria interpretada como
// meia-noite UTC e poderia voltar um dia no fuso de quem lê.
const toDate = (d: string) => new Date(`${d}T00:00:00`)

export default function sitemap(): MetadataRoute.Sitemap {
  return getAllPosts().map(({ frontmatter }) => ({
    url: `https://seotecnico.dev.br/blog/${frontmatter.slug}`,
    lastModified: toDate(frontmatter.dateModified),
  }))
}
```

The comment says the date is built in local time, not UTC:
`new Date('2026-07-20')` would be parsed as midnight UTC and could slip back a
day in the reader's time zone. Notice that `getAllPosts()` returns objects
with the frontmatter nested (`frontmatter.slug`, `frontmatter.dateModified`),
because the function separates the validated frontmatter from the MDX body.
That validation runs at build time: a `title` over 60 characters or a missing
required field breaks the build before anything reaches the sitemap.

Here's the same logic as the diagram above, in table form:

| Source | Derivation | Sitemap output | When the content changes |
|---|---|---|---|
| `content/blog/*.mdx`, frontmatter | `getAllPosts()` reads each file's frontmatter | `<loc>` and `<lastmod>`, the latter from `dateModified` | editing the post updates `lastmod` automatically, because the date lives in the file itself |
| diagrams exported from the post | `postImages` maps each slug to its files | `<image:loc>` | declaring a new diagram adds it to the sitemap with no extra edit |
| *(alternative not used here)* hand-maintained list | none; the list is typed in | `<loc>` with no reliable `lastmod` | nothing updates on its own: the list goes stale until someone remembers it |

That last row is what most Next.js projects end up with by default: a
literal array that works until someone forgets to add a new URL, or deletes a
page without removing it from the list. Deriving from content eliminates that
whole class of error, because the sitemap can't drift out of sync: it *is* a
projection of the content.

It's worth pointing out what stays outside that derivation: static pages
with no associated content date, like `/ferramentas`, `/sobre` and
`/politica-de-privacidade`, have no `dateModified` to derive from. The next
section explains why leaving them out is deliberate, not an oversight.

## The `lastmod` problem

The condition Google publishes for using `<lastmod>` is specific: the value
has to be consistent and verifiable, for example by comparing it to the
page's real last modification. In practice, that rules out the pattern in
nearly every sitemap example out there, including the Next.js docs:

```ts
// o padrão que ensina o Google a ignorar o lastmod
{ url: '...', lastModified: new Date() }
```

That's the pattern that teaches Google to ignore `lastmod` (as the comment in
the snippet says). `new Date()` runs at build time, so every time the site
deploys, whether or not that page's content changed, the URL claims it
changed just now. A Monday redeploy with nothing changed produces the same
`lastmod` as a Tuesday redeploy where the article was rewritten from scratch.
Google has nothing to check that date against, because it never matches a
real change. That's the practical reason behind the guidance that the value
should only reflect meaningful updates (main content, structured data, links),
not a build or copyright date.

This site's rule flips that logic, and the comment sits at the top of the
production file (it says lastmod is only emitted when it can be derived from
the frontmatter, because a lastmod that changes on every build without a real
content change teaches Google to ignore it):

```ts
// lastmod só é emitido quando derivável do frontmatter: um lastmod que muda a
// cada build sem mudança real de conteúdo ensina o Google a ignorá-lo.
```

In practice, that produces three different behaviors inside the same
`sitemap.ts`:

- **Blog posts**: `lastModified` comes from the frontmatter's `dateModified`.
  If the post doesn't change, neither does the field, even if the site
  redeploys ten times that week.
- **Home and `/blog`**: they take `lastModified` from the most recent
  `dateModified` across the guide and all posts, because those pages really
  do change when the content they list changes. It's still verifiable: the
  date reflects a real change in what's being displayed.
- **Static pages with no content date**: they get no `lastModified` at all.
  Leaving it out is the decision. Making up a date would be worse than saying
  nothing, because it would bring back exactly the unverifiable pattern
  described above.

That third point is the one people usually question: why not use the deploy
date here too? Because the deploy date isn't when that page's *content*
changed; it's when the *code* changed, which happens for reasons that have
nothing to do with the content, like a dependency update or a style tweak in
some other component. Declaring that as `lastmod` would be technically easy
and editorially false.

## `robots.ts`: the default is not to index

`robots.ts` solves a different problem from `sitemap.ts`, but the two go
together because `robots.txt` is what announces the sitemap. The design
decision here is that the default is *not* to index, and anything that strays
from the happy path in production falls back to that default automatically
(this excerpt is from the July 2026 version; the file now also declares
groups per AI agent, and the fail-safe is unchanged):

```ts
// src/app/robots.ts (julho de 2026)
export default function robots(): MetadataRoute.Robots {
  if (!indexable) {
    return { rules: [{ userAgent: '*', disallow: '/' }] }
  }

  return {
    rules: [{ userAgent: '*', allow: '/', disallow: ['/api/'] }],
    sitemap: `${site.url}/sitemap.xml`,
  }
}
```

And `indexable` comes from an environment variable, in `src/lib/site.ts`:

```ts
export const indexable = process.env.SITE_INDEXABLE === 'true'
```

What matters is which way it fails. `indexable` is only `true` if the
variable exists *and* equals exactly `'true'`. A missing variable, a Vercel
preview deployment, a local build: they all fail *closed*. A missing setting
produces `Disallow: /`, not the reverse. Indexing is opt-in, and the opt-in is
a variable that only exists in production.

That prevents a common and expensive accident: a staging URL gets indexed,
shows up in search and competes with the matching production page, two URLs
for the same content splitting signals. With the default flipped, that
accident would require someone to actively *set* the wrong variable in an
environment that shouldn't be indexed, rather than simply forgetting to set
it, which is by far the more common way things go wrong.

An audit of this site's own crawl baseline, run on July 20, 2026, turned up a
real bug: the `/busca` page was marked `noindex, follow` in its `robots` meta
tag **and** blocked by `Disallow: /busca` in `robots.txt` at the same time.

It looks redundant (two ways of saying "keep this out of search"), but the
two rules don't add up; they cancel each other out. `Disallow` prevents
crawling: Googlebot never downloads the page, so it never reads the `noindex`
in the HTML. If Google finds the URL some other way, like an external link, it
can still index it, now as a URL-only result with no title or description,
because it was never allowed to look at the content.

| Goal | Use | Don't use |
|---|---|---|
| remove the URL from the index | `noindex` on the page | `Disallow` on the same URL, which stops the `noindex` from being read |
| stop the URL from being crawled | `Disallow` in `robots.txt` | `noindex`, expecting it to prevent crawling on its own |
| both on the same URL | n/a | never; `Disallow` wins by keeping the other directive from being read |

The practical rule, no exceptions: use `noindex` when you want the URL out of
the index; use `Disallow` only when you want to prevent crawling entirely.
Never both on the same URL.

The fix here was to remove `Disallow: /busca` from `robots.ts` and keep only
the `noindex` on the page, so Googlebot can crawl it, read the directive and
actually honor it. That's why the code block in the previous section only
lists `/api/` under `disallow`.

## Images, languages and large sitemaps

An entry's `images` field emits `<image:image><image:loc>` in the sitemap
protocol's image namespace. On this site, it declares each post's diagrams,
with no need for a separate image sitemap:

```ts
const postImages: Record<string, string[]> = {
  'melhorar-lcp-nextjs': ['/images/blog/melhorar-lcp-nextjs/lcp-subpartes-timeline.webp'],
}

// dentro do map dos posts:
images: postImages[frontmatter.slug]?.map((path) => `${base}${path}`),
```

Two details the documentation's example doesn't spell out. First, the URLs
must be absolute, hence the `${base}` in front of the path. Second, the
optional chaining returns `undefined` for posts with no declared image, and
Next.js simply leaves the field out, which is what you want, rather than
emitting an empty list.

The `alternates.languages` field emits
`<xhtml:link rel="alternate" hreflang="…">` for each entry. This site has had
pt-BR/en pairs since September 2026, but it declares hreflang in each page's
`<head>`, generated from a single map in `src/lib/hreflang.ts`, so no sitemap
entry uses the field. Google accepts either approach; the
[hreflang in Next.js article](/en/blog/nextjs-hreflang) shows how that map
works.

For large sites, `generateSitemaps` splits the output into multiple files to
respect the limit of 50,000 URLs or 50 MB uncompressed per file, whichever
comes first. The output lives at paths like `/product/sitemap/1.xml`. To be
blunt: **you probably don't need this.** That limit is for sites with tens of
thousands of URLs; below that, splitting the sitemap adds complexity with no
measurable benefit.

## The sitemap as the tests' source of truth

This is the twist most articles on Next.js sitemaps don't cover, because it
means treating `sitemap.ts` not as an output but as an input to something
else.

This site's SEO test suite, written in Playwright, imports the sitemap
function directly and builds its list of routes from it:

```ts
// tests/seo/seo.spec.ts
import sitemap from '../../src/app/sitemap'

const sitemapPaths = sitemap().map((entry) => new URL(entry.url).pathname)
const routes = [...sitemapPaths, ...noindexPaths]
```

The practical effect: every route in the sitemap automatically goes through
the full set of assertions (exactly one `<h1>`, a title and description within
the limits, a self-referencing canonical, JSON-LD that parses, a `robots` meta
with the right value). Publishing an MDX file doesn't just add the URL to the
sitemap; it adds the URL to *every SEO test there is*, without a single line
of configuration.

There's also a dedicated test that confirms the live `/sitemap.xml` really
contains every URL the function lists. It covers a specific failure mode: the
function is correct, but what reaches visitors is stale (a CDN cache, a
revalidation that didn't fire, a partial deploy). Without that test,
`sitemap.ts` can be perfect in the code and still lie in production.

The same derive-from-content pattern produces `feed.xml` in
`src/app/feed.xml/route.ts`, declared for autodiscovery through
`alternates.types` in the metadata. It's not the subject of this article, but
it's the same principle applied to a different format.

## How to check that it's working

None of this matters until you've confirmed it against what actually happens,
not just what the code is supposed to do:

1. **Search Console's Sitemaps report.** Submit the sitemap URL, or confirm
   Google has already found it through `robots.txt`, and watch the count of
   discovered URLs. That number reflects what Google read from the file.
2. **Open `/sitemap.xml` and `/robots.txt` directly in your browser.** That
   confirms what's being served in production; it's the manual version of the
   dedicated test in the previous section.
3. **Run the repository's baseline crawl.** That's what caught the `/busca`
   bug. Running it after any change to `robots.ts` or `sitemap.ts` catches
   this kind of mistake before it hits production.
4. **Don't confuse discovery with indexing.** A URL showing up as discovered
   means Google knows it exists, not that it will be indexed. Indexing
   depends on the content, the canonical and the other signals covered in the
   rest of this guide's articles.
