Between September and October 2026, I tested five AI assistants on a page
of this site with a code that existed only in its JSON-LD. Only Grok reported
that code. ChatGPT, Claude, Gemini, and DeepSeek didn't report it in any
round. That's no reason to remove JSON-LD, since Google still uses it for
rich results. What changes is where the important fact lives. Put it in the
visible text too.

These numbers come from the experiment
[Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript),
which documents the full method. Here I use only the part that answers a
single question. What happens to data that exists only inside a
`<script type="application/ld+json">` block?

Writing in Portuguese about "schema for AI" tends to mix up two different
things. One is what Google does with JSON-LD when it indexes a page. The
other is what an assistant does when you paste a URL into the chat and it
opens the page. Google documents the first. I measured the second.

## What Google does with JSON-LD

Google uses structured data to understand a page and to show rich results.
Its
[official feature
gallery](https://developers.google.com/search/docs/appearance/structured-data/search-gallery),
last updated June 15, 2026, lists the features it can show, including
Article, Breadcrumb, Product, Local business, Event, Recipe, and Video. FAQ
rich results are no longer on that list. According to the
[documentation update log](https://developers.google.com/search/updates),
they stopped appearing in Search on May 7, 2026.

Two rules in Google's documentation matter for this article. First, markup
makes a page eligible for a feature but doesn't guarantee it will appear.
Second, the
[general structured data
guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)
tell you not to mark up content readers can't see. If your JSON-LD describes
a price, the page body has to show the same price.

On AI, Google's
[guide to generative AI features in
Search](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide),
updated July 10, 2026, says structured data isn't required for generative AI
search and that there's no special schema.org markup for it. It still
recommends using structured data, because that's what makes a page eligible
for rich results. Keep its scope in mind, though. The guide covers AI features
inside Google Search, such as AI Overviews and AI Mode. It doesn't describe
what an assistant does when it opens a URL inside a chat.

For that second case, I looked for official documentation from the five
assistants' vendors on how their tools use schema.org when they open a page.
As of October 2026, I haven't found any. What's out there instead are
third-party guides claiming that every assistant reads schema, without
measuring any assistant.

If you don't have a JSON-LD block yet, this site's
[JSON-LD generator](/en/tools/json-ld-generator) can help you build one. For
the App Router implementation, see
[JSON-LD in Next.js](/en/blog/nextjs-json-ld).

## What the assistants did with it: the experiment

On the lab page, a JSON-LD block carries a code that starts with `LD-`. That
code exists **only** in the block's `identifier` field. It isn't in the
visible text, and no JavaScript generates it. The block is in the HTML of
every server response. Each assistant gets its own secret URL, so the server
log shows which one made each request.

I varied the prompt across three conditions. In the neutral one, I asked each
assistant to report the page's codes without saying where to look. In the
other two, my prompt said where the code was, with different levels of
detail. My
[full experiment](/en/blog/which-ai-assistants-run-javascript) defines each
condition exactly.

| Assistant (plan) | Neutral | With location | With address |
|---|---|---|---|
| ChatGPT (Go) | 0 of 5 | 0 of 3 | 0 of 3 |
| Claude (Pro) | 0 of 5 | 0 of 3 | 0 of 3 |
| Gemini (free) | 0 of 8 | 0 of 3 | 0 of 3 |
| DeepSeek (free) | 0 of 5 | 0 of 3 | 0 of 3 |
| Grok (free) | 2 of 5 | 3 of 3 | 3 of 3 |

Rounds in which the assistant reported the `LD-` code, September 25 to
October 2, 2026.

Four of the five never reported the code. Zero in 11 rounds for ChatGPT,
Claude, and DeepSeek doesn't prove it never happens. What it does tell you
is that if the real chance of reporting the code were higher than about one
in four, it would most likely have shown up at least once. With Gemini's 14
rounds, that limit drops to about one in five.

Grok reported the code in 2 of 5 neutral rounds and in 6 of 6 rounds with a
hint. That difference isn't statistically significant (p = 0.06). What
Grok's result does show is capability. Its tool can deliver the block's
content to the model. The result doesn't show that the hint caused the
improvement.

For ChatGPT and Claude, the neutral rounds are the September control I
published in
[Does ChatGPT read JavaScript?](/en/blog/does-chatgpt-read-javascript).
Adding a hint in October didn't change the zero for either one.

Keep in mind what the experiment measures. It records what each assistant
**reported**, not what it received. "Never reported" is the data. "Never
received" is a hypothesis, and the next section discusses it.

In the lab, the code lives only in the JSON-LD on purpose, because that's
what I'm measuring. On a real page, data that's marked up but hidden from
readers would already break the Google guideline cited above.

## Why most don't read it: extractors throw out `<script>`

When you give an assistant a URL, the model doesn't open the page the way a
browser does. A fetch or search tool downloads the HTML and converts it into
something that fits in the model's context, usually text. That conversion
tends to discard elements that look like code rather than content. JSON-LD
is a `<script>` element. If the tool strips scripts, the block goes with
them, and a fact that existed only there is gone before the model reads
anything.

This has nothing to do with running JavaScript. JSON-LD is already in the
HTML the server delivers, so it doesn't depend on rendering. The data gets
lost during text extraction, not during rendering.

In one case, an assistant described this mechanism itself. In round 41, on
October 2, 2026, Claude on the Pro plan explained that its tool converts
HTML to text and removes `<script>` blocks, including
`application/ld+json`. That's the assistant's explanation, not data. I
include it because the server log for that round is consistent with it.

For ChatGPT, Gemini, and DeepSeek, I have no explanation that matches the
log. Stripping scripts is the simplest hypothesis for their zeros, but it
isn't confirmed. I also don't know why Grok's tool keeps the block at least
part of the time. I haven't tested that.

Here's the same difference between the two readers, as a table.

| Reader | What it reads | What it loses |
|---|---|---|
| Googlebot (Google Search) | The HTML, including the JSON-LD block and the visible text | Nothing in the delivered or rendered HTML |
| An assistant's text extractor that removes `<script>` | The converted visible text | Everything that exists only inside `<script>`, including the JSON-LD |
| The practical rule | The important fact in both the JSON-LD and the text | Nothing. A reader that sees only one of the two still finds the fact |

## The Gemini case: when the AI says the schema doesn't exist

Gemini (free) had more neutral rounds than any other assistant, eight, and
reported the code in none of them. What stands out is what it said. On
October 2, 2026, in five rounds, its answer stated that the JSON-LD with the
code wasn't in the HTML it received. In one of them, round 62, it said the
page had no JSON-LD at all.

Yet the block was in the HTML of every server response. Grok read it in all
six of its rounds that day.

One possible reading is that Gemini's answer accurately describes what its
tool delivered to the model, and is wrong about the page. I can't confirm
that from the log. You don't need to confirm it to see the consequence. When
you ask an assistant whether your page has structured data, you're asking
about its tool's output, not about your page.

[SEO audit with ChatGPT](/en/blog/seo-audit-with-chatgpt) covers this case
and others where an AI's explanation contradicts the server.

None of this says anything about what Google Search does with the same
block. For that, your sources are still the Rich Results Test and URL
Inspection in Search Console.

## The rule: state the fact twice

You don't have to give up JSON-LD. Write the important fact twice, once in
the schema for Google and once in the visible text for any reader that
doesn't open the block. None of this goes beyond what Google's guideline
already asks for. Only the motivation changes.

Not every field needs a mirror. My test is whether someone might want to
quote or check that value.

| Fact | Where it is in the JSON-LD | Where it appears in the text | Mirror? |
|---|---|---|---|
| Price and availability | `offers.price`, `offers.availability` | Product details | Yes |
| Publication and update dates | `datePublished`, `dateModified` | Byline | Yes |
| Author | `author` | Byline | Yes |
| Technical specifications | Product properties | Specs table | Yes |
| Contact and opening hours | `telephone`, `openingHoursSpecification` | Footer or contact page | Yes |
| Keywords and topic | `keywords`, `about` | Not needed | No |
| Main image | `image` | The image appears, not its URL | No |

Here's an illustrative product example. Before, the price exists only in the
JSON-LD.

```html
<!-- illustrative: the price exists only in the JSON-LD -->
<h1>FX-750 impact drill</h1>
<p>750 W motor, 13 mm chuck.</p>
<button type="button">Buy</button>

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "FX-750 impact drill",
  "offers": {
    "@type": "Offer",
    "price": "74.90",
    "priceCurrency": "USD",
    "availability": "https://schema.org/InStock"
  }
}
</script>
```

After, the same price and the availability appear in the product details.

```html
<!-- illustrative: the same fact in the text and in the JSON-LD -->
<h1>FX-750 impact drill</h1>
<p>750 W motor, 13 mm chuck.</p>
<p>$74.90 · in stock</p>
<button type="button">Buy</button>

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "FX-750 impact drill",
  "offers": {
    "@type": "Offer",
    "price": "74.90",
    "priceCurrency": "USD",
    "availability": "https://schema.org/InStock"
  }
}
</script>
```

Even the "after" version isn't always enough. If JavaScript inserts the
visible price in the browser and the server sends only the JSON-LD, that
text isn't in the initial HTML. An extractor that doesn't run
JavaScript won't find it in either place. That
[same experiment](/en/blog/which-ai-assistants-run-javascript) covers which
assistants run JavaScript, and under what conditions.

One caveat matters here. I didn't measure whether mirroring a fact increases
how often assistants cite a page. The experiment shows the other side. A
fact that existed only in the schema didn't appear in answers from four of
the five assistants. Mirroring removes that point of failure. It doesn't
guarantee a citation.

## How to check

Three checks settle most cases. These commands are illustrative.

**Is the block in the server's HTML?** Count the JSON-LD blocks in the
response.

```bash
curl -s https://example.com/product | grep -c 'application/ld+json'
```

**Does the fact exist outside the scripts?** Remove every `<script>`
block and search for the value as readers see it.

```bash
curl -s https://example.com/product \
  | perl -0pe 's/<script\b.*?<\/script>//gs' \
  | grep -c '\$74\.90'
```

This is a rough simulation of an extractor that discards scripts. If the
result is 0, the fact exists only inside some `<script>`, either in the
JSON-LD or in a JavaScript payload. The check has limits. It doesn't remove
elements hidden by CSS, doesn't decode HTML entities, and doesn't know that
74.90 and $74.90 are the same number. Search for the value the way a reader
would see it.

**Does Google read the block?** Use the Rich Results Test for the types
that produce rich results, and schema.org's Schema Markup Validator for any
type. URL Inspection in Search Console shows the HTML Google rendered. For
the rest of the `<head>` (title, description, canonical), use the
[meta tag validator](/en/tools/meta-tag-validator).

Asking the assistant isn't on this list. As the Gemini case shows, its
answer describes its tool, not your page.

## In Next.js: one frontmatter, two outputs

On this site, each article is an MDX file with frontmatter, and one object
feeds two outputs: the page you read and the JSON-LD. Title, summary, short
answer, dates, and author come from the same field in both places.

Here's how the frontmatter becomes the article's JSON-LD.

```tsx
// src/components/seo/JsonLd.tsx (lines 114–131)
headline: frontmatter.title,
description: frontmatter.description,
// `abstract` é a resposta curta do frontmatter: a mesma frase que o leitor
// vê no topo da página, disponível como dado para quem extrai.
...(frontmatter.tldr ? { abstract: frontmatter.tldr } : {}),
datePublished: frontmatter.datePublished,
dateModified: frontmatter.dateModified,
inLanguage: frontmatter.lang,
url,
mainEntityOfPage: { '@type': 'WebPage', '@id': url },
isPartOf: { '@id': WEBSITE_ID },
image: `${site.url}${imagePath ?? '/opengraph-image'}`,
// A ÚNICA query que a página persegue (CLAUDE.md §10) é também o assunto
// dela — declarar as duas coisas pela mesma fonte impede que divirjam.
keywords: frontmatter.primaryQuery,
about: { '@type': 'Thing', name: frontmatter.primaryQuery },
author: personSchema(),
publisher: organizationSchema(),
```

The comments are in Portuguese, as in the repository. The first says
`abstract` is the frontmatter's short answer, the same sentence readers see
at the top of the page, available as data for anything that extracts it.
The second says the page's single target query is also its topic, and
declaring both from one source keeps them from drifting apart.

On the page, the `<h1>` is the same `frontmatter.title`, the paragraph below
it is the `description`, the "Short answer" box is the `tldr`, and the byline
shows both dates.

FAQs follow the same pattern. One array, `items`, generates both the visible
accordion and the `FAQPage` block.

```tsx
// src/components/sections/FaqSection.tsx (lines 98–106)
__html: JSON.stringify({
  '@context': 'https://schema.org',
  '@type': 'FAQPage',
  mainEntity: items.map(({ question, answer }) => ({
    '@type': 'Question',
    name: question,
    acceptedAnswer: { '@type': 'Answer', text: answer },
  })),
}).replace(/</g, '\\u003c'),
```

FAQ rich results left Search in May 2026, but `FAQPage` stays here because
it comes from the same array as the accordion. There's no second place to
maintain.

This approach has a limit. On this site, mirroring is guaranteed by
construction, not by a test. No test compares the JSON-LD with the rendered
text. If someone changes one of the components to read a different field,
nothing in the build will warn. A few fields stay only in the JSON-LD:
`keywords`, `about`, and the `image` URL. By the test in the previous
section, that's acceptable, because none of them is a fact someone needs to
see quoted.

The same principle works in any App Router project. If the server component
that writes the `<script type="application/ld+json">` and the component that
renders the text read from the same source, you get mirroring for free. If
each one keeps its own copy of the data, the two versions will drift apart at
some point.

[JSON-LD in Next.js](/en/blog/nextjs-json-ld). The rest of technical SEO in
the App Router is in the
[pillar guide on technical SEO for Next.js](/en/guide/technical-seo-nextjs).
