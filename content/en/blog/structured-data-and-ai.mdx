In this site's test, run between September and October 2026 with five AI
assistants, only Grok reported a code that existed solely in the page's
JSON-LD. ChatGPT, Claude, Gemini and DeepSeek didn't report it in a single
round. JSON-LD is still what Google uses for rich results, so there's no
reason to remove it. The practical takeaway is different: important facts
need to be in the visible text too.

The numbers come from the experiment [Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript), which describes
the full method. Here I only use the part that answers one question: what
happens to a piece of data that exists only inside a `<script
type="application/ld+json">` block?

Articles about "schema for AI" tend to conflate two different things. One is
what Google does with JSON-LD when it indexes a page. The other is what an
assistant does when you paste a URL into a chat and it opens the page. Google
documents the first. I measured the second.

## What Google does with JSON-LD

Google uses structured data to understand a page and to show rich results.
The [official feature
gallery](https://developers.google.com/search/docs/appearance/structured-data/search-gallery),
as updated on June 15, 2026, lists the ones it shows, including Article,
Breadcrumb, Product, Local business, Event, Recipe and Video. The FAQ rich
result is no longer on the list: according to the [documentation update
log](https://developers.google.com/search/updates), it stopped appearing in
Search on May 7, 2026.

Two rules from the documentation matter here. First, markup makes a page
eligible for a feature but doesn't guarantee it will appear. Second, from the
[general structured data
guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies):
don't mark up content that readers can't see. If the JSON-LD describes a
price, the page body has to show the same price.

On AI, Google's [guide to generative AI features in
Search](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide),
updated on July 10, 2026, says structured data isn't required for generative
AI search and that there's no special schema.org markup for it. It recommends
you keep using it for rich result eligibility. That guide covers Google
Search's AI features, like AI Overviews and AI Mode. It doesn't describe what
an assistant does when it opens a URL inside a chat.

For that second case, I looked for official documentation from the vendors of
the five assistants tested on how they use schema.org when opening a page. As
of October 2026, I found none. What's out there are third-party guides
claiming every assistant reads schema, without ever measuring an assistant.

If your page doesn't have the block yet, this site's [JSON-LD
generator](/en/tools/json-ld-generator) can help you build it. The App Router
implementation is covered in the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs).

## What the assistants did with it: the experiment

The lab page has a JSON-LD block containing a code that starts with `LD-`.
That code exists **only** in the JSON-LD's `identifier` field: it isn't in the
visible text and isn't generated by JavaScript. The block ships in the HTML of
every server response. Each assistant gets its own secret URL, which is what
identifies who made each request in the server log.

The prompt varied across three conditions. In the neutral one, the assistant
was asked to report the page's codes, with no hint about where to look. In
the other two, the prompt said where the code was, with different levels of
detail. Each condition is defined precisely in the [full
experiment](/en/blog/which-ai-assistants-run-javascript).

| Assistant (plan) | Neutral | With location | With address |
|---|---|---|---|
| ChatGPT (Go) | 0 of 5 | 0 of 3 | 0 of 3 |
| Claude (Pro) | 0 of 5 | 0 of 3 | 0 of 3 |
| Gemini (free) | 0 of 8 | 0 of 3 | 0 of 3 |
| DeepSeek (free) | 0 of 5 | 0 of 3 | 0 of 3 |
| Grok (free) | 2 of 5 | 3 of 3 | 3 of 3 |

Rounds in which the assistant reported the `LD-` code, between September 25
and October 2, 2026.

Four of the five never reported the code. Zero out of 11 rounds for ChatGPT,
Claude and DeepSeek doesn't prove it never happens. It means that if the real
chance of reporting the code were higher than about one in four, it would most
likely have shown up at least once. For Gemini, with 14 rounds, that ceiling
drops to about one in five.

Grok reported the code in 2 of 5 neutral prompts and in 6 of 6 with a hint.
The difference isn't statistically significant (p = 0.06). What the result
shows is capability: Grok's tool can pass the block's contents to the model.
It doesn't show that the hint caused the improvement.

The neutral rounds for ChatGPT and Claude come from the September control
test, described in the [AI crawler detection case
study](/en/case-studies/ai-crawler-detection). The October rounds with hints
didn't change the zero for either of them.

A note on interpretation: the experiment measures what the assistant
**reported**, not what it received. "Never reported" is the data. "Never
received" is a hypothesis, discussed in the next section.

A note on the design: in the lab, the code lives only in the JSON-LD on
purpose, because that's what's being measured. On a real page, data that's
marked up but hidden from readers would already go against the Google
guideline quoted above.

## Why most don't read it: extractors throw out `<script>`

When you give an assistant a URL, the model doesn't open the page the way a
browser does. A fetching tool downloads the HTML and converts it into
something that fits in the model's context, usually text. During that
conversion, elements that look like code rather than content tend to get
thrown out. JSON-LD is a `<script>` element. If the tool strips scripts, the
block goes with them, and any fact that only existed there is gone before the
model reads anything.

Note that this has nothing to do with running JavaScript. The JSON-LD is
already in the HTML the server sends; it doesn't depend on rendering. The data
is lost during text extraction, not rendering.

In one case, the assistant itself described the mechanism. In round 41, on
October 2, 2026, Claude on the Pro plan explained that its tool converts the
HTML to text and removes `<script>` blocks, including the
`application/ld+json` one. That's the assistant's explanation, not data. I
include it because the server log for that round is consistent with it.

For ChatGPT, Gemini and DeepSeek, I have no explanation that matches the
log. The same mechanism is the simplest explanation for the zero, but it isn't
confirmed. Nor do I know why Grok's tool keeps the block at least some of the
time; that wasn't tested.

The same comparison, as a table:

| Reader | What it reads | What it loses |
|---|---|---|
| Googlebot (Google Search) | the HTML, including the JSON-LD block and the visible text | nothing that's in the served or rendered HTML |
| An assistant's text extractor that strips `<script>` | the visible text, after conversion | everything that only exists inside `<script>`, JSON-LD included |
| The practical rule | the important fact in both the JSON-LD and the text | nothing: a reader that only sees one of the two still finds the fact |

## The Gemini case: when the AI says the schema doesn't exist

Gemini on the free plan had more neutral rounds than the others (8) and
didn't report the code in any of them. What stands out is what it said. On
October 2, 2026, in five rounds, its answer stated that the JSON-LD with the
code wasn't in the HTML it received. In one of them, round 62, it said there
was no JSON-LD on the page at all.

The block was in the HTML of every server response, and Grok read it in all
six of its rounds that same day.

One possible explanation is that Gemini's sentence accurately describes what
its tool passed to the model, and is false about the page. I can't confirm
that from the log. The practical consequence doesn't depend on confirming it:
asking an assistant whether your page has structured data is asking about its
tool's output, not about your page. This case and others where an AI's
explanation contradicts the server are covered in [SEO audit with
ChatGPT](/en/blog/seo-audit-with-chatgpt).

The result also tells you nothing about what Google Search does with the same
block. For that, the sources are still the Rich Results Test and URL
Inspection in Search Console.

## The rule: state the fact twice

The answer isn't to drop JSON-LD. It's to state the important fact twice: in
the schema, for Google, and in the visible text, for any reader that doesn't
open the block. This asks nothing Google's guidelines don't already require;
only the motivation is different.

Not every field needs to be mirrored. The test I use is whether someone might
want to quote or check that value.

| Fact | Where it lives in the JSON-LD | Where it appears in the text | Mirror it? |
|---|---|---|---|
| Price and availability | `offers.price`, `offers.availability` | product details | yes |
| Publication and update dates | `datePublished`, `dateModified` | byline | yes |
| Author | `author` | byline | yes |
| Technical specifications | product properties | specs table | yes |
| Contact details and opening hours | `telephone`, `openingHoursSpecification` | footer or contact page | yes |
| Keywords and topic | `keywords`, `about` | not needed | no |
| Main image | `image` | the image is shown; the URL isn't | no |

Here's an illustrative product example. Before, the price only exists in the
JSON-LD:

```html
<!-- illustrative: the price exists only in the JSON-LD -->
<h1>FX-750 impact drill</h1>
<p>750 W motor, 13 mm chuck.</p>
<button type="button">Buy</button>

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "FX-750 impact drill",
  "offers": {
    "@type": "Offer",
    "price": "74.90",
    "priceCurrency": "USD",
    "availability": "https://schema.org/InStock"
  }
}
</script>
```

After, the same price and availability appear in the product details:

```html
<!-- illustrative: the same fact in the text and in the JSON-LD -->
<h1>FX-750 impact drill</h1>
<p>750 W motor, 13 mm chuck.</p>
<p>$74.90 · in stock</p>
<button type="button">Buy</button>

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "FX-750 impact drill",
  "offers": {
    "@type": "Offer",
    "price": "74.90",
    "priceCurrency": "USD",
    "availability": "https://schema.org/InStock"
  }
}
</script>
```

There's one case where the "after" still isn't enough. If the visible price
is inserted by JavaScript in the browser, and only the JSON-LD comes ready-made
from the server, the price text isn't in the initial HTML. An extractor that
doesn't run JavaScript won't find it in either place. Which assistants run
JavaScript, and under what conditions, is covered in the [same
experiment](/en/blog/which-ai-assistants-run-javascript).

An important caveat: I didn't measure whether mirroring a fact makes
assistants cite a page more often. What the experiment shows is the flip side:
the fact that only existed in the schema didn't show up in the answers of four
out of five assistants. Mirroring removes that point of failure. It doesn't
guarantee a citation.

## How to check

Three checks settle most cases. The commands below are illustrative.

**Is the block in the server's HTML?** Count the JSON-LD blocks in the
response:

```bash
curl -s https://example.com/product | grep -c 'application/ld+json'
```

**Does the fact exist outside the scripts?** Strip every `<script>` block and
search for the value in the format readers see:

```bash
curl -s https://example.com/product \
  | perl -0pe 's/<script\b.*?<\/script>//gs' \
  | grep -c '\$74\.90'
```

This roughly simulates an extractor that throws out scripts. If the result is
0, the fact only exists inside some `<script>`: in the JSON-LD or in a
JavaScript payload. The simulation has limits: it doesn't remove elements
hidden by CSS, doesn't decode HTML entities and doesn't know that 74.90 and
$74.90 are the same number. Search for the value the way a reader would see
it.

**Does Google read the block?** The Rich Results Test validates the types
that produce rich results; schema.org's Schema Markup Validator validates any
type. URL Inspection in Search Console shows the HTML Google rendered. For the
rest of the `<head>`, like the title, description and canonical, use the [meta
tag validator](/en/tools/meta-tag-validator).

What's not on the list is asking the assistant. As the Gemini case above
shows, its answer describes its tool, not your page.

## In Next.js: one frontmatter, two outputs

On this site, every article is an MDX file with frontmatter. That one object
feeds two outputs: the page readers see, and the JSON-LD. The title, summary,
short answer, dates and author flow from the same field into both.

The article's JSON-LD is built from the frontmatter:

```tsx
// src/components/seo/JsonLd.tsx (lines 114–131)
headline: frontmatter.title,
description: frontmatter.description,
// `abstract` é a resposta curta do frontmatter: a mesma frase que o leitor
// vê no topo da página, disponível como dado para quem extrai.
...(frontmatter.tldr ? { abstract: frontmatter.tldr } : {}),
datePublished: frontmatter.datePublished,
dateModified: frontmatter.dateModified,
inLanguage: frontmatter.lang,
url,
mainEntityOfPage: { '@type': 'WebPage', '@id': url },
isPartOf: { '@id': WEBSITE_ID },
image: `${site.url}${imagePath ?? '/opengraph-image'}`,
// A ÚNICA query que a página persegue (CLAUDE.md §10) é também o assunto
// dela — declarar as duas coisas pela mesma fonte impede que divirjam.
keywords: frontmatter.primaryQuery,
about: { '@type': 'Thing', name: frontmatter.primaryQuery },
author: personSchema(),
publisher: organizationSchema(),
```

The code comments are in Portuguese, as they are in the repository: the first
says `abstract` is the same short answer readers see at the top of the page;
the second says the page's single target query is also its declared topic.

On the page, the `<h1>` is that same `frontmatter.title`, the paragraph below
it is the `description`, the "Short answer" box is the `tldr`, and the byline
shows both dates.

The FAQ follows the same pattern: a single array, `items`, produces both the
visible accordion and the `FAQPage` block.

```tsx
// src/components/sections/FaqSection.tsx (lines 98–106)
__html: JSON.stringify({
  '@context': 'https://schema.org',
  '@type': 'FAQPage',
  mainEntity: items.map(({ question, answer }) => ({
    '@type': 'Question',
    name: question,
    acceptedAnswer: { '@type': 'Answer', text: answer },
  })),
}).replace(/</g, '\\u003c'),
```

The FAQ rich result disappeared from Search in May 2026, but `FAQPage` stays
here because it comes from the same array as the accordion: there's no second
copy to maintain.

I should be upfront about the limits here. The mirroring on this site is
guaranteed by design, not by a test. No test compares the JSON-LD with the
rendered text; if someone changes one of the components to read a different
field, nothing in the build will flag it. And some fields only live in the
JSON-LD: `keywords`, `about` and the `image` URL. That's acceptable under the
test from the previous section, because none of them is a fact anyone needs to
see quoted.

In any App Router project, the principle is the same: if the server
component that writes the `<script type="application/ld+json">` and the
component that renders the text read from the same source, you get mirroring
for free. If each has its own copy of the data, the two will drift apart
sooner or later. The rest of technical SEO in the App Router is covered in the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs).
