In the App Router, hreflang comes from the Metadata API's
`alternates.languages` field, which the framework turns into
`<link rel="alternate" hreflang>` tags in the `<head>`. The syntax is the easy
part. Whether it works depends on **reciprocity**: if page A declares B as an
alternate and B doesn't declare A back, Google throws out the whole cluster,
with no build error, no warning in the HTML and no visible symptom. This
article shows an implementation that holds up, using this site's code: the
English version of the guide, the pair declared in a single source, the test
that checks the return link in the served HTML, and a Next.js quirk that made
this site's own audit report missing hreflang on a page that was perfectly
fine.

## The three rules that decide whether hreflang works

| Rule | What it requires | What happens if you get it wrong |
| --- | --- | --- |
| Reciprocity | If A declares B, B declares A | Google ignores the annotation, silently |
| Self-reference | Each page lists itself among the alternates | The block stops being identical on both sides and starts to drift |
| `x-default` | A version for anyone who matches no language | Google decides on its own which one to serve |

Self-reference is the rule that surprises people most, so it's worth
explaining: because each page lists **every** version, itself included, the
block of tags comes out **exactly the same** on both sides of the pair. That
isn't redundancy; it's what makes reciprocity easy to check. Two blocks that
should be identical are easy to compare; two blocks that should complement each
other aren't.

## Where to declare it: `alternates.languages`

Here's the field, which sits in the same `alternates` object as the
canonical:

```ts
// illustrative example — this site's real implementation comes in the next section
export const metadata: Metadata = {
  alternates: {
    canonical: "/guia/seo-tecnico-nextjs",
    languages: {
      "pt-BR": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
      en: "https://seotecnico.dev.br/en/guide/technical-seo-nextjs",
      "x-default": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
    },
  },
};
```

Two points the documentation doesn't emphasize. The URLs must be
**absolute** (relative hreflang URLs don't count, which is why the example
repeats the domain). And `alternates`, like `openGraph`, is **replaced, not
merged**, between layout and page: a language block defined only in the
layout disappears on the first route that declares its own `alternates`. It's
the same [Metadata API shallow merge](/en/blog/nextjs-metadata-api) that
already broke this site's Open Graph once.

But neither of those is the real problem with the snippet above. The real
problem is that it's written **on the page**.

## The pair has to come from a single source

Declaring the pair by hand on each page works on the day you write it and
breaks at the first refactor: someone renames a route, updates the hreflang on
the side they were editing, and the other side keeps pointing to a URL that
no longer exists. No error. Just a cluster that quietly stopped existing.

The fix is structural: the pairs live in one module, and both sides are
generated from the **same object**. Here's an excerpt from this site's
production map, in `src/lib/hreflang.ts` (the first pair; the rest follow the
same shape):

```ts
export const TRANSLATION_PAIRS: readonly TranslationPair[] = [
  {
    id: 'seo-tecnico-nextjs',
    paths: {
      'pt-BR': '/guia/seo-tecnico-nextjs',
      en: '/en/guide/technical-seo-nextjs',
    },
  },
] as const
```

And the single metadata helper **derives** the language block from the
route's path instead of taking it as an argument; the snippet below is this
site's `buildMetadata()`:

```ts
const languagePaths = languageAlternatePaths(path)

return {
  alternates: {
    canonical: path,
    ...(languagePaths
      ? {
          languages: Object.fromEntries(
            Object.entries(languagePaths).map(([lang, target]) => [
              lang,
              absoluteUrl(target),
            ])
          ),
        }
      : {}),
    // …
  },
}
```

The payoff is that the page can no longer get it wrong. It doesn't declare
the pair; it just states its own path, and the pair comes from the one place
that knows. A route with no translation emits nothing, because a one-page
cluster is just noise. And since both sides read from the same structure, the
block comes out identical on each, which is exactly what the self-reference
rule calls for.

## The camelCase attribute that fools audits

This part is original, and it cost me a debugging session.

When the reciprocity check was switched on in CI, it reported that the
English version **had no hreflang tags at all**, on a page whose
`view-source` showed all three tags, correctly. The cause: Next.js
serializes the attribute as `hrefLang`, in camelCase, in the HTML it sends:

```html
<link rel="alternate" hrefLang="pt-BR" href="https://seotecnico.dev.br/guia/seo-tecnico-nextjs"/>
```

That's **valid**. HTML attribute names are case-insensitive: the browser's
parser normalizes it to `hreflang`, the DOM returns it in lowercase, and
Google reads it without any trouble. What can't read it is any script that
searches a raw HTTP response for the string `hreflang=` with a case-sensitive
match.

What makes it treacherous is that the same check passes or fails depending
on **where** you read the page. Read the DOM of a page open in a browser, and
the attribute is lowercase and everything passes. Read the same page over
HTTP, and it's camelCase and the result is zero. This site's audit did both
(the DOM for the current page, HTTP for the alternate), which is why it
reported exactly the missing return link.

The fix is one line, and it applies to any scripted hreflang audit (the
comment says the `i` flags are the fix):

```ts
// tests/seo/seo.spec.ts — as flags `i` são o conserto
return (html.match(/<link\b[^>]*>/gi) ?? [])
  .filter((tag) => /rel="alternate"/i.test(tag) && /\bhreflang=/i.test(tag))
```

If you've ever run your own crawler on a Next.js site and concluded it had no
hreflang, recheck with a case-insensitive search before filing a ticket. This
site's [meta tag validator](/en/tools/meta-tag-validator) reads the server's
HTML for the same reason this article argues for: it normalizes attribute
names. It doesn't check hreflang yet, but when it does, it'll follow the same
rule.

## `<html lang>`: what the App Router won't let you do

The question that comes up right after you create the English route: how do
you change the `<html>` element's `lang` just for that route?

In the App Router, you **can't**, at least not from a nested layout. The
`<html>` tag belongs to the root layout, and a child layout can't rewrite it.
There are two ways out, and neither is free:

1. **Two root layouts, using route groups** (`app/(pt)/layout.tsx` and
   `app/(en)/layout.tsx`, each with its own `<html lang>`). This is the
   framework's official answer. The cost is that navigating between the two
   groups triggers a **full page load** rather than a client-side navigation,
   and every existing route has to move into one of the groups.
2. **Mark the subtree**: `<article lang="en">` on the English page, leaving
   `<html lang="pt-BR">` as it is.

This site went with the second option, and not out of laziness. The header,
the footer and the consent banner around the article **really are in
Portuguese**. Switching the whole document to `en` would mislabel that
frame; marking only the English part as English is the honest description of
a page whose content and interface speak different languages.

The SEO impact is zero, and it's worth saying plainly: Google **ignores** the
`lang` attribute for language detection and reads the content instead. What
doesn't ignore it is assistive technology, which is why the markup has to be
right. Once `/en` has its own frame, option 1 becomes worth the price.

**Update (September 2026):** `/en` got its own frame (home page, about page,
header, footer and consent banner in English), and the site switched to
option 1. `<html lang>` now matches each page's hreflang, and the SEO test
suite enforces that on every route with a pair. The full page load when
switching languages was confirmed, and the migration came with three more
costs:

- **A 404 with no shared layout.** With two root layouts, the page for a URL
  that doesn't exist has no layout to inherit. The fix was
  `global-not-found.tsx`, which in Next.js 16 still requires
  `experimental.globalNotFound`.
- **Wasted prefetches.** A `<Link>` to a route in the other group gets
  prefetched like any other, but the navigation reloads the whole page and
  throws away what was fetched. Links that cross languages, like the language
  switcher, now use `prefetch={false}`.
- **OG images with new URLs.** Inside a route group, metadata images generated
  by file convention get a hash in their URL, so every hand-written URL points
  to a 404. That case is covered in the [article on the Next.js Metadata
  API](/en/blog/nextjs-metadata-api).

## The translated version's URL

There are two defensible approaches: mirror the path
(`/en/guia/seo-tecnico-nextjs`) or translate the slug
(`/en/guide/technical-seo-nextjs`). This site chose the second, because the
URL is part of what the page says it is: an English page with a Portuguese
slug sends the wrong signal right there in the address.

The cost is real and worth noting: with different slugs, you can't derive one
side's path from the other with a regex, which is exactly why the map in the
previous section exists. Mirroring the path would have made the map
unnecessary; this was a deliberate trade-off.

## The visible link that contradicts the hreflang

A common failure, and an easy one to miss: correct hreflang in the `<head>`,
and a language switcher in the menu that points to the other language's
**home page**. A reader who clicks "English" on an article lands on a generic
home page and leaves, and the two signals the site sends about the same
relationship disagree with each other.

The prevention is the same as in the map section: the switcher reads from
the **same source** that generates the tags. Here, it looks up the
counterpart's path through the pair, so the visible link and the
machine-readable declaration can't drift apart. The label, by the way, is
written in the target language ("Português" on the English page): someone
looking for the other version reads the language they're looking for, not
the one they're already in.

## How to lock it in with CI

None of this survives six months of maintenance without a test. And the
right test doesn't read the source code: it reads the **served HTML**, fetches
the declared alternate and checks that the alternate links back:

```ts
// tests/seo/seo.spec.ts — roda em toda rota do sitemap
const alternateResponse = await page.request.get(alternatePath)
expect(alternateResponse.status()).toBe(200)

const reciprocal = extractHreflangLinks(await alternateResponse.text())
expect(
  reciprocal.map((l) => new URL(l.href).pathname),
  `${alternatePath} must link back to ${route} via hreflang`
).toContain(route)
```

The comment says it runs on every route in the sitemap. Notice what it
catches that a code review wouldn't: the alternate **returns a 200** (hreflang
pointing to a broken URL is a common migration mistake), and the return link
**exists in the HTML actually sent**, not just in the developer's intentions.

A process detail that's worth more than the code: that test was written
**before** any English page existed, with a guard that kept it idle while no
route emitted hreflang. It sat dormant for weeks and switched itself on the
day the `/en` route was added to the sitemap, and the first thing it did was
find the camelCase problem. Writing the assertion alongside the rule, even
when there's nothing to assert yet, is cheap, and it's the future version of
the site that benefits, not the current one.

## How to know it worked

Correct markup isn't a result. The signal that settles it lives in Search
Console, in **URL Inspection** for each version: compare the user-declared
canonical with the **Google-selected canonical**. If Google picks one
language's URL as the canonical for the other, it has merged the two pages
into one: the cluster was rejected, and no amount of correct tags in your code
will change that. As long as both languages keep their own canonicals and each
shows up in searches in its own language, it's working.

Search Console's page indexing report has a section on alternate languages
that helps, but URL-by-URL inspection is what really answers the question.

And in the interest of transparency: the English version of the guide went
live on July 26, 2026, along with this implementation. **There's no verdict
yet**: a 28-day window has to close before any number here means anything,
and the registered hypothesis is that the English version earns its own
impressions **without** dragging down the Portuguese version's. If it does
drag them down, the pair is being read as duplication and the implementation
has failed. The result will appear here once it exists, not before.
