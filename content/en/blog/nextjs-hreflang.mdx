In the App Router, hreflang comes from the Metadata API's
`alternates.languages` field, and the framework turns that object into the
`<link rel="alternate" hreflang>` tags in the `<head>`. The syntax is the easy
part. What decides whether it works is **reciprocity**: if page A declares B as
an alternative and B doesn't declare A back, Google discards the whole cluster,
with no build error, no warning in the HTML, no visible symptom. This article
shows the implementation that survives that, with this site's code: the English
version of the guide, the pair declared in a single source, the test that checks
the return link in the served HTML, and a Next.js trap that made this site's
audit report missing hreflang on a page that was perfectly correct.

## The three rules that decide whether hreflang works

| Rule | What it requires | What happens if you get it wrong |
| --- | --- | --- |
| Reciprocity | If A declares B, B declares A | Google disregards the annotation, silently |
| Self-reference | Each page lists itself among the alternatives | The block stops being identical on both sides and becomes a source of drift |
| `x-default` | A version for anyone who matches no language | Google chooses on its own which one to serve |

Self-reference is the one that causes the most surprise, so it is worth
explaining: since each page lists **every** version, itself included, the block
of tags comes out **exactly the same** on both sides of the pair. That is not
redundancy; it is what makes reciprocity checkable. Two blocks that should be
identical are easy to compare; two blocks that should be complementary are not.

## Where to declare it: `alternates.languages`

This is the field, and it sits in the same `alternates` object that carries the
canonical:

```ts
// illustrative example — this site's real implementation comes in the next section
export const metadata: Metadata = {
  alternates: {
    canonical: "/guia/seo-tecnico-nextjs",
    languages: {
      "pt-BR": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
      en: "https://seotecnico.dev.br/en/guide/technical-seo-nextjs",
      "x-default": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
    },
  },
};
```

Two observations the documentation doesn't highlight. The URLs must be
**absolute** (relative hreflang doesn't count, which is why the example above
repeats the domain). And `alternates`, like `openGraph`, is **replaced, not
merged** between layout and page: a language block defined only in the layout
disappears on the first route that declares its own `alternates`. It is the
same [Metadata API shallow merge](/en/blog/nextjs-metadata-api) that already
broke this site's Open Graph once.

But the real problem with the snippet above is neither of those. It is that it
is written **on the page**.

## The pair has to come from a single source

Declaring the pair by hand on each page works on the day you write it, and
breaks at the first refactor: someone renames a route, updates the hreflang on
the side they were editing, and the other side keeps pointing to a URL that no
longer exists. There is no error. There is a cluster that stopped existing.

The fix is structural: the pairs live in a module, and both sides are generated
from the **same object**. This is an excerpt of this site's production map, in
`src/lib/hreflang.ts` (the first pair; the others follow the same shape):

```ts
export const TRANSLATION_PAIRS: readonly TranslationPair[] = [
  {
    id: 'seo-tecnico-nextjs',
    paths: {
      'pt-BR': '/guia/seo-tecnico-nextjs',
      en: '/en/guide/technical-seo-nextjs',
    },
  },
] as const
```

And the single metadata helper **derives** the language block from the route's
path, instead of receiving it as an argument; the snippet below is this site's
`buildMetadata()`:

```ts
const languagePaths = languageAlternatePaths(path)

return {
  alternates: {
    canonical: path,
    ...(languagePaths
      ? {
          languages: Object.fromEntries(
            Object.entries(languagePaths).map(([lang, target]) => [
              lang,
              absoluteUrl(target),
            ])
          ),
        }
      : {}),
    // …
  },
}
```

The gain is that the page loses the ability to get it wrong. It doesn't declare
the pair: it states its own path, and the pair comes from whoever knows. A route
with no translation emits nothing, because a one-item cluster is just noise. And
since both sides query the same structure, the block comes out identical on
both, which is exactly what the self-reference rule asked for.

## The camelCase attribute that fools audits

This part is original, and it cost a debugging session here.

When the reciprocity check was turned on in CI, it reported that the English
version **had no hreflang tag at all**, on a page whose `view-source` showed the
three tags, correct. The cause: Next.js serializes the attribute as
`hrefLang`, in camelCase, in the HTML it delivers:

```html
<link rel="alternate" hrefLang="pt-BR" href="https://seotecnico.dev.br/guia/seo-tecnico-nextjs"/>
```

That is **valid**. HTML attribute names are case-insensitive: the browser's
parser normalizes it to `hreflang`, the DOM returns lowercase, and Google reads
it without trouble. What doesn't read it is any script that searches for the
string `hreflang=` in a raw HTTP response with a case-sensitive search.

The detail that makes it treacherous is that the same check passes or fails
depending on **where** you read the page. Reading the DOM of a page open in the
browser, the attribute appears in lowercase and everything passes. Reading the
same page over HTTP, it appears in camelCase and the result is zero. This site's
audit did both (the DOM for the current page, HTTP for the alternative), and
that is why it reported exactly the missing return link.

The fix is one line, and it applies to any hreflang audit done by script (the
comment says the `i` flags are the fix):

```ts
// tests/seo/seo.spec.ts — as flags `i` são o conserto
return (html.match(/<link\b[^>]*>/gi) ?? [])
  .filter((tag) => /rel="alternate"/i.test(tag) && /\bhreflang=/i.test(tag))
```

If you have ever run your own crawler on a Next.js site and concluded it had no
hreflang, it is worth rechecking with a case-insensitive search before opening a
ticket. This site's [meta tag validator](/ferramentas/validador-meta-tags) reads
the server's HTML for the same reason this article argues for: it normalizes
attribute names, and it doesn't check hreflang yet; when it does, it will be by
that yardstick (its interface is in Portuguese).

## `<html lang>`: what the App Router won't let you do

The question that comes up right after creating the English route: how do you
change the `<html>` `lang` only there?

In the App Router, you **don't**, not from a nested layout. The `<html>` tag
belongs to the root layout, and a child layout doesn't rewrite it. There are two
ways out, and neither is free:

1. **Two root layouts, by route group** (`app/(pt)/layout.tsx` and
   `app/(en)/layout.tsx`, each with its own `<html lang>`). It is the framework's
   canonical answer. The cost is that navigating between the two groups causes a
   **full page load**, not a client-side navigation, and every existing route has
   to move into one of the groups.
2. **Mark the subtree**: `<article lang="en">` on the English page, with
   `<html lang="pt-BR">` left intact.

This site chose the second, and not out of laziness. The header, the footer and
the consent banner around the article **really are in Portuguese**. Switching
the whole document to `en` would mislabel that frame; marking as English only
what is English is the honest description of a page whose content and interface
speak different languages.

The SEO impact of that is nil, and it is worth saying plainly: Google
**ignores** the `lang` attribute for language detection; it reads the content.
What doesn't ignore it is assistive technology, and that is why the markup has to
be right. When `/en` has a frame of its own, option 1 becomes worth the price.

**Update (September 2026):** `/en` got its own frame (home, about page, header,
footer and consent banner in English), and the site moved to option 1. The
`<html lang>` now follows each page's hreflang, and the SEO suite requires that
on every route with a pair. The full page load when switching languages was
confirmed, and the migration charged three more things:

- **A 404 with no common layout.** With two root layouts, the page for a
  non-existent URL has no layout to inherit from. The way out was
  `global-not-found.tsx`, which in Next.js 16 still depends on
  `experimental.globalNotFound`.
- **Wasted prefetch.** A `<Link>` to a route in the other group is prefetched
  like any other, but the navigation reloads the whole page and throws away what
  was fetched. Links that cross languages, such as the language switcher, now
  use `prefetch={false}`.
- **OG images with a new URL.** Inside a route group, metadata images generated
  by file convention get a hash in their URL, and every hand-written URL points
  to a 404. The case is in the [article on the Next.js Metadata
  API](/en/blog/nextjs-metadata-api).

## The translated version's URL

Two defensible forms: mirror the path (`/en/guia/seo-tecnico-nextjs`) or
translate the slug (`/en/guide/technical-seo-nextjs`). This site chose the
second, because the URL is part of what the page claims to be: an English page
with a Portuguese slug gives a wrong hint right in the address.

The cost is real and worth recording: with different slugs, one side's path
cannot be derived from the other by regex, and that is precisely why the map in
the previous section exists. Mirroring the path would make the map unnecessary;
it was a trade-off made consciously.

## The visible link that contradicts the hreflang

A common failure, and an annoying one to notice: correct hreflang in the
`<head>`, and the menu's language switcher pointing to the other language's
**home**. A reader who clicks "English" on an article page lands on a generic
home and leaves, and the two signals the site emits about the same relationship
disagree.

The prevention is the same as in the map section: the switcher reads the **same
source** that generates the tags. Here it resolves the counterpart's path through
the pair, so the visible link and the machine declaration can't drift apart. The
label, incidentally, is written in the target language ("Português" on the
English page): whoever is looking for the other version reads the language they
are looking for, not the one they are already seeing.

## How to lock it in CI

None of the above survives six months of maintenance without a test. And the
right test doesn't read the source code: it reads the **served HTML**, fetches
the declared alternative and checks that it declares the return link:

```ts
// tests/seo/seo.spec.ts — roda em toda rota do sitemap
const alternateResponse = await page.request.get(alternatePath)
expect(alternateResponse.status()).toBe(200)

const reciprocal = extractHreflangLinks(await alternateResponse.text())
expect(
  reciprocal.map((l) => new URL(l.href).pathname),
  `${alternatePath} must link back to ${route} via hreflang`
).toContain(route)
```

The comment says it runs on every route in the sitemap. Note what it covers
that a code inspection wouldn't: the alternative **responds with 200** (hreflang
to a broken URL is a common error in migrations) and the return link **exists
in the delivered HTML**, not in the developer's intent.

A process detail worth more than the code: that test was written **before** any
English page existed, with a guard that kept it inert while no route emitted
hreflang. It lay dormant for weeks and started running on its own the day the
`/en` route entered the sitemap, and the first thing it did was find the
camelCase problem. Writing the assertion together with the rule, even with
nothing to assert yet, is cheap; and the one who pays is the future version of
the site, not the current one.

## How to know it worked

Correct markup is not a result. The signal that decides it sits in Search
Console, in each version's **URL Inspection**: compare the user-declared
canonical with the **Google-selected canonical**. If Google picks one language's
URL as the canonical of the other, it merged the two pages into one: the cluster
was rejected, and no amount of correct tags in the code changes that. As long as
both languages keep their own canonicals and each shows up in searches in its own
language, it is working.

Search Console's pages report has a section on alternate languages that helps,
but URL-by-URL inspection is what really answers the question.

And the transparency this site owes: the English version of the guide went live
on 26 July 2026, together with this implementation. **The verdict doesn't exist
yet**: a 28-day window has to close before any number here means anything, and
the registered hypothesis is that the English version gains its own impressions
**without** pulling down the Portuguese version's. If it does pull them down,
the pair is being read as duplication and the implementation failed. The result
appears here when it exists, not before.
