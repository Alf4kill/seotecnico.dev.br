In the Next.js App Router, hreflang comes from the Metadata API's
`alternates.languages` field, and the framework turns that object into
`<link rel="alternate" hreflang>` tags in the `<head>`. Getting the syntax
right is the easy part. Whether hreflang works depends on **reciprocity**. If
page A declares B as an alternate and B doesn't declare A back, Google
discards the whole cluster, and you get no build error, no warning in the
HTML, and no visible symptom.

This article walks through an implementation that holds up, using this
site's own code: the English version of the guide, a pair declared in a
single source, a test that checks for the return link in the served HTML,
and a Next.js trap that led this site's audit to report hreflang missing
from a page that was perfectly correct.

## The three rules that decide whether hreflang works

Hreflang works when all three of these hold:

| Rule | What it requires | What happens if you get it wrong |
|---|---|---|
| Reciprocity | If A declares B, B declares A | Google disregards the annotation, silently |
| Self-reference | Each page lists itself among the alternates | The block is no longer identical on both sides and becomes a source of divergence |
| `x-default` | A version for anyone who matches no declared language | Google decides on its own which version to serve |

Self-reference surprises people most, so it's worth explaining. Each page
lists **every** version, itself included, so its tag block comes out
**exactly the same** on both sides of the pair. That isn't redundancy. It's
what makes reciprocity verifiable. Comparing two blocks that should be
identical is easy. Comparing two that should complement each other isn't.

## Where to declare it: `alternates.languages`

You declare it in the same `alternates` object that carries the canonical.
It looks like this:

```ts
// illustrative example — this site's real implementation comes in the next section
export const metadata: Metadata = {
  alternates: {
    canonical: "/guia/seo-tecnico-nextjs",
    languages: {
      "pt-BR": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
      en: "https://seotecnico.dev.br/en/guide/technical-seo-nextjs",
      "x-default": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
    },
  },
};
```

Two details don't get much attention in the documentation:

- URLs must be **absolute**. Relative hreflang doesn't count, which is why
  the example repeats the domain.
- `alternates`, like `openGraph`, is **replaced, not merged** between a
  layout and a page. A language block defined only in the layout disappears
  on the first route that declares its own `alternates`. It's the same
  [Metadata API shallow merge](/en/blog/nextjs-metadata-api) that already
  broke this site's Open Graph.

Neither of these is what's really wrong with the snippet, though. What's
wrong is that the pair is written **on the page**.

## The pair has to come from a single source

Declaring the pair by hand on each page works the day you write it and
breaks at the first refactor. Someone renames a route and updates hreflang
on the side they were editing, while the other side keeps pointing to a URL
that no longer exists. There's no error, just a cluster that stopped
existing.

Fixing this takes a structural change. Pairs live in one module, and both
sides are generated from the **same object**. Here's an excerpt of this
site's production map, in `src/lib/hreflang.ts`, with the first pair. The
rest follow the same shape.

```ts
export const TRANSLATION_PAIRS: readonly TranslationPair[] = [
  {
    id: 'seo-tecnico-nextjs',
    paths: {
      'pt-BR': '/guia/seo-tecnico-nextjs',
      en: '/en/guide/technical-seo-nextjs',
    },
  },
] as const
```

The site has a single metadata helper, and instead of taking the language
block as an argument, it **derives** that block from the route's path.
Here's the helper, `buildMetadata()`:

```ts
const languagePaths = languageAlternatePaths(path)

return {
  alternates: {
    canonical: path,
    ...(languagePaths
      ? {
          languages: Object.fromEntries(
            Object.entries(languagePaths).map(([lang, target]) => [
              lang,
              absoluteUrl(target),
            ])
          ),
        }
      : {}),
    // …
  },
}
```

Now the page can't get it wrong. It doesn't declare the pair. It states its
own path, and the pair comes from the map, the one place that knows it. A
route without a translation emits nothing, because a one-item cluster is
noise.
And since both sides query the same structure, their blocks come out
identical, which is exactly what the self-reference rule asked for.

## The camelCase attribute that fools audits

This part is original, and finding it cost me a debugging session. When I
turned on the reciprocity check in CI, it reported that the English version
**had no hreflang tag at all**, even though its `view-source` showed three
tags, all of them correct.

It turns out that Next.js serializes the attribute in camelCase, as
`hrefLang`, in the HTML it serves:

```html
<link rel="alternate" hrefLang="pt-BR" href="https://seotecnico.dev.br/guia/seo-tecnico-nextjs"/>
```

That's **valid**. HTML attribute names are case-insensitive, so the
browser's parser normalizes it to `hreflang`, the DOM returns it in
lowercase, and Google reads it without trouble. What can't read it is any
script that runs a case-sensitive search for the string `hreflang=` in a raw
HTTP response.

It's treacherous because the same check passes or fails depending on
**where** you read the page. Read the DOM of a page open in the browser and
you get lowercase, so it passes. Fetch the same page over HTTP and you get
camelCase, so the count is zero. This site's audit did both, reading the
DOM for the current page and HTTP for the alternate, which is exactly why it
reported the return link as missing.

The fix is one line, and it applies to any scripted hreflang audit. As the
comment in the snippet notes, the `i` flags do it:

```ts
// tests/seo/seo.spec.ts — as flags `i` são o conserto
return (html.match(/<link\b[^>]*>/gi) ?? [])
  .filter((tag) => /rel="alternate"/i.test(tag) && /\bhreflang=/i.test(tag))
```

If you've run your own crawler on a Next.js site and concluded it had no
hreflang, recheck with a case-insensitive search before you open a ticket.

This site's [meta tag validator](/en/tools/meta-tag-validator) reads the
server's HTML, for the same reason this article argues for, and it
normalizes attribute names. It doesn't check hreflang yet. When it does,
it'll use this same rule.

## `<html lang>`: what the App Router won't let you do

Once you've created the English route, the next question is how to change
the `lang` of `<html>` on that route alone. In the App Router, you **can't**,
at least not from a nested layout. `<html>` belongs to the root layout, and
a child layout doesn't rewrite it. You have two ways out, and neither is
free:

1. **Two root layouts, by route group** (`app/(pt)/layout.tsx` and
   `app/(en)/layout.tsx`, each with its own `<html lang>`). This is the
   framework's official answer. It costs you a **full page load** whenever
   you navigate between the two groups, instead of a client-side
   navigation, and every existing route has to move into one of the groups.
2. **Mark the subtree** with `<article lang="en">` on the English page,
   leaving `<html lang="pt-BR">` intact.

This site originally chose the second, and not out of laziness. Around the
article, the header, footer, and consent banner **really were in Portuguese**.
Switching the whole document to `en` would have mislabeled that frame.
Marking only the English content as English honestly described a page whose
content and interface spoke different languages.

To be clear, this choice had no SEO impact. Google **ignores** the `lang`
attribute when detecting language and reads the content instead. Assistive
technology doesn't ignore it, which is why the markup has to be right.
Option 1 would be worth its price once `/en` had its own frame.

**Update (September 2026):** `/en` got its own frame (home, about page,
header, footer, and consent banner in English), and the site moved to
option 1. `<html lang>` now follows each page's hreflang, and the SEO suite
requires it on every route with a pair. As expected, switching languages
now causes a full page load. The migration had three other costs:

- **A 404 without a shared layout.** With two root layouts, the page for a
  nonexistent URL has no layout to inherit from. The fix is
  `global-not-found.tsx`, which in Next.js 16 still depends on
  `experimental.globalNotFound`.
- **Wasted prefetch.** A `<Link>` to a route in the other group gets
  prefetched like any other, but the navigation reloads the whole page and
  throws away what was fetched. Cross-language links, such as the language
  switcher, now use `prefetch={false}`.
- **OG images with a new URL.** Inside a route group, file-convention
  metadata images get a hash in their URL, so every hand-written URL points
  to a 404. There's more on this in the
  [article on the Next.js Metadata API](/en/blog/nextjs-metadata-api).

## The translated version's URL

There are two defensible options: mirror the path
(`/en/guia/seo-tecnico-nextjs`) or translate the slug
(`/en/guide/technical-seo-nextjs`). This site chose the second, because a
URL is part of what a page says it is. An English page with a Portuguese
slug gives the wrong clue right in its address.

That choice has a real cost, and it's worth writing down. With different
slugs, you can't derive one side's path from the other with a regex, and
that's exactly why the map from the earlier section exists. Mirroring would
have made the map unnecessary. I accepted that trade-off deliberately.

## The visible link that contradicts the hreflang

This failure is common, and it's easy to miss. Hreflang in the
`<head>` is correct, but the menu's language switcher points to the other
language's **home page**. A reader who clicks "Português" on an article
lands on a generic home page and leaves, and the site ends up sending two
signals about the same relationship that disagree.

You prevent it the way the map does. The switcher reads the **same
source** that generates the tags. On this site, it resolves the
counterpart's path through the pair, so a visible link and its
machine-readable declaration can't diverge.

Its label is written in the target language, so the English page shows
"Português". Anyone looking for the other version sees the name of the
language they want, not the one they're reading.

## How to lock it in with CI

None of the above survives six months of maintenance without a test, and
that test should read the **served HTML**, not source code. It fetches the
declared alternate and checks that the alternate declares the return link.
It runs on every route in the sitemap:

```ts
// tests/seo/seo.spec.ts — roda em toda rota do sitemap
const alternateResponse = await page.request.get(alternatePath)
expect(alternateResponse.status()).toBe(200)

const reciprocal = extractHreflangLinks(await alternateResponse.text())
expect(
  reciprocal.map((l) => new URL(l.href).pathname),
  `${alternatePath} must link back to ${route} via hreflang`
).toContain(route)
```

It catches two things that code inspection wouldn't. First, it
checks that the alternate **returns 200**, since hreflang pointing to a
broken URL is a common migration error. Second, it checks that the return
link **exists in the delivered HTML**, not just in the developer's
intention.

One detail of the process is worth more than the code. I wrote the test
**before** any English page existed, with a guard that kept it inert while
no route emitted hreflang. It sat dormant for weeks and started running on
its own the day the `/en` route entered the sitemap. Its first catch was the
camelCase problem. Writing an assertion along with the rule, even before
there's anything to assert, costs little, and the future version of the site
collects the payoff, not the current one.

## How to know it worked

Correct markup isn't a result. Search Console has the signal that settles
it. Run **URL Inspection** on each version and compare the user-declared
canonical with the **Google-selected canonical**. If Google picks one
language's URL as the other's canonical, it has merged the two pages
into one and rejected the cluster, and no amount of correct tags in the
code will change that. As long as both languages keep their own canonicals
and each one appears in search results in its own language, it's working.

Search Console's page indexing report has a section on alternate languages
that helps, but URL-by-URL inspection is what answers the question.
