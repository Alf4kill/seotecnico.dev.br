Googlebot renders JavaScript. Google's documentation describes three stages
(crawling, rendering and indexing), and content built by scripts makes it into
the index once the page has gone through the rendering queue. AI assistants
are a different kind of reader. In the test I ran on this site between
September and October 2026, ChatGPT (Go plan), Claude (Pro) and Gemini (free)
didn't run the page's JavaScript in any round. DeepSeek (free) ran it every
time but only returned the loaded value in 3 of 5, and Grok (free) in 5 of 5.
The only content that reached all five was visible text already present in the
first render.

For years, "Google renders JavaScript" was the argument for not worrying
about what the server sends. Now that AI assistants read pages too, that
argument only covers one of the readers. This article treats them separately
and says where each claim comes from: Googlebot's behavior comes from the
official documentation; the assistants' behavior comes from this site's
measurements.

One note on scope before going further: what I measured was **assistants
responding to a user's prompt** that includes a page's address, on specific
plans and dates. I didn't measure training crawlers (the ones that collect
pages in bulk), and the results don't automatically apply to them.

## How Google handles JavaScript

Google Search Central's [JavaScript SEO
basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
page (updated March 4, 2026) describes the process like this:

1. **Crawling.** Googlebot fetches the URL, checks `robots.txt` and reads the
   response HTML. Links in `<a href>` are added to the crawl queue at this
   stage.
2. **Rendering.** Pages that return a `200` status go into a rendering queue,
   whether or not they use JavaScript, unless a robots meta tag or header
   tells Google not to index them. When resources allow, a headless Chromium
   runs the scripts. The documentation says a page may sit in the queue for a
   few seconds, but it can take longer. There's no published deadline.
3. **Indexing.** Google uses the rendered HTML for indexing and to discover
   new links.

The renderer's Chromium is "evergreen": it tracks the current stable browser
rather than being stuck on an old version. In practice, modern JavaScript
APIs work; what the documentation asks is that you be careful with features
that can't be used without a polyfill.

Three details from the same documentation matter for this article:

- **The page itself recommends server-side rendering or pre-rendering**,
  because it makes the site faster for users and crawlers alike, and because
  not every bot runs JavaScript.
- **A `noindex` in the original HTML may make Google skip rendering.** A
  script that removes the `noindex` later may simply never run.
- **A canonical changed by JavaScript** shouldn't point somewhere other than
  the canonical in the original HTML.

Dynamic rendering (serving pre-rendered HTML only to bots) is now described
in the documentation as a [workaround, not a recommended
solution](https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering);
Google points to SSR, static rendering or hydration instead.

## How the AI assistants handled it

The test is described in detail in [Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript), which extends the
positive control summarized in the [AI crawler detection case
study](/en/case-studies/ai-crawler-detection). Here's the minimum you need to
read the numbers.

A lab page shows two codes. The first, `UC-`, is text a Client Component
outputs in the first render, so it's in the HTML the server sends. The
second, `JS-`, only exists after a `fetch` inside `useEffect` completes, so it
only shows up if something runs the page's JavaScript and waits for the
response. Each assistant gets its own secret URL, so the URL, not the user
agent, tells me who fetched the page. The server also logs whether the
`fetch` endpoint was called, which shows whether the script ran regardless of
what the assistant says.

There are two conclusions the table doesn't support:

**Zero doesn't mean "never".** With 0 of 5, a true rate of nearly half of all
visits is still consistent with the result (one-sided 95% upper bound). With
0 of 8, in Gemini's case, the ceiling drops to about a third. What you can
say is what happened in those rounds, on those plans, on those dates. An
assistant may behave differently the following week.

**The result doesn't explain why.** Gemini comes from the same company as
Googlebot and still didn't run the script in any of its 8 rounds. I don't
know what the assistant's page-reading pipeline looks like, and the table
doesn't tell us. What it does show is that "Google renders" and "Google's
assistant renders" were, in this test, two different things.

The practical conclusion is narrow, and that's what makes it reliable:
visible text in the served HTML reached all of them; what depended on the
`fetch` reached two out of five. Note the word "visible": JSON-LD is also in
the served HTML, and only Grok read it, as covered in [structured data and
AI](/en/blog/structured-data-and-ai).

## The middle case: rendering isn't enough

DeepSeek (free) is the most useful result in the table, because it pulls
apart two things usually treated as one: running JavaScript, and returning
the content that JavaScript produces.

According to the server log, the script ran in all 11 of DeepSeek's rounds,
across the experiment's three conditions. Even so, the value only made it
into some of the answers:

- **Neutral rounds:** 3 of 5.
- **With a hint about where the value was:** 0 of 3.
- **With the endpoint's address in the prompt:** 3 of 3.

In the 5 rounds where the value didn't come through, the answer said the page
only showed "carregando…" ("loading…"), the state before the `fetch`
completes. That's consistent with the text being captured before the value
arrived, but it's my interpretation, not something the log proves. With the
address in the prompt, the log shows something different: besides rendering
the page, DeepSeek opened the JSON address directly, the way you'd open a
link. That the answer took the value from that direct request rather than the
rendered page **is an inference**: the server records the requests, not the
order in which the assistant read things.

The lesson for publishers: even with a reader that runs JavaScript, content
that depends on an asynchronous request is at the mercy of when that reader
decides the page is "done". The first render doesn't have that problem.

## What usually ends up outside the first render

The only pattern I measured was a `fetch` inside `useEffect`. The rest of
this list follows from the mechanism: if the content isn't in the served
HTML, it depends on something running the JavaScript. I don't have numbers
for these.

- **Data fetched on the client after mount.** This is the measured case:
  `fetch` in `useEffect`, or SWR and React Query with no initial data from the
  server.
- **Client-only components.** In Next.js, `dynamic(() => import('./X'), { ssr:
  false })` deliberately removes the component from the served HTML.
- **Content that only mounts after an interaction.** Tabs, accordions and
  modals that **only mount** their content on click don't have it in the HTML.
  If the content is rendered and just hidden with CSS, it's there.
- **"Load more" lists and infinite scroll.** The first batch may be in the
  HTML; the rest isn't.
- **Third-party widgets.** Reviews, prices and stock levels injected by an
  external script.
- **Metadata and structured data injected by JavaScript.** Google accepts
  script-generated JSON-LD, but it depends on rendering. For the assistants,
  JSON-LD is a problem even when it comes straight from the server; I cover
  that in [structured data and AI](/en/blog/structured-data-and-ai).

## How to get content into the first render, stack by stack

The goal is the same in any stack: the text that matters has to ship in the
response HTML, before any script runs. The examples below are illustrative;
only Next.js was measured here.

**Next.js (App Router).** Server Components already render on the server, and
Client Components are pre-rendered on first load too. The fix is to fetch
data on the server instead of in `useEffect`. An illustrative example:

```tsx
// app/product/[id]/page.tsx (illustrative)
import { getProduct } from '@/lib/products'

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const product = await getProduct(id)

  return <p>{product.description}</p>
}
```

**WordPress and PHP.** PHP builds the page on the server, so you get the
first render for free. People who come from shared hosting, like me, tend to
underestimate that advantage. The risk shows up when a plugin or theme starts
fetching content via AJAX or REST after the page loads. Here's the
difference, in illustrative form:

```php
<?php // illustrative: the price ships in the served HTML ?>
<p class="price"><?= htmlspecialchars($product['price']) ?></p>

<!-- illustrative: the price only exists after the script runs -->
<p class="price" id="price"></p>
<script>
  fetch('/wp-json/shop/v1/price/123')
    .then((r) => r.json())
    .then((d) => (document.getElementById('price').textContent = d.price))
</script>
```

**React SPA built with Vite.** By default, the served HTML is an empty shell,
and everything the user sees is built by the script:

```html
<!-- illustrative: the index.html a React SPA built with Vite serves -->
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>My shop</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/assets/index-a1b2c3.js"></script>
  </body>
</html>
```

To a reader that doesn't run JavaScript, this page has a title and nothing
else. The way out is to pre-render routes at build time, or to move the pages
that need to be read to a framework with SSR. I didn't test an SPA in the
lab, so I'll stick to the mechanism here: I have no data on how each
assistant handles a page built entirely on the client.

## How to check

The test is always the same: is the text that matters in the HTML the server
sends?

1. **Fetch the raw HTML.** A `curl` shows exactly what a reader without
   JavaScript receives:

   ```bash
   # illustrative: does the text appear in the served HTML?
   curl -s https://example.com/product/123 | grep -c "Free shipping"
   ```

   If the result is `0`, the text isn't in the first render.

2. **Compare the page source with the DOM.** The browser's "View page source"
   (Ctrl+U) shows the served HTML; the DevTools Elements panel shows the DOM
   after JavaScript has run. Anything that only appears in the second depends
   on rendering.

3. **Disable JavaScript.** In DevTools, open the command menu (Ctrl+Shift+P),
   run "Disable JavaScript" and reload. What's left on screen is what a text
   extractor gets.

4. **Check the metadata.** The [meta tag
   validator](/en/tools/meta-tag-validator) shows whether `title`,
   `description` and the canonical are present in the HTML the server sends.

5. **See Google's version.** In Search Console's URL Inspection tool, the
   live test shows the HTML Google rendered for the tested page. That's
   confirmation from Googlebot's side, and only from its side.

6. **Automate it.** On this site, a Playwright test checks the lab's codes in
   the served HTML without running the page's JavaScript. It strips out every
   `<script>` and searches for each code in what's left:

```ts
// tests/seo/lab-control.spec.ts (lines 39–50)
// O texto visível, sem nenhum <script> (JSON-LD e payload RSC incluídos).
const text = html.replace(/<script\b[^>]*>[\s\S]*?<\/script>/gi, '')
expect(text).toContain(codes.SRV)
expect(text).toContain(codes.UC)
expect(text, 'LD- must not be in the visible text').not.toContain(codes.LD)

const jsonLd = [...html.matchAll(/<script type="application\/ld\+json">([\s\S]*?)<\/script>/g)]
  .map((m) => JSON.parse(m[1]) as { identifier?: string })
expect(jsonLd.map((node) => node.identifier)).toContain(codes.LD)

// Nem no texto nem em script algum: o JS- só existe depois do fetch.
expect(html, 'JS- must not be in the served HTML at all').not.toContain(codes.JS)
```

The comments are in Portuguese, as they are in the repository. The first
says the visible text is the HTML without any `<script>`, JSON-LD and the RSC
payload included; the last says `JS-` appears neither in the text nor in any
script, because it only exists after the `fetch`.

A note on logs: in the lab, each assistant's identity comes from its secret
URL. In your own server log, all you have is a request profile. The most you
can say is "requests identifying themselves as X", and an assistant's own
explanation of what it read is no substitute for the server log.

## In Next.js: the probe's two components

The lab page uses two components side by side. Both are Client Components in
the same file. The difference is **when** the content exists:

```tsx
// src/components/lab/ControlCodes.tsx (lines 19–44)
export function RenderedByClientComponent({ code }: { code: string }) {
  return (
    <p>
      Código do componente cliente: <strong>{code}</strong>
    </p>
  )
}

export function FetchedCode({ endpoint }: { endpoint: string }) {
  const [code, setCode] = useState<string | null>(null)
  const [failed, setFailed] = useState(false)

  useEffect(() => {
    fetch(endpoint, { cache: 'no-store' })
      .then((response) => (response.ok ? response.json() : Promise.reject(response.status)))
      .then((data: { code: string }) => setCode(data.code))
      .catch(() => setFailed(true))
  }, [endpoint])

  return (
    <p>
      Código carregado no navegador:{' '}
      <strong data-testid="fetched-code">{code ?? (failed ? 'indisponível' : 'carregando…')}</strong>
    </p>
  )
}
```

The page's labels are in Portuguese: "Código do componente cliente" means
"Client Component code", "Código carregado no navegador" means "code loaded
in the browser", and "carregando…" means "loading…".

The `UC-` component is marked `'use client'`, but its text is in the served
HTML, because Next.js pre-renders Client Components on the server. Across the
28 neutral rounds, between September and October 2026, that text showed up in
all five assistants' answers every single time. The `JS-` component builds its
value inside `useEffect`, which only runs in the browser after hydration. So
for a reader that doesn't run the script, the value simply doesn't exist:
what's left in the HTML is the "carregando…" that the answers without the
value reported.

The takeaway for a Next.js project is straightforward: `'use client'` isn't
the problem. The problem is putting content that needs to be read behind an
effect, a `dynamic` import with `ssr: false`, or a user interaction.

Outside the lab, no text on this site's pages depends on JavaScript to exist.
I don't use `dynamic`, and the few `useEffect` calls in the codebase handle
the consent banner, search, the copy-code button and Web Vitals measurement,
never content. The probe exists precisely to measure what happens when
someone does the opposite.
