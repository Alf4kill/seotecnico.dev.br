JavaScript SEO now has two readers to satisfy, and they behave differently.
Google's documentation says Googlebot renders JavaScript. It crawls a page,
renders it, and indexes the result, so content built by a script enters the
index once the page has gone through the rendering queue. AI assistants are
a different kind of reader, and in a test I ran on this site between
September and October 2026, most of them didn't run the script. ChatGPT (Go
plan), Claude (Pro), and Gemini (free) didn't run the page's JavaScript in
any round. DeepSeek (free) ran it in every round but returned the loaded
value in only 3 of 5, and Grok (free) returned it in 5 of 5. Only visible
text that was already in the first render reached all five.

For years, "Google renders JavaScript" was the argument for not worrying
about what the server delivers. Now that AI assistants fetch pages too, that
argument covers only one of the readers. This article keeps the two apart
and says where each claim comes from. Everything about Googlebot comes from
Google's official documentation. Everything about the assistants comes from
my measurements on this site.

Keep the scope in mind. I measured **assistants responding to a user's
prompt** that includes a page's address, on specific plans and dates.
I didn't measure training crawlers, the ones that collect pages in bulk, and
the result doesn't automatically carry over to them.

## How Google handles JavaScript

Google describes a three-step pipeline in the Search Central page
[JavaScript SEO
basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics),
last updated March 4, 2026:

1. **Crawling.** Googlebot fetches the URL, checks `robots.txt`, and reads
   the HTML in the response. Links in `<a href>` already go into the crawl
   queue at this stage.
2. **Rendering.** Pages that return a `200` status go into a rendering
   queue, whether or not they use JavaScript, unless a robots meta tag or
   header asks Google not to index them. When resources are available, a
   headless Chromium runs the scripts. According to the docs, a page may sit
   in the queue for a few seconds, but it may take longer. Google doesn't
   publish a deadline.
3. **Indexing.** Google uses the rendered HTML to index the page and to
   discover new links.

Rendering runs on an "evergreen" Chromium, which tracks the stable browser
version instead of staying stuck on an old one. In practice, modern
JavaScript APIs work. The docs do ask you to be careful with features you
can't use without a polyfill.

Three more details from the same docs matter here:

- **The page itself recommends server-side rendering or pre-rendering**,
  because it makes the site faster for users and crawlers, and because not
  every bot runs JavaScript.
- **A `noindex` in the original HTML may make Google skip rendering.** A
  script that removes the `noindex` later may never run.
- **A canonical changed by JavaScript** shouldn't point somewhere other
  than the canonical in the original HTML.

Google now presents dynamic rendering (serving pre-rendered HTML only to
bots) as a
[workaround, not a recommended
solution](https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering).
It points to server-side rendering, static rendering, or hydration instead.

## How the AI assistants handled it

I wrote up the full test in
[Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript).
It extends the positive control I published in
[Does ChatGPT read JavaScript?](/en/blog/does-chatgpt-read-javascript).
You need only a little of the method to read the numbers.

A lab page shows two codes. `UC-` is text that a Client Component outputs in
the first render, so it's in the HTML the server delivers. `JS-` exists only
after a `fetch` inside `useEffect` finishes, so it shows up only if
something runs the page's JavaScript and waits for the response. Each
assistant gets its own secret URL, which tells me who fetched the page
without relying on the user agent. The server also logs whether the `fetch`
endpoint was called, so I know whether the script ran regardless of what the
assistant says.

Don't read two things into this table.

**Zero doesn't mean "never."** With 0 of 5, a true frequency of nearly half
the visits is still compatible with the result (one-sided 95% upper bound).
For Gemini's 0 of 8, the ceiling drops to about a third. I can only state
what happened in those rounds, on those plans, on those dates. An assistant
may behave differently the following week.

**The result doesn't explain why.** Gemini comes from the same company as
Googlebot, and it still didn't run the script in any of its 8 rounds. I
don't know what Gemini's reading pipeline looks like, and the table doesn't
explain it. It does show that, in this test, "Google renders" and
"Google's assistant renders" were different things.

You can take away only a narrow conclusion, and that's what makes it
reliable. Visible text in the served HTML reached all five assistants.
Anything that depended on the `fetch` reached two of five. Note the word
"visible." JSON-LD is in the served HTML too, and only Grok read it, as I
cover in
[structured data and AI](/en/blog/structured-data-and-ai).

## The middle case: rendering isn't enough

DeepSeek (free) is the most useful result in the table. It pulls apart two
things that usually get treated as one: running the JavaScript and
delivering the content that JavaScript produces.

According to the server log, the script ran in all 11 DeepSeek rounds,
across the experiment's three conditions. Only some of those answers carried
the value:

- **Neutral rounds:** 3 of 5.
- **With a hint about where the value was:** 0 of 3.
- **With the endpoint's address in the prompt:** 3 of 3.

In the 5 rounds where the value didn't arrive, the answer said the page
showed only "carregando…" ("loading…"), the state before the `fetch`
finishes. That fits text captured before the value arrived, but it's my
interpretation, not something the log proves.

With the address in the prompt, the log shows something else. Besides
rendering the page, DeepSeek requested the JSON address directly, the way
you'd open a link. I **infer** that the answer took the value from that
direct request and not from the built page. The server records requests,
not DeepSeek's internal reading order.

If you publish content, the lesson holds even for readers that run
JavaScript. Content that depends on an asynchronous request is at the mercy
of whenever the reader decides the page is "done." Anything in the first
render avoids that problem.

## What usually ends up outside the first render

I measured only one of these patterns, a `fetch` inside `useEffect`. The
rest follow from the mechanism, and I don't have numbers for them. If
content isn't in the served HTML, it depends on something running the
JavaScript.

- **Data fetched on the client after mount.** This covers a `fetch` in
  `useEffect`, the case I measured, and SWR or React Query with no initial
  data from the server.
- **Client-only components.** In Next.js,
  `dynamic(() => import('./X'), { ssr: false })`
  leaves the component out of the served HTML on purpose.
- **Content that only mounts after an interaction.** Tabs, accordions, and
  modals that **only mount** their content on click don't have it in the
  HTML. If the content is rendered and just hidden with CSS, it's there.
- **"Load more" lists and infinite scroll.** The first batch may be in the
  HTML. The batches after it aren't.
- **Third-party widgets.** Reviews, prices, or stock levels injected by an
  external script.
- **Metadata and structured data injected by JavaScript.** Google accepts
  JSON-LD generated by a script, but that depends on rendering. For the
  assistants, JSON-LD is a problem even when it comes ready from the server,
  as I explain in [structured data and AI](/en/blog/structured-data-and-ai).

## How to get content into the first render, stack by stack

Whatever your stack, the goal is the same. Text that matters has to ship in
the response HTML, before any script runs. The examples below are
illustrative, and Next.js is the only stack I measured here.

**Next.js (App Router).** Server Components already render on the server,
and Client Components are pre-rendered on first load too. To keep content
in the first render, fetch data on the server instead of in `useEffect`.
To pick a rendering mode, see
[SSR, SSG, and ISR in Next.js](/en/blog/nextjs-ssr-ssg-isr). Here's an
illustrative example:

```tsx
// app/product/[id]/page.tsx (illustrative)
import { getProduct } from '@/lib/products'

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const product = await getProduct(id)

  return <p>{product.description}</p>
}
```

**WordPress and PHP.** PHP builds the page on the server, so you get the
first render for free. People who come from shared hosting, like me, tend to
underestimate that advantage. The risk starts when a plugin or theme fetches
content through AJAX or REST after load. Here's an illustrative version of
the difference:

```php
<?php // illustrative: the price ships in the served HTML ?>
<p class="price"><?= htmlspecialchars($product['price']) ?></p>

<!-- illustrative: the price only exists after the script runs -->
<p class="price" id="price"></p>
<script>
  fetch('/wp-json/shop/v1/price/123')
    .then((r) => r.json())
    .then((d) => (document.getElementById('price').textContent = d.price))
</script>
```

**React SPA built with Vite.** By default, the served HTML is an empty
shell, and the script builds everything the user sees:

```html
<!-- illustrative: the index.html a React SPA built with Vite serves -->
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>My shop</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/assets/index-a1b2c3.js"></script>
  </body>
</html>
```

To a reader that doesn't run JavaScript, this page has a title and nothing
else. You can pre-render routes at build time, or move the pages that need
to be read to a framework with SSR. I haven't measured an SPA in the lab, so
this stays at the level of mechanism, and I have no data on how each
assistant handles a page built entirely on the client.

## How to check

Every check here asks one question. Is the text that matters in the HTML the
server delivers?

1. **Fetch the raw HTML.** A `curl` shows exactly what a reader without
   JavaScript receives:

   ```bash
   # illustrative: does the text appear in the served HTML?
   curl -s https://example.com/product/123 | grep -c "Free shipping"
   ```

   If the result is `0`, the text isn't in the first render.
2. **Compare the page source with the DOM.** Your browser's "View page
   source" (Ctrl+U) shows the served HTML. The Elements panel in DevTools
   shows the DOM after JavaScript runs. Anything that appears only in the
   Elements panel depends on rendering.
3. **Disable JavaScript.** In DevTools, open the command menu
   (Ctrl+Shift+P), run "Disable JavaScript", and reload. What's left on
   screen is what a text extractor gets.
4. **Check the metadata.** The
   [meta tag validator](/en/tools/meta-tag-validator) shows whether `title`,
   `description`, and the canonical are present in the HTML the server
   delivers.
5. **See Google's version.** In Search Console, the live URL test in URL
   Inspection shows the HTML Google rendered for the tested page. That
   confirms Googlebot's side, and only its side.
6. **Automate it.** On this site, a Playwright test checks for the lab codes
   in the served HTML without running the page's JavaScript. It strips every
   `<script>` and searches for each code in what's left:

```ts
// tests/seo/lab-control.spec.ts (lines 39–50)
// O texto visível, sem nenhum <script> (JSON-LD e payload RSC incluídos).
const text = html.replace(/<script\b[^>]*>[\s\S]*?<\/script>/gi, '')
expect(text).toContain(codes.SRV)
expect(text).toContain(codes.UC)
expect(text, 'LD- must not be in the visible text').not.toContain(codes.LD)

const jsonLd = [...html.matchAll(/<script type="application\/ld\+json">([\s\S]*?)<\/script>/g)]
  .map((m) => JSON.parse(m[1]) as { identifier?: string })
expect(jsonLd.map((node) => node.identifier)).toContain(codes.LD)

// Nem no texto nem em script algum: o JS- só existe depois do fetch.
expect(html, 'JS- must not be in the served HTML at all').not.toContain(codes.JS)
```

The comments are in Portuguese, as they are in the repository. The first one
says visible text means the HTML with every `<script>` removed, JSON-LD and
the RSC payload among them. The last one says `JS-` is neither in the text
nor in any script, because it exists only after the `fetch`.

A note on logs. In the lab, I identify each assistant by its secret URL.
In your own server log, you only have a request profile, so the
most you can write is "requests identifying themselves as X." And an
assistant's explanation of what it read is no substitute for the server
log.

## In Next.js: the probe's two components

On the lab page, two components sit side by side. Both are Client
Components, in the same file, and they differ in **when** their content
exists:

```tsx
// src/components/lab/ControlCodes.tsx (lines 19–44)
export function RenderedByClientComponent({ code }: { code: string }) {
  return (
    <p>
      Código do componente cliente: <strong>{code}</strong>
    </p>
  )
}

export function FetchedCode({ endpoint }: { endpoint: string }) {
  const [code, setCode] = useState<string | null>(null)
  const [failed, setFailed] = useState(false)

  useEffect(() => {
    fetch(endpoint, { cache: 'no-store' })
      .then((response) => (response.ok ? response.json() : Promise.reject(response.status)))
      .then((data: { code: string }) => setCode(data.code))
      .catch(() => setFailed(true))
  }, [endpoint])

  return (
    <p>
      Código carregado no navegador:{' '}
      <strong data-testid="fetched-code">{code ?? (failed ? 'indisponível' : 'carregando…')}</strong>
    </p>
  )
}
```

Labels on the page are in Portuguese. "Código do componente cliente" means
"Client Component code," "Código carregado no navegador" means "code loaded
in the browser," and "carregando…" means "loading…".

Even with `'use client'`, the `UC-` component's text is in the served HTML,
because Next.js pre-renders Client Components on the server. In all 28
neutral rounds, between September and October 2026, that text appeared in
the answers of all five assistants, every time.

`JS-` works differently. Its component builds the value inside `useEffect`,
which runs only in the browser after hydration. For a reader that doesn't
run the script, the value doesn't exist. The HTML keeps only the
"carregando…" that the answers without the value reported.

For a Next.js project, then, `'use client'` isn't the problem. Trouble
starts when you put content that needs to be read behind an effect, a
`dynamic` with `ssr: false`, or an interaction.

Outside the lab, no text on this site's pages depends on JavaScript to
exist. I don't use `dynamic`, and the few `useEffect` hooks I have handle
the consent banner, search, the copy-code button, and Web Vitals
measurement, never content. The probe exists precisely to measure what
happens when someone does the opposite.
