`next/image` takes care of the performance side of images (modern formats,
`srcset`, dimensions reserved to prevent CLS) but **does nothing for
indexing**: alt text, the surrounding text, the file name and the sitemap
entry are still up to you, and the component can't see images declared in
CSS. Search results treat "image SEO" as a synonym for "image performance";
this article covers the half the component doesn't touch, which is precisely
the half that decides whether the image exists as far as the index is
concerned.

## What next/image gives you for free

The standard summary, in one paragraph: the component serves the lightest
format the browser accepts, generates a `srcset` for each pixel density and
viewport, reserves the image's space in the layout (`width` and `height` are
required) and lazy-loads by default. This site's configuration enables AVIF
and WebP with breakpoints tuned to its layout (the Portuguese comments say:
modern formats in order of preference, and breakpoints for the responsive
srcset):

```ts
// next.config.ts
  // ── Otimização de imagens ──────────────────────────────────────────────────
  images: {
    // Formatos modernos em ordem de preferência (avif < webp < original)
    formats: ['image/avif', 'image/webp'],

    // Breakpoints para srcset responsivo
    deviceSizes: [640, 750, 828, 1080, 1200, 1920],
    imageSizes:  [16, 32, 48, 64, 96, 128, 256, 384],
  },
```

You can see the practical result of that setup in this site's baseline from
2026-07-20: **CLS 0.000 on all 10 pages**. With explicit dimensions on every
image, image-driven layout shift simply doesn't happen. That's what the
component buys you. Now for what it doesn't.

## What it doesn't give you (and nobody warns you)

`next/image` doesn't write your alt text, doesn't add the image to the
sitemap, doesn't give the file a meaningful name, doesn't create any text
around the image, and doesn't see CSS `background-image`. None of those are
minor details: they're exactly the signals Google uses to understand and
index an image. The component optimizes how the file is **delivered**;
**indexing** what the file shows is a separate job, and it doesn't come in the
box.

## Alt text: the one part of image indexing that's entirely yours

`alt` is required by the component (TypeScript complains if it's missing),
but required doesn't mean good. Good alt text describes what the image shows
to someone who can't see it, without keyword stuffing: "Search Console report
with the 'Crawled - currently not indexed' status highlighted", not "seo
nextjs search console indexing".

### A decorative image gets an empty alt, not a pretty one

A decorative image (a background, an ornament, a visual duplicate) gets an
empty `alt`. An attribute that's present but empty tells screen readers and
crawlers to skip the image. The real-world example at the end of this article
shows a component on this site where that matters in practice: the blurred
background copy gets an empty `alt` and `aria-hidden`, and the description
lives only on the content image.

### Alt text in the page's language

This is a rule in this repository, not an opinion: alt text is written in the
page's language, pt-BR on pt-BR pages and English on English ones. Alt text
is part of the page's textual relevance; English alt text on a Portuguese
article sends a mixed signal, and it's useless to the screen reader of the
page's actual audience.

## sizes: the attribute that decides which file the user downloads

`srcset` provides the options; `sizes` tells the browser which one to pick
**before** the layout exists. Without it, responsive images assume the image
spans 100vw, so a 400px card downloads the 1080px file. The format is one
media query per layout rule:

```tsx
<Image
  src="/images/blog/exemplo/diagrama.webp"
  alt="…"
  width={1200}
  height={675}
  sizes="(max-width: 768px) 100vw, 720px"
/>
```

Read it from the end: on large screens the image renders at 720px, so
download the closest variant; below 768px it takes up the full viewport.
Getting `sizes` wrong doesn't break anything visible; it just quietly wastes
bytes, which is why almost nobody fixes it.

## preload: one shot, and why this site didn't use it

Most search results on this are out of date, so the version matters:
**starting with Next.js 16, the `priority` prop is deprecated in favor of
`preload`**; the component's types mark `priority` as deprecated and point to
the new prop. For most cases, the documentation recommends `loading="eager"`
or `fetchPriority="high"` rather than a full preload. `preload` does
everything at once: it turns off lazy loading, emits a `<link rel="preload">`
in the head and signals high fetch priority.

The rule for using it didn't change with the name: **one shot per page**,
used only on the LCP element, and only when that element is an image.
Prioritization works by contrast, so marking three images as priority is
telling the browser that none of them are.

And here's why this site didn't use it: **the LCP here is text**, on every
page measured. There's no hero image, and content images sit below the fold
and should stay lazy. The comment in this repository's MDX components file
exists so nobody "optimizes" that by mistake (it says `Image` is the
sanctioned way to embed images in articles, requires explicit width and
height and serves an optimized format, and that content images sit below the
fold, so `preload` must never be used there):

```tsx
// src/components/mdx/mdx-components.tsx
// ─────────────────────────────────────────────────────────────────────────────
// Componentes disponíveis dentro dos arquivos MDX de /content.
//
// `Image` (next/image) é a forma sancionada de embutir imagens em artigos:
// exige width/height explícitos (sem CLS) e serve formato otimizado (§6).
// Imagens de conteúdo ficam abaixo da dobra — nunca usar `preload` aqui.
// ─────────────────────────────────────────────────────────────────────────────
```

I'm not going to fake a before-and-after for a hero image this site doesn't
have. If your LCP **is** an image, the [guide to improving
LCP](/en/blog/improve-lcp-nextjs) covers the full mechanism: discovery,
priority and the cost of every millisecond of delay.

## The blind spot: CSS background-image

`next/image` renders an `<img>`. An image declared in CSS (`background-image`)
is outside all of it: outside the optimization pipeline, outside the
`srcset`, invisible to the browser's preload scanner and invisible to Google
Images, which doesn't index images loaded through CSS. If the image is content
(a product, a cover, a diagram), it needs to be an `<img>` tag in the HTML.

The specific damage `background-image` does to LCP (late discovery, a scanner
that can't see it) is covered in the [list of LCP
anti-patterns](/en/blog/nextjs-high-lcp); here's the indexing verdict: as far
as Google Images is concerned, a CSS image doesn't exist.

## Images in the sitemap: the field almost nobody fills in

The sitemap protocol lets you list images for each URL, and the App Router's
`sitemap.ts` exposes that as the `images` field on each entry. It's the
official way to help Google discover images it wouldn't find through the
HTML, and it's what this site uses to get the articles' diagrams into Google
Images (the comment says these are per-article image assets declared in the
image sitemap, diagrams exported to `/public`):

```ts
// src/app/sitemap.ts
// Ativos de imagem por artigo, declarados no image sitemap (diagramas
// exportados de /public — os "ativos de link" do cluster).
const postImages: Record<string, string[]> = {
  'melhorar-lcp-nextjs': ['/images/blog/melhorar-lcp-nextjs/lcp-subpartes-timeline.webp'],
  'lcp-alto-next-js': ['/images/blog/lcp-alto-next-js/preload-scanner-visivel-invisivel.webp'],
  // …one asset per article
}

const postPages: MetadataRoute.Sitemap = posts.map(({ frontmatter }) => ({
  url: `${base}/blog/${frontmatter.slug}`,
  lastModified: toDate(frontmatter.dateModified),
  changeFrequency: 'monthly',
  priority: 0.7,
  images: postImages[frontmatter.slug]?.map((path) => `${base}${path}`),
}))
```

Why the diagrams need that channel is the subject of the next section.

## A diagram should be inline SVG, not an image

Here's a content architecture decision on this site that no `next/image`
guide discusses: **a diagram that teaches something isn't an `<Image>`; it's
an inline `<svg>` in the MDX.**

### Text inside the SVG can be crawled and cited

Every label in this site's diagrams is a real `<text>` element inside the
SVG. Google reads that text as part of the page, and an LLM processing the
HTML reads "preload scanner → doesn't see background-image" straight from the
markup. A PNG with the same labels is a black box: the diagram's content
simply doesn't exist as text. On a site competing to be cited in AI-generated
answers, that difference is everything.

The trade-off, stated up front: Google Images does **not** treat inline SVG as
an image resource. That's why each article exports its main diagram as a
raster copy in `public/images/blog/`, whose only job is to feed the sitemap's
`images` field. The inline version serves people and LLMs; the raster copy
serves the image search channel.

### The SVG follows the theme; the PNG doesn't

The diagrams get all their colors from CSS tokens (`--foreground`,
`--color-accent`, `--color-diagram-*`). In the dark theme, the whole diagram
follows along: text, axes, fills. A PNG exported from the light theme ends up
with a glaring white background in dark mode, or you need two exports and a
`<picture>` with a media query. Inline SVG handles that for free.

## A real example: two Image tags, one download

This site's `BlurFillImage` component renders the same image twice: a blurred
copy in the background with `object-cover` (filling the container) and the
full image in front with `object-contain`. Here's the actual code (the
Portuguese comments read "blurred background, fills the frame" and "real
image, whole, uncropped"):

```tsx
// src/components/ui/BlurFillImage.tsx
export function BlurFillImage({
  src,
  alt,
  title,
  sizes,
  preload,
  className,
}: BlurFillImageProps) {
  return (
    <>
      {/* Fundo borrado — preenche o frame */}
      <Image
        src={src}
        alt=""
        aria-hidden
        fill
        sizes={sizes}
        preload={preload}
        className="scale-150 object-cover blur-2xl"
      />
      {/* Imagem real — inteira, sem corte */}
      <Image
        src={src}
        alt={alt}
        title={title || alt || undefined}
        fill
        sizes={sizes}
        preload={preload}
        className={`object-contain${className ? ` ${className}` : ''}`}
      />
    </>
  )
}
```

That component makes two SEO points. First, network cost: the two `<Image>`
tags share the same `src` and the same layout dimensions, so the pipeline
resolves the identical variant and **the browser downloads it once and reuses
it**. Two tags, one request. Second, accessibility that doubles as indexing:
the background copy gets an empty `alt` and `aria-hidden` because it's
decoration, and the description lives on the image in front. That's the
empty-alt rule in practice, not theory.

network request, which the browser reuses for both renders. Doubling the
visual effect doesn't double the cost.

## How to check

To close the loop, as the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs) recommends:

1. **DevTools → Network, Img filter.** Check which format is served (AVIF or
   WebP, not the original), and for duplicates like `BlurFillImage`, that the
   same `src` produced just one request.
2. **View source.** Is the `alt` in the first response's HTML, descriptive and
   in the page's language? Do the decorative images have the empty attribute?
3. **Sitemap.** Open the production `/sitemap.xml` and confirm the entries
   include the images field with absolute URLs to the raster files.
4. **Lighthouse.** Do the image audits (format, sizing, lazy loading) pass?
   And does CLS stay at 0 with explicit dimensions?
5. **The articles' JSON-LD.** If your pages declare `image` in the `Article`
   schema, validate the block; the [JSON-LD
   generator](/en/tools/json-ld-generator) produces the format this site
   uses.
