`next/image` solves the performance side of images (a modern format,
`srcset`, and dimensions reserved against CLS) and **does nothing for
indexing**. Alt text, surrounding text, file names, and presence in the
sitemap are still up to you, and the component can't see images declared in
CSS. Every search result for this topic treats "image SEO" as another name
for image performance. This article covers the other half, the part the
component doesn't touch and the part that decides whether your image exists
as far as the index is concerned.

## What next/image gives you for free

Here's the consensus in one paragraph. `next/image` serves the lightest
format the browser accepts, generates a `srcset` for each density and
viewport, reserves layout space for the image (`width` and `height` are
required), and lazy-loads by default. This site's config covers AVIF and
WebP, with breakpoints tuned to its layout:

```ts
// next.config.ts
  // ── Otimização de imagens ──────────────────────────────────────────────────
  images: {
    // Formatos modernos em ordem de preferência (avif < webp < original)
    formats: ['image/avif', 'image/webp'],

    // Breakpoints para srcset responsivo
    deviceSizes: [640, 750, 828, 1080, 1200, 1920],
    imageSizes:  [16, 32, 48, 64, 96, 128, 256, 384],
  },
```

In this site's baseline from July 20, 2026, **CLS was 0.000 on all 10 pages**.
When every image has explicit dimensions, images cause no layout shift at
all. That's what the component buys you. Now for what it doesn't.

## What it doesn't give you (and nobody warns you)

`next/image` doesn't write your `alt`. It doesn't put the image in the
sitemap, give the file a meaningful name, or create any text around the
image. And it can't see a CSS `background-image`.

None of these is a detail. They're exactly the signals Google uses to
understand and index an image. What the component optimizes is how the file
gets **delivered**. **Indexing** what the file shows is a different
discipline, and it isn't in the box.

## Alt text: the one part of image indexing that's entirely yours

The component requires `alt`, and TypeScript complains when it's missing.
Required isn't the same as good, though. Good alt text describes what the
image shows to someone who can't see it, without keyword stuffing.

- Good: "Search Console report with the 'Crawled - currently not indexed'
  status highlighted"
- Bad: "seo nextjs search console indexing"

### A decorative image gets an empty alt, not a pretty one

Give a decorative image (a background, an ornament, a visual duplicate) an
empty `alt`. When the attribute is present and empty, screen readers and
crawlers know to ignore the image. You'll see where this matters in practice
in the real example at the end of this article. One of this site's
components gives its blurred background copy an empty `alt` and
`aria-hidden`, and only the content image carries a description.

### Alt text in the page's language

This is a rule in this repository, not an opinion. On pt-BR pages, alt text
is written in pt-BR. Alt text counts toward a page's textual relevance, and
English alt text on a Portuguese article sends a mixed signal. It also does
nothing for the people the page is actually written for when they use a screen reader.

## sizes: the attribute that decides which file the user downloads

`srcset` lists the options, and `sizes` tells the browser which one to pick
**before** layout exists. Without it, the browser assumes a responsive image
takes up 100vw, so a 400px card downloads the 1080px file. You write `sizes`
as one media query per layout rule:

```tsx
<Image
  src="/images/blog/exemplo/diagrama.webp"
  alt="…"
  width={1200}
  height={675}
  sizes="(max-width: 768px) 100vw, 720px"
/>
```

Read it from the end. On large screens the image renders at 720px, so the
browser downloads the closest variant. Below 768px, it takes the whole
viewport.

A wrong `sizes` doesn't break anything you can see. It only wastes bytes,
silently, which is why almost nobody fixes it.

## preload: one shot, and why this site didn't use it

Portuguese-language (pt-BR) search results on this topic are almost all out
of date, so here's the version that matters. **Starting with Next.js 16, the
`priority` prop was deprecated in favor of `preload`.** The component's
types mark `priority` as deprecated and point to the new prop. For most
cases, the docs recommend `loading="eager"` or `fetchPriority="high"`
instead of a full preload.

`preload` is the whole package. It turns off lazy loading, emits a
`<link rel="preload">` in the head, and signals high fetch priority. The
rename didn't change how you use it. You get **one shot per page**, and you
spend it only on the LCP element, when that element is an image.
Prioritization works by contrast. Mark three images as priority and you've
told the browser that nothing is.

This site doesn't spend that shot at all. **The LCP here is text**, on every
page measured. There's no hero image, and content images sit below the
fold, where they need to stay lazy. A comment in this repository's MDX
override is there so nobody "optimizes" that by mistake:

```tsx
// src/components/mdx/mdx-components.tsx
// ─────────────────────────────────────────────────────────────────────────────
// Componentes disponíveis dentro dos arquivos MDX de /content.
//
// `Image` (next/image) é a forma sancionada de embutir imagens em artigos:
// exige width/height explícitos (sem CLS) e serve formato otimizado (§6).
// Imagens de conteúdo ficam abaixo da dobra — nunca usar `preload` aqui.
// ─────────────────────────────────────────────────────────────────────────────
```

I won't fake a before/after for a hero image this site doesn't have. If
your LCP **is** an image, the
[guide to improving LCP](/en/blog/improve-lcp-nextjs) covers the full
mechanism: discovery, priority, and what every millisecond of delay costs.

## The blind spot: CSS background-image

`next/image` renders an `<img>`. An image declared in CSS with
`background-image` gets none of what that brings. It skips the optimization
pipeline and `srcset`, and the browser's preload scanner can't see it.
Neither can Google Images, which doesn't index images loaded through CSS. If
the image is content (a product, a cover, a diagram), it needs to be an
`<img>` tag in the HTML.

For the specific LCP damage `background-image` does (late discovery, a
scanner that doesn't see it), see the
[catalog of LCP anti-patterns](/en/blog/nextjs-high-lcp). This section only
gives the indexing verdict. As far as Google Images is concerned, a CSS
image doesn't exist.

## Images in the sitemap: the field almost nobody fills in

Each URL in a sitemap can list the images associated with it. In the App
Router, `sitemap.ts` exposes that list as the `images` field on each
entry. It's the official channel for Google to discover images it wouldn't
find through the HTML, and it's how this site gives its articles' diagrams a
presence in Google Images:

```ts
// src/app/sitemap.ts
// Ativos de imagem por artigo, declarados no image sitemap (diagramas
// exportados de /public — os "ativos de link" do cluster).
const postImages: Record<string, string[]> = {
  'melhorar-lcp-nextjs': ['/images/blog/melhorar-lcp-nextjs/lcp-subpartes-timeline.webp'],
  'lcp-alto-next-js': ['/images/blog/lcp-alto-next-js/preload-scanner-visivel-invisivel.webp'],
  // …um ativo por artigo
}

const postPages: MetadataRoute.Sitemap = posts.map(({ frontmatter }) => ({
  url: `${base}/blog/${frontmatter.slug}`,
  lastModified: toDate(frontmatter.dateModified),
  changeFrequency: 'monthly',
  priority: 0.7,
  images: postImages[frontmatter.slug]?.map((path) => `${base}${path}`),
}))
```

Why do the diagrams need that channel? That's the next section.

## A diagram should be inline SVG, not an image

No `next/image` guide discusses this content architecture decision. On this
site, **a diagram that teaches isn't `<Image>`. It's inline `<svg>` in
the MDX.**

### Text inside the SVG can be crawled and cited

Every label in this site's diagrams is a real `<text>` element inside the
SVG. Google reads that text as part of the page, and an LLM processing the
HTML reads "preload scanner → doesn't see background-image" straight from
the markup. A PNG with the same labels is a black box, and none of its
content exists as text. On a site competing to be cited in
AI-generated answers, that difference is the whole game.

This choice has a cost, though. Google Images does **not** treat inline SVG
as an image resource. That's why each article's main diagram is also
exported as a raster copy in `public/images/blog/`, and the copy's only job
is to feed the sitemap's `images` field. Inline SVG serves people and LLMs,
and the raster copy serves the image channel.

### The SVG follows the theme; the PNG doesn't

Diagrams get their color only from CSS tokens (`--foreground`,
`--color-accent`, `--color-diagram-*`). Switch to the dark theme and the
whole diagram follows, including text, axes, and fills. A PNG exported from
the light theme keeps a glaring white background in dark mode, unless you
export it twice and serve it through a `<picture>` with a media query.
Inline SVG handles this for free.

## A real example: two Image tags, one download

This site's `BlurFillImage` component renders the same image twice. A
blurred copy sits in the back with `object-cover`, filling the container,
and the whole image sits in front with `object-contain`. Here's the actual
code:

```tsx
// src/components/ui/BlurFillImage.tsx
export function BlurFillImage({
  src,
  alt,
  title,
  sizes,
  preload,
  className,
}: BlurFillImageProps) {
  return (
    <>
      {/* Fundo borrado — preenche o frame */}
      <Image
        src={src}
        alt=""
        aria-hidden
        fill
        sizes={sizes}
        preload={preload}
        className="scale-150 object-cover blur-2xl"
      />
      {/* Imagem real — inteira, sem corte */}
      <Image
        src={src}
        alt={alt}
        title={title || alt || undefined}
        fill
        sizes={sizes}
        preload={preload}
        className={`object-contain${className ? ` ${className}` : ''}`}
      />
    </>
  )
}
```

It illustrates two SEO points.

1. **Network cost.** Both `<Image>` tags share the same `src` and the same
   layout dimensions, so the pipeline resolves an identical variant for
   each, and **the browser downloads it once and reuses it**. Two tags, one
   request.
2. **Accessibility that's also indexing.** Because the background copy is
   decoration, it gets an empty `alt` and `aria-hidden`. The description
   lives on the front image. This is the empty-alt rule in practice, not in
   theory.

## How to check

Close the loop, as the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs)
prescribes:

1. **DevTools → Network, Img filter.** Check the format served (AVIF/WebP,
   not the original). For duplicates like `BlurFillImage`, confirm that the
   same `src` produced only one request.
2. **View source.** Is the `alt` in the initial HTML response, descriptive,
   and in the page's language? Do decorative images have the
   empty attribute?
3. **Sitemap.** Open `/sitemap.xml` in production and confirm that its
   entries carry the `images` field with absolute URLs for the raster files.
4. **Lighthouse.** Do the image audits (format, sizing, lazy loading) pass?
   Does CLS stay at 0 with explicit dimensions?
5. **The articles' JSON-LD.** If the pages declare `image` in the `Article`
   schema, validate that block. The
   [JSON-LD generator](/en/tools/json-ld-generator) produces the format this
   site uses.
