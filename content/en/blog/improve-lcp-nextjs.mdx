To improve LCP in Next.js, start by finding out which of the four subparts
is eating the time: **TTFB**, **resource load delay**, **resource load
duration** or **element render delay**. Each one has its own fixes, and
optimizing the wrong subpart changes nothing. In practice, four moves cover
most cases: make sure the LCP element is in the initial HTML (a Server
Component), use `preload` in `next/image` on the LCP image only (Next.js 16
deprecated `priority`), load fonts with `next/font`, and confirm the result
in PageSpeed Insights' subparts.

```tsx
// app/page.tsx — the essentials in a single example
import Image from 'next/image'

export default function Page() {
  return (
    <section className="relative aspect-[16/9]">
      {/* Server Component: the <img> exists in the initial HTML,
          visible to the browser's preload scanner */}
      <Image
        src="/hero.webp"
        alt="A real description of the image"
        fill
        sizes="100vw"
        preload // Next.js 16: replaces the old `priority`
      />
    </section>
  )
}
```

Starting with Next.js 16, the `images.qualities` setting is required in
`next.config`; without it, the build complains. The full example is in the
[resource load duration](#resource-load-duration-the-file-itself) section.

The rest of this guide explains **why** each of those moves works, one
mechanism at a time, and, more importantly, how to work out which of them
your case actually needs.

## What LCP measures (and what it doesn't)

LCP (Largest Contentful Paint) is the time it takes for the largest visible
content element in the viewport to finish rendering. The official threshold
is **2.5 seconds or less at the 75th percentile of field data**, and it didn't
change in 2026, whatever some articles say (details in the [FAQ](#faq-titulo)).
The reference is [web.dev's documentation](https://web.dev/articles/lcp).

Two details change how you make decisions:

**Lab isn't field.** The Lighthouse score you get on your machine is a
synthetic test; what Google uses is the p75 of real users (CrUX), over a
rolling 28-day window. A fix can improve the lab number today and only show
up in the field weeks later. To see where your domain's field data stands
right now, the [Core Web Vitals checker](/en/tools/cwv-checker) queries that
same CrUX p75, including how visits are distributed across each band, which a
single number hides.

That gap has a practical consequence few people spell out: **your lab budget
needs to be stricter than the field threshold.** The lab runs on an emulated
device and an emulated network, usually with a cold cache and always in the
same scenario. The field p75 includes the slow tail: the old phone, the
spotty 4G, the tab restored from the background. A page that scores 2.4 s in
the lab isn't "almost passing". It has no margin at all, and in the field
it's likely to go over 2.5 s. That's why this site's CI fails the build above
**2.0 s in the lab**, not 2.5 s. It isn't a disagreement with Google's
threshold; it's the headroom between a synthetic number and a real one.

**The LCP element isn't necessarily an image.** It can be a headline, a block
of text or a card rendered from data. That matters because almost everything
written about LCP assumes an image, and if your LCP element is text,
optimizing images is effort with zero return.

This article covers LCP only. It's part of this site's [technical SEO guide
for Next.js](/en/guide/technical-seo-nextjs), which puts all three Core Web
Vitals in context.

## Before optimizing: find out what your LCP element is

The first step isn't optimizing anything; it's identifying the element. In
Chrome DevTools, open the **Performance** tab, record a page load and click
the **LCP** marker: it highlights the exact element on the page. PageSpeed
Insights also shows the element in its "LCP breakdown" insight.

Two gotchas I always check for:

- **Mobile and desktop can have different LCP elements.** A layout that hides
  the hero on mobile can make the headline the LCP there, and Google looks at
  mobile first.
- **The element can change while the page loads.** If something larger
  renders later (hydration, a slider), LCP gets recorded again at that point.
  That kind of trap gets its own article in this cluster, on the [mistakes
  that keep LCP from improving](/en/blog/nextjs-high-lcp).

Once you've identified the element, the question becomes: where is the time
going?

| Subpart | What it is | Main fix | Where to see it |
|---|---|---|---|
| **TTFB** | Time to the first byte of HTML | Caching, streaming, CDN | PSI, `web-vitals` |
| **Resource load delay** | From TTFB until the browser *starts* downloading the LCP resource | Resource in the initial HTML + `preload` | Waterfall |
| **Resource load duration** | The download itself | Format, `sizes`, compression | Waterfall |
| **Element render delay** | From the end of the download until paint | Render-blocking CSS, fonts | Trace |

Here's the insight that changes the strategy: **in most diagnoses I run, the
bottleneck is in the delays (discovery and render), not the download**. The
image file, the only thing most guides optimize, is just one of the four
phases, and often the shortest. That's why compressing the image a third time
doesn't move the number.

The next four sections take one subpart each.

## TTFB: your LCP's floor

Nothing renders before the first byte of HTML arrives, so TTFB is a floor
that everything else stacks on top of. If your TTFB is 1.8 s, your LCP will
never be good, no matter what you do to your images.

In Next.js, these are the levers in order of impact:

**Static rendering wherever possible.** A static page served from a CDN takes
server time out of the equation. In the App Router, that means not using
dynamic APIs (`cookies()`, `headers()`) on pages that don't need them.

**Streaming when data fetching is slow.** If the page depends on data, don't
hold the whole HTML hostage to the fetch: send the shell right away and let
the slow part arrive through `Suspense`:

```tsx
// app/produtos/page.tsx
import { Suspense } from 'react'
import { ListaProdutos } from './lista-produtos'

export default function Page() {
  return (
    <main>
      {/* Static shell: arrives with the first byte.
          The LCP candidate should be HERE, outside Suspense. */}
      <h1>Produtos</h1>
      <Suspense fallback={<SkeletonLista />}>
        {/* Block that depends on a fetch: arrives via streaming */}
        <ListaProdutos />
      </Suspense>
    </main>
  )
}
```

That improves TTFB because the server responds before the fetch finishes; the
mechanism is guaranteed. How much it improves *LCP* depends on where the LCP
element is: if it's inside the `Suspense` boundary, streaming won't fix it
(that case gets its own section [further down](#when-the-lcp-element-isnt-an-image)).

**Infrastructure.** A deployment region close to your audience (for a
Brazilian site, an edge location or region in South America), Next's data
cache and a CDN in front. In Next.js 16 the caching model changed to Cache
Components, so if you're coming from experimental PPR, reread the docs before
assuming how it behaves.

Coming from PHP on shared hosting, this was the dominant subpart by
definition: the server rendered everything on every request, and TTFB ate the
whole budget. In Next.js with static rendering and streaming, the bottleneck
usually shifts to the next two subparts. That's a good thing, because those
are under your code's control, not your infrastructure's.

## Resource load delay: the browser needs to discover the image early

Load delay measures how long the browser took to *start* downloading the LCP
resource after TTFB. A high delay almost always means **late discovery**: the
browser didn't know the resource existed.

Here's the mechanism: the browser has a preload scanner, a secondary parser
that skims the raw HTML and kicks off downloads early, even before the main
parser finishes. It reads **markup, not CSS or JavaScript**
([web.dev](https://web.dev/learn/performance/optimize-resource-loading)). An
`<img>` in the response HTML gets discovered immediately; an image that only
exists inside CSS, or appears after a script runs, doesn't. The patterns the
scanner can't see (background-image, a hero behind `"use client"`, `@import`
chains) deserve an article of their own, and the full list is in [why LCP
doesn't improve even after optimizing](/en/blog/nextjs-high-lcp).

Once discovery is taken care of, the second step is **priority**. In
Next.js 16:

```tsx
// components/hero.tsx
import Image from 'next/image'

// ❌ Next.js ≤15 — `priority` is deprecated in v16:
// <Image src="/hero.webp" alt="..." fill sizes="100vw" priority />

// ✅ Next.js 16:
export function Hero() {
  return (
    <div className="relative aspect-[16/9]">
      <Image src="/hero.webp" alt="..." fill sizes="100vw" preload />
    </div>
  )
}
```

The `preload` prop injects a `<link rel="preload">` into the `<head>` and
applies `fetchPriority="high"` for you, so you don't need both. And the golden
rule: **one image with `preload` per page**, the one that's actually the LCP
element. Preloading several images makes them compete for bandwidth with each
other and with critical CSS, which can make LCP *worse*. Preload helps when
the bottleneck is the right element's load delay, and hurts once it turns
into competition.

If the hero really does have to be a CSS background (a legitimate design
choice in some layouts), tell the browser about it yourself:

```tsx
// app/layout.tsx (or in the page component)
import { preload } from 'react-dom'

export default function Layout({ children }: { children: React.ReactNode }) {
  preload('/hero.webp', { as: 'image', fetchPriority: 'high' })
  return <>{children}</>
}
```

That restores the early discovery a background-image loses. The mechanism is
guaranteed; how much it helps depends on how late the image was being
discovered before.

## Resource load duration: the file itself

Load duration is the download itself, and it's the only subpart image
compression affects. Next.js gives you three levers:

**Format: let `next/image` negotiate it.** The component serves AVIF or WebP
automatically, depending on what the browser accepts. You don't need to
convert anything by hand; you just need to avoid turning optimization off
(`unoptimized`) without a reason.

**The right `sizes`.** With `fill`, if you leave out `sizes`, the browser
assumes `100vw`, and in a 3-column grid that means downloading an image 3x
bigger than needed. For a full-width hero, `sizes="100vw"` is correct; for any
other layout, describe what's actually there:

```tsx
// components/card-produto.tsx
<Image
  src={produto.imagem}
  alt={produto.nome}
  fill
  sizes="(max-width: 768px) 100vw, 33vw"
/>
```

**`qualities` in the config (required in v16):**

```ts
// next.config.ts
import type { NextConfig } from 'next'

const config: NextConfig = {
  images: {
    qualities: [50, 75], // 75 for heroes, 50 for thumbnails
  },
}

export default config
```

Dropping quality from 75 to 50 on a thumbnail cuts bytes with no visible
difference at that size, but you only gain LCP if duration was the
bottleneck. Check the waterfall before spending time here.

## Element render delay: the image has arrived but still has to paint

Render delay is the least understood subpart: the resource has finished
downloading, but nothing gets painted. The mechanism: **the browser doesn't
build the render tree until the CSSOM is complete**, and all CSS is
render-blocking by definition
([web.dev](https://web.dev/learn/performance/understanding-the-critical-path)).
An image that downloaded in 400 ms can sit in memory for 2 s while a slow
stylesheet holds up rendering for the entire page.

In Next.js, the most common avoidable cause of render delay is **fonts**:

```tsx
// app/layout.tsx
import { Inter } from 'next/font/google'

const inter = Inter({ subsets: ['latin'], display: 'swap' })

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" className={inter.className}>
      <body>{children}</body>
    </html>
  )
}
```

`next/font` downloads the font at build time and serves it from your own
domain, which removes Google Fonts' external render-blocking request and the
discovery chain it sets off. That improves render delay because it takes a
blocking resource from another origin out of the critical path; how much
depends on the latency to the third party and the user's cache.

When the LCP element is **text**, `display: 'swap'` matters even more: without
it, text stays invisible during the font's block period, and invisible text
doesn't count as rendered for LCP.

This site has loaded its fonts through `next/font` since the very first
deploy. And since the site doesn't show up in CrUX yet (CrUX requires a
minimum amount of traffic), I set up my own RUM: `web-vitals` reports each
visit's real LCP, with the 4 subparts as parameters, straight to GA4 (the
code is in the [verification section](#how-to-check-it-worked)). Once there's
field data over a window long enough to be statistically useful, I'll update
this section with the measurement.

Other causes of render delay (a fade-in on the hero, anti-flicker snippets
from A/B testing tools, `@import` chains) are anti-patterns, and they're
covered in this cluster's article on the [mistakes that hold LCP
back](/en/blog/nextjs-high-lcp).

## When the LCP element isn't an image

If your LCP element is a headline, follow the previous section: load the font
through `next/font`, use `display: 'swap'`, and make sure the text is in the
initial HTML. There's no "optimizing the image" here, which is exactly why
identifying the element comes first. (That's the case on this site's own home
page: the LCP element is the opening paragraph, and the real breakdown is in
the [verification section](#how-to-check-it-worked).)

The hardest case is the **data-driven LCP**: a product list, a dashboard's
main card, a search result. The LCP element only exists after the fetch, so
your LCP is held hostage by the database.

The decision comes down to three paths: image LCP → discovery and priority
(load delay) plus the file (duration); text LCP → fonts and CSS (render
delay); data-driven LCP → streaming architecture, covered next.

The options, from best to last resort:

1. **Take the LCP candidate off the data path.** If the page has a static
   headline or banner that can be the largest element above the fold, keep it
   outside `Suspense`: it arrives in the first flush and makes for a fast LCP
   while the data streams in below.
2. **Cache the data that determines the LCP.** If the main card rarely
   changes, Next's data cache (with periodic revalidation) turns a slow fetch
   into a cache read.
3. **Watch out for skeletons bigger than the content.** If the `Suspense`
   fallback is *bigger* than the final content, the skeleton can become the
   provisional LCP, and the real content resets LCP when it arrives: you "pay"
   for the fetch time anyway. Use a skeleton the same size or smaller.

This scenario rarely comes up in LCP guides because there's no one-line fix;
it's an architecture decision. But it's the reality for any Next.js app that
renders data above the fold.

## How to check it worked

Optimizing without verifying is guesswork. Here's the routine I follow, in
order:

1. **PSI → subparts.** Run PageSpeed Insights and look at the LCP breakdown:
   which subpart dominates? That tells you which section of this guide to go
   back to.
2. **Local DevTools Performance panel.** Record a trace with network
   throttling (Fast 4G) and CPU throttling (4x): the LCP marker shows the
   element, and the waterfall shows when the resource was discovered versus
   when it finished.
3. **View source, not the DOM.** Confirm that the LCP `<img>` and the
   `<link rel="preload">` generated by the `preload` prop are in the server's
   response HTML. The DevTools DOM shows the state *after* JS and CSS have
   run, which isn't what the preload scanner saw.
4. **Your own RUM.** The `web-vitals` package (attribution build) reports real
   users' LCP along with the dominant subpart. That's what this site does: the
   event goes to GA4 through GTM, with no backend at all (consent is handled
   by Consent Mode, like any other tag):

```ts
// lib/rum.ts — this site's real code (simplified)
import { onLCP } from 'web-vitals/attribution'

onLCP(({ value, rating, attribution }) => {
  window.dataLayer?.push({
    event: 'web_vitals',
    metric_name: 'LCP',
    metric_value: Math.round(value),
    metric_rating: rating,
    lcp_element: attribution.target, // v5: was `element` until v4
    lcp_ttfb: Math.round(attribution.timeToFirstByte),
    lcp_load_delay: Math.round(attribution.resourceLoadDelay),
    lcp_load_duration: Math.round(attribution.resourceLoadDuration),
    lcp_render_delay: Math.round(attribution.elementRenderDelay),
  })
})
```

   In GTM, a Custom Event trigger on `web_vitals` feeds a GA4 tag with those
   parameters, and the subparts become columns in an exploration. Two
   implementation notes: in `web-vitals` **v5** the element selector moved
   from `attribution.element` to `attribution.target` (in plain JS, the old
   field just returns `undefined` without any warning); and the callback only
   fires once the metric is *final* (when the page is hidden or on the first
   interaction), so don't expect the event on load. If you have a backend with
   storage, `navigator.sendBeacon` to your own endpoint works too; on a
   serverless deployment with no database, GA4 is the sink you have left.

5. **Field data, with patience.** CrUX and GSC use a rolling 28-day window at
   the p75, so don't judge a fix the next day. And if the site is new, CrUX
   may simply not report anything yet (it needs a minimum amount of traffic);
   the RUM from step 4 covers that gap.

This site's [free technical SEO tools](/en/tools) include a [Core Web Vitals
checker](/en/tools/cwv-checker) built on CrUX, designed for step 5 of this
routine.
