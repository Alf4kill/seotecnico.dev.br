To improve LCP in Next.js, start by finding out which of its four subparts
takes the time: **TTFB**, **resource load delay**, **resource load
duration**, or **element render delay**. Each one has its own fixes, and if
you optimize the wrong subpart, nothing changes. Four moves resolve most
cases:

1. Keep the LCP element in the initial HTML by rendering it in a Server
   Component.
2. Add `preload` to `next/image` on the LCP image only (Next.js 16
   deprecated `priority`).
3. Load fonts with `next/font`.
4. Confirm the result in PageSpeed Insights' subpart breakdown.

```tsx
// app/page.tsx — the essentials in a single example
import Image from 'next/image'

export default function Page() {
  return (
    <section className="relative aspect-[16/9]">
      {/* Server Component: the <img> exists in the initial HTML,
          visible to the browser's preload scanner */}
      <Image
        src="/hero.webp"
        alt="A real description of the image"
        fill
        sizes="100vw"
        preload // Next.js 16: replaces the old `priority`
      />
    </section>
  )
}
```

Starting with Next.js 16, you also need an `images.qualities` setting in
`next.config`, or the build complains. You'll find a full example in the
[resource load duration section](#resource-load-duration-the-file-itself).

This guide explains **why** each move works, one mechanism at a time. More
importantly, it shows you how to find out which one your case actually
needs.

## What LCP measures (and what it doesn't)

Largest Contentful Paint (LCP) measures how long it takes for the largest
content element visible in the viewport to finish rendering. Google's
official threshold is **2.5 seconds or less at the 75th percentile of
field data**, according to
[web.dev's documentation](https://web.dev/articles/lcp). It didn't change in
2026, despite what some articles claim (details in the [FAQ](#faq-titulo)).

Two details change the decisions you make.

**Lab isn't field.** When you run Lighthouse on your machine, the number
comes from a synthetic test. Google uses the 75th percentile of real users
(CrUX) over a rolling 28-day window. A fix can improve your lab score
today and only show up in field data weeks later. To see where your domain's
field data stands
right now, use the [Core Web Vitals checker](/en/tools/cwv-checker). It
queries that same CrUX p75 and also shows how visits are distributed across
the bands, which a single number hides.

Almost no one spells out what this means in practice. **Your lab budget needs
to be stricter than the field threshold.** A lab run uses one emulated
device on an emulated network, usually with a cold cache, and repeats the
same scenario every time. Field p75 includes the slow tail: the old device,
the bad 4G connection, the restored tab. A page at 2.4 s in the lab isn't
"almost passing." It has no margin at all, and in the field it's very
likely to go over 2.5 s. That's why this site's CI fails the build above
**2.0 s in the lab**, not at 2.5 s. This isn't a disagreement with Google's
threshold. It's the headroom between a synthetic number and a real one.

**The LCP element isn't necessarily an image.** It can be a headline, a
block of text, or a card rendered from data. This matters because almost
all LCP advice assumes an image. If your LCP element is text, optimizing
images is wasted effort.

This article covers LCP only. It's part of this site's
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs), which
puts the three Core Web Vitals metrics in context.

## Before optimizing: find out what your LCP element is

Your first step isn't to optimize anything. It's to identify the element.
In Chrome DevTools, open the **Performance** tab, record a page load, and
click the **LCP** marker. DevTools highlights the exact element on the page.
PageSpeed Insights shows it too, in its "LCP breakdown" insight.

I always check for two gotchas:

- **Mobile and desktop can have different LCP elements.** If your layout
  hides the hero on mobile, the headline can become the LCP element there,
  and Google evaluates mobile first.
- **The element can change during loading.** If something larger renders
  later (after hydration, or in a slider), LCP moves to it at that moment.
  That kind of trap gets its own article in this cluster, on the
  [mistakes that keep LCP from improving](/en/blog/nextjs-high-lcp).

Once you know the element, the next question is where the time goes.

| Subpart | What it is | Main fix | Where to see it |
|---|---|---|---|
| **TTFB** | Time to the first byte of HTML | Cache, streaming, CDN | PSI, `web-vitals` |
| **Resource load delay** | From TTFB until the browser *starts* downloading the LCP resource | Resource in the initial HTML + `preload` | Waterfall |
| **Resource load duration** | The download itself | Format, `sizes`, compression | Waterfall |
| **Element render delay** | From end of download to paint | Render-blocking CSS, fonts | Trace |

This insight should change your strategy. **In most of my diagnoses, the bottleneck
sits in the delays (discovery and render), not in the download.** Most
guides only optimize the image file, one of four phases and often the
shortest. That's why a third round of compression doesn't move your LCP.

Each of the next four sections tackles one subpart.

## TTFB: your LCP's floor

Nothing renders before the first byte of HTML arrives, so TTFB is a floor
under everything else. If your TTFB is 1.8 s, LCP will never be good,
whatever you do with images.

In Next.js, these are your levers, in order of impact.

**Static rendering whenever possible.** A static page served from a CDN
takes server time out of the equation. In the App Router, that means not
calling dynamic APIs (`cookies()`, `headers()`) on pages that don't need
them.

**Streaming when data fetching is slow.** If the page depends on data,
don't hold the whole HTML back until the fetch finishes. Send the shell
right away and let the slow block arrive through `Suspense`.

```tsx
// app/produtos/page.tsx
import { Suspense } from 'react'
import { ListaProdutos } from './lista-produtos'

export default function Page() {
  return (
    <main>
      {/* Static shell: arrives with the first byte.
          The LCP candidate should be HERE, outside Suspense. */}
      <h1>Produtos</h1>
      <Suspense fallback={<SkeletonLista />}>
        {/* Block that depends on a fetch: arrives via streaming */}
        <ListaProdutos />
      </Suspense>
    </main>
  )
}
```

Streaming improves TTFB because the server responds before the fetch ends.
That much follows from the mechanism. How much it improves *LCP*
depends on where the LCP element sits. If it's inside the `Suspense`
boundary, streaming doesn't solve it, and that case has
[its own section further down](#when-the-lcp-element-isnt-an-image).

**Infrastructure.** Deploy in a region close to your audience (for a
Brazilian site, an edge or region in South America), use Next's data cache,
and put a CDN in front. Next.js 16 changed the caching model to Cache
Components. If you're coming from experimental PPR, reread the docs before
you assume how it behaves.

On PHP with shared hosting, TTFB was the dominant subpart by definition. The server rendered everything on every request, and
TTFB ate the whole budget. In Next.js, with static rendering or streaming,
the bottleneck typically moves to the next two subparts. That's good news,
because your code controls those, not your infrastructure.

## Resource load delay: the browser needs to discover the image early

Load delay is how long the browser takes to *start* downloading the LCP
resource after TTFB. A high load delay almost always means **late
discovery**. The browser didn't know the resource existed.

Browsers run a preload scanner, a secondary parser that scans the raw HTML
and starts downloads before the main parser even finishes. It reads
**markup, not CSS or JavaScript**
([web.dev](https://web.dev/learn/performance/optimize-resource-loading)). An
`<img>` in the response HTML gets discovered immediately. An image that only
exists inside CSS, or that appears after a script runs, doesn't.

Some patterns are invisible to the scanner (background-image, a hero behind
`"use client"`, `@import` chains), and they deserve an article of their own.
You'll find the catalog in
[why LCP doesn't improve even after optimizing](/en/blog/nextjs-high-lcp).

Once the browser can discover the image early, your second step is
**priority**. In Next.js 16, it looks like this:

```tsx
// components/hero.tsx
import Image from 'next/image'

// ❌ Next.js ≤15 — `priority` is deprecated in v16:
// <Image src="/hero.webp" alt="..." fill sizes="100vw" priority />

// ✅ Next.js 16:
export function Hero() {
  return (
    <div className="relative aspect-[16/9]">
      <Image src="/hero.webp" alt="..." fill sizes="100vw" preload />
    </div>
  )
}
```

Setting `preload` injects a `<link rel="preload">` into the `<head>` and
already applies `fetchPriority="high"`, so you don't need both. Follow one
golden rule: **one image with `preload` per page**, the one that really is
the LCP element.

If you preload several images, they compete for bandwidth with each other
and with critical CSS, and they can make LCP *worse*. Preloading helps when
the bottleneck is load delay on the right element. It hurts once it turns
into competition.

Sometimes the hero really has to be a CSS background, and in some layouts
that's a legitimate design decision. In that case, tell the browser
yourself:

```tsx
// app/layout.tsx (or in the page component)
import { preload } from 'react-dom'

export default function Layout({ children }: { children: React.ReactNode }) {
  preload('/hero.webp', { as: 'image', fetchPriority: 'high' })
  return <>{children}</>
}
```

This restores the early discovery that background-image loses. The
mechanism guarantees that much. How much you gain depends on how late the
browser found the image before.

## Resource load duration: the file itself

Load duration is the download itself, and it's the only subpart that image
compression affects. Next.js gives you three levers.

**Format: let `next/image` negotiate.** It serves AVIF or WebP
automatically, depending on what the browser accepts. You don't need to
convert anything by hand. Only turn off optimization (`unoptimized`) if you
have a reason.

**Correct `sizes`.** With `fill`, if you omit `sizes`, the browser assumes
`100vw`. In a 3-column grid, that means downloading an image 3x larger than
it needs to be. For a full-width hero, `sizes="100vw"` is right. For any other
layout, describe what the layout really does.

```tsx
// components/card-produto.tsx
<Image
  src={produto.imagem}
  alt={produto.nome}
  fill
  sizes="(max-width: 768px) 100vw, 33vw"
/>
```

**`qualities` in the config (required in v16):**

```ts
// next.config.ts
import type { NextConfig } from 'next'

const config: NextConfig = {
  images: {
    qualities: [50, 75], // 75 for heroes, 50 for thumbnails
  },
}

export default config
```

Dropping quality from 75 to 50 on a thumbnail cuts bytes with no
perceptible difference at that size. It only improves LCP if duration was
the bottleneck, though, so check the waterfall before you spend time here.

## Element render delay: the image has arrived but still has to paint

Render delay is the least understood subpart. It covers the time after the
resource has downloaded but before anything paints. One mechanism explains
it. **The browser doesn't build the render tree until the
CSSOM is complete**, and all CSS is render-blocking by definition
([web.dev](https://web.dev/learn/performance/understanding-the-critical-path)).
An image downloaded in 400 ms can sit idle in memory for 2 s while a slow
stylesheet holds up rendering for the whole page.

In Next.js, the most common avoidable cause of render delay is **fonts**:

```tsx
// app/layout.tsx
import { Inter } from 'next/font/google'

const inter = Inter({ subsets: ['latin'], display: 'swap' })

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" className={inter.className}>
      <body>{children}</body>
    </html>
  )
}
```

`next/font` downloads the font at build time and serves it from your own
domain. That removes the external, render-blocking request to Google Fonts
and the discovery chain it creates. It improves render delay because it
takes a blocking resource from another origin off the critical path. How
much it helps depends on latency to the third party and on the user's
cache.

When the LCP element is **text**, `display: 'swap'` matters even more.
Without it, text stays invisible during the font's block period, and
invisible text doesn't count as rendered for LCP.

This site has loaded its font through `next/font` since its first deploy.
CrUX doesn't report the site yet, because it requires a minimum volume of
traffic, so I set up my own RUM. `web-vitals` sends each visit's real LCP
straight to GA4, with the 4 subparts as parameters. You'll find the code in
the [verification section](#how-to-check-it-worked). Once I have field data
over a statistically useful window, I'll update this section with the
measurement.

Hero fade-ins, A/B testing anti-flicker snippets, and `@import` chains cause
render delay too. They're anti-patterns, and I catalog them in the cluster
article on the [mistakes that hold LCP back](/en/blog/nextjs-high-lcp).

## When the LCP element isn't an image

If your LCP element is a headline, go back to the previous section. Load
your font with `next/font`, use `display: 'swap'`, and make sure your text
is in the initial HTML. There's no "optimizing the image" here, which is why
you identify the element first. (This site's own home page is a case in point.
Its LCP element is the opening paragraph, and you'll find its real
breakdown in the [verification section](#how-to-check-it-worked).)

**Data-driven LCP** is the hardest case: a product list, a dashboard's main
card, a search result. The element only exists after the fetch, so the
database holds LCP hostage.

In short, you have three paths. Image LCP → discovery and priority (load
delay), then the file itself (duration). Text LCP → fonts and CSS (render
delay). Data-driven LCP → a streaming architecture, described next.

Here are your options, from best to last resort:

1. **Take the LCP candidate off the data path.** If the page has a static
   headline or banner that can be the largest element above the fold, keep
   it outside `Suspense`. It arrives in the first flush and becomes a fast
   LCP while the data streams in below.
2. **Cache the data that defines the LCP.** If the main card changes
   rarely, Next's data cache with periodic revalidation turns the slow fetch
   into a cache read.
3. **Beware skeletons bigger than the content.** If the `Suspense` fallback
   is *bigger* than the final content, the skeleton can become the
   provisional LCP, and LCP moves to the real content when it arrives. You
   "pay" for the fetch time anyway. Keep skeletons the same size as the
   content or smaller.

LCP guides barely mention this scenario because there's no one-line fix.
It's an architecture decision. Still, any Next.js app that renders data
above the fold runs into it.

## How to check it worked

Optimizing without verifying is guesswork. Here's the routine I use, in
order:

1. **PSI → subparts.** Run PageSpeed Insights and look at the LCP
   breakdown. Which subpart dominates? The answer tells you which section
   of this guide to reread.
2. **Local DevTools Performance.** Record a trace with network throttling
   (Fast 4G) and CPU throttling (4x). In the trace, the LCP marker shows the
   element, and the waterfall shows when the resource was discovered and
   when it finished.
3. **View source, not the DOM.** Confirm that the LCP `<img>` and the
   `<link rel="preload">` generated by the `preload` prop are in the
   server's response HTML. DevTools shows you the DOM *after* JS and CSS
   run, which isn't what the preload scanner saw.
4. **Your own RUM.** The `web-vitals` package (attribution build) reports
   real users' LCP along with the dominant subpart. This site does exactly
   that, sending the event to GA4 through GTM with no backend at all.
   Consent Mode handles consent as it does for any other tag:

```ts
// lib/rum.ts — this site's real code (simplified)
import { onLCP } from 'web-vitals/attribution'

onLCP(({ value, rating, attribution }) => {
  window.dataLayer?.push({
    event: 'web_vitals',
    metric_name: 'LCP',
    metric_value: Math.round(value),
    metric_rating: rating,
    lcp_element: attribution.target, // v5: was `element` until v4
    lcp_ttfb: Math.round(attribution.timeToFirstByte),
    lcp_load_delay: Math.round(attribution.resourceLoadDelay),
    lcp_load_duration: Math.round(attribution.resourceLoadDuration),
    lcp_render_delay: Math.round(attribution.elementRenderDelay),
  })
})
```

   In GTM, a Custom Event trigger on `web_vitals` feeds a GA4 tag with those
   parameters, and the subparts become columns in an exploration. Keep two
   implementation details in mind. First, in `web-vitals` **v5**, the element
   selector moved from `attribution.element` to `attribution.target`, and
   in plain JS the old field silently returns `undefined`, with no error or
   warning. Second, the callback only fires when the metric *finalizes* (when
   the page becomes hidden, or on the first interaction), so don't expect
   the event on load.

   If you have a backend with storage, `navigator.sendBeacon` to your own
   endpoint works too. In a serverless deploy with no database, GA4 is the
   one sink you have left.

5. **Field data, with patience.** CrUX and GSC use a rolling 28-day window
   at the p75, so don't judge a fix by the next day. If the site is new,
   CrUX may simply not report it yet, since it needs a minimum volume of
   traffic. Your own RUM from step 4 covers that gap.

The [Core Web Vitals checker](/en/tools/cwv-checker), one of this site's
[free technical SEO tools](/en/tools), queries CrUX and was built for
step 5 of this routine.
