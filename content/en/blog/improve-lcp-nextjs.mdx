To improve LCP in Next.js, first find out which of the four subparts the time
is going to: **TTFB**, **resource load delay**, **resource load duration** or
**element render delay**. Each has different fixes, and optimizing the wrong
subpart changes nothing. In practice, the four moves that solve most cases are:
making sure the LCP element is in the initial HTML (Server Component), using
`preload` in `next/image` only on the LCP image (Next.js 16 deprecated
`priority`), loading fonts with `next/font`, and confirming the result in
PageSpeed Insights' subparts.

```tsx
// app/page.tsx — the essentials in a single example
import Image from 'next/image'

export default function Page() {
  return (
    <section className="relative aspect-[16/9]">
      {/* Server Component: the <img> exists in the initial HTML,
          visible to the browser's preload scanner */}
      <Image
        src="/hero.webp"
        alt="A real description of the image"
        fill
        sizes="100vw"
        preload // Next.js 16: replaces the old `priority`
      />
    </section>
  )
}
```

From Next.js 16 on, the `images.qualities` config is required in
`next.config`; without it the build complains. The full example is in the
[resource load duration](#resource-load-duration-now-the-file) section.

The rest of this guide explains **why** each of those moves works, mechanism
by mechanism, and, more importantly, how to find out which of them your case
really needs.

## What LCP measures (and what it doesn't)

LCP (Largest Contentful Paint) is the time until the largest visible content
element in the viewport finishes rendering. The official threshold is
**2.5 seconds or less at the 75th percentile of field data**; it did not change
in 2026, despite articles claiming otherwise (details in the [FAQ](#faq-titulo)).
The reference is [web.dev's documentation](https://web.dev/articles/lcp).

Two details that change decisions:

**Lab is not field.** The Lighthouse number running on your machine is a
synthetic test; what Google uses is the p75 of real users (CrUX), over a
rolling 28-day window. A fix can improve the lab today and only show up in the
field weeks later. To see where your domain's field data stands now, the [Core
Web Vitals checker](/en/tools/cwv-checker) queries that same CrUX p75,
including the distribution of visits across each band, which the number alone
hides.

That difference has a practical consequence almost nobody spells out: **your
lab budget needs to be stricter than the field threshold.** The lab runs on an
emulated device, on an emulated network, usually with a cold cache and always
in the same scenario. The field p75 includes the slow tail: the old phone, the
bad 4G, the restored tab. A page that scores 2.4 s in the lab is not "almost
passing": it has no margin at all, and in the field it is well placed to go
over 2.5 s. That is why this site's CI fails the build above **2.0 s in the
lab**, not at 2.5 s. It is not a disagreement with Google's threshold; it is the
headroom that separates a synthetic number from a real one.

**The LCP element is not necessarily an image.** It can be a headline, a block
of text or a card rendered from data. That matters because almost all content
about LCP assumes an image, and if your LCP element is text, optimizing images
is effort with zero return.

This article covers only LCP; it is part of this site's [technical SEO guide
for Next.js](/en/guide/technical-seo-nextjs), which puts the three Core Web
Vitals metrics in context.

## Before optimizing: find out what your LCP element is

The first step is not to optimize anything; it is to identify the element. In
Chrome DevTools, open the **Performance** tab, record a page load and click the
**LCP** marker: it highlights the exact element on the page. PageSpeed Insights
also shows the element in the "LCP breakdown" insight.

Two gotchas I always check:

- **Mobile and desktop can have different LCP elements.** A layout that hides
  the hero on mobile can make the headline the LCP there, and Google evaluates
  mobile first.
- **The element can change during loading.** If something re-renders larger
  later (hydration, a slider), the LCP is re-marked at that moment. That kind of
  trap has its own article in the cluster, on the [mistakes that keep LCP from
  improving](/en/blog/nextjs-high-lcp).

With the element identified, the question becomes: where is the time going?

| Subpart | What it is | Main fix | Where to see it |
|---|---|---|---|
| **TTFB** | Time to the HTML's first byte | Caching, streaming, CDN | PSI, `web-vitals` |
| **Resource load delay** | From TTFB until the browser *starts* downloading the LCP resource | Resource in the initial HTML + `preload` | Waterfall |
| **Resource load duration** | The download itself | Format, `sizes`, compression | Waterfall |
| **Element render delay** | From the end of the download to the paint | Render-blocking CSS, fonts | Trace |

The insight that changes the strategy: **in most of the diagnoses I do, the
bottleneck is in the delays (discovery and render), not in the download**. The
image file (the only thing most guides optimize) is one of the four phases, and
often the shortest. That is why compressing the image for the third time does
not move the number.

The next four sections tackle one subpart each.

## TTFB: your LCP's floor

Nothing renders before the HTML's first byte arrives; TTFB is a floor that adds
to everything else. If your TTFB is 1.8 s, LCP will never be good, no matter
what you do with images.

In Next.js, the levers in order of impact:

**Static rendering whenever possible.** A static page served from a CDN takes
server time out of the equation. In the App Router, that means not using
dynamic APIs (`cookies()`, `headers()`) on pages that don't need them.

**Streaming when there is slow data fetching.** If the page depends on data,
don't hold the whole HTML behind the fetch: send the shell immediately and let
the slow block arrive through `Suspense`:

```tsx
// app/produtos/page.tsx
import { Suspense } from 'react'
import { ListaProdutos } from './lista-produtos'

export default function Page() {
  return (
    <main>
      {/* Static shell: arrives with the first byte.
          The LCP candidate should be HERE, outside Suspense. */}
      <h1>Produtos</h1>
      <Suspense fallback={<SkeletonLista />}>
        {/* Block that depends on a fetch: arrives via streaming */}
        <ListaProdutos />
      </Suspense>
    </main>
  )
}
```

That improves TTFB because the server responds before the fetch finishes; the
mechanism is guaranteed. How much it improves *LCP* depends on where the LCP
element is: if it is inside the `Suspense`, streaming does not solve it (that
case has its own section [further down](#when-the-lcp-element-isnt-an-image)).

**Infrastructure.** A deploy region close to the audience (for a Brazilian
site, an edge/region in South America), Next's data cache and a CDN in front.
In Next.js 16, the caching model changed to Cache Components; if you were coming
from experimental PPR, it is worth rereading the docs before assuming behaviour.

Coming from PHP on shared hosting, this was the dominant subpart by definition:
the server rendered everything on every request and TTFB swallowed the whole
budget. In Next.js with static rendering and streaming, the bottleneck
typically moves to the next two subparts, which is good, because they are under
the code's control, not the infrastructure's.

## Resource load delay: the browser needs to discover the image early

Load delay measures how long the browser took to *start* downloading the LCP
resource after TTFB. A high delay almost always means **late discovery**: the
browser did not know the resource existed.

The mechanism behind it: the browser has a preload scanner, a secondary parser
that scans the raw HTML and starts downloads early, even before the main parse
finishes. It reads **markup, not CSS or JavaScript**
([web.dev](https://web.dev/learn/performance/optimize-resource-loading)). An
`<img>` in the response HTML is discovered immediately; an image that only
exists inside CSS, or after a script runs, is not. The patterns invisible to
the scanner (background-image, a hero behind `"use client"`, `@import` chains)
deserve a whole dedicated article; the catalogue is in [why LCP doesn't improve
even after optimizing](/en/blog/nextjs-high-lcp).

With discovery secured, the second step is **priority**. In Next.js 16:

```tsx
// components/hero.tsx
import Image from 'next/image'

// ❌ Next.js ≤15 — `priority` is deprecated in v16:
// <Image src="/hero.webp" alt="..." fill sizes="100vw" priority />

// ✅ Next.js 16:
export function Hero() {
  return (
    <div className="relative aspect-[16/9]">
      <Image src="/hero.webp" alt="..." fill sizes="100vw" preload />
    </div>
  )
}
```

The `preload` prop injects a `<link rel="preload">` into the `<head>` and
already applies `fetchPriority="high"`; you don't need both. And the golden
rule: **one image with `preload` per page**, the one that really is the LCP
element. Preloading several images makes them compete for bandwidth with each
other and with critical CSS, which can *worsen* LCP: it helps when the
bottleneck is the right element's load delay, and gets in the way when it turns
into competition.

If the hero really has to be a CSS background (a legitimate design decision in
some layouts), tell the browser manually:

```tsx
// app/layout.tsx (or in the page component)
import { preload } from 'react-dom'

export default function Layout({ children }: { children: React.ReactNode }) {
  preload('/hero.webp', { as: 'image', fetchPriority: 'high' })
  return <>{children}</>
}
```

That restores the early discovery background-image loses; the mechanism is
guaranteed, and the magnitude depends on how late the image used to be
discovered.

## Resource load duration: now, the file

Load duration is the download itself, the only subpart image compression
affects. Three levers in Next.js:

**Format: let `next/image` negotiate.** The component serves AVIF/WebP
automatically depending on what the browser accepts. You don't need to convert
manually; you just need not to turn off optimization (`unoptimized`) without a
reason.

**Correct `sizes`.** With `fill`, if you omit `sizes`, the browser assumes
`100vw`, and in a 3-column grid that means downloading an image 3x larger than
needed. For a full-width hero, `sizes="100vw"` is right; for any other layout,
describe reality:

```tsx
// components/card-produto.tsx
<Image
  src={produto.imagem}
  alt={produto.nome}
  fill
  sizes="(max-width: 768px) 100vw, 33vw"
/>
```

**`qualities` in the config (required in v16):**

```ts
// next.config.ts
import type { NextConfig } from 'next'

const config: NextConfig = {
  images: {
    qualities: [50, 75], // 75 for heroes, 50 for thumbnails
  },
}

export default config
```

Lowering quality from 75 to 50 on a thumbnail cuts bytes with no perceptible
visual difference at that size, but the LCP gain only exists if the bottleneck
was duration. Check the waterfall before spending time here.

## Element render delay: the image arrived, it still has to paint

Render delay is the least understood subpart: the resource has downloaded, but
the paint does not happen. The mechanism: **the browser does not build the
render tree until the CSSOM is complete**; all CSS is render-blocking by
definition
([web.dev](https://web.dev/learn/performance/understanding-the-critical-path)).
An image that downloaded in 400 ms can wait 2 s sitting in memory while a slow
stylesheet holds back rendering of the whole page.

In Next.js, the most common case of avoidable render delay is **fonts**:

```tsx
// app/layout.tsx
import { Inter } from 'next/font/google'

const inter = Inter({ subsets: ['latin'], display: 'swap' })

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" className={inter.className}>
      <body>{children}</body>
    </html>
  )
}
```

`next/font` downloads the font at build time and serves it from your own
domain, removing Google Fonts' external render-blocking request and the
discovery chain it creates. That improves render delay because it takes a
blocking resource from another origin out of the critical path; the magnitude
depends on the latency to the third party and the user's cache.

When the LCP element is **text**, `display: 'swap'` matters twice over: without
it, the text stays invisible during the font's block period, and invisible
text does not count as rendered for LCP.

On this very site, the font has loaded through `next/font` since the first
deploy. And since the site does not yet appear in CrUX (which requires a
minimum traffic volume), I set up my own RUM: `web-vitals` reports each
visit's real LCP, with the 4 subparts as parameters, straight to GA4 (the code
is in the [verification section](#how-to-check-it-worked)). When there is field
data over a statistically useful window, I will update this section with the
measurement.

Other causes of render delay (a fade-in on the hero, A/B testing anti-flicker,
`@import` chains) are anti-patterns, and they are catalogued in the cluster's
article on the [mistakes that hold LCP back](/en/blog/nextjs-high-lcp).

## When the LCP element isn't an image

If your LCP element is a headline, the path is the previous section: font
through `next/font`, `display: 'swap'`, and making sure the text is in the
initial HTML. There is no "optimizing the image" here, and that is why
identifying the element comes before everything. (It is the case of this site's
own home: the LCP element is the opening paragraph; the real breakdown is in
the [verification section](#how-to-check-it-worked).)

The hardest case is the **data-driven LCP**: a product list, a dashboard's main
card, a search result. The LCP element only exists after the fetch, so LCP is
held hostage by the database.

The decision comes down to three paths: image LCP → discovery and priority
(load delay) + the file (duration); text LCP → fonts and CSS (render delay);
data-driven LCP → streaming architecture, described next.

The options, from best to emergency:

1. **Take the LCP candidate out of the data path.** If the page has a static
   headline or banner that can be the largest element above the fold, keep it
   outside `Suspense`: it arrives in the first flush and becomes a fast LCP,
   while the data streams in below.
2. **Cache the data that defines the LCP.** If the main card changes little,
   Next's data cache (periodic revalidation) turns the slow fetch into a cache
   read.
3. **Beware of skeletons larger than the content.** If the `Suspense` fallback
   is *larger* than the final content, the skeleton can become the provisional
   LCP and the real content re-marks the LCP when it arrives: you "pay" for the
   fetch time anyway. Use a skeleton the same size or smaller.

This scenario hardly appears in LCP guides because it has no one-line fix; it
is an architecture decision. But it is the real case of any Next.js app that
renders data above the fold.

## How to check it worked

Optimization without verification is guesswork. The routine I use, in order:

1. **PSI → subparts.** Run PageSpeed Insights and look at the LCP breakdown:
   which subpart dominates? It points to which section of this guide to reread.
2. **Local DevTools Performance.** Record a trace with network throttling (Fast
   4G) and CPU throttling (4x): the LCP marker shows the element and the
   waterfall shows when the resource was discovered vs. when it finished.
3. **View-source, not the DOM.** Confirm that the LCP `<img>` and the
   `<link rel="preload">` generated by the `preload` prop are in the server's
   response HTML; DevTools' DOM shows the state *after* JS/CSS, which is not
   what the preload scanner saw.
4. **Your own RUM.** The `web-vitals` package (attribution build) reports real
   users' LCP with the dominant subpart. That is what this site does: the event
   goes to GA4 through GTM, with no backend at all (consent is handled by
   Consent Mode, like any other tag):

```ts
// lib/rum.ts — this site's real code (simplified)
import { onLCP } from 'web-vitals/attribution'

onLCP(({ value, rating, attribution }) => {
  window.dataLayer?.push({
    event: 'web_vitals',
    metric_name: 'LCP',
    metric_value: Math.round(value),
    metric_rating: rating,
    lcp_element: attribution.target, // v5: was `element` until v4
    lcp_ttfb: Math.round(attribution.timeToFirstByte),
    lcp_load_delay: Math.round(attribution.resourceLoadDelay),
    lcp_load_duration: Math.round(attribution.resourceLoadDuration),
    lcp_render_delay: Math.round(attribution.elementRenderDelay),
  })
})
```

   In GTM, a Custom Event trigger for `web_vitals` feeds a GA4 tag with those
   parameters, and the subparts become columns in an exploration. Two
   implementation notes: in `web-vitals` **v5** the element selector changed
   from `attribution.element` to `attribution.target` (in plain JS, the old
   field returns `undefined` without complaining); and the callback only fires
   when the metric *finalizes* (the page becoming hidden, or the first
   interaction), so don't expect the event on load. If you have a backend with
   storage, `navigator.sendBeacon` to your own endpoint also works; on a
   serverless deploy with no database, GA4 is the sink that's left.

5. **Field data, with patience.** CrUX/GSC use a rolling 28-day window at the
   p75: don't judge a fix by the next day. And if the site is new, CrUX may
   simply not report yet (it requires a minimum traffic volume); the RUM from
   step 4 covers that gap.

Among this site's [free technical SEO tools](/en/tools) is a [Core Web
Vitals checker](/en/tools/cwv-checker) via CrUX, built for step 5 of this
routine.
