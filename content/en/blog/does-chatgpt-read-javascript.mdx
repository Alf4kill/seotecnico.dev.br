No. I ran 15 controlled rounds on this site in September 2026, and ChatGPT
and Claude read **only the text of the HTML the server delivers**. Neither
one executed JavaScript, and neither read the JSON-LD. Content from a
`'use client'` component reached them normally, because that component is
also rendered on the server. Perplexity, on the free plan, didn't even fetch
the page. It answered from its own index. My server logged every page fetch
the assistants said they made, each with a verified identity.

## Results at a glance

I gave each assistant the same prompt five times, asking it to open a page
and report four codes. Each code reaches the page through a different
rendering path, and the codes change every round.

| Assistant | Opened the page | Server text | `'use client'` component | Only in JSON-LD | Only after JavaScript | Requests to the server |
|---|---|---|---|---|---|---|
| ChatGPT | 5 of 5 | **5 of 5** | **5 of 5** | 0 of 5 | 0 of 5 | 5, verified identity |
| Claude | 5 of 5 | **5 of 5** | **5 of 5** | 0 of 5 | 0 of 5 | 5, verified identity |
| Perplexity (free) | 0 of 5 | n/a | n/a | n/a | n/a | 0 |

No assistant invented a code. I asked for 60 codes in total, and whenever
one didn't reach an assistant, its answer said it hadn't found that code.

## How the test was built

I built the test page as a Next.js route at `/lab/<slug>`. It isn't in the
sitemap, the on-site search doesn't index it, and nothing links to it. Its
`<slug>` is secret and lives only in a production environment variable.

That secrecy matters for this test in particular. Assistants can search
GitHub, and this site's repo is public. If the address or the codes sat in
a versioned file, an assistant could look them up on GitHub and answer
without opening the page. Then the test would measure search, not page
reading.

Here are the four codes, one per rendering path.

| Code | Where it lives | If the assistant reports it, that proves… |
|---|---|---|
| `SRV-` | Text in a Server Component | It read the served HTML |
| `UC-` | Text rendered by a `'use client'` component | Nothing beyond `SRV-`, since it's in the HTML too |
| `LD-` | Only in the JSON-LD's `identifier` field | Its reader keeps the contents of `<script type="application/ld+json">` |
| `JS-` | Fetched by a `fetch` inside `useEffect`, after mount | The assistant ran JavaScript |

Each code is an HMAC of the slug with the round number, so every round gets
fresh codes and no answer from an earlier round can be reused.

If you write Next.js, the interesting part is the client component in
[`src/components/lab/ControlCodes.tsx`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/src/components/lab/ControlCodes.tsx).
Its comments are in Portuguese. The first component produces its code
during render, so the code ends up in the HTML even though the file is
`'use client'`. The second gets its code only after mount, and without
JavaScript that code doesn't exist.

```tsx
'use client'

import { useEffect, useState } from 'react'

// Renderiza o código DURANTE o render: sai no HTML, mesmo sendo 'use client'.
export function RenderedByClientComponent({ code }: { code: string }) {
  return (
    <p>
      Código do componente cliente: <strong>{code}</strong>
    </p>
  )
}

// Só obtém o código DEPOIS da montagem: sem JavaScript, ele não existe.
export function FetchedCode({ endpoint }: { endpoint: string }) {
  const [code, setCode] = useState<string | null>(null)
  const [failed, setFailed] = useState(false)

  useEffect(() => {
    fetch(endpoint, { cache: 'no-store' })
      .then((response) => (response.ok ? response.json() : Promise.reject(response.status)))
      .then((data: { code: string }) => setCode(data.code))
      .catch(() => setFailed(true))
  }, [endpoint])

  return (
    <p>
      Código carregado no navegador:{' '}
      <strong data-testid="fetched-code">{code ?? (failed ? 'indisponível' : 'carregando…')}</strong>
    </p>
  )
}
```

The labels you see on the page are in Portuguese too. In English, "Código
do componente cliente" is "Client Component code," "carregando…" is
"loading…," and "Código carregado no navegador" is "code loaded in the
browser."

I put both components in the same `'use client'` file on purpose, because
the difference between them is the whole experiment.

A test in the site's suite,
[`tests/seo/lab-control.spec.ts`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/tests/seo/lab-control.spec.ts),
checks the served HTML to confirm that each code sits exactly where the
table says. `SRV-` and `UC-` are in the text, `LD-` is only inside the
JSON-LD, and `JS-` appears nowhere until the `fetch` runs.

I used the same prompt in every round, always in a new conversation with
web browsing turned on. I wrote it in Portuguese, and in English it reads:

> Open this page. Tell me every code starting with SRV-, UC-, LD-, or JS-
> that you find on it, exactly as it appears, and which part of the page
> each one was in. If you don't find one, say so, and don't make one up.

I ran the 15 rounds interleaved (ChatGPT, Claude, Perplexity, then again),
at least three minutes apart, on September 25, 2026, between 11:56 and
13:04 UTC. You'll find the protocol, the full answers, and the deviations
in the repo, in
[`docs/lab-control-rounds.md`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/lab-control-rounds.md).

## The server saw every visit

Before reading any result, I had to settle a question of method. Does the
instrument that records visits work? If it misses an agent's arrival, it
produces the same zero as an agent that never came. So before anything
else, this test is a **positive control**, a visit I know happened, at a
known time, used to check that the log shows it.

It did. My site's proxy logged **5 requests from ChatGPT-User and 5 from
Claude-User**, all from IP ranges that OpenAI and Anthropic publish. Each
round used a URL that assistant had never fetched, and the codes exist only
on this server, so every correct answer required a fresh request, and the
log has every one of them. I verified identities with the method from my
[article on how to tell if AI uses your content](/en/blog/detect-ai-crawlers).

One detail about the instrument almost became a false finding. When I ran the same query in GA4 on
the day of the rounds, it showed 3 and 2 requests instead of 5 and 5,
because GA4's Explore hadn't finished processing that day. Taken literally,
that export would have reported five instrument failures that never
happened. Since then, my rule on this site is to wait for the day to close,
plus 24 hours, before I analyze any export.

## `'use client'` hides nothing

`UC-` showed up every time `SRV-` did, in 10 of 10 rounds across both
assistants. To them, text that a `'use client'` component draws on first
render is indistinguishable from Server Component text.

That contradicts a common reading of the directive. `'use client'` doesn't
mean "rendered only in the browser." Next.js renders a client component on
the server like any other, then hydrates it in the browser, and whatever it
produces on first render goes into the HTML.

So the line that matters isn't Server Component versus Client Component.
It's **what exists on the first render** versus **what only appears
later**. My [article on SSR, SSG, and ISR](/en/blog/nextjs-ssr-ssg-isr)
makes the same point for Googlebot. This test measures it for AI
assistants.

## What gets left out: JavaScript and JSON-LD

**JavaScript.** Neither assistant reported `JS-` in 10 rounds, and the
endpoint the `fetch` would call got no request from either one. In their
answers, both described that line of the page as "carregando…" (loading…),
the text the component shows before the `fetch` finishes. They read the
page as it exists before any JavaScript runs.

**JSON-LD.** `LD-` also came back 0 of 10, against 10 of 10 for `SRV-`,
even though both sat in the same HTML. Claude explained why without being
asked, in more than one round. Its reading tool downloads the HTML,
converts it to text, and discards the contents of `<script>` tags, which is
where JSON-LD lives.

That doesn't make JSON-LD useless. Google still uses it for rich results,
and my [article on JSON-LD in Next.js](/en/blog/nextjs-json-ld) shows how to
generate it. But a fact that exists only in JSON-LD doesn't reach these two
assistants. If you want an AI to cite a piece of data, put it in the
visible text too.

## Perplexity: the answer comes from the index

Perplexity failed all five rounds, each time with the same message saying
it couldn't open the page. Four checks I ran outside the protocol explain
why.

1. **It wasn't a block.** My hosting provider's firewall had no active bot
   rule, and none of the IPs blocked that day belonged to Perplexity's
   published ranges. This site's robots.txt allows both Perplexity agents.
2. **The on-demand agent never came.** In two months of logs, PerplexityBot,
   the indexer, fetched this domain 6 times, all with verified identity: the
   home page, robots.txt, the guide, and a social sharing image.
   Perplexity-User, the agent that should fetch a page when someone asks
   about it, made **zero** requests, in the rounds or outside them.
3. **It answers from the index.** When I asked about the home page, which
   PerplexityBot had already visited, Perplexity answered correctly, with
   the title and first paragraph, **without any request reaching the
   server**. The test page and an article the indexer hadn't visited both
   failed.
4. **Given room, it fills in.** With an open-ended prompt ("analyze the
   content of this page") about an article that wasn't in the index, it
   wrote a long, convincing analysis deduced from the words in the URL. A
   single sentence admitted it hadn't read the page, and it came after a
   first section that already presented the content as if it came from the
   article. With the test's closed prompt ("don't make one up"), it admitted
   failure five times out of five. The way I phrased the question decided
   between honesty and invention.

This conclusion holds for the **free plan**, which is the one I tested. In at
least two of the conversations, the interface showed a notice offering a
free preview of the paid plan's advanced search, but the account stayed
free. A paid account may fetch pages live. I didn't measure that.

## What to do on a Next.js site

- **Put what must be read in the first render.** Server Component text and
  Client Component text from the first render reach the assistant. Content
  that depends on a `fetch` in the browser, a collapsed tab that loads on
  demand, or a `useEffect` doesn't.
- **The rest applies to any site.** Repeat whatever is in the JSON-LD in
  the visible text, and check the raw HTML before you trust what the AI
  tells you. You'll find the full rule, measured later with five assistants,
  under
  [what to do on your site](/en/blog/which-ai-assistants-run-javascript#what-to-do-on-your-site).
  For metadata, this site's [meta tag validator](/en/tools/meta-tag-validator)
  reads the raw HTML.
- **For Perplexity, the index comes before the question.** On the free
  plan, a page appears only after PerplexityBot has crawled it. Keep the
  agent allowed in robots.txt and the page in the sitemap, and give it
  time.

## The limits of this test

- **Five rounds measure capability, not rate.** With five rounds per
  assistant, "5 of 5" means that, with 95% confidence, the behavior happens
  at least 55% of the time, and "0 of 5" means at most 45%. With ChatGPT
  and Claude pooled, "0 of 10" for JavaScript and for JSON-LD stays below
  26%. The numbers on this page are counts with that bound, never
  percentages.
- **One site, one date.** I ran the test on September 25, 2026. Assistants'
  reading tools change without notice, so any claim about them holds for
  the date it was measured.
- **Recorded deviations.** By mistake, the first three rounds used the
  round number from the initial check, and I didn't note the model names
  for ChatGPT and Claude. Neither deviation changes the result, and both
  are in the test's public record.
- **Plans, confirmed afterward.** ChatGPT and Claude weren't on free plans.
  ChatGPT was on the Go plan, and Claude was on the Pro plan with the
  Opus 5.5 model. The result holds for those plans.
  (Added October 4, 2026.)

**Follow-up:** in October I ran the same test with Gemini, DeepSeek, and
Grok, and put all five assistants through a round with hints. Two of them
run JavaScript, and one reads JSON-LD. You'll find the results in

This test answers one part of what the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) calls
measuring instead of assuming: what each reader, human or automated,
actually receives from your page.
