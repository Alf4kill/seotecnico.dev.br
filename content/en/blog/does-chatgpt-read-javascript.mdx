No. In 15 controlled rounds on this site in September 2026, **ChatGPT and
Claude read only the text of the HTML the server sends**. Neither ran
JavaScript, and neither read the JSON-LD. The content of a `'use client'`
component reached them just fine, because that component is also rendered on
the server. Perplexity, on the free plan, didn't even fetch the page: it
answered from its own index. And the server logged, with verified identity,
every page visit the assistants said they made.

## The result in one table

Each assistant got the same prompt five times: open a page and report four
codes. Each code reaches the page through a different rendering path, and
they change every round.

| Assistant | Opened the page | Server text | `'use client'` component | Only in JSON-LD | Only after JavaScript | Requests to the server |
|---|---|---|---|---|---|---|
| ChatGPT | 5 of 5 | **5 of 5** | **5 of 5** | 0 of 5 | 0 of 5 | 5, verified identity |
| Claude | 5 of 5 | **5 of 5** | **5 of 5** | 0 of 5 | 0 of 5 | 5, verified identity |
| Perplexity (free) | 0 of 5 | n/a | n/a | n/a | n/a | 0 |

No assistant made up a code. Sixty codes were requested, and every time a
code didn't reach the assistant, the answer said it wasn't found.

## How the test was built

The test page is a Next.js route at `/lab/<slug>`. It's left out of the
sitemap and the site search, and nothing links to it. The `<slug>` is secret
and lives only in a production environment variable. The reason is specific
to this test: the assistants can search GitHub, and this site's repository is
public. If the address or the codes were in a versioned file, an assistant
could answer by finding the code on GitHub without opening the page, and the
test would measure search instead of page reading.

The page holds four codes, one per rendering path:

| Code | Where it lives | If the assistant reports it, that proves… |
|---|---|---|
| `SRV-` | text in a Server Component | it read the served HTML |
| `UC-` | text rendered by a `'use client'` component | nothing beyond `SRV-`: it's in the HTML too |
| `LD-` | only in the JSON-LD's `identifier` field | its reader keeps the contents of `<script type="application/ld+json">` |
| `JS-` | loaded by a `fetch` inside `useEffect`, after mount | the assistant ran JavaScript |

The codes are an HMAC of the slug and the round number, so each round gets
fresh codes and no answer can be recycled from an earlier one. The part that
matters to anyone writing Next.js is the client component, in
[`src/components/lab/ControlCodes.tsx`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/src/components/lab/ControlCodes.tsx).
The Portuguese comments explain that the first component renders the code
DURING render, so it ships in the HTML even though it's `'use client'`, and
that the second only gets the code AFTER mount, so without JavaScript it
never exists:

```tsx
'use client'

import { useEffect, useState } from 'react'

// Renderiza o código DURANTE o render: sai no HTML, mesmo sendo 'use client'.
export function RenderedByClientComponent({ code }: { code: string }) {
  return (
    <p>
      Código do componente cliente: <strong>{code}</strong>
    </p>
  )
}

// Só obtém o código DEPOIS da montagem: sem JavaScript, ele não existe.
export function FetchedCode({ endpoint }: { endpoint: string }) {
  const [code, setCode] = useState<string | null>(null)
  const [failed, setFailed] = useState(false)

  useEffect(() => {
    fetch(endpoint, { cache: 'no-store' })
      .then((response) => (response.ok ? response.json() : Promise.reject(response.status)))
      .then((data: { code: string }) => setCode(data.code))
      .catch(() => setFailed(true))
  }, [endpoint])

  return (
    <p>
      Código carregado no navegador:{' '}
      <strong data-testid="fetched-code">{code ?? (failed ? 'indisponível' : 'carregando…')}</strong>
    </p>
  )
}
```

The page's labels are in Portuguese: "Código do componente cliente" means
"Client Component code", "Código carregado no navegador" means "code loaded
in the browser", and "carregando…" means "loading…".

Both components live in the same `'use client'` file on purpose: the
difference between them is the whole experiment. The site's test suite
checks the served HTML to confirm each code is exactly where the table says:
`SRV-` and `UC-` in the text, `LD-` only inside the JSON-LD, and `JS-`
nowhere until the `fetch` runs
([`tests/seo/lab-control.spec.ts`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/tests/seo/lab-control.spec.ts)).

The prompt was identical every round, always in a new conversation with web
browsing turned on. It was written in Portuguese; in English it reads:

> Open this page and tell me, exactly as they appear, every code starting with
> SRV-, UC-, LD- or JS- that you find on it, and which part of the page each
> one was in. If you don't find one, say you didn't find it; don't make one up.

The 15 rounds were interleaved (ChatGPT, Claude, Perplexity, then again), at
least three minutes apart, on September 25, 2026, between 11:56 and 13:04
UTC. The protocol, the full answers and the deviations are recorded in the
repository, in
[`docs/lab-control-rounds.md`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/lab-control-rounds.md).

## The server saw every visit

Before interpreting what the assistants read, there's a methodological
question: does the instrument that records visits actually work? An
instrument that fails to see an agent arrive produces the same zero as an
agent that never came. So this test is, first and foremost, a **positive
control**: a visit that's known to have happened, at a known time, to check
that it shows up in the record.

It did. The site's proxy logged **5 requests from ChatGPT-User and 5 from
Claude-User**, all from IP ranges published by OpenAI and Anthropic. Each
round used a URL that assistant had never fetched before, and the codes only
exist on this server, so every correct answer required a fresh request, and
every one was logged. The identity verification method is explained in the
[article on how to tell if AI uses your content](/en/blog/detect-ai-crawlers).

One detail about the instrument nearly turned into a false finding: the same
GA4 query, run on the day of the rounds, showed 3 and 2 requests instead of 5
and 5. GA4's Explore reports simply hadn't finished processing that day. Read
at face value, that export would have reported five instrument failures that
never happened. Since then, this site's rule is to wait until the day closes,
plus 24 hours, before analyzing any export.

## `'use client'` hides nothing

`UC-` appeared every time `SRV-` did, for both assistants: 10 out of 10. To
them, the text a `'use client'` component renders on the first pass is
indistinguishable from a Server Component's text.

That runs against a common reading of the directive. `'use client'` doesn't
mean "rendered only in the browser". The component is rendered on the server
like any other, then hydrated in the browser, and whatever it outputs on the
first render ships in the HTML. The line that matters isn't between Server
and Client Components; it's between **what exists on the first render** and
**what only shows up later**. It's the same point the [article on SSR, SSG
and ISR](/en/blog/nextjs-ssr-ssg-isr) makes about Googlebot, now measured on
AI assistants.

## What gets left out: JavaScript and JSON-LD

**JavaScript.** Neither assistant reported `JS-` in 10 rounds, and the
endpoint the `fetch` would have called got no request from either of them. In
their answers, both described that line of the page as "carregando…"
(loading…), the text the component shows before the `fetch` completes. The
page they read is the page as it exists before any JavaScript runs.

**JSON-LD.** `LD-` also stayed at 0 of 10, versus 10 of 10 for `SRV-`, even
though it was in the same HTML. Claude explained why without being asked, in
more than one round: its page-reading tool downloads the HTML, converts it to
text and throws away the contents of `<script>` tags, which is where JSON-LD
lives.

That doesn't make JSON-LD useless. It's still what Google uses for rich
results, and the [article on JSON-LD in Next.js](/en/blog/nextjs-json-ld)
shows how to generate it. But a fact that only exists in JSON-LD never
reaches these two assistants. If you want an AI to cite a piece of data, it
also has to be in the visible text.

## Perplexity: the answer comes from the index

Perplexity failed all five rounds, always with the same message: it couldn't
open the page. Four checks outside the protocol explain why:

1. **It wasn't a block.** The hosting firewall had no active bot rule, and
   none of the IPs blocked that day belonged to the ranges Perplexity
   publishes. This site's robots.txt allows both Perplexity agents.
2. **The on-demand fetching agent never showed up.** In two months of logs,
   PerplexityBot, the indexer, fetched this domain 6 times, all with verified
   identity: the home page, robots.txt, the guide and a social sharing image.
   Perplexity-User, the agent that's supposed to fetch a page when someone
   asks, made **zero** requests, both during the rounds and outside them.
3. **It answers from the index.** Asked about the home page, which
   PerplexityBot had already visited, Perplexity got it right, title and first
   paragraph included, **without a single request reaching the server**. The
   test page and an article the indexer hadn't visited both failed.
4. **Give it room and it fills in the gaps.** Given an open-ended prompt
   ("analyze the content of this page") about an article that wasn't in the
   index, Perplexity wrote a long, convincing analysis inferred from the words
   in the URL. It admitted it hadn't read the page in a single sentence, after
   an opening section that already presented the content as if it came from
   the article. With the test's tightly worded prompt ("don't make one up"),
   it admitted failure five times out of five. How the question was phrased
   made the difference between honesty and invention.

The conclusion applies to the **free plan**, which is what was tested. In at
least two of the conversations, the interface showed a notice offering a free
preview of the paid plan's advanced search; the account stayed on the free
plan. A paid account may well fetch pages live; that wasn't measured here.

## What to do on a Next.js site

- **Put anything that needs to be read in the first render.** Server
  Component text and Client Component text from the first render reach the
  assistant. Content that depends on a `fetch` in the browser, a collapsed tab
  that loads on demand, or a `useEffect` doesn't.
- **The rest applies to any site.** Repeat in the visible text whatever is in
  your JSON-LD, and check the raw HTML before trusting what an AI tells you.
  The full rule, measured later across five assistants, is in [what to do on
  your site](/en/blog/which-ai-assistants-run-javascript#what-to-do-on-your-site).
  For metadata, this site's [meta tag validator](/en/tools/meta-tag-validator)
  reads the raw HTML.
- **For Perplexity, the index comes before the question.** On the free plan, a
  page only shows up after PerplexityBot has crawled it. Keep the agent
  allowed in robots.txt and the page in your sitemap, and give it time.

## The limits of this test

- **Five rounds per assistant measure capability, not frequency.** "5 of 5"
  means, with 95% confidence, that the behavior happens at least 55% of the
  time; "0 of 5" means at most 45%. Pooling ChatGPT and Claude, "0 of 10" for
  JavaScript and for JSON-LD stays below 26%. The figures above are counts
  with those bounds, never percentages.
- **One site, one date.** The test ran on September 25, 2026. The assistants'
  page-reading tools change without notice, and any claim about them only
  holds for the date it was measured.
- **Recorded deviations.** The first three rounds mistakenly used the round
  number from the initial check, and the ChatGPT and Claude model names
  weren't noted. Neither deviation changes the result, and both are in the
  test's public record.
- **Plans, confirmed afterward.** ChatGPT and Claude weren't on free plans:
  ChatGPT was on the Go plan, and Claude on the Pro plan with the Opus 5.5
  model. The result holds for those plans. (Added October 4, 2026.)

**Follow-up:** in October, the same test was run with Gemini, DeepSeek and
Grok, and all five assistants went through a round with hints. Two of them
run JavaScript, and one reads JSON-LD. The results are in [which AI
assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript).

The question this test answers is part of what the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs) calls measuring instead of assuming:
what each reader, human or automated, actually gets from your page.
