Screaming Frog's free version crawls up to 500 URLs per crawl, and under
that limit it audits a whole site. It reports status codes, titles,
descriptions, canonicals, hreflang, internal and external links, and click
depth, and it builds an issues report. It locks configuration (the user
agent and crawl speed are fixed), saving the crawl, JavaScript rendering,
custom extraction, and the Google Analytics and Search Console integrations.
On this 68-page site, the free version was enough for the inventory, and I
covered what it locks with advertools and Playwright. The audit's most
serious finding wasn't in the HTML.

This article walks through the whole case: the setup, the numbers, what
each reported issue turned out to be worth, and what a crawler finds that
an SEO test suite doesn't. Every number comes from exports and commands I ran
on October 23, 2026, and the scripts are in the
[site's repository](https://github.com/Alf4kill/seotecnico.dev.br/tree/main/audits).

## What the free version does and what it locks

Screaming Frog's FAQ, which I checked on October 23, 2026, says the free
version can crawl up to 500 URLs at a time. Without a license, you can't
save or open crawls, and you can't use any configuration options. A
license costs £199 per year and also unlocks JavaScript rendering, custom
extraction, and the Google Analytics and Search Console integrations.

The app itself agrees. Under Crawl Config › Spider › Rendering, the
selector is stuck on "Text Only", next to a notice that these options
require a license.

| Feature | Free version | What I used instead |
|---|---|---|
| Crawl up to 500 URLs | Yes | — |
| Issues report and CSV export | Yes | — |
| Configurable user agent and speed | No | advertools, with its own user agent and a delay between requests |
| Save and reopen crawls | No | Export the CSVs right after the crawl |
| JavaScript rendering | No | Playwright, with JavaScript off and on |
| Custom extraction (XPath, CSS) | No | advertools |
| Search Console integration | No | Manual export of Performance → Pages |

Losing configuration hurt the most. Since I couldn't change the user agent
or the crawl speed, I didn't want to point the crawler at production. This
site measures who visits it, as part of an
[experiment on AI crawlers](/en/blog/detect-ai-crawlers), and an audit crawl
would show up in that data as a visitor. So I ran the crawl against a local
production build, which sends nothing to GA4.

## Crawl setup

I ran three crawlers against the same build:

- **Screaming Frog 24.3, free version**: the reference crawl and the issues
  report.
- **advertools 0.18 (built on Scrapy)**: an identifiable user agent,
  `robots.txt` obeyed, XPath extraction, the link graph, and a join with the
  sitemap.
- **Playwright**: opened each sitemap URL with JavaScript off and on, and
  compared text, links, headings, and JSON-LD.

One detail of the local build decides whether the crawl leaks into
production. Canonicals, hreflang, and the sitemap all use absolute URLs, so
the site's domain has to point to `localhost`. Leave the production domain
in place, and a crawler that follows canonical and hreflang links walks off
localhost and onto the real site.

```python
# audits/scripts/crawl_audit.py (excerpt)
USER_AGENT = 'seotecnico-audit/1.0 (+https://seotecnico.dev.br/sobre)'

adv.crawl(
    f'{base}/',
    str(raw),
    follow_links=True,
    allowed_domains=[urlsplit(base).hostname],
    xpath_selectors=XPATH,
    custom_settings={
        'USER_AGENT': USER_AGENT,
        'ROBOTSTXT_OBEY': True,
        'DOWNLOAD_DELAY': delay,
        'CONCURRENT_REQUESTS_PER_DOMAIN': 1,
        # 3xx/4xx/5xx are findings, not noise
        'HTTPERROR_ALLOW_ALL': True,
    },
)
```

Production got only a minimal pass. I requested 9 hand-picked URLs with the
user agent above, at one request per second, without following links. I
logged the time window so the experiment's analyses can exclude it.

## The numbers: three crawlers, one inventory

| | Screaming Frog | advertools |
|---|---|---|
| URLs encountered | 198 (86 internal, 112 external) | 69 internal + 420 external links |
| HTML pages | 68 | 68 |
| Other internal URLs | 14 scripts, 3 images, 1 feed | 1 feed |
| Pages whose depth differs between the two | 0 | 0 |

Both crawlers listed the same 68 pages, with the same click depth for each
one, and the production sitemap also has 68 URLs. That agreement is what
lets me treat the two sets of numbers as one.

- **Depth:** 1 page at level 0, 15 at level 1, 36 at level 2, and 16 at
  level 3. No page is more than 3 clicks from the home page.
- **Internal links:** 2,442, with none broken and none pointing to a
  redirect.
- **Orphan pages:** none, in either direction. Every sitemap URL receives a
  link, and every linked page is in the sitemap. The least-linked page has 2
  pages linking to it.
- **Hreflang:** 66 pages in pairs with `x-default`, with no reciprocity
  errors. The 2 pages without hreflang have no Portuguese version.
- **External links:** 64 distinct URLs, each checked once. One answered with
  a 308 redirect (Perplexity's documentation), and I fixed it. Another, a
  DOI, ends in a 403 for bots at the publisher's anti-bot wall. I kept it,
  because a DOI is the correct way to cite a scientific paper.

## Raw and rendered HTML: the same on all 68 pages

Neither the free Screaming Frog nor advertools runs JavaScript, so I opened
each page in Chromium twice. With JavaScript off, you see the page the way
a reader that only downloads the HTML sees it. That's Googlebot on its
first pass and, as this site measured, the
[AI assistants that don't run
JavaScript](/en/blog/which-ai-assistants-run-javascript).

Text, links, headings, JSON-LD, and the title were identical on all 68
pages. The only difference was the "COPY" label on the code blocks' copy
button, which appears only after hydration. It added 1 to 12 words on 44
pages, and nothing else changed. The site's three tools serve their
explanatory text and form in the HTML. Only the result depends on
JavaScript.

## The issues report, item by item

Screaming Frog listed 19 issue types. I checked each one against the code
and against production. They fall into four groups.

**Side effects of crawling on localhost, not real findings.**

| Issue | Why |
|---|---|
| Security: HTTP URLs (86 URLs, high priority) | The crawl ran on `http://localhost`. In production, `http://` answers 308 to `https://`. |
| Security: Form on HTTP URL (4) | The tools' forms, on the same localhost |
| Links: Outlinks To Localhost (68) | The build pointed the domain to localhost on purpose |

**Valid and fixed.**

| Issue | Fix |
|---|---|
| Missing `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy` (86 of 86 URLs) | Three headers in `next.config.ts`, locked by a test in CI |

**Valid and kept, with a reason.**

| Issue | Where | Reason |
|---|---|---|
| Missing Content-Security-Policy (83 URLs) | Every page | A CSP that really protects needs a nonce or hash for GTM, inline scripts, and JSON-LD. It is a separate decision, with a performance cost still to be measured. |
| Title over 561 px | 2 pages | 1 to 3 px over an estimate, with titles of up to 60 characters |
| Description over 985 px | 2 pages | 2 to 5 px over the same estimate |
| Alt over 100 characters | 3 images | PageSpeed Insights screenshots whose alt text describes the measured values |
| Duplicate H2 | 4 pages | Same section headings in two articles of the same experiment series |
| Low content (under 200 words) | 2 pages | The tool index pages, not articles |

**Not applicable.**

- Flesch readability is calibrated for English and says nothing about
  Portuguese text.
- "Bad Content Type" is almost certainly the RSS feed, served as
  `application/rss+xml`.
- "H2 multiple", "title same as H1", and "high external outlinks" are
  informational filters, as the program itself describes them.

Almost half the issue types weren't real problems. That's what I'd expect
from any automated report, and it's why a raw report can't go straight to
a client without validation.

## The most serious finding was outside the HTML

Before I realized I needed the local build, I pointed Screaming Frog at
production. The crawl stopped at the home page, and not because of
configuration. Screaming Frog couldn't open a connection to the domain.

My apex domain (the one without `www`) had a single A record,
`216.198.79.1`, from the newer IP range that Vercel recommends today. From
my home connection, I couldn't open a TCP connection to port 443 on that
IP. Requests to `www` worked because it resolves to two IPs, and one of
them answered.

To tell whether the site was down or only the route to it, I tested TCP
connections from several countries with check-host.net, without sending
any HTTP request:

- 17 of 18 nodes connected, and so did a node in São Paulo, Brazil, that I
  tested separately.
- From my connection, `traceroute` passes through my ISP's core and stops
  at the next hop.
- A `traceroute` to `76.76.21.21`, another Vercel entry IP, follows the
  same path and reaches it at hop 12.

The site was up. The route between my ISP and that IP range wasn't.

I fixed it by changing the A record to `76.76.21.21`. Vercel's knowledge
base still documents that value for apex domains, and the dashboard calls it
a legacy record that keeps working. I'll keep it until the route is
repaired. After the change, I checked DNS, TCP, and the TLS certificate,
again without sending any HTTP request.

No test in the repository could have found this. CI runs against a local
build, which never touches DNS or Vercel's network. A crawler pointed at
production found it by failing to open the first page.

## What the crawler found and the test suite did not

This site has a Playwright suite that blocks a deploy if a page loses its
h1, canonical, JSON-LD, or hreflang. It tests the URLs the sitemap
**declares**. A crawler tests the ones **reachable through links**, plus
every link target, every external link, and every response header. Four
things the suite didn't see made it into the report:

1. The main domain was unreachable from one ISP.
2. No URL had a security header.
3. An external link had changed address.
4. Raw and rendered HTML matched on all 68 pages, measured across the whole
   site for the first time.

CI was green the whole time, and it wasn't wrong, because it tests none of
those things. A green CI tells you that what it measures didn't break. An
audit looks at everything else.

On the same day, an accessibility suite built on axe-core flagged 266
violations that the SEO suite also missed, 224 of them on the brand link in
every page's header. What that means for an AI agent gets its own article,
on
[how AI agents read the page through the accessibility
tree](/en/blog/accessibility-tree).

## In Next.js: security headers in `next.config.ts`

As in my [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs),
the App Router is the reference implementation here. To fix the headers, I
added a `headers()` function to the config, with one rule that matches every
route.

```ts
// next.config.ts
async headers() {
  return [
    {
      source: '/:path*',
      headers: [
        { key: 'X-Content-Type-Options', value: 'nosniff' },
        { key: 'X-Frame-Options', value: 'DENY' },
        { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
      ],
    },
  ]
},
```

A test in the same file as the SEO suite keeps the finding from coming back.

```ts
// tests/seo/seo.spec.ts
for (const path of ['/', '/robots.txt', '/feed.xml']) {
  test(`security headers on ${path}`, async ({ request }) => {
    const headers = (await request.get(path)).headers()
    expect(headers['x-content-type-options']).toBe('nosniff')
    expect(headers['x-frame-options']).toBe('DENY')
    expect(headers['referrer-policy']).toBe('strict-origin-when-cross-origin')
  })
}
```

None of these headers changes what Googlebot reads.
`X-Frame-Options: DENY` stops anyone from embedding the site in an iframe,
and this site isn't embedded anywhere. If yours is, you need a different
rule.

In Next.js, the crawl build needs care too. This site reads its domain from
an environment variable, which decides whether canonicals and hreflang send
the crawler to localhost or to production.

```bash
NEXT_PUBLIC_GTM_ID= SITE_INDEXABLE=true NEXT_PUBLIC_DOMAIN=http://localhost:3000 npm run build
```

`SITE_INDEXABLE=true` matters as well. Without it, this site serves
`Disallow: /` in `robots.txt`, and a crawler that obeys the file, such as
Screaming Frog, crawls nothing.

After the crawl, you can check title and description page by page in the
[meta tag validator](/en/tools/meta-tag-validator), which shows both side by
side with a search result preview.
