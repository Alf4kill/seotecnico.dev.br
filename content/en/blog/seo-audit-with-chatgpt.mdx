Yes, you can use ChatGPT, or any AI assistant, in an SEO audit, but only to
interpret data you collected and handed to it yourself. Don't use it as the
source for what the page contains. An assistant audits whatever its fetching
tool brought back, not the page itself, and when that tool drops something,
the explanation it gives sounds as confident as a correct answer. In this
site's lab, I compared what five assistants said with what my server
recorded, and the disagreements show up at exactly that point.

All the data here comes from two experiments I've published, and each one
documents its full method:
[Does ChatGPT read JavaScript?](/en/blog/does-chatgpt-read-javascript) and
[Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript).
This page covers only the cases where an assistant's explanation and the
server log disagree, and what that means for how you ask for an audit.

This isn't a list of vendor bugs. Each case holds for one date, one plan, and
one test condition. What repeats across cases is the mechanism, and if
you're auditing a site, the mechanism is what matters.

## When Gemini said the JSON-LD wasn't there

In one of the experiment's conditions, the lab page carries a
`<script type="application/ld+json">` block holding the code the assistant
has to report. It's in the HTML of every server response, doesn't depend on
JavaScript, and isn't injected after load.

On October 2, 2026, Gemini on the free plan said in five rounds that the
JSON-LD with the code wasn't in the HTML it received. In round 62 it went
further and said "the response obtained from the page did not contain a
JSON-LD script block" (translated from Portuguese). In other words, no
JSON-LD at all.

Rounds 47, 57, and 67 show the same pattern with a different resource, the
direct address of a JSON file included in the prompt. In all three, Gemini
answered that it couldn't access the JSON. In round 47, it put it as "not
possible to access the endpoint" (translated from Portuguese). My server log
shows the JSON was requested in the same second as the page in all three
rounds, and served every time.

Five rounds aren't enough to compare Gemini with the other assistants, and
that comparison isn't the point. What matters is that the answer describes
the page as if the assistant had read all of it, when it read a version
processed by a tool it doesn't control.

## When DeepSeek said it doesn't run the page's JavaScript

Another condition uses a page with a script, and the server records whether
it runs. In round 43, on October 2, 2026, DeepSeek on the free plan explained
that it receives the content "without running the page's JS" (translated
from Portuguese). My server log shows that script running in 11 of 11
DeepSeek rounds.

That sentence matches what many people already believe about AI and
JavaScript, which is why it goes unchallenged. In the measured case, it was
wrong about DeepSeek's own tool. If you took the answer as a diagnosis,
you'd conclude that content rendered by JavaScript is invisible to DeepSeek.
For that page, in that period, the log doesn't support it.

Which assistants run JavaScript, and under what conditions, is measured in
[Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript).
What matters here is that the wrong explanation came from the assistant
itself.

## Why this happens: the explanation is the model guessing about its own tool

When you ask an assistant to audit a URL, two things happen. First, a
fetching or search tool downloads the page and converts it into something
that fits in the model's context. Then the model reads that result and
writes the answer. It never sees the original page, only what the tool
delivered.

Extraction tools usually convert HTML into text, and along the way they may
drop `<script>`, parts of the `<head>`, and other bits that don't look like
content. If the JSON-LD was dropped at that stage, then as far as the model
is concerned, it never existed. "No JSON-LD on the page" then becomes an
accurate description of what the model received, and a false one about the
page.

The explanation is the bigger problem. A model has no access to its tool's
code, or to any record of what that tool did with the page. Ask it why
something didn't show up and it produces the most plausible explanation, in
the same tone as a verified answer. That's probably why DeepSeek described a
limitation the server didn't confirm. Its sentence was plausible, not
observed.

So an assistant's explanation of its own tool isn't data. It counts only when
it matches something you can check outside the assistant, and whatever you
write should say which of the two is your source.

## How closed and open prompts change the answer

The experiments used a closed prompt. It asked each assistant to report the
codes present on the page and to say "not found" when one was missing. You
can verify that kind of answer, because the code either matches or it
doesn't. With that prompt, the five assistants returned no wrong code out of
232.

Zero in 232 doesn't prove that errors can't happen. By the rule of three, at
95% confidence, the true rate of invented codes for this kind of prompt is
below about 1 in 77 answers. Both failures above were in the explanation,
too, not in the code the assistant delivered.

An open prompt behaves differently. On September 25, 2026, using a free
Perplexity account with the advanced-search preview its interface offered, I
sent the address of an article on this site along with a quick prompt typed
in Portuguese, roughly "open this site and analyze what its content is
about." Perplexity's indexer hadn't visited that article yet, and my server
recorded 0 requests. The answer still presented a long analysis of the
content, built from the words in the URL and 10 third-party sources, none of
them from this site. Only after a first section that already treated that
content as the article's did a single sentence admit the page hadn't been
opened.

That's one case, on a free account, in a feature still in preview. It
doesn't describe Perplexity in general or its paid plans. It describes what
an open prompt allows. With the test's closed prompt, the same Perplexity
admitted the failure in 5 of 5 rounds.

When a question accepts any plausible text as an answer, a model can fill
that gap with what it knows about the topic, the title, or search results.
Without checking, you can't tell an invented summary from a real one. In an
audit, "analyze the SEO of this URL" is an open prompt. "From the HTML below,
copy the exact value of the `<title>`, the meta description and the
canonical" is a closed one.

## Recommended workflow: collect, hand over, then ask for interpretation

When information reaches the model as text you pasted yourself, the
assistant's fetching tool drops out of the path, and so does the filter that
caused the errors above. I use a three-step workflow:

1. **Collect with a tool.** Get the HTML as the server delivers it, with
   `curl` or "View page source" in your browser. The Elements panel in
   DevTools shows the DOM after JavaScript has run, which is something else.
   For `<head>` tags, use the
   [meta tag validator](/en/tools/meta-tag-validator). For structured data,
   use Google's Rich Results Test, and for the version Google rendered, URL
   Inspection in Search Console.
2. **Hand it over as text.** Paste the HTML, or the parts that matter, into
   the chat. Don't pass the URL. On large pages, cut it down to the `<head>`
   and the relevant sections, because HTML that's too long may be truncated
   before it reaches the model.
3. **Ask for interpretation with a closed prompt.** Forbid invention, require
   a source for every claim, and keep what's in the HTML separate from
   opinion.

Here's an illustrative prompt. Adjust the items to whatever you're auditing.

```text
Below I will paste a page's HTML, exactly as the server delivers it.
Use only this HTML. Do not access the URL and do not use what you know
about the site.

1. Copy, without rewriting, the content of: title, meta description,
   link rel="canonical", meta robots and every application/ld+json block.
2. For each item, point to the passage of the HTML you took the value from.
3. If an item is not in the HTML, write "absent from the pasted HTML".
   Do not infer, do not estimate, do not fill in.
4. Only after that, point out SEO problems, quoting the passage that
   supports each one.

HTML:
[paste here]
```

You can check steps 1 to 3 of this prompt against the HTML in seconds, value
by value. Step 4 is where the assistant is genuinely useful, and that's where
it should be working, on data you control.

## What goes wrong in an AI audit

Not every item carries the same weight of evidence, so this table separates
what I measured from what is still a hypothesis.

| Item audited | Status | What to do |
|---|---|---|
| Structured data (JSON-LD) | Measured: an assistant denied a block present in the HTML of every response | Check the HTML or the Rich Results Test |
| Content generated by JavaScript | Measured: an assistant said it does not run JS, and the script ran in 11 of 11 rounds | Check the server log or a controlled measurement |
| Access to a resource | Measured: an assistant said it could not access a JSON file the server served | Check the server log |
| Meta tags in the `<head>` | Hypothesis, not measured | Check the HTML before acting |

For per-assistant detail on structured data, see
[structured data and AI](/en/blog/structured-data-and-ai). If an assistant
says it can't open your site,
[ChatGPT can't access your website](/en/blog/chatgpt-cant-access-website)
covers the possible causes and how to tell them apart.

I left the meta tag row as a hypothesis on purpose. If the extraction tool
converts only the page body to text, `<head>` tags could vanish before
reaching the model too, and an assistant could report "no meta description"
on a page that has one. I haven't tested this, so I don't know whether it
happens, or with which assistants. Until it's measured, treat any AI claim
about meta tags as something to verify.

## How to check what the AI received

Three checks settle most cases.

**Is the data in the server's HTML?** This illustrative command counts how
many JSON-LD blocks the server response contains:

```bash
curl -s https://example.com/page | grep -c 'application/ld+json'
```

If the result is greater than zero and the assistant says there's no
structured data, the problem lies in the path between page and model, not in
your code.

**Does Google see the same thing?** Google's Rich Results Test shows the
structured data Google extracted, and URL Inspection in Search Console shows
the rendered HTML. For Google, those are the sources that matter, and an
assistant's opinion doesn't count.

**Was there a request?** Check your server log for the time you asked. Zero
requests followed by a detailed summary of the page means the content came
from somewhere else.

In the lab, each assistant gets a secret URL, and the URL identifies who made
the request. Your log gives you only a profile, the user agent each
request claims. So the right wording is "requests identifying themselves as
ChatGPT", not "ChatGPT accessed the page". The
[AI crawler detection pilot](/en/blog/detect-ai-crawlers) shows how to
separate profile from identity.

## In Next.js

In the App Router, JSON-LD is usually rendered as a
`<script type="application/ld+json">` inside the HTML the server generates.
On this site, `src/components/seo/JsonLd.tsx` does that in a Server
Component. It's part of the server response and doesn't depend on
hydration, which makes it exactly the kind of block Gemini denied in the
first case.

If an assistant tells you your Next.js page has no structured data, run the
`curl` command above before you touch any component. "Fixing" a JSON-LD
block that's already in the HTML only adds the risk of duplicating it.
