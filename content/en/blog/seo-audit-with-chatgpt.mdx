You can use ChatGPT, or any other assistant, in an SEO audit, but only to
interpret data you collected and handed to it yourself. Don't treat it as the
source of what's on the page: the assistant audits whatever its fetching tool
brought back, not the page itself, and when that tool drops something, the
explanation comes with the same confidence as a correct answer. In this site's
lab, I compared what five assistants said with what the server recorded, and
that's exactly where they disagreed.

The data comes from two published experiments: [Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript) and the [first
control test with ChatGPT, Claude and
Perplexity](/en/case-studies/ai-crawler-detection). The full method is
described there. Here I only use the cases where the assistant's explanation
and the server log disagree, and what that means for how you ask for an
audit.

This isn't a list of vendor bugs. Each case below holds for one date, one
plan and one test condition. What repeats across them is the mechanism, and
the mechanism is what matters to anyone running an audit.

## The case: "the JSON-LD wasn't there"

In one of the experiment's conditions, the lab page includes a `<script
type="application/ld+json">` block containing the code the assistant has to
report. The block is in the HTML of every server response. It doesn't depend
on JavaScript and isn't injected after the page loads.

On October 2, 2026, on the free plan, Gemini said in five rounds that the
JSON-LD with the code wasn't in the HTML it received. In one of them, round
62, the answer went further and said the response it got from the page didn't
contain a JSON-LD script block (translated from Portuguese). In other words,
no JSON-LD at all.

In rounds 47, 57 and 67, the same pattern showed up with a different
resource: the direct address of a JSON file, which was included in the
prompt. All three answers said the JSON couldn't be accessed; in round 47,
Gemini said it was "not possible to access the endpoint" (translated from
Portuguese). The server log shows the JSON being requested in the same second
as the page in all three rounds, and served every time.

Five rounds aren't enough to compare Gemini with the other assistants, and
that isn't the point. The point is that the answer describes the page as if
the assistant had read all of it, when what it actually read was a version
processed by a tool it doesn't control.

## The other case: "without running the page's JS"

In another condition, the page has a script whose execution gets recorded on
the server. In round 43, on October 2, 2026, DeepSeek on the free plan
explained that it receives the content "without running the page's JS"
(translated from Portuguese). The server recorded the script running in all
11 of DeepSeek's rounds.

That sentence is exactly what many people already believe about AI and
JavaScript, which is why nobody questions it. In the measured case, the
assistant was wrong about its own tool. Anyone who took that answer as a
diagnosis would conclude that JavaScript-rendered content is invisible to
DeepSeek, and the log doesn't support that conclusion for that page, in that
period.

Which assistants run JavaScript, and under what conditions, is measured in
[Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript). What matters here
is something else: the wrong explanation came from the assistant itself.

## Why this happens: the explanation is the model guessing about its own tool

When you ask an assistant to audit a URL, two components are involved. The
first is the fetching tool, which downloads the page and converts it into
something that fits in the model's context. The second is the model, which
reads that output and writes the answer. The model never sees the original
page; it sees whatever the tool gave it.

Extraction tools usually convert HTML to text, and along the way they may
throw out `<script>` tags, parts of the `<head>` and other bits that don't
look like content. If the JSON-LD got dropped at that stage, then as far as
the model is concerned it never existed. "There's no JSON-LD on the page" is
an accurate description of what it received, and false about the page.

The bigger problem is the explanation. The model has no access to its own
tool's code, or to any record of what the tool did with the page. When it
explains why something didn't show up, it produces the most plausible
explanation, in the same tone as a verified answer. That's probably why
DeepSeek described a limitation the server didn't confirm: the sentence was
plausible, not observed.

The rule that follows: an assistant's explanation of its own tool isn't
data. It only counts when it matches something you can verify independently,
and anything you write about it should make clear which of the two is your
source.

## How you phrase the prompt decides it: closed vs. open

In the experiments, the prompt was closed: report the codes on the page and
say "not found" when one is missing. An answer like that can be verified,
because the code either matches or it doesn't. With that closed prompt, the
five assistants returned zero wrong codes out of 232.

Zero out of 232 doesn't prove the error is impossible. By the rule of three,
with 95% confidence, the true rate of made-up codes under this kind of prompt
is below about 1 in 77 answers. Notice, too, where the failures in the two
cases above were: in the explanation, not in the code returned.

An open-ended prompt is a different story. On September 25, 2026, using a
free Perplexity account with the advanced-search preview the interface was
offering, I sent the address of an article on this site with a quick,
open-ended request in Portuguese, roughly "open this site and analyze what
its content is about". Perplexity's indexer hadn't visited the article yet,
and the server recorded 0 requests. The answer still laid out a long analysis
of the content, built from the words in the URL and from 10 third-party
sources, none of them this site. Only after an opening section that already
presented that content as the article's did a single sentence admit the page
hadn't been opened.

The caveat matters: this is one case, on a free account, using a feature in
preview. It doesn't describe Perplexity in general or its paid plans. It
describes what an open-ended prompt allows. With the test's closed prompt, the
same Perplexity admitted failure in 5 of 5 rounds. When a question accepts any
plausible text as an answer, the model can fill the gap with what it knows
about the topic, the title or the search results, and you can't tell a
made-up summary from a real one without checking.

In an audit, "analyze the SEO of this URL" is an open prompt. "From the HTML
below, copy the exact value of the `<title>`, the meta description and the
canonical" is a closed one.

## Recommended workflow: collect, hand over, then ask for interpretation

If the information reaches the model as text you pasted in yourself, the
assistant's fetching tool is out of the picture, and so is the filter that
caused the errors above. The workflow I use has three steps.

1. **Collect it with a tool.** Get the HTML as the server sends it, with
   `curl` or "View page source" in your browser. The DevTools Elements panel
   shows the DOM after JavaScript has run, which is something else. For
   `<head>` tags, use the [meta tag validator](/en/tools/meta-tag-validator).
   For structured data, use Google's Rich Results Test; for the version Google
   rendered, use URL Inspection in Search Console.
2. **Hand it over as text.** Paste the HTML, or the relevant parts, into the
   chat. Don't give it the URL. On large pages, trim it down to the `<head>`
   and the sections that matter: HTML that's too long may get truncated before
   it reaches the model.
3. **Ask for interpretation with a closed prompt.** Tell it not to invent
   anything, require a source for every claim, and keep what's in the HTML
   separate from opinion.

The prompt below is illustrative. Adjust the items to whatever you're
auditing.

```text
Below I will paste a page's HTML, exactly as the server delivers it.
Use only this HTML. Do not access the URL and do not use what you know
about the site.

1. Copy, without rewriting, the content of: title, meta description,
   link rel="canonical", meta robots and every application/ld+json block.
2. For each item, point to the passage of the HTML you took the value from.
3. If an item is not in the HTML, write "absent from the pasted HTML".
   Do not infer, do not estimate, do not fill in.
4. Only after that, point out SEO problems, quoting the passage that
   supports each one.

HTML:
[paste here]
```

Steps 1 to 3 of the prompt are verifiable: you can check each value against
the HTML in seconds. Step 4 is where the assistant adds real value, and that's
where it should be doing the work, on data you control.

## What goes wrong in an AI audit

Not everything here rests on the same strength of evidence. The table keeps
what was measured separate from what's only a hypothesis.

| Item audited | Status | What to do |
|---|---|---|
| Structured data (JSON-LD) | measured: an assistant denied a block that was in the HTML of every response | check the HTML or the Rich Results Test |
| JavaScript-generated content | measured: an assistant said it doesn't run JS, and the script ran in 11 of 11 rounds | check the server log or a controlled measurement |
| Access to a resource | measured: an assistant said it couldn't access a JSON file the server served | check the server log |
| Meta tags in the `<head>` | hypothesis, not measured | check the HTML before acting |

For structured data, the per-assistant breakdown is in [structured data and
AI](/en/blog/structured-data-and-ai). When an assistant says it can't open
your site, the possible causes and how to tell them apart are in [ChatGPT
can't access your website](/en/blog/chatgpt-cant-access-website).

The meta tag row is deliberately marked as a hypothesis. If the extraction
tool only converts the page body to text, the `<head>` tags may disappear
before they reach the model too, and an assistant could report "no meta
description" on a page that has one. I haven't tested this, and I don't know
whether it happens, or with which assistants. Until it's measured, treat any
AI claim about meta tags as something to verify.

## How to check what the AI received

When an assistant tells you something about your page, three checks settle
most cases.

**Is the data in the server's HTML?** The command below is illustrative: it
counts how many JSON-LD blocks the server response contains.

```bash
curl -s https://example.com/page | grep -c 'application/ld+json'
```

If the result is greater than zero and the assistant says there's no
structured data, the problem lies somewhere between the page and the model,
not in your code.

**Does Google see the same thing?** The Rich Results Test shows the
structured data Google extracted, and URL Inspection in Search Console shows
the rendered HTML. Those are the sources that matter for Google; an
assistant's opinion doesn't factor in.

**Was there a request?** Check the server log around the time you asked the
question. Zero requests followed by a detailed summary of the page means the
content came from somewhere else. One distinction matters here: in the lab,
each assistant gets a secret URL, and that's what identifies who made the
request. In your log, all you have is a profile, so the accurate wording is
"requests identifying themselves as ChatGPT", not "ChatGPT accessed the
page". How to tell a profile from a verified identity is covered in the [AI
crawler detection case study](/en/case-studies/ai-crawler-detection).

## In Next.js

In the App Router, JSON-LD is usually rendered as a `<script
type="application/ld+json">` inside the server-generated HTML. On this site,
that's what `src/components/seo/JsonLd.tsx` does, in a Server Component. The
block is in the server response and doesn't depend on hydration, which is
exactly the kind of block Gemini denied existed.

If an assistant says your Next.js page has no structured data, run the `curl`
above before touching any component. "Fixing" JSON-LD that's already in the
HTML just risks duplicating the block. The rest of the SEO implementation in
the App Router is covered in the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs).
