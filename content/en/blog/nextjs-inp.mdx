INP (Interaction to Next Paint) measures the time between a user's
interaction and the next frame the browser paints on screen. It's good at
≤200 ms at the p75 of field data. In Next.js, overruns typically come from
hydration competing with the first click and from long handlers that hold
the main thread. INP also comes with a trap of its own. **Lighthouse doesn't measure
INP**, so if you only audit in the lab, you can't see it. This
article shows how to collect your own field data and what to fix once you
have it.

## What INP is and why Lighthouse doesn't show it

INP replaced FID as a Core Web Vital on March 12, 2024. They differ in
scope. FID measured only the *input delay* of a visit's first interaction,
meaning how long the browser took to start responding. INP covers every
interaction in the visit and its full cycle, including handler processing
and painting the frame that results. It's a harder metric, and that's why it
catches problems FID let through.

Here are the field thresholds at the p75:

| Rating | Value at the p75 |
|---|---|
| Good | ≤200 ms |
| Needs improvement | 200–500 ms |
| Poor | >500 ms |

One point changes how you work. **Lighthouse has no INP metric.** It isn't
missing from the interface. It can't exist there at all, because INP needs a
real user interacting with the page, and Lighthouse runs in a lab where
nobody clicks anything.

What the lab offers instead is TBT (Total Blocking Time), a proxy that adds
up how long the main thread was blocked during load. It correlates with
INP, but it isn't INP. This site's Lighthouse CI budget uses exactly that,
TBT ≤200 ms as a lab proxy, checked on every pull request. It's the best the
lab can give you, and it's worth keeping. It's still a proxy, though, and a
proxy doesn't replace measurement.

Small sites have a double blind spot. With no interaction in the lab,
Lighthouse has no INP. Below CrUX's traffic threshold, PageSpeed Insights
and Search Console have no INP either, and that's where this site is today.
All that's left is to measure your own INP in the field.

## The 3 subparts of every interaction

Before you measure, you need to know what you're measuring. Every
interaction breaks down into three phases, and the right fix depends on
which one runs long.

INP is the sum of the three phases:

| Phase | What happens | Typical cause of an overrun |
|---|---|---|
| **Input delay** | Time from the click until the handler starts | A busy main thread (hydration, a third-party script, a long task) |
| **Processing duration** | The handler and the re-render run | A long handler, an expensive synchronous re-render, forced layout |
| **Presentation delay** | Time until the browser paints the frame | A large DOM, expensive styles, a long list without virtualization |

This split isn't academic. It's what `web-vitals` attribution reports, and
it lets you fix the actual cause instead of guessing.

## How this site measures its own INP

Without CrUX, the alternative is to run your own RUM. This is the code
running in production in `src/lib/rum.ts` today. It imports from
`web-vitals/attribution` (v5) and sends a single `web_vitals` event to the
dataLayer through a typed helper. The code comment is in Portuguese. It says
that an empty `interactionTarget` means the element left the DOM after the
interaction.

```ts
// src/lib/rum.ts
export function reportINP(metric: INPMetricWithAttribution): void {
  const { attribution } = metric
  pushEvent({
    event: 'web_vitals',
    metric_name: 'INP',
    metric_id: metric.id,
    metric_value: Math.round(metric.value),
    metric_rating: metric.rating,
    // interactionTarget vazio = elemento removido do DOM após a interação
    inp_element: (attribution.interactionTarget || '(unknown)').slice(0, MAX_SELECTOR_LENGTH),
    inp_interaction_type: attribution.interactionType,
    inp_load_state: attribution.loadState,
    inp_input_delay: Math.round(attribution.inputDelay),
    inp_processing_duration: Math.round(attribution.processingDuration),
    inp_presentation_delay: Math.round(attribution.presentationDelay),
  })
}
```

Initializing it is trivial, with one guard for SSR and another against a
double call.

```ts
// src/lib/rum.ts
export function initRum(): void {
  if (started || typeof window === 'undefined') return
  started = true
  onLCP(reportLCP)
  onINP(reportINP)
}
```

Three details here aren't obvious, and each one cost me time:

- **`MAX_SELECTOR_LENGTH = 100`.** GA4 truncates event parameters at 100
  characters. Without the `slice`, long selectors show up in the report
  silently truncated. It's better to cut them yourself and know it.
- **`interactionTarget` can come back empty.** When the element leaves the
  DOM after the interaction (a modal closes, a list item disappears),
  attribution can no longer resolve the selector. That's what the
  `'(unknown)'` fallback is for. Without it, the per-element breakdown has
  gaps.
- **INP reports again.** When the page comes back from `hidden`, the library
  may send a worse value with the **same `metric_id`**. If you sum or count
  events, you inflate the number. Take the **maximum per `metric_id`**
  instead. In this site's field data, this happened in 1 of the 9 page loads
  measured.

After the dataLayer, GTM reads six `inp_*` Data Layer Variables mapped in
the tag, and GA4 receives three custom dimensions (element, interaction
type, and load state) and three event-scoped custom metrics in milliseconds.
This pipeline has been live in production since July 22, 2026.

Because this is analytics, a word on LGPD, Brazil's data protection law.
The site runs Consent Mode v2 in advanced mode. When consent
is denied, the hit becomes a cookieless ping, so performance data doesn't
turn into user tracking.

### What the field data showed (and what it hasn't yet)

**Update (September 2026):** when this article came out on July 22, the
pipeline had been in production for a few hours. I promised to publish real
percentiles after 28 days of collection, the same window CrUX uses. This
section keeps that promise as far as the data allows, and says where it
runs out.

These numbers come from a GA4 Exploration filtered by `metric_name = INP`,
covering July 22 to September 12, 2026, with one row per `metric_id`. I set
three rules before I calculated anything:

- **July 22 excluded.** I set up and validated the pipeline that day. One of
  its two measurements arrived without any `inp_*` parameter, which is
  consistent with the GTM tag still being put together. Test traffic isn't
  field data.
- **August 30 and September 4 kept.** There's no way to know whether those
  visits were tests, and excluding them without evidence would mean picking
  the result.
- **Maximum per `metric_id` counts.** One load reported twice, first 8 ms
  and then 56 ms. It counts as 56.

That leaves **9 page loads with measured INP over 52 days** (July 23 to
September 12). Only 5 fall inside the promised 28-day window. The site gets
little traffic, and only visitors who don't block GTM reach GA4.

| Metric | 52 days (n = 9) | Last 28 days (n = 5) |
|---|---|---|
| Median | 80 ms | 88 ms |
| p75 | 144 ms | 168 ms |
| Maximum | 168 ms | 168 ms |
| Above 200 ms | 0 | 0 |

I computed the p75 with the *nearest rank* method, which takes the smallest
value that covers at least 75% of the measurements.

#### Does this prove this site's INP is good? Not yet

All 9 measurements are below 200 ms, and the data still doesn't settle the
question. For the p75 to be below 200 ms, at most 25% of loads can exceed
it. With 0 of 9 above the threshold, the 95% upper bound (Clopper-Pearson)
on the true share above 200 ms is **28.3%**. That's above 25%, so the data
is consistent with both a good INP and an INP right at the limit.

In closed form, with zero above the threshold in *n* loads, the 95% upper
bound is 1 − 0.05^(1/*n*). It doesn't drop below 25% until **n = 11**. For
the last 28 days, with n = 5, the bound is 45.1%.

That's why the exclusion rule had to come before the calculation. With
July 22 included, n would be 11 and the bound would fall to 23.8%, which
would flip the conclusion. I based the exclusion on where the visits came
from, not on its effect on the number.

#### By subpart

| Subpart | Sum across the 9 measurements | Share | Largest subpart in |
|---|---|---|---|
| Input delay | 215 ms | 25% | 1 measurement |
| Processing duration | 194 ms | 22% | 3 measurements |
| Presentation delay | 456 ms | 53% | 5 measurements |

What weighs most on this site is **painting the frame**, not running
JavaScript. All 9 interactions had `inp_load_state = complete`, so none of
them happened during hydration, the classic case behind item 7 in the fixes
below. With n = 9, this is a pattern to watch, not a proven characteristic
of the site.

#### By element

These routes are the Portuguese pages' paths, as GA4 recorded them.

| Route recorded in GA4 | Element | INP | Input delay | Processing | Presentation |
|---|---|---|---|---|---|
| `/ferramentas/validador-meta-tags` | "Validar" (validate) button | 168 ms | 60 | 20 | 88 |
| `/ferramentas/validador-meta-tags` | `(unknown)` | 168 ms | 62 | 28 | 78 |
| `/blog/hreflang-nextjs` | Description on a listing card | 144 ms | 2 | 4 | 138 |
| `/guia/seo-tecnico-nextjs` | Theme toggle icon | 88 ms | 18 | 3 | 67 |
| `/ferramentas` | Social media icon in the footer | 80 ms | 9 | 68 | 3 |
| `/` | `(unknown)` | 64 ms | 15 | 29 | 20 |
| `/ferramentas/validador-meta-tags` | URL field | 64 ms | 15 | 0 | 49 |
| `/ferramentas` | `(unknown)` | 56 ms | 1 | 42 | 13 |
| `/guia/seo-tecnico-nextjs` | `(unknown)` | 32 ms | 33 | 0 | 0 |

Subparts are in milliseconds, and each is rounded separately, which is why
the last row adds up to 33. With one or two measurements per element,
there's no per-element percentile. The table shows measurements, not
distributions.

It still points to what to investigate:

- **The two highest INPs are on the meta tag validator**, with the two
  highest input delays (60 and 62 ms), on a page that had already loaded.
  Something held the main thread before the handler started. The second
  row's `(unknown)` is consistent with a click on that button's icon.
  During validation, the icon is swapped for a spinner, so the clicked
  element leaves the DOM. It's the first thing to record in the Performance
  panel.
- **A tap on text cost 138 ms of presentation alone.** Processing took
  4 ms. Almost all of it went between the handler finishing and the next
  frame, on a tap that navigated to another route.
- **4 of the 9 measurements came with an `(unknown)` element.** That's the
  fallback in the code above. The clicked element was no longer in the DOM
  when attribution tried to resolve the selector, which happens when the
  click swaps what's on screen or goes to another route.

#### A trap that only showed up in the data: the event's route can be wrong

Row 3 doesn't add up. Its selector is the description of a card in the
listings on the home page and `/blog`, an element that doesn't exist on an
article page. Yet the event arrived with the route `/blog/hreflang-nextjs`.

The `metric_id` explains it. `web-vitals` (5.3.0) builds the id from `v5-`,
`Date.now()`, and a random number. In this site's data, each load's LCP and
INP were created in the same millisecond, or 1 ms apart. If you match each
INP with the LCP from the same load, you can see what happened:

- The card's load started at `/blog`, where its LCP was recorded. The tap on
  the card navigated to the article, and the INP was sent from the article.
- One load started at `/ferramentas/checador-cwv` and had its INP recorded
  at `/ferramentas`.
- The load with two reports started at `/`. The first report arrived with
  `/`, and the second, worse one with `/ferramentas`.

**3 of the 9 measurements reached GA4 with a route different from the one
where the page loaded.**

The App Router itself causes this. Navigation happens on the client, so the
page load stays the same. INP belongs to that whole page load, and GA4
records the route at send time, when the page becomes hidden.

In GA4, a per-route INP report can attribute the interaction to the wrong
page without any warning. For the card, that's certain. For the other two,
the data doesn't say which route the click happened on. If you want to
break INP down by route with confidence, capture the route at the moment of
the interaction and send it with the metric, instead of relying on the
event's route.

## Diagnosis: DevTools and Long Animation Frames

RUM tells you *that* INP is high and *on which element*. To find out *why*,
use the DevTools Performance panel. Record a session, interact with the
element RUM pointed to, and look for long tasks around the interaction.

Today, the Long Animation Frames API (`long-animation-frame`) makes this
much more direct. It's available in Chrome and Edge, and `web-vitals`
attribution uses it to point to the script that held the frame. You get the
script itself, not just "something blocked the main thread."

The two work well together. Field data gives you the element and the
phase, and the Performance panel gives you the script and the stack.
Without field data, you end up optimizing what doesn't hurt.

## Fixes for INP in Next.js

Here are the fixes, from cheapest to most expensive.

### 1. Less JavaScript to hydrate

In the App Router, the best-value fix is structural. Use Server Components
by default, and put `'use client'` only at the leaves of the tree. Every
component that hydrates keeps the main thread busy at the worst possible
moment, during load, exactly when the user first interacts. For heavy
islands below the fold, `next/dynamic` defers the cost.

To be honest, this site hasn't needed a dynamic import yet. Its bundle is
small enough not to justify one. I'm saying so because the alternative
would be to fake an optimization that doesn't exist here.

### 2. Break up long tasks with `scheduler.yield()`

A handler that runs for 300 ms holds the frame for 300 ms. Instead, yield
the main thread partway through. Paint the visual feedback first, then do
the rest.

```ts
// utils/yield-to-main.ts
export function yieldToMain(): Promise<void> {
  if (typeof globalThis.scheduler?.yield === 'function') {
    return globalThis.scheduler.yield()
  }
  return new Promise((resolve) => setTimeout(resolve, 0))
}
```

Don't skip the fallback. `scheduler.yield()` is available in Chrome 129 and
Edge 129 (September 2024) and in Firefox 142 (August 2025). Safari still
doesn't support it (checked July 22, 2026), so it isn't Baseline. In Safari,
`setTimeout(0)` yields the thread just the same, but you lose the
prioritized continuation.

### 3. `useTransition` and `useDeferredValue`

If the re-render is the problem (processing duration), React 19 lets you
mark what's urgent. Wrap the expensive update in `useTransition`, and use
`useDeferredValue` to defer a derived value. The input stays responsive
while the heavy list recalculates.

### 4. Avoid forced synchronous layout

It happens when a handler reads layout (`offsetHeight`,
`getBoundingClientRect`), writes to the DOM, and then reads again. Each read
after a write forces the browser to recalculate everything. Fix it by
batching. Do all the reads first, then all the writes.

### 5. Presentation delay: DOM and styles

If attribution shows a high `inp_presentation_delay`, the handler has
already finished and painting is the bottleneck. Go after DOM size and style
cost. Virtualize long lists, and use `content-visibility` on off-viewport
blocks where it fits.

### 6. Third-party scripts compete for the same thread

Every tag and analytics script competes with your UI for the main thread,
and that includes GTM, which feeds the measurement described above. This
site's RUM pipeline has a cost, and I'd rather say so.

To measure it, record the Performance panel twice, once with the GTM
request blocked and once without, and compare the long tasks.

### 7. Input delay is rarely the problem on its own

Input delay is almost never the problem by itself. If `inp_input_delay` is
high, the handler hadn't even started, because the main thread was busy
with something else. That's a symptom of items 1 and 2, not a separate
category. `inp_load_state` usually reveals the most common case, an
interaction during hydration.

## What NOT to do

It's tempting to remove interactivity to score better. You drop the filter
users rely on, cut the JavaScript that makes the product work, or delay
loading things people need. The number improves and the site gets worse.

INP exists to measure how responsive a page feels, not to be beaten. A site
with no interaction has a perfect INP and no use at all.

## How to check

After any fix, verify it in four places:

1. **In GA4**: build an Exploration with `metric_name = INP`, `metric_id` in
   the rows, and Event count among the metrics, then export it. Explorations
   **sum** custom metrics, so you have to calculate the **maximum per
   `metric_id`** outside GA4. A row with an Event count above 1 is a sum of
   reports, not a measurement. Then break the data down by `inp_element` and
   the three subparts without trusting the event's route (see the trap
   above), and compare the window before the deploy with the one after.
2. **In DevTools**: repeat the Performance panel recording on the same
   interaction, and check whether the long task you went after has left the
   trace.
3. **In Lighthouse**: **TBT** is what moves, not INP. Use it as an indirect
   signal, and don't confuse the two.
4. **In CrUX**: if and when the site crosses the traffic threshold, the
   window is 28 days, so field data takes a while to reflect the fix. To
   check whether your domain is in CrUX yet, and see its field INP if it is,
   use the [Core Web Vitals checker](/en/tools/cwv-checker).

Whatever you fix, the order stays the same. A fix without field measurement
is a guess with nice syntax.
