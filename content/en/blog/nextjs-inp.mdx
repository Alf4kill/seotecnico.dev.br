INP (Interaction to Next Paint) measures the time between a user interaction and the next frame painted on screen; a good value is ≤200 ms at the p75 of field data. In Next.js, the usual culprits are hydration competing with the first click and long handlers tying up the main thread. And this metric comes with a trap of its own: **Lighthouse doesn't measure INP**. If you only audit in the lab, you can't see it at all. This article shows how to collect your own field data and what to fix once you have it.

## What INP is and why Lighthouse doesn't show it

INP replaced FID as a Core Web Vital on March 12, 2024. The difference is scope: FID only measured the *input delay* of a visit's first interaction, the time until the browser starts responding. INP looks at every interaction during the visit and measures the full cycle, including the handler's processing and painting the resulting frame. It's a tougher metric, which is why it catches problems FID let slide.

The field thresholds, at the p75:

| Rating | Value at the p75 |
|---|---|
| Good | ≤200 ms |
| Needs improvement | 200–500 ms |
| Poor | >500 ms |

Now for the point that changes how you work: **Lighthouse has no INP metric.** That's not a gap in the interface; it's conceptually impossible. INP needs a real user actually interacting, and Lighthouse runs in a lab environment where nobody clicks anything. What the lab audit offers instead is TBT (Total Blocking Time), a proxy that adds up how long the main thread was blocked during load. It correlates with INP, but it isn't INP.

This site's Lighthouse CI budget works on exactly that logic: TBT ≤200 ms as a lab proxy, checked on every pull request. It's the best the lab can give you, and it's worth keeping. But it's a proxy, and a proxy is no substitute for measurement.

For small sites, that adds up to a double blind spot. With no interaction in the lab, there's no INP in Lighthouse. And below CrUX's traffic threshold, there's no INP in PageSpeed Insights or Search Console either, which is where this site is today. There's only one way out: measure your own INP in the field.

## The 3 subparts of every interaction

Before you measure, you need to know what you're measuring. Every interaction breaks down into three phases, and the right fix depends on which one is running long.

INP is the sum of the three phases:

| Phase | What happens | Typical reason it runs long |
|---|---|---|
| **Input delay** | Time between the click and the handler starting | A busy main thread: hydration, third-party scripts, long tasks |
| **Processing duration** | Running the handler and the re-render | A long handler, an expensive synchronous re-render, forced layout |
| **Presentation delay** | Time until the browser paints the frame | A large DOM, expensive styles, a long list without virtualization |

That breakdown isn't academic: it's what `web-vitals` attribution reports, and it's what lets you fix the actual cause instead of guessing.

## How this site measures its own INP

Without CrUX, the alternative is your own RUM. The code below is what's running in production in `src/lib/rum.ts` right now: it imports from `web-vitals/attribution` (v5) and sends a single `web_vitals` event to the dataLayer through a typed helper. The Portuguese comment says an empty `interactionTarget` means the element was removed from the DOM after the interaction:

```ts
// src/lib/rum.ts
export function reportINP(metric: INPMetricWithAttribution): void {
  const { attribution } = metric
  pushEvent({
    event: 'web_vitals',
    metric_name: 'INP',
    metric_id: metric.id,
    metric_value: Math.round(metric.value),
    metric_rating: metric.rating,
    // interactionTarget vazio = elemento removido do DOM após a interação
    inp_element: (attribution.interactionTarget || '(unknown)').slice(0, MAX_SELECTOR_LENGTH),
    inp_interaction_type: attribution.interactionType,
    inp_load_state: attribution.loadState,
    inp_input_delay: Math.round(attribution.inputDelay),
    inp_processing_duration: Math.round(attribution.processingDuration),
    inp_presentation_delay: Math.round(attribution.presentationDelay),
  })
}
```

Initialization is trivial, with guards against SSR and against being called twice:

```ts
// src/lib/rum.ts
export function initRum(): void {
  if (started || typeof window === 'undefined') return
  started = true
  onLCP(reportLCP)
  onINP(reportINP)
}
```

Three details in that code aren't obvious, and each one cost me time:

- **`MAX_SELECTOR_LENGTH = 100`.** GA4 truncates event parameters at 100 characters. Without the `slice`, long selectors show up in the report silently cut off; better to cut them deliberately and know about it.
- **`interactionTarget` can come back empty.** When the element leaves the DOM after the interaction (a modal that closes, a list item that disappears), attribution can no longer resolve the selector. Hence the `'(unknown)'` fallback; without it, the per-element breakdown has gaps.
- **INP can report more than once.** When the page comes back from `hidden`, the library can emit a worse value with the **same `metric_id`**. Any analysis that sums or counts events will inflate the number. The right reading is the **maximum per `metric_id`**. In this site's field data, it happened in 1 of the 9 page loads measured.

From the dataLayer, the data keeps moving: GTM reads six `inp_*` Data Layer Variables mapped in the tag, and GA4 receives three custom dimensions (element, interaction type, load state) and three event-scoped custom metrics in milliseconds. The pipeline has been live in production since July 22, 2026.

A note on privacy (Brazil's data protection law, the LGPD), since this is about analytics: the site runs Consent Mode v2 in advanced mode. When consent is denied, the hit becomes a cookieless ping, so performance data doesn't turn into user tracking.

### What the field data showed (and what it hasn't yet)

**Update (September 2026):** when this article was published on July 22, the pipeline had been in production for a few hours, and I promised to publish the real percentiles after 28 days of collection, the same window CrUX uses. This section keeps that promise as far as the data allows, and says where the data stops supporting conclusions.

The data comes from a GA4 Exploration filtered on `metric_name = INP`, from July 22 to September 12, 2026, with one row per `metric_id`. Three rules were set before calculating any numbers:

- **July 22 was excluded.** That was the day the pipeline was set up and validated. One of that day's two measurements came in without any `inp_*` parameters, which fits with the GTM tag still being put together. Test traffic isn't field data.
- **August 30 and September 4 were kept.** There's no way to know whether those visits were tests, and excluding them without evidence would mean choosing the result.
- **The maximum per `metric_id` is what counts.** One page load reported twice, first 8 ms and then 56 ms; it counts as 56.

That leaves **9 page loads with a measured INP over 52 days** (July 23 to September 12). In the promised 28-day window, there were 5. The site gets little traffic, and only visitors who don't block GTM show up in GA4.

| Metric | 52 days (n = 9) | Last 28 days (n = 5) |
|---|---|---|
| Median | 80 ms | 88 ms |
| p75 | 144 ms | 168 ms |
| Maximum | 168 ms | 168 ms |
| Above 200 ms | 0 | 0 |

The p75 was calculated using the *nearest rank* method: the smallest value that covers at least 75% of the measurements.

#### Does this prove this site's INP is good? Not yet

All 9 measurements came in under 200 ms, and the data still doesn't settle the question. The p75 stays under 200 ms as long as no more than 25% of page loads go over that value. With 0 of 9 measurements above the threshold, the 95% upper bound (Clopper-Pearson) on the true share above 200 ms is **28.3%**. Since that's above 25%, the data is consistent with a good INP and with an INP right on the edge.

The calculation has a closed form: with zero measurements above the threshold out of *n*, the 95% upper bound is 1 − 0.05^(1/*n*). It only drops below 25% once **n = 11**. In the last 28 days, with n = 5, the bound is 45.1%.

The exclusion rule had to be set before the calculation for a concrete reason. With July 22 included, n would be 11 and the bound would drop to 23.8%, which would flip the conclusion. The exclusion was based on where the visits came from, not on how it affected the number.

And all 9 interactions happened with `inp_load_state = complete`: none during hydration, which is the classic case in item 7 of the fixes below. With n = 9, that's a pattern to keep an eye on, not a proven trait of the site.

| `/ferramentas` | `(unknown)` | 56 ms | 1 | 42 | 13 |

Subparts are in ms and rounded individually, which is why the last row adds up to 33. With one or two measurements per element, there's no per-element percentile: the table shows individual measurements, not distributions. Here's what it suggests looking into:

- **The two highest INPs are on the meta tag validator**, and they have the two highest input delays (60 and 62 ms), with the page already loaded. Something was tying up the main thread before the handler started. The `(unknown)` in the second row fits a click on that same button's icon: during validation, the icon is swapped for a spinner, so the clicked element leaves the DOM. It's the first thing to record in the Performance panel.
- **A tap on text cost 138 ms in presentation alone.** Processing took 4 ms; nearly all the time went between the end of the handler and the next frame, on a tap that navigated to another route.
- **4 of the 9 measurements came in with an `(unknown)` element.** That's the fallback in the code above: the clicked element was no longer in the DOM when attribution tried to resolve the selector, which happens when a click swaps out content on screen or navigates to another route.

#### A trap that only showed up in the data: the event's route can be wrong

The third row of the table has an inconsistency: the selector belongs to the description of a card in the home page and `/blog` listings, an element that doesn't exist on an article page, yet the event arrived with the route `/blog/hreflang-nextjs`. The explanation lies in the `metric_id`. `web-vitals` (5.3.0) builds the id from `v5-` + `Date.now()` + a random number, and in this site's data the LCP and INP for each page load were created in the same millisecond, or 1 ms apart. Matching each INP with the LCP from the same page load:

- the card's page load started at `/blog` (that's where the LCP was recorded), the tap on the card navigated to the article, and the INP was sent from the article;
- one page load started at `/ferramentas/checador-cwv` and had its INP recorded at `/ferramentas`;
- the page load with two reports started at `/`: the first arrived with `/`, and the second, worse one with `/ferramentas`.

**3 of the 9 measurements reached GA4 with a different route from the one where the page loaded.** The mechanism is the App Router itself: navigation happens on the client, the page load stays the same, the INP belongs to that entire page load, and GA4 records whatever route is current when the event is sent, which is when the page becomes hidden. A per-route INP report in GA4 can attribute an interaction to the wrong page without any warning. In the card's case, that's certain; for the other two, the data doesn't say which route the click happened on. To break INP down by route reliably, send the route along with the metric, captured at the moment of the interaction, instead of relying on the event's route.

## Diagnosis: DevTools and Long Animation Frames

RUM tells you *that* INP is high and *on which element*. To find out *why*, go to the Performance panel in DevTools: record a session, interact with the element RUM flagged, and look for long tasks around the interaction.

What makes that diagnosis much more direct today is the Long Animation Frames API (`long-animation-frame`), available in Chrome and Edge. It's what `web-vitals` attribution uses to point to the script responsible for holding up the frame: instead of "something blocked the main thread", you get the actual script.

A combination that works well: field data gives you the element and the phase; the Performance panel gives you the script and the stack trace. Without the first, you end up optimizing things that aren't hurting you.

## Fixes for INP in Next.js

Ordered from cheapest to most expensive.

### 1. Less JavaScript to hydrate

The best value-for-effort fix in the App Router is structural: Server Components by default, and `'use client'` only at the leaves of the tree. Every component that hydrates ties up the main thread at the worst possible moment, during load, which is exactly when the user makes their first interaction.

For heavy islands below the fold, `next/dynamic` defers the cost. To be upfront: this site hasn't needed dynamic imports yet, because the bundle is small enough not to justify them. I mention that because the alternative would be pretending to an optimization that doesn't exist here.

### 2. Break up long tasks with `scheduler.yield()`

A handler that runs for 300 ms holds up the frame for 300 ms. The solution is to yield the main thread partway through: paint the visual feedback first, then do the rest.

```ts
// utils/yield-to-main.ts
export function yieldToMain(): Promise<void> {
  if (typeof globalThis.scheduler?.yield === 'function') {
    return globalThis.scheduler.yield()
  }
  return new Promise((resolve) => setTimeout(resolve, 0))
}
```

The fallback isn't optional. `scheduler.yield()` is available in Chrome 129 and Edge 129 (September 2024) and Firefox 142 (August 2025), and still isn't supported in Safari (checked on July 22, 2026), so it isn't Baseline. In Safari, `setTimeout(0)` yields the thread just the same; what you lose is the prioritized continuation.

### 3. `useTransition` and `useDeferredValue`

When the problem is the re-render (processing duration), React 19 lets you mark urgency: `useTransition` wraps the expensive update and `useDeferredValue` defers a derived value. The input stays responsive while the heavy list recalculates.

### 4. Avoid forced synchronous layout

The pattern that causes it is reading layout (`offsetHeight`, `getBoundingClientRect`), writing to the DOM and reading again in the same handler; every read after a write forces the browser to recalculate everything. The fix is to batch: do all your reads first, then all your writes.

### 5. Presentation delay: DOM and styles

If attribution points to a high `inp_presentation_delay`, the handler has already finished and the bottleneck is painting. That makes DOM size and style cost the targets: virtualize long lists, and use `content-visibility` on off-screen blocks where it makes sense.

### 6. Third-party scripts compete for the same thread

Every tag and analytics script competes with your UI for the main thread, including the GTM that feeds the measurement described above. It's worth being honest about that: this site's RUM pipeline has a cost. To measure it, record the Performance panel twice, once with the GTM request blocked and once without, and compare the long tasks.

### 7. Input delay is rarely the problem on its own

If `inp_input_delay` is high, the handler hadn't even started yet; the main thread was busy with something else. It's a symptom of items 1 and 2, not a separate category. The `inp_load_state` field usually gives away the most common case: an interaction during hydration.

## What NOT to do

The obvious temptation is to strip out interactivity to get a better score: removing the filter users rely on, cutting the JavaScript that makes the product work, delaying things people need. That improves the number and makes the site worse.

INP exists to measure how responsive a site feels, not to be gamed. A site with no interaction has a perfect INP and zero usefulness.

## How to check

After applying any of the fixes above:

1. **In GA4**, build an Exploration with `metric_name = INP`, `metric_id` as the rows and Event count among the metrics, then export it. Explorations **sum** custom metrics, so the **maximum per `metric_id`** has to be calculated outside GA4: a row with an Event count above 1 is a sum of reports, not a single measurement. Then break it down by `inp_element` and the three subparts, without trusting the event's route (see the trap above), and compare the windows before and after the deploy.
2. **In DevTools**, record the same interaction in the Performance panel again and check whether the long task you were chasing is gone from the trace.
3. **In Lighthouse**, what will move is **TBT**, not INP; treat it as an indirect signal and don't confuse the two.
4. **In CrUX**, if and when the site crosses the traffic threshold, remember the window is 28 days, so field data takes time to reflect a fix. To find out whether your domain is in CrUX yet, and what its field INP is if so, use the [Core Web Vitals checker](/en/tools/cwv-checker).

The order of operations never changes: a fix without field measurement is just a guess with nice syntax.
