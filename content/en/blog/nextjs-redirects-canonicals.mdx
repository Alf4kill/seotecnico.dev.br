`next.config.ts` and middleware both handle redirects, in different ways. The
config's `redirects()` is static, evaluated before routing, with no
per-request cost. Middleware runs on **every** request and is the only one of
the two that can decide based on a cookie, a header or the visitor's location.
The practical rule: **if the rule is known at build time, it doesn't belong in
middleware.** But a question comes first, and it matters more:
does this problem actually call for a redirect, or for a canonical, or a
`noindex`? Almost every "duplicate page" status in Search
Console comes from picking the wrong tool.

## Three tools, three problems

Here's the decision table the whole article is built around:

| The situation | The tool | What it tells Google |
| --- | --- | --- |
| The old URL should stop existing | permanent redirect (301/308) | "this moved: transfer everything to the new address" |
| Both URLs exist, but one should consolidate the signals | canonical | "index that one; this is a variant" |
| The page exists for users, not for the index | `noindex` | "crawl it if you like, but don't index it" |
| Both URLs exist and hold different content | nothing | there's no problem to solve |

Getting that choice wrong doesn't produce an error; it produces a symptom
months later, in the indexing report. The rest of the article goes through
each tool and ends with a case, measured on this site, where two of them
cancel each other out.

## redirects() in next.config: the default path

When the rule is known at build time (a slug migration, a legacy URL, a
renamed path), it belongs in the config's `redirects()` array. Here's the
format (illustrative; this site's only production redirect comes right
after):

```ts
// next.config.ts — illustrative example, not this site's code
async redirects() {
  return [
    { source: "/blog/old-slug", destination: "/blog/new-slug", permanent: true },
  ];
}
```

In the interest of transparency: this site's production `redirects()` array
has **exactly one rule**, added in September 2026 when `/en` became the
English home page. `/en/guide` is a path segment with no page of its own, so
anyone who trimmed the English guide's URL landed on a 404 (the comment says
exactly that, and that `permanent` means 308):

```ts
// next.config.ts
  async redirects() {
    return [
      // /en/guide é só um segmento de caminho, sem página: quem encurta a URL
      // do guia inglês caía num 404. Com /en virando home, este era o último
      // beco sem saída da camada inglesa. `permanent` ⇒ 308.
      { source: '/en/guide', destination: '/en/guide/technical-seo-nextjs', permanent: true },
    ]
  },
```

Other than that one, there are none. The site launched in July 2026 with its
current URL structure already in place, and **a redirect is a debt to the
past, not a best practice in itself**. If you have no legacy URLs, you have
nothing to redirect, and every redirect you don't need to create is a chain
that will never exist.

### permanent: true is 308, not 301, and why it doesn't matter

`permanent: true` returns HTTP **308**, not 301. The technical difference: a
308 requires the client to keep the request's method (a POST stays a POST),
while a 301 allows switching to GET. For SEO, it makes no difference: Google
treats both as permanent redirects and consolidates signals at the
destination. If an audit tool complains that "it isn't a 301", the tool is out
of date, not your site.

### source, destination and path matching

`source` accepts parameters (`/blog/:slug`) and `destination` can reuse them,
which lets you migrate an entire structure with one rule. What to watch out
for is order and overlap: overly broad rules catch paths they shouldn't, and
the first matching rule wins. Test every new rule against a real path before
you deploy; the verification section shows how.

## Middleware: when the rule only exists at runtime

Middleware intercepts every request before routing and can respond with a
redirect. It's the right tool for exactly one kind of case: **a decision that
depends on information that only exists in the request**, like a session
cookie, a header or the visitor's country. In Next.js 16, middleware was
renamed **Proxy**: the file is `proxy.ts` and exports a function called
`proxy`, but it works the same way. Here's a hypothetical example (this site's
proxy doesn't redirect anything; the next section explains what it does):

```ts
// proxy.ts — hypothetical example; middleware.ts up to Next.js 15
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  if (request.cookies.has("beta-optin")) {
    return NextResponse.redirect(new URL("/beta", request.url));
  }
}
```

### The cost: it runs on every request

Every request to the site (a page, an asset that matches the matcher, a
crawler) runs the middleware. That's latency added in front of everything,
Googlebot included. The cost is justified when the logic is truly dynamic; for
a static rule, it's pure waste.

This site pays that cost deliberately, and not for redirects: `src/proxy.ts`
logs every page request to measure whether and how AI crawlers read the
content, since crawlers don't run GTM's JavaScript. It's code that sits in
front of every page the matcher lets through, accepted because there's nowhere
else that measurement could go.

### Redirects in middleware aren't for URLs you already know

It's worth repeating as a code review rule: if the `source` and the
`destination` are known before deploy, the rule belongs in the config. A fixed
mapping inside middleware gives you the same result while paying for it on
every request, and it splits your redirect logic across two places, which is
how accidental chains happen.

## redirect() and permanentRedirect() inside the component

The third option: the `redirect()` and `permanentRedirect()` functions from
`next/navigation`, called inside the component itself or a Server Action. The
legitimate use case is a decision that depends on **the route's data**: the
requested slug exists, but the content has moved; the product was
discontinued and the page points to its replacement. The decision gets made
where the data is (in the component that just loaded it) and couldn't live in
a static config.

## Canonical: a strong hint, not a directive

The canonical flips the hierarchy of the previous tools: a redirect is a
**directive** Google can't ignore (the old URL's content literally isn't served
anymore), while a canonical is a **hint** Google weighs alongside other
signals.

### Self-referencing on every page

This is where this site's implementation is most mature: every indexable
route emits a canonical pointing to itself, with a matching `og:url`, through
a single metadata helper (the Portuguese comments say "… hreflang, when the
route has a translation", and that feed autodiscovery has to live here, not in
the root layout, because the page's `alternates` replaces the inherited one):

```ts
// src/lib/metadata.ts
  return {
    title: absoluteTitle ? { absolute: title } : title,
    description,
    alternates: {
      canonical: path,
      // … hreflang, quando a rota tem tradução
      // Autodiscovery do feed em toda página. Precisa estar aqui (e não no
      // root layout) porque `alternates` da página substitui o herdado.
      types: {
        'application/rss+xml': [{ url: '/feed.xml', title: site.name }],
      },
    },
    openGraph: {
      url: absoluteUrl(path),
      siteName: site.name,
      locale: og.locale,
      // …
    },
    robots: {
      index: indexable && !noindex,
      follow: indexable,
    },
  }
```

How that helper works, and the incident that led to it, are covered in the
[Metadata API article](/en/blog/nextjs-metadata-api). Here, what matters about
the canonical is **conflict**: what happens when it disagrees with the other
signals.

### What happens when the signals contradict each other

Google reads the canonical alongside the sitemap, internal links, redirects
and content similarity. When the canonical points to A, the [sitemap lists
B](/en/blog/nextjs-dynamic-sitemap) and internal links go to C, Google breaks
the tie itself, and the result shows up in Search Console as "Duplicate,
Google chose different canonical than user". That status is almost never a
Google bug; it's the site telling three different stories. In this project,
the canonical and the sitemap come out of the same content pipeline precisely
so that telling different stories is impossible by design.

## When it's noindex, not a redirect

The third tool covers pages that **should exist for users but not in the
index**: internal search, confirmation pages, utility sections. Redirecting
would break the page; a canonical would be a lie (it isn't a variant of
anything). In the App Router, `noindex` comes from the same metadata helper on
this site, as an explicit option (the comment says it's for utility routes like
`/busca` that shouldn't be indexed):

```ts
// src/lib/metadata.ts
export interface BuildMetadataInput {
  // …
  /** Para rotas utilitárias (ex.: /busca) que não devem ser indexadas. */
  noindex?: boolean
}

// e, na montagem do objeto Metadata:
robots: {
  index: indexable && !noindex,
  follow: indexable,
},
```

Note that `noindex` only affects `index`. In production, `follow` stays
`true`: the page shouldn't be indexed, but its links still count for
discovery. `noindex` doesn't have to come with `nofollow`; they're separate
decisions. `indexable` is the site's fail-safe: outside production, both are
denied on every page.

And that very page, internal search, is the subject of the real case below.

## Tools that cancel each other out: a real case on this site

In the 2026-07-20 baseline, this site's audit found the `/busca` page with
`noindex` in its meta tag **and** a `Disallow` in robots.txt at the same time.
It looks like belt and suspenders; in fact, each one cancels the other.

Here's how it works: robots.txt is checked **before** crawling. A blocked URL
isn't crawled; a URL that isn't crawled never has its `noindex` meta tag read;
and a URL that's blocked but known (through links, through history) can still
**appear as a URL-only result**, with no snippet. The tool that would have
removed the page from the index was locked behind the door the other tool had
shut.

In short: with `noindex` alone, Googlebot crawls the page, reads the meta tag
and removes it from the index. With `noindex` plus `Disallow`, Googlebot is
stopped before it reads anything, and the URL can still be shown.

The fix, made the same day: **remove the `Disallow`** and let `noindex` do its
job. It's what takes the page out of the index, and to do that it has to be
read. The production `robots.ts` ended up like this, with the reasoning
recorded in the code itself (this is the July 2026 version; the file later
gained groups per AI agent, and the `*` group keeps the same comment, which
says `/busca` does NOT go here because the page is already noindex, and a
Disallow would keep Googlebot from crawling it, and therefore from reading its
noindex):

```ts
// src/app/robots.ts (julho de 2026)
export default function robots(): MetadataRoute.Robots {
  if (!indexable) {
    return { rules: [{ userAgent: '*', disallow: '/' }] }
  }

  return {
    rules: [
      {
        userAgent: '*',
        allow: '/',
        // /busca NÃO entra aqui: a página já é noindex, e um Disallow impediria
        // o Googlebot de rastreá-la — logo, de ler o próprio noindex. As duas
        // diretivas se cancelam. Ver /blog/sitemap-dinamico-nextjs.
        disallow: ['/api/'],
      },
    ],
    sitemap: `${site.url}/sitemap.xml`,
  }
}
```

And the final measurement, recorded in `docs/experiment-log.md`: the
production recrawl confirmed **11 URLs, 0 errors, 0 warnings**. Hypothesis,
fix, verification: the full cycle, with dates.

## Trailing slashes: pick one form and stick to it

`/blog/my-post` and `/blog/my-post/` are different URLs, so serving both as
pages creates a duplicate for every route. The rule has three parts: pick one
form; make sure the other **redirects** (not canonicalizes: a redirect, so it
doesn't even exist as a page); and keep the sitemap, internal links and
canonicals all agreeing on the chosen form. In Next.js, the config's
`trailingSlash` option controls this; this site sticks with the default (no
trailing slash), and the consistency of those three signals is what the CI
test checks.

## How to check: redirect chains, the real status and the selected canonical

1. **The real status, without a browser:** run `curl -sI https://example.com/old-url`
   and check for `HTTP/2 308` (or 301) and the `location` header. Browsers hide
   chains; `curl` shows one hop at a time.
2. **The full chain:** `curl -sIL` follows the redirects; if more than one hop
   appears before the final 200, you have a chain to flatten, and the rule
   should point straight to the final destination.
3. **The canonical according to Google:** Search Console → URL Inspection →
   compare the "User-declared canonical" with the "Google-selected canonical".
   A mismatch there is a symptom of conflicting signals; check the canonical,
   sitemap and internal links until all three agree. Before that, to see what
   the page actually **declares**, the [meta tag
   validator](/en/tools/meta-tag-validator) distinguishes the three ways of
   getting a canonical wrong: missing, relative, or pointing to another URL.
4. **The noindex case:** for a page that should drop out of the index, confirm
   both halves: the `noindex` meta tag is in the HTML **and** the URL is
   crawlable (not blocked in robots.txt). One without the other doesn't work;
   this site has the scar to prove it.
5. **The destination page's JSON-LD:** after consolidating URLs, the schema's
   `@id`/`url` needs to point to the final canonical URL; the [JSON-LD
   generator](/en/tools/json-ld-generator) produces the format used on this
   site. And as always in the [technical SEO guide for
   Next.js](/en/guide/technical-seo-nextjs): any rule that matters becomes a CI
   test, because an indexing fix without verification is a promise, not
   engineering.
