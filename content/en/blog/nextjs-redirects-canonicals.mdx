`redirects()` in `next.config.ts` and middleware can both redirect a URL, but
they get there differently. `redirects()` in the config is static, runs
before routing, and costs nothing per request. Middleware runs on **every**
request, and it's the only one of the two that can decide based on a cookie,
a header, or the visitor's location. **If you know the rule at build time, it
has no business in middleware.**

A more important question comes before that choice, and almost nobody asks
it. Does this problem call for a redirect, a canonical, or a `noindex`?
Almost every "duplicate page" status in Search Console comes from picking the
wrong tool.

## Three tools, three problems

I organized the rest of this article around this table.

| The situation | The tool | What it tells Google |
|---|---|---|
| The old URL should stop existing | Permanent redirect (301/308) | "This address moved — transfer everything there" |
| Both URLs exist, but one should consolidate the signals | Canonical | "Index that one — this one is a variant" |
| The page exists for users, not for the index | `noindex` | "Crawl it if you want, but don't index it" |
| Both URLs exist and hold distinct content | Nothing | No problem to solve |

Picking the wrong tool doesn't produce an error. It produces a symptom months
later, in the indexing report. The sections below cover each tool in turn and
end with a case, measured on this site, where two of them cancel each other
out when you combine them.

## `redirects()` in next.config: the default path

Any rule you know at build time goes in the config's `redirects()` array.
That covers a slug migration, a legacy URL, or a renamed path. Here's the
format in an illustrative example, followed by this site's only production
redirect.

```ts
// next.config.ts — illustrative example, not this site's code
async redirects() {
  return [
    { source: "/blog/old-slug", destination: "/blog/new-slug", permanent: true },
  ];
}
```

For the record, this site's production `redirects()` array has **exactly one
rule**. It dates from September 2026, when `/en` became the English home
page. `/en/guide` is a path segment with no page behind it, so anyone who
trimmed the English guide's URL landed on a 404. Its comment says so, notes
that `permanent` means 308, and records that this was the English layer's
last dead end.

```ts
// next.config.ts
  async redirects() {
    return [
      // /en/guide é só um segmento de caminho, sem página: quem encurta a URL
      // do guia inglês caía num 404. Com /en virando home, este era o último
      // beco sem saída da camada inglesa. `permanent` ⇒ 308.
      { source: '/en/guide', destination: '/en/guide/technical-seo-nextjs', permanent: true },
    ]
  },
```

There are no others. The site launched in July 2026 with its current URL
structure already in place, and **a redirect is debt from the past, not good
practice in itself**. With no legacy URLs, you have nothing to redirect, and
every redirect you don't need to create is a chain that will never exist.

### `permanent: true` is 308, not 301, and why it doesn't matter

`permanent: true` emits HTTP **308**, not 301. A 308 forces the client to keep
the request method, so a POST stays a POST, while a 301 lets it fall back to
GET. For SEO, it makes no difference. Google treats both as permanent and
consolidates signals at the destination. If an audit tool complains that "it
isn't a 301," the tool is out of date, not your site.

### `source`, `destination`, and path matching

`source` accepts parameters (`/blog/:slug`) and `destination` reuses them, so
a single rule can migrate a whole structure. Watch the order and any overlap.
An overly generic rule catches paths it shouldn't, and the first rule that
matches wins. Test every new rule against a real path before you deploy it.
The verification section at the end shows how.

## Middleware: when the rule only exists at runtime

Middleware intercepts every request before routing, and it can answer with a
redirect. It's the right tool for **exactly one kind of case**: a decision
that depends on information that exists only in the request, such as a
session cookie, a header, or a country of origin.

Next.js 16 renamed middleware to **Proxy**. The file is now `proxy.ts`, it
exports a function named `proxy`, and it works the same way.

Here's a hypothetical example. This site's proxy doesn't redirect anything,
and the next section explains what it does instead.

```ts
// proxy.ts — hypothetical example; middleware.ts up to Next.js 15
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  if (request.cookies.has("beta-optin")) {
    return NextResponse.redirect(new URL("/beta", request.url));
  }
}
```

### The cost: it runs on every request

Middleware runs on every request the site gets, including pages, assets that
pass the matcher, and crawlers. That adds latency in front of everything,
Googlebot
included. When the logic is truly dynamic, the cost is justified. For a
static rule, it's pure waste.

This site pays that cost on purpose, though not for redirects. `src/proxy.ts`
logs every page request to measure whether and how AI crawlers read the
content, since crawlers don't run GTM's JavaScript. That puts code in front of
every page the matcher lets through, and I accept it because there's no other
place where that measurement fits.

### Redirects in middleware aren't for URLs you already know

Treat this as a code review rule. If you know `source` and `destination`
before you deploy, the rule belongs in the config. A fixed mapping inside
middleware gets the same result and pays for an execution on every request.
It also splits redirect logic across two places, which is how accidental
chains start.

## `redirect()` and `permanentRedirect()` inside the component

There's a third option. You can call `redirect()` or `permanentRedirect()`
from `next/navigation` in the component itself or in a Server Action.

Use it when the decision depends on **the route's data**. Maybe the slug you
looked up exists, but its content moved to a new address. Maybe a
discontinued product's page points to its successor. Either way, the decision
starts where the data lives, in the component that just loaded it, and no
static config could make it.

## Canonical: a strong hint, not a directive

A canonical doesn't work like the tools so far. A redirect is a
**directive** that Google can't ignore, because the old URL's content
literally isn't served anymore. A canonical is a **hint**, which Google weighs
along with the other signals.

### Self-referencing on every page

Canonicals are the most mature part of this site's implementation. A single
metadata helper gives every indexable route a canonical that points to
itself, with a matching `og:url`. Its code comments add two points. The
helper also emits hreflang when the route has a translation. And feed
autodiscovery, which every page carries, has to live in the helper rather
than in the root layout, because a page's `alternates` replaces the inherited
one.

```ts
// src/lib/metadata.ts
  return {
    title: absoluteTitle ? { absolute: title } : title,
    description,
    alternates: {
      canonical: path,
      // … hreflang, quando a rota tem tradução
      // Autodiscovery do feed em toda página. Precisa estar aqui (e não no
      // root layout) porque `alternates` da página substitui o herdado.
      types: {
        'application/rss+xml': [{ url: '/feed.xml', title: site.name }],
      },
    },
    openGraph: {
      url: absoluteUrl(path),
      siteName: site.name,
      locale: og.locale,
      // …
    },
    robots: {
      index: indexable && !noindex,
      follow: indexable,
    },
  }
```

The [article on the Metadata API](/en/blog/nextjs-metadata-api) covers how
the helper works and the incident that led to it. Here, the focus is
**conflict**, meaning what happens when the canonical disagrees with the
other signals.

### What happens when the signals contradict each other

Google reads the canonical alongside the sitemap, internal links, redirects,
and content similarity. Say the canonical points to A, the
[sitemap lists B](/en/blog/nextjs-dynamic-sitemap), and internal links go to
C. Google breaks the tie on its own, and Search Console shows the result as
"Duplicate, Google chose different canonical than user".

That status is almost never a Google bug. It's the site telling three
different stories. In this project, the canonical and sitemap come from the
same content pipeline, so by design they can't tell different stories.

## When it's noindex, not a redirect

`noindex` is for pages that **should exist for users but not in the index**,
such as internal search, confirmation pages, and utility areas. A redirect
would break what the page does, and a canonical would be a lie, since the
page isn't a variant of anything.

In the App Router, this site emits `noindex` through an explicit option in
the same metadata helper. Its code comment reserves it for utility routes
that shouldn't be indexed, such as `/busca` (Portuguese for "search," the
site's internal search page).

```ts
// src/lib/metadata.ts
export interface BuildMetadataInput {
  // …
  /** Para rotas utilitárias (ex.: /busca) que não devem ser indexadas. */
  noindex?: boolean
}

// e, na montagem do objeto Metadata:
robots: {
  index: indexable && !noindex,
  follow: indexable,
},
```

`noindex` only touches `index`. In production, `follow` stays `true`, so the
page stays out of the index while its links still count for discovery. You
don't have to pair `noindex` with `nofollow`, because they're separate
decisions. `indexable` is the site's fail-safe. Outside production, both
directives are denied on every page.

That same page, internal search, is what the real case below is about.

## Tools that cancel each other out: a real case on this site

In the baseline run on July 20, 2026, this site's audit found `/busca` with a
`noindex` meta **and** a `Disallow` in robots.txt at the same time. That looks
like belt and suspenders, but one cancels the other.

Crawlers check robots.txt **before** they crawl. A crawler doesn't fetch a
blocked URL, so it never reads that page's `noindex` meta. If Google already
knows the URL, from links or from its history, the URL remains **eligible to
appear as a URL-only result**, with no snippet. The one tool that would have
removed the page from the index was locked behind the door the other one
shut.

With only `noindex`, Googlebot crawls the page, reads the meta, and removes it
from the index. With `noindex` plus `Disallow`, Googlebot stops before reading
anything, and the URL stays eligible to be shown.

This was fixed the same day by **removing the `Disallow`** and letting
`noindex` do its job. `noindex` is what removes a page from the index, and
it only works if crawlers can read it.

Here's `robots.ts` as it ran in production after the fix. Its comment
explains why `/busca` stays out of the Disallow. The page is already noindex,
and a Disallow would keep Googlebot from crawling it, and so from reading
that noindex. The two directives cancel each other. This is the July 2026
version. The file later gained a group for each AI agent, and
the `*` group keeps the same comment.

```ts
// src/app/robots.ts (julho de 2026)
export default function robots(): MetadataRoute.Robots {
  if (!indexable) {
    return { rules: [{ userAgent: '*', disallow: '/' }] }
  }

  return {
    rules: [
      {
        userAgent: '*',
        allow: '/',
        // /busca NÃO entra aqui: a página já é noindex, e um Disallow impediria
        // o Googlebot de rastreá-la — logo, de ler o próprio noindex. As duas
        // diretivas se cancelam. Ver /blog/sitemap-dinamico-nextjs.
        disallow: ['/api/'],
      },
    ],
    sitemap: `${site.url}/sitemap.xml`,
  }
}
```

A production recrawl, recorded in `docs/experiment-log.md`, confirmed **11
URLs, 0 errors, 0 warnings**. That's the full cycle, with dates: hypothesis,
fix, and verification.

## Trailing slashes: pick one form and stick to it

`/blog/my-post` and `/blog/my-post/` are different URLs. If you serve both as
pages, you get one duplicate per route. The rule has three parts:

- Pick one form.
- Make sure the other one **redirects**. Don't canonicalize it. Redirect it,
  so it doesn't even exist as a page.
- Make your sitemap, internal links, and canonicals all use the form you
  chose.

In Next.js, the `trailingSlash` option in the config controls this. This site
keeps the default (no trailing slash), and a CI test checks that the three
signals stay consistent.

## How to check: redirect chains, the real status, and the selected canonical

1. **The real status, without a browser:** run
   `curl -sI https://example.com/old-url` and look for `HTTP/2 308` (or 301)
   and the `location` header. Browsers hide chains, but `curl` shows one hop
   at a time.
2. **The full chain:** `curl -sIL` follows redirects. If you see more than one
   hop before the final 200, you have a chain to flatten. Point the rule
   straight at the final destination.
3. **The canonical according to Google:** in Search Console, open URL
   Inspection and compare "User-declared canonical" with "Google-selected
   canonical". A mismatch is a symptom of contradictory signals, so check the
   canonical, sitemap, and internal links until all three agree. Before that,
   run the page through the [meta tag validator](/en/tools/meta-tag-validator)
   to see what it **declares**. It tells apart the three ways a canonical goes
   wrong: missing, relative, or pointing to another URL.
4. **The noindex case:** for a page that should leave the index, confirm both
   halves. The `noindex` meta is in the HTML, **and** the URL is crawlable,
   not blocked in robots.txt. One without the other doesn't work, and this
   site has the scar to prove it.
5. **The destination page's JSON-LD:** after you consolidate URLs, the
   schema's `@id`/`url` must point to the final canonical URL. The
   [JSON-LD generator](/en/tools/json-ld-generator) emits the format this site
   uses. And as everywhere in the
   [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs), the rule
   that matters becomes a CI test, because an indexing fix without
   verification is a promise, not engineering.
