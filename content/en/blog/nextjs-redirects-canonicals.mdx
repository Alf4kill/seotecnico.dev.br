`next.config.ts` and middleware do the same thing by different paths: the
config's `redirects()` is static, evaluated before routing and with no
per-request cost; middleware runs on **every** request and is the only one that
can decide based on a cookie, a header or geography. The practical rule: **if
the rule is known at build time, it has no business in middleware.** But the
question that comes before that one is more important, and it is the one almost
nobody asks: does this problem really call for a redirect, or does it call for a
canonical, or a `noindex`? Almost every "duplicate page" status in Search Console
is born from choosing the wrong instrument.

## Three instruments, three problems

The decision table that organizes the whole article:

| The situation | The instrument | What it tells Google |
| --- | --- | --- |
| The old URL should stop existing | permanent redirect (301/308) | "this changed address: transfer everything there" |
| Both URLs exist, but one consolidates the signals | canonical | "index that one; this is a variant" |
| The page exists for the user, not for the index | `noindex` | "crawl it if you like, but don't index it" |
| Both URLs exist and are distinct content | nothing | there is no problem to solve |

Getting that choice wrong produces no error; it produces a symptom months later,
in the indexing report. The rest of the article goes through each instrument and
ends with the case in which two of them, combined, cancel each other out,
measured on this site.

## redirects() in next.config: the default path

When the rule is known at build time (the slug migration, the legacy URL, the
renamed path), its place is the config's `redirects()` array. The format
(illustrative; this site's only production redirect comes right after):

```ts
// next.config.ts — illustrative example, not this site's code
async redirects() {
  return [
    { source: "/blog/old-slug", destination: "/blog/new-slug", permanent: true },
  ];
}
```

And the transparency this site owes the reader: the production `redirects()`
array here has **a single rule**, created in September 2026, when `/en` became
the English home. `/en/guide` is a path segment with no page, and anyone who
shortened the English guide's URL landed on a 404 (the comment says exactly
that, and that `permanent` means 308):

```ts
// next.config.ts
  async redirects() {
    return [
      // /en/guide é só um segmento de caminho, sem página: quem encurta a URL
      // do guia inglês caía num 404. Com /en virando home, este era o último
      // beco sem saída da camada inglesa. `permanent` ⇒ 308.
      { source: '/en/guide', destination: '/en/guide/technical-seo-nextjs', permanent: true },
    ]
  },
```

Apart from that one, none. The site was born in July 2026 already with its
current URL structure, and **a redirect is history debt, not good practice in
itself**. If you have no legacy URL, you have nothing to redirect, and every
redirect you don't need to create is a chain that will never exist.

### permanent: true is 308, not 301, and why it doesn't matter

`permanent: true` emits HTTP **308**, not 301. The technical difference: a 308
requires the client to preserve the request's method (a POST stays a POST),
while a 301 allows downgrading to GET. For SEO, it makes no difference: Google
treats both as a permanent redirect and consolidates the signals at the
destination. If some audit tool complains that "it isn't a 301", the tool is out
of date, not your site.

### source, destination and path matching

`source` accepts parameters (`/blog/:slug`) and `destination` reuses them, which
lets you migrate a whole structure in one rule. The point of attention is order
and overlap: overly generic rules capture paths they shouldn't, and the first
rule that matches wins. Every new rule deserves a test against a real path
before the deploy; the verification section shows how.

## Middleware: when the rule only exists at runtime

Middleware intercepts every request before routing and can respond with a
redirect. It is the right tool for exactly one kind of case: **the decision that
depends on information that only exists in the request**: a session cookie, a
header, a country of origin. In Next.js 16, middleware was renamed **Proxy**:
the file is `proxy.ts` and exports a function called `proxy`, with the same
mechanism. A hypothetical example (this site's proxy doesn't redirect anything;
the next section says what it does):

```ts
// proxy.ts — hypothetical example; middleware.ts up to Next.js 15
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  if (request.cookies.has("beta-optin")) {
    return NextResponse.redirect(new URL("/beta", request.url));
  }
}
```

### The cost: it runs on every request

Every request on the site (a page, an asset that passes the matcher, a crawler)
runs the middleware. It is latency added in front of everything, including in
front of Googlebot. That cost is justified when the logic is truly dynamic; for
a static rule, it is pure waste.

This site pays that cost on purpose, and not for redirects: `src/proxy.ts`
records each page request to measure whether and how AI crawlers read the
content, because crawlers don't run GTM's JavaScript. It is code in front of
every page the matcher lets through, accepted because there is no other place
where that measurement fits.

### Redirect in middleware is not for URLs you already know

It is worth repeating as a code review rule: if the `source` and the
`destination` are known before the deploy, the rule belongs in the config. A
fixed mapping inside middleware delivers the same result while paying for
execution per request, and spreads the redirect logic across two places, which
is how accidental chains are born.

## redirect() and permanentRedirect() inside the component

The third way: the `redirect()` and `permanentRedirect()` functions from
`next/navigation`, called inside the component itself or a Server Action. The
legitimate use case is the decision that depends on **the route's data**: the
requested slug exists, but the content changed address; the product was
discontinued and the page points to its successor. The decision is born where
the data is (in the component that just loaded it) and could not live in a
static config.

## Canonical: a strong hint, not an order

The canonical inverts the hierarchy of the previous instruments: a redirect is
an **order** Google cannot ignore (the old URL's content is literally no longer
served); a canonical is a **hint** Google weighs together with the other
signals.

### Self-referencing on every page

This site's implementation is the mature side of this article: every indexable
route emits a canonical pointing to itself, with a matching `og:url`, through a
single metadata helper (the Portuguese comments say: "… hreflang, when the route
has a translation", and that feed autodiscovery has to live here, not in the
root layout, because the page's `alternates` replaces the inherited one):

```ts
// src/lib/metadata.ts
  return {
    title: absoluteTitle ? { absolute: title } : title,
    description,
    alternates: {
      canonical: path,
      // … hreflang, quando a rota tem tradução
      // Autodiscovery do feed em toda página. Precisa estar aqui (e não no
      // root layout) porque `alternates` da página substitui o herdado.
      types: {
        'application/rss+xml': [{ url: '/feed.xml', title: site.name }],
      },
    },
    openGraph: {
      url: absoluteUrl(path),
      siteName: site.name,
      locale: og.locale,
      // …
    },
    robots: {
      index: indexable && !noindex,
      follow: indexable,
    },
  }
```

The full mechanics of that helper, and the incident that motivated it, are in
the [Metadata API article](/en/blog/nextjs-metadata-api). Here the canonical
matters from the angle of **conflict**: what happens when it disagrees with the
other signals.

### What happens when the signals contradict each other

Google reads the canonical alongside the sitemap, internal links, redirects and
content similarity. When the canonical points to A, the [sitemap lists
B](/en/blog/nextjs-dynamic-sitemap) and the internal links go to C, Google breaks
the tie on its own, and the result shows up in Search Console as "Duplicate,
Google chose different canonical than user". That status is almost never a
Google bug: it is the site telling three stories. In this project, canonical and
sitemap come out of the same content pipeline precisely so that telling
different stories is impossible by construction.

## When it's noindex, not a redirect

The third instrument covers the page that **should exist for the user and should
not exist in the index**: internal search, confirmation pages, utility areas.
Redirecting would break the page's function; a canonical would be a lie (it is
nobody's variant). In the App Router, `noindex` comes out of this site's same
metadata helper, as an explicit option (the comment says it is for utility
routes such as `/busca` that should not be indexed):

```ts
// src/lib/metadata.ts
export interface BuildMetadataInput {
  // …
  /** Para rotas utilitárias (ex.: /busca) que não devem ser indexadas. */
  noindex?: boolean
}

// e, na montagem do objeto Metadata:
robots: {
  index: indexable && !noindex,
  follow: indexable,
},
```

Note that `noindex` only touches `index`. In production, `follow` stays `true`:
the page should not be indexed, but its links still count for discovery.
`noindex` doesn't need to come with `nofollow`; they are separate decisions.
`indexable` is the site's fail-safe: outside production, both directives are
denied on every page.

And it is exactly that page, the internal search, that stars in the real case.

## Instruments that cancel each other: a real case on this site

In the 2026-07-20 baseline, this site's audit found the `/busca` page with
`noindex` in the meta **and** `Disallow` in robots.txt at the same time. It looks
like belt and braces; it is one cancelling the other.

The mechanics: robots.txt is consulted **before** crawling. A blocked URL is not
crawled; a URL that isn't crawled never has its `noindex` meta read; and a
blocked-but-known URL (through links, through history) remains **eligible to
appear as a URL-only result**, with no snippet. The instrument that would remove
the page from the index was locked inside the door the other instrument had
closed.

In words: with `noindex` alone, Googlebot crawls the page, reads the meta and
removes it from the index. With `noindex` plus `Disallow`, Googlebot is stopped
before reading anything, and the URL remains eligible to be shown.

The fix, made the same day: **remove the `Disallow`** and let `noindex` do its
job; it is what removes the page from the index, and to do that it has to be
read. The production `robots.ts` ended up like this, with the reason recorded in
the code itself (this is the July 2026 version; later the file gained groups per
AI agent, and the `*` group keeps the same comment, which says that `/busca`
does NOT go here because the page is already noindex, and a Disallow would keep
Googlebot from crawling it, and therefore from reading its own noindex):

```ts
// src/app/robots.ts (julho de 2026)
export default function robots(): MetadataRoute.Robots {
  if (!indexable) {
    return { rules: [{ userAgent: '*', disallow: '/' }] }
  }

  return {
    rules: [
      {
        userAgent: '*',
        allow: '/',
        // /busca NÃO entra aqui: a página já é noindex, e um Disallow impediria
        // o Googlebot de rastreá-la — logo, de ler o próprio noindex. As duas
        // diretivas se cancelam. Ver /blog/sitemap-dinamico-nextjs.
        disallow: ['/api/'],
      },
    ],
    sitemap: `${site.url}/sitemap.xml`,
  }
}
```

And the closing measurement, recorded in `docs/experiment-log.md`: the
production recrawl confirmed **11 URLs, 0 errors, 0 warnings**. Hypothesis, fix,
verification: the full cycle, with dates.

## Trailing slash: choose one form and be consistent

`/blog/my-post` and `/blog/my-post/` are different URLs; serving both as pages
creates a duplicate per route. The rule has three parts: choose one form; make
sure the other **redirects** (not canonicalizes: a redirect, so it doesn't even
exist as a page); and keep the sitemap, internal links and canonicals unanimous
on the chosen form. In Next.js, the config's `trailingSlash` option controls the
behaviour; this site stays on the default (no trailing slash), and the
consistency of the three signals is what the CI test checks.

## How to check: redirect chain, real status and the selected canonical

1. **The real status, without a browser:** `curl -sI https://example.com/old-url`
   and read `HTTP/2 308` (or 301) and the `location` header. Browsers hide
   chains; `curl` shows one hop at a time.
2. **The whole chain:** `curl -sIL` follows the redirects; if more than one hop
   appears before the final 200, you have a chain to flatten: the rule should
   point straight to the final destination.
3. **The canonical according to Google:** Search Console → URL Inspection → the
   "User-declared canonical" field against the "Google-selected canonical". A
   divergence there is the symptom of contradictory signals; check canonical,
   sitemap and internal links until the three agree. Before that, to know what
   the page **declares**, the [meta tag validator](/en/tools/meta-tag-validator)
   separates the three ways of getting the canonical wrong: missing, relative, or
   pointing to another URL.
4. **The noindex case:** for a page that should leave the index, confirm both
   halves: the `noindex` meta present in the HTML **and** the URL crawlable (out
   of robots.txt). One without the other doesn't work; this site has the scar to
   prove it.
5. **The destination page's JSON-LD:** after consolidating URLs, the schema's
   `@id`/`url` needs to point to the final canonical URL; the [JSON-LD
   generator](/en/tools/json-ld-generator) emits the format used on this site.
   And as always in the [technical SEO guide for
   Next.js](/en/guide/technical-seo-nextjs): the rule that matters becomes a CI
   test, because an indexing instrument without verification is a promise, not
   engineering.
