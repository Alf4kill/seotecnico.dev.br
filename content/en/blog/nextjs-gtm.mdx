In a Next.js app, GTM's **All Pages** trigger only fires on the first load;
every navigation after that uses `history.pushState` and doesn't reload the
page. The fix is the **History Change** trigger, and the mistake almost
everyone makes is turning it on in GTM **and** leaving GA4's Enhanced
Measurement listening for the same events, which counts every pageview twice.
This article documents this site's full implementation (one pageview per
navigation, Consent Mode v2 with a denied default, and validation against real
requests), because the hard part was never getting the event to fire. It's
getting it to fire **exactly once**, and only after consent.

## Why All Pages stops firing after the first page

Under the hood, GTM's All Pages trigger is the classic page view event: it
fires when the container loads along with the page. On a traditional site,
every navigation is a new page load, so the container reloads and the trigger
fires. In a Next.js app, the container loads **once**; from then on, the
router swaps content through the History API without reloading. The result:
GA4 records the landing page and goes blind for the rest of the session, the
bounce rate drops artificially and inner pages vanish from your reports.

## Installing GTM in the App Router

### @next/third-parties, and why not a hand-written script

The sanctioned approach is the `GoogleTagManager` component from the
`@next/third-parties` package, which injects the container with the right
loading strategy for the App Router: no `<script>` pasted by hand into the
layout, no snippet copied from the dashboard. Below is the document shell this
site's root layouts share (there's one layout per language, and both render
the same component, `RootShell`), in the order the pieces load. The
Portuguese comment says: Consent Mode v2, default "denied" BEFORE any Google
tag loads; the banner (`ConsentBanner`) updates `analytics_storage` after the
user's choice; `ad_*` stay denied (the site doesn't run ads):

```tsx
// src/components/layout/RootShell.tsx
// Consent Mode v2 — default "denied" ANTES de qualquer tag do Google carregar.
// O banner (ConsentBanner) atualiza analytics_storage após a escolha do
// usuário; ad_* permanecem negados (o site não veicula anúncios).
const consentDefaultScript = `
window.dataLayer = window.dataLayer || [];
function gtag(){dataLayer.push(arguments);}
gtag('consent', 'default', {
  ad_storage: 'denied',
  ad_user_data: 'denied',
  ad_personalization: 'denied',
  analytics_storage: 'denied',
  wait_for_update: 500
});
`
```

```tsx
// src/components/layout/RootShell.tsx (corpo do documento)
      <body className="flex min-h-screen flex-col font-sans antialiased">
        {/* eslint-disable-next-line @next/next/no-before-interactive-script-outside-document */}
        <Script
          id="consent-default"
          strategy="beforeInteractive"
          dangerouslySetInnerHTML={{ __html: consentDefaultScript }}
        />
        {withSearch ? (
          <SearchProvider>
            {chrome}
            <SearchModal items={buildSearchIndex()} />
          </SearchProvider>
        ) : (
          chrome
        )}
        <ConsentBanner lang={lang} />
        <WebVitalsReporter />
        {site.gtmId && <GoogleTagManager gtmId={site.gtmId} />}
      </body>
```

### Order matters: consent before the container

Notice how the snippet above is structured: the script that sets the
**consent default** runs `beforeInteractive`, and the container comes later,
at the end of the body. That order isn't cosmetic: the consent default has to
exist **before** any tag wakes up. The Consent Mode section below explains
what happens when the order is reversed.

## History Change: the trigger that fixes SPA pageviews

In the container (with the UI in English, as this project has it set up):
one trigger of type **History Change**, and the GA4 `page_view` event tag it
fires, with the path and title taken from the built-in variables
(`{{Page Path}}`, `{{Page Title}}`). The trigger listens for changes to the
History API, which is exactly what the Next.js router does on every
navigation, and it covers what All Pages misses.

The detail that prevents a classic bug: the initial page load has to be
covered either by the GA4 configuration tag's automatic page view **or** by
History Change, never both added together without thinking. On this site,
the container's full recipe (tags, triggers, variables and the decision on
how the initial load is covered) is documented in `docs/measurement-plan.md`,
and the container implements the plan, not the other way around.

## The duplication nobody notices

This is the heart of the article, because it's the part no "History Change in
5 minutes" tutorial mentions: GA4 has its own SPA pageview mechanism. In
Enhanced Measurement, the page views option based on browser history events
does the same job as the History Change trigger, and with both turned on, they
count **every navigation twice**.

### GTM or Enhanced Measurement: pick one

Both work; the mistake is not picking. This site chose **GTM** as its single
pageview source, for an engineering reason: in GTM, the logic is versioned and
visible in the container, so you can audit when and why each event fires.
Enhanced Measurement is a panel of checkboxes in the GA4 dashboard, and it's
easy for someone to switch an option back on without realizing the
consequences. The opposite choice (Enhanced Measurement on, no history
trigger in GTM) is just as valid. What isn't valid is running both.

### The same logic applies to scrolls and outbound clicks

Duplication isn't limited to pageviews. Enhanced Measurement's "Scrolls" and
"Outbound clicks" are also **off** on this site, for the same reason: their
equivalents (`scroll_depth`, outbound clicks) are tracked through GTM, where
the thresholds and conditions are documented in the measurement plan. One
source per metric, for every metric.

## Consent Mode v2 and the LGPD: denied by default

This site's position: **no analytics cookies before explicit consent**.
Consent Mode v2 is the mechanism that makes Google's tags respect that
choice, and the implementation has three pitfalls, all verified here in
production.

A note on scope first: Brazil's data protection law (LGPD) doesn't require
"Consent Mode"; it requires a legal basis and a genuine choice by the data
subject. What I'm describing is how this site implemented that choice in
Google's tags. It isn't legal advice.

### The default has to come before the container loads

The correct sequence is strict: first the consent default command (everything
denied), then the container, then, only if and when the user accepts, the
consent update. If the default is set after the container loads, the tags
wake up with no instructions and act as if everything were allowed: data has
already leaked before the banner even appears.

Step by step, the order is:

1. `consent default` with everything denied, as a `beforeInteractive` script;
2. the GTM container loads;
3. the tags run in cookieless mode (pings with no identifier);
4. the user makes a choice in the banner → `consent update` with that choice.

### The `arguments` trap

This is the classic silent Consent Mode bug: consent commands have to reach
the `dataLayer` as the function's `arguments` object, **not** as an array. In
practice, that means `gtag` has to be a *function declaration*: an arrow
function has no `arguments` of its own, so the push still happens but consent
never updates, and nothing throws an error. This site's actual code carries a
comment and an `eslint-disable` explaining the exception (the comment says
consent commands must be sent as the `arguments` object, not an array, hence
a function declaration instead of an arrow function):

```ts
// src/lib/analytics.ts
/**
 * Empurra um comando gtag('consent', ...) para o dataLayer.
 * IMPORTANTE: os comandos de consent precisam ser enviados como objeto
 * `arguments` (não array) — por isso a function declaration, não arrow.
 */
function gtag(...args: unknown[]): void {
  void args // parâmetros tipados para os call sites; o GTM lê `arguments`
  window.dataLayer = window.dataLayer ?? []
  // eslint-disable-next-line prefer-rest-params
  window.dataLayer.push(arguments)
}

/** Aplica a escolha do usuário (banner ou escolha salva de visita anterior). */
export function applyConsent(choice: ConsentChoice): void {
  if (typeof window === 'undefined') return
  gtag('consent', 'update', { analytics_storage: choice })
}
```

### What a cookieless ping is

In Consent Mode's advanced mode, denying consent doesn't silence the tags:
they send pings **with no cookies and no user identifier**, which Google uses
for aggregate modeling. This site's validation, on 2026-07-13, was done by
inspecting real `/g/collect` requests rather than trusting preview mode. With
the denied default, the consent state shows up in the initial `dataLayer` and
**no `_ga` cookie is created**; pings go out with `gcs=G100`. After clicking
"Aceitar" (accept), hits switch to `gcs=G101`. After "Recusar" (decline), they
stay at G100, cookieless. The `page_view` was confirmed to fire on load
**and** on SPA navigation, with the correct URL and title parameters on every
hit.

## A typed dataLayer: no stray pushes in components

This site has an architectural rule: **no** stray `window.dataLayer.push`
calls inside components. There's a union type listing the allowed events and
a single `pushEvent()` function; an event that isn't in the type won't
compile:

```ts
// src/lib/analytics.ts
// ─────────────────────────────────────────────────────────────────────────────
// Typed dataLayer helper — the ONLY way custom events are pushed on this site.
// Never call window.dataLayer.push directly from components (CLAUDE.md §7.2).
//
// Every event here MUST be documented in /docs/measurement-plan.md BEFORE
// being implemented.
// ─────────────────────────────────────────────────────────────────────────────

/** Custom events documented in docs/measurement-plan.md */
export type AnalyticsEvent =
  | { event: 'tool_generate_jsonld'; schema_type: string }
  | { event: 'tool_validate_meta'; issues_found: number }
  | { event: 'tool_check_cwv'; lcp_bucket: 'good' | 'needs-improvement' | 'poor' | 'no-data' }
  | { event: 'article_read'; article_slug: string }
  | { event: 'outbound_click'; link_domain: string }
  // …the web_vitals events (LCP and INP) follow in the same union

export function pushEvent(e: AnalyticsEvent): void {
  if (typeof window === 'undefined') return
  window.dataLayer = window.dataLayer ?? []
  window.dataLayer.push(e)
}
```

TypeScript becomes the line of defense against "let me just quickly track
this one thing" analytics. If an event hasn't been documented and typed, it
doesn't exist. The site's own RUM follows the same path, and the `web_vitals`
events behind the [INP analysis](/en/blog/nextjs-inp) go through the same
helper, under the same contract. It's a philosophy that runs through the whole
project, from the [JSON-LD generator](/en/tools/json-ld-generator) to the
sitemap: one typed source, nothing assembled ad hoc.

## DOM triggers in an SPA: re-arming after navigation

This site's `article_read` event fires when the reader reaches the end of an
article, using an **Element Visibility** trigger aimed at a stable `id` (the
comment says it's a stable id, the target of the element visibility trigger
for the `article_read` event in GTM):

```tsx
// src/components/article/ArticleLayout.tsx
            {/* id estável: alvo do trigger de element visibility do evento
                `article_read` no GTM (docs/measurement-plan.md). */}
            <footer id="article-end" className="mt-8 max-w-[68ch] border-t border-gray pt-4">
              <p className="font-mono text-xs leading-6 text-label">{copyright}</p>
            </footer>
```

Here's the detail search results almost never mention: in SPA navigation the
DOM gets replaced without a page load, and the visibility trigger **doesn't
re-arm itself**. Without the **Observe DOM changes** option turned on in the
trigger, `article_read` works on the first article in the session and never
again. With it on, GTM watches for DOM mutations and re-arms the trigger when
the next article's `#article-end` shows up.

## Document before you implement

The rule that ties all of this together: **no event gets implemented before
it's documented** in `docs/measurement-plan.md`, which holds the event table
(name, parameters, trigger and purpose), the container setup recipe and the
validation checklist. The plan is the source of truth; the container and the
typed helper are the implementation. When the three disagree, the plan wins
and everything else is a bug. Without that, six months from now nobody will
know why there's a trigger called "scroll 75 old v2", and everyone will be
afraid to delete it.

It's the same discipline the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs) applies to the rest of the stack:
anything that matters becomes a versioned artifact (schema derived from the
frontmatter, a sitemap derived from the content, events derived from a plan
written before the code).

## How to validate: Tag Assistant, DebugView and the real hit

Three layers, in increasing order of confidence:

1. **Tag Assistant (GTM preview).** Confirm the sequence: on the initial
   load, the consent default appears **before** the container; on SPA
   navigations, History Change fires once per route, and no tag fires twice.
2. **GA4 DebugView.** Check that events arrive with the measurement plan's
   parameters, one navigation at a time.
3. **The real requests.** The layer that doesn't lie: DevTools → Network,
   filtered by `collect`. One `page_view` per navigation, a `gcs` parameter
   that matches the consent state, and, when consent is declined, no `_ga`
   cookie under Application → Cookies. That's how this site's implementation
   was validated, and it's the only method that tests what real users
   actually experience.

One practical caveat I ran into while validating this site: triggers based
on `IntersectionObserver` and `requestAnimationFrame` (like `article_read` and
`scroll_depth`) **can't be exercised in a headless or background tab**,
because browsers suspend that work in tabs that aren't visible. Validating
those events had to be done by hand, in Tag Assistant, with the tab in the
foreground. If your automated QA script says the scroll event "doesn't work",
it may just be running in a tab that was never visible.
