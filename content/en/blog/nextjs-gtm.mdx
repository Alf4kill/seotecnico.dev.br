In a Next.js app, GTM's **All Pages** trigger fires only on the first load.
Every navigation after that is a `history.pushState` call, and the page never
reloads. The fix is the **History Change** trigger. Then comes the decision
almost everyone gets wrong. If you turn that trigger on in GTM **and** leave
GA4's Enhanced Measurement listening for the same events, every pageview gets
counted twice.

This article walks through this site's full implementation, which counts one
pageview per navigation, keeps Consent Mode v2 denied by default, and was
validated against real requests. Making the event fire was never the problem. Making it fire **only
once**, and only after consent, is.

## Why All Pages stops firing after the first page

Under the hood, GTM's All Pages trigger is the classic page view event. It
fires when a page loads and brings the container with it. On a traditional
site, every navigation loads a new page, so the container loads again and All
Pages fires again.

A Next.js app loads the container **once**. After that, its router swaps
content through the History API, with no page load. GA4 records the landing
page and goes blind to everything after it. Your "bounce" rate drops
artificially, and inner pages disappear from your reports.

## Installing GTM in the App Router

### @next/third-parties, and why not a hand-written script

Load the container with the `GoogleTagManager` component from
`@next/third-parties`. It's the sanctioned path, and it injects GTM with a
loading strategy built for the App Router. You don't hand-paste a `<script>`
into your layout or copy a snippet from GTM's dashboard.

Below is the HTML document that both of this site's root layouts share. Each
language has its own layout, and both render one component, `RootShell`. I
show its pieces in the order they enter the page. Comments stay in
Portuguese, as they are in the repository. The first one says three things:
the Consent Mode v2 default is "denied" before any Google tag loads, the
banner (`ConsentBanner`) updates `analytics_storage` once the user chooses,
and `ad_*` types stay denied because this site runs no ads.

```tsx
// src/components/layout/RootShell.tsx
// Consent Mode v2 — default "denied" ANTES de qualquer tag do Google carregar.
// O banner (ConsentBanner) atualiza analytics_storage após a escolha do
// usuário; ad_* permanecem negados (o site não veicula anúncios).
const consentDefaultScript = `
window.dataLayer = window.dataLayer || [];
function gtag(){dataLayer.push(arguments);}
gtag('consent', 'default', {
  ad_storage: 'denied',
  ad_user_data: 'denied',
  ad_personalization: 'denied',
  analytics_storage: 'denied',
  wait_for_update: 500
});
`
```

```tsx
// src/components/layout/RootShell.tsx (corpo do documento)
      <body className="flex min-h-screen flex-col font-sans antialiased">

      </body>
```

### Order matters: consent before the container

Look at where each script sits in that snippet. The **consent default**
script runs `beforeInteractive`, and the container comes after it, at the end
of the body. That order isn't cosmetic. A consent default has to exist
**before** any tag wakes up. The Consent Mode section below shows what happens
if you reverse it.

## History Change: the trigger that fixes SPA pageviews

In the container (this project runs it with English UI labels), create a
**History Change** trigger and a GA4 event tag that sends `page_view`, fired
by that trigger. Take the path and title from the built-in variables
`{{Page Path}}` and `{{Page Title}}`.

This trigger listens for History API changes, which is exactly what the
Next.js router produces on every navigation, so it covers what All Pages
misses.

One detail avoids a classic bug. For the initial load, your GA4 configuration
tag needs either its automatic page view **or** a History Change trigger that
covers that load. Never both, stacked blindly.

On this site, `docs/measurement-plan.md` holds the full recipe for the
container: tags, triggers, variables, and how the initial load is covered.
The container implements the plan, not the other way around.

## The duplication nobody notices

This is what the article is really about, because no "History Change in 5
minutes" tutorial mentions it. GA4 has its own pageview mechanism for SPAs. In
Enhanced Measurement, the page views setting for browser history events does
the same job as the History Change trigger. Turn both on and you count **each
navigation twice**.

### GTM or Enhanced Measurement: pick one

Both work. Not choosing is the mistake. I picked **GTM** as this site's single
pageview source, for an engineering reason. In GTM, the logic is versioned and
visible in the container, so you can audit when and why each event fires.
Enhanced Measurement is a set of toggles in the GA4 panel, and it's easy for
someone to turn one back on without noticing the consequence.

Choosing the opposite, with Enhanced Measurement on and no history trigger in
GTM, is just as valid. Running both isn't.

### The same logic applies to scrolls and outbound clicks

Duplication isn't limited to pageviews. On this site, Enhanced Measurement's
"Scrolls" and "Outbound clicks" options are also **off**, for the same
reason. GTM measures the equivalents (`scroll_depth` and outbound clicks), and
the measurement plan documents their thresholds and conditions. One source per
metric, for every metric.

## Consent Mode v2 and the LGPD: denied by default

A note on scope first. The LGPD, Brazil's data protection law, doesn't require
"Consent Mode". It requires a legal basis and a real choice by the data
subject. Here I describe how this site implemented that choice in Google's
tags. It isn't legal advice.

This site follows one rule: **no analytics cookie before explicit consent**.
Consent Mode v2 is the mechanism that makes Google tags respect that choice.
Implementing it has three pitfalls, and I verified all three here in
production.

### The default has to come before the container loads

Only one sequence works:

1. the consent default command, with everything denied
2. the container
3. only if and when the user accepts, the consent update

If you set the default after the container loads, the tags wake up with no
instruction and act as if everything were allowed. Data leaks before the
banner even appears.

1. `consent default` with everything denied, as a `beforeInteractive` script

### The `arguments` trap

This is Consent Mode's classic silent bug. Consent commands have to reach the
`dataLayer` as the function's `arguments` object, **not** as an array. In
practice, that means `gtag` has to be a *function declaration*. An arrow
function has no `arguments` of its own, so the push still happens, but consent
never updates and nothing throws an error.

In this site's real code, a comment and an `eslint-disable` explain the
exception. The comment, in Portuguese, says consent commands must go out as
the `arguments` object rather than an array, which is why `gtag` is a
function declaration and not an arrow function.

```ts
// src/lib/analytics.ts
/**
 * Empurra um comando gtag('consent', ...) para o dataLayer.
 * IMPORTANTE: os comandos de consent precisam ser enviados como objeto
 * `arguments` (não array) — por isso a function declaration, não arrow.
 */
function gtag(...args: unknown[]): void {
  void args // parâmetros tipados para os call sites; o GTM lê `arguments`
  window.dataLayer = window.dataLayer ?? []
  // eslint-disable-next-line prefer-rest-params
  window.dataLayer.push(arguments)
}

/** Aplica a escolha do usuário (banner ou escolha salva de visita anterior). */
export function applyConsent(choice: ConsentChoice): void {
  if (typeof window === 'undefined') return
  gtag('consent', 'update', { analytics_storage: choice })
}
```

### What a cookieless ping is

In advanced Consent Mode, denying consent doesn't silence the tags. They send
pings **with no cookies and no user identifier**, and Google uses them for
aggregate modeling.

I validated this site on July 13, 2026, by inspecting the real `/g/collect`
requests instead of trusting preview mode. With the default denied, that state
shows up in the initial `dataLayer`, **no `_ga` cookie is created**, and pings
go out with `gcs=G100`. After "Aceitar" (accept), hits switch to `gcs=G101`.
After "Recusar" (decline), they stay at G100, cookieless. I also confirmed
that `page_view` fires on load **and** on SPA navigation, with the correct
URL and title parameters in every hit.

## A typed dataLayer: no stray pushes in components

This site has one rule for custom events: **no** stray `window.dataLayer.push`
in a component. Instead, a union type lists the allowed events, and a single
function, `pushEvent()`, sends them. An event that isn't in the type doesn't
compile.

```ts
// src/lib/analytics.ts
// ─────────────────────────────────────────────────────────────────────────────
// Typed dataLayer helper — the ONLY way custom events are pushed on this site.
// Never call window.dataLayer.push directly from components (CLAUDE.md §7.2).
//
// Every event here MUST be documented in /docs/measurement-plan.md BEFORE
// being implemented.
// ─────────────────────────────────────────────────────────────────────────────

/** Custom events documented in docs/measurement-plan.md */
export type AnalyticsEvent =
  | { event: 'tool_generate_jsonld'; schema_type: string }
  | { event: 'tool_validate_meta'; issues_found: number }
  | { event: 'tool_check_cwv'; lcp_bucket: 'good' | 'needs-improvement' | 'poor' | 'no-data' }
  | { event: 'article_read'; article_slug: string }
  | { event: 'outbound_click'; link_domain: string }
  // …the web_vitals events (LCP and INP) follow in the same union

export function pushEvent(e: AnalyticsEvent): void {
  if (typeof window === 'undefined') return
  window.dataLayer = window.dataLayer ?? []
  window.dataLayer.push(e)
}
```

TypeScript becomes the line of defense against "let me just measure this
little thing" analytics. If an event wasn't documented and typed, it doesn't
exist.

This site's own RUM works the same way. Its `web_vitals` events, which feed
my [INP analysis](/en/blog/nextjs-inp), go through that helper under the same
contract. One idea runs through the whole project, from the
[JSON-LD generator](/en/tools/json-ld-generator) to the sitemap. Everything
comes from one typed source, with zero ad hoc assembly.

## DOM triggers in an SPA: re-arming after navigation

This site's `article_read` event fires when you reach the end of an article.
It uses an **Element Visibility** trigger pointed at a stable `id`. In the
code, a Portuguese comment marks that `id` as the target of GTM's element
visibility trigger for `article_read`, documented in
`docs/measurement-plan.md`.

```tsx
// src/components/article/ArticleLayout.tsx
            {/* id estável: alvo do trigger de element visibility do evento
                `article_read` no GTM (docs/measurement-plan.md). */}
            <footer id="article-end" className="mt-8 max-w-[68ch] border-t border-gray pt-4">
              <p className="font-mono text-xs leading-6 text-label">{copyright}</p>
            </footer>
```

Here's the detail search results almost never mention. In SPA navigation,
Next's router replaces the DOM without a page load, and a visibility trigger
**doesn't re-arm by itself**. Unless you turn on **Observe DOM changes** in
the trigger, `article_read` works on a session's first article and never
again. With it on, GTM watches DOM mutations and re-arms the trigger when the
next article's `#article-end` appears.

## Document before you implement

**No event is implemented before it is documented** in
`docs/measurement-plan.md`. That file holds the event table (name,
parameters, trigger, purpose), the recipe for setting up the container, and a
validation checklist. I treat the plan as the source, and the container and
typed helper as its implementation. When the three diverge, the plan wins and
everything else is a bug.

Skip this, and six months later nobody knows why there's a trigger called
"scroll 75 old v2", and everyone is afraid to delete it.

It's the same discipline the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) applies to
everything else in the stack. Whatever matters becomes a versioned artifact: schema
derived from frontmatter, a sitemap derived from content, an event derived
from a plan written before the code.

## How to validate: Tag Assistant, DebugView, and the real hit

Validate in three layers, in increasing order of confidence:

1. **Tag Assistant (GTM preview).** Confirm the sequence. On the initial
   load, the consent default appears **before** the container. On SPA
   navigations, History Change fires once per route, and no tag fires twice.
2. **GA4 DebugView.** Check that events arrive with the parameters from the
   measurement plan, navigation by navigation.
3. **The real requests.** This is the layer that doesn't lie. In DevTools →
   Network, filter by `collect`. You should see one `page_view` per
   navigation and a `gcs` parameter consistent with the consent state. In the
   decline scenario, Application → Cookies shows no `_ga` cookie. That's how I
   validated this site's implementation, and it's the only method that tests
   what a real user experiences.

One honest, practical note from validating this site. Triggers based on
`IntersectionObserver` and `requestAnimationFrame`, like `article_read` and
`scroll_depth`, **can't be exercised in a headless or hidden tab**, because
browsers suspend that work in tabs that aren't visible. I had to validate
those events manually in Tag Assistant, with the tab in the foreground. If
your automated QA script says the scroll event "doesn't work," maybe it's
just running in a tab that was never visible.
