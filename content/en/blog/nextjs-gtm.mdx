In a Next.js app, GTM's **All Pages** trigger only fires on the first load; the
following navigations are `history.pushState` and do not reload the page. The
fix is the **History Change** trigger; and the decision almost everyone gets
wrong is turning it on in GTM **and** leaving GA4's Enhanced Measurement
listening to the same events, counting every pageview twice. This article
documents this site's full implementation (a single pageview per navigation,
Consent Mode v2 with a denied default and validation on the real requests),
because the problem was never making the event fire: it is making it fire
**only once**, and only after consent.

## Why All Pages stops firing after the first page

GTM's All Pages trigger is, underneath, the classic page view event: it fires
when the container loads with the page. On a traditional site, every
navigation is a new page load, the container reloads, the trigger fires. In a
Next.js app, the container loads **once**; from then on the router swaps the
content through the History API, with no load. Result: GA4 records the entry on
the first page and goes blind for the rest of the session; the "bounce" rate
drops falsely and the inner pages disappear from the report.

## Installing GTM in the App Router

### @next/third-parties, and why not a hand-written script

The sanctioned path is the `GoogleTagManager` component from the
`@next/third-parties` package, which injects the container with the right
loading strategy for the App Router: no `<script>` pasted by hand in the layout,
no snippet copied from the dashboard. The document this site's root layouts
share (there is one layout per language, and both render the same component,
`RootShell`), in the order the pieces come in. The Portuguese comment says:
Consent Mode v2, default "denied" BEFORE any Google tag loads; the banner
(`ConsentBanner`) updates `analytics_storage` after the user's choice; `ad_*`
stay denied (the site runs no ads):

```tsx
// src/components/layout/RootShell.tsx
// Consent Mode v2 — default "denied" ANTES de qualquer tag do Google carregar.
// O banner (ConsentBanner) atualiza analytics_storage após a escolha do
// usuário; ad_* permanecem negados (o site não veicula anúncios).
const consentDefaultScript = `
window.dataLayer = window.dataLayer || [];
function gtag(){dataLayer.push(arguments);}
gtag('consent', 'default', {
  ad_storage: 'denied',
  ad_user_data: 'denied',
  ad_personalization: 'denied',
  analytics_storage: 'denied',
  wait_for_update: 500
});
`
```

```tsx
// src/components/layout/RootShell.tsx (corpo do documento)
      <body className="flex min-h-screen flex-col font-sans antialiased">
        {/* eslint-disable-next-line @next/next/no-before-interactive-script-outside-document */}
        <Script
          id="consent-default"
          strategy="beforeInteractive"
          dangerouslySetInnerHTML={{ __html: consentDefaultScript }}
        />
        {withSearch ? (
          <SearchProvider>
            {chrome}
            <SearchModal items={buildSearchIndex()} />
          </SearchProvider>
        ) : (
          chrome
        )}
        <ConsentBanner lang={lang} />
        <WebVitalsReporter />
        {site.gtmId && <GoogleTagManager gtmId={site.gtmId} />}
      </body>
```

### Order matters: consent before the container

Note the structure of the snippet above: the script that sets the **consent
default** runs `beforeInteractive`, and the container comes later, at the end
of the body. That order is not aesthetic: the consent default has to exist
**before** any tag wakes up. The Consent Mode section details what happens when
that order is reversed.

## History Change: the trigger that solves the SPA pageview

In the container (UI labels in English, as this project configures it): a
trigger of type **History Change**, and the GA4 `page_view` event tag fired by
it, with the path and title coming from the built-in variables
(`{{Page Path}}`, `{{Page Title}}`). The trigger listens to changes in the
History API, exactly what the Next.js router does on every navigation, and
covers what All Pages doesn't see.

The detail that avoids a classic bug: the GA4 configuration tag must have the
automatic page view of the initial load **or** History Change covering the
load, never the blind sum of both. On this site, the container's full recipe
(tags, triggers, variables and the decision on covering the initial load) is
documented in `docs/measurement-plan.md`, and the container implements the
plan, not the other way round.

## The duplication nobody notices

Here is the core of the article, because it is the part no "History Change in 5
minutes" tutorial mentions: GA4 has its own SPA pageview mechanism. In Enhanced
Measurement, the page views option based on browser history events does the
same job as the History Change trigger, and with both turned on they count
**every navigation twice**.

### GTM or Enhanced Measurement: choose one

Both work; the mistake is not choosing. This site chose **GTM** as the single
pageview source, for an engineering reason: in GTM the logic is versioned and
visible in the container, so you can audit when and why each event fires.
Enhanced Measurement is a box of options in the GA4 dashboard, easy for someone
to turn back on without noticing the consequence. The opposite choice
(Enhanced Measurement on, no history trigger in GTM) is equally valid; what is
not valid is the sum.

### The same reasoning applies to scroll and outbound

Duplication is not exclusive to the pageview. Enhanced Measurement's "Scrolls"
and "Outbound clicks" are also **off** on this site, for the same reason: the
equivalents (`scroll_depth`, outbound clicks) are measured through GTM, where
the thresholds and conditions are documented in the measurement plan. One
source per metric, any metric.

## Consent Mode v2 and the LGPD: denied by default

This site's stance: **no analytics cookie before explicit consent**. Consent
Mode v2 is the mechanism that makes Google's tags respect that choice, and the
implementation has three traps, all verified here in production.

A scope note first: Brazil's LGPD does not require "Consent Mode"; it requires a
legal basis and a real choice by the data subject. What I describe is how this
site implemented that choice in Google's tags; it is not legal advice.

### The default has to come before the container loads

The correct sequence is rigid: first the consent default command (everything
denied), then the container, then (only if and when the user accepts) the
consent update. If the default is set after the container loads, the tags wake
up without instructions and operate as if everything were allowed: the data
leaked before the banner appeared.

In words, the order is:

1. `consent default` with everything denied, as a `beforeInteractive` script;
2. the GTM container loads;
3. the tags operate in cookieless mode (pings with no identifier);
4. the user chooses in the banner → `consent update` with the real choice.

### The arguments trap

The classic silent Consent Mode bug: consent commands have to reach the
`dataLayer` as the function's `arguments` object, **not** as an array. In
practice, that forces the `gtag` function to be a *function declaration*: an
arrow function has no `arguments` of its own, the push still happens, but
consent never updates, and nothing throws. This site's real code carries the
comment and the `eslint-disable` that explain the exception (the comment says
that consent commands must be sent as the `arguments` object, not an array,
hence the function declaration instead of an arrow):

```ts
// src/lib/analytics.ts
/**
 * Empurra um comando gtag('consent', ...) para o dataLayer.
 * IMPORTANTE: os comandos de consent precisam ser enviados como objeto
 * `arguments` (não array) — por isso a function declaration, não arrow.
 */
function gtag(...args: unknown[]): void {
  void args // parâmetros tipados para os call sites; o GTM lê `arguments`
  window.dataLayer = window.dataLayer ?? []
  // eslint-disable-next-line prefer-rest-params
  window.dataLayer.push(arguments)
}

/** Aplica a escolha do usuário (banner ou escolha salva de visita anterior). */
export function applyConsent(choice: ConsentChoice): void {
  if (typeof window === 'undefined') return
  gtag('consent', 'update', { analytics_storage: choice })
}
```

### What a cookieless ping is

In Consent Mode's advanced mode, denying consent does not silence the tags:
they send pings **with no cookies and no user identifier**, which Google uses
for aggregate modelling. This site's validation, on 2026-07-13, was done by
inspecting the real `/g/collect` requests, not by trusting preview mode: with
the denied default, the state appears in the initial `dataLayer` and **no
`_ga` cookie is created**; the pings go out with `gcs=G100`. After "Aceitar"
(accept), the hits move to `gcs=G101`. After "Recusar" (decline), it stays
G100, cookieless. The `page_view` was confirmed firing on load **and** on SPA
navigation, with the right URL and title parameters on each hit.

## A typed dataLayer: no loose push in a component

This site's architecture rule: **no** loose `window.dataLayer.push` in a
component. There is a union type with the allowed events and a single
`pushEvent()` function; an event that is not in the type doesn't compile:

```ts
// src/lib/analytics.ts
// ─────────────────────────────────────────────────────────────────────────────
// Typed dataLayer helper — the ONLY way custom events are pushed on this site.
// Never call window.dataLayer.push directly from components (CLAUDE.md §7.2).
//
// Every event here MUST be documented in /docs/measurement-plan.md BEFORE
// being implemented.
// ─────────────────────────────────────────────────────────────────────────────

/** Custom events documented in docs/measurement-plan.md */
export type AnalyticsEvent =
  | { event: 'tool_generate_jsonld'; schema_type: string }
  | { event: 'tool_validate_meta'; issues_found: number }
  | { event: 'tool_check_cwv'; lcp_bucket: 'good' | 'needs-improvement' | 'poor' | 'no-data' }
  | { event: 'article_read'; article_slug: string }
  | { event: 'outbound_click'; link_domain: string }
  // …the web_vitals events (LCP and INP) follow in the same union

export function pushEvent(e: AnalyticsEvent): void {
  if (typeof window === 'undefined') return
  window.dataLayer = window.dataLayer ?? []
  window.dataLayer.push(e)
}
```

TypeScript becomes the line of defence against "let me just measure this little
thing here" analytics: if the event was not documented and typed, it doesn't
exist. The site's own RUM follows the same path: the `web_vitals` events that
feed the [INP analysis](/en/blog/nextjs-inp) go through the same helper, with
the same contract. It is the philosophy that repeats across this project, from
the [JSON-LD generator](/ferramentas/gerador-json-ld) (its interface is in
Portuguese) to the sitemap: one typed source, zero ad hoc assembly.

## DOM triggers in an SPA: re-arming after navigation

This site's `article_read` event fires when the reader reaches the end of the
article: an **Element Visibility** trigger pointed at a stable `id` (the
comment says it is a stable id, the target of the element visibility trigger of
the `article_read` event in GTM):

```tsx
// src/components/article/ArticleLayout.tsx
            {/* id estável: alvo do trigger de element visibility do evento
                `article_read` no GTM (docs/measurement-plan.md). */}
            <footer id="article-end" className="mt-8 max-w-[68ch] border-t border-gray pt-4">
              <p className="font-mono text-xs leading-6 text-label">{copyright}</p>
            </footer>
```

The detail the SERP almost never mentions: in an SPA navigation the DOM is
replaced without a page load, and the visibility trigger **does not re-arm on
its own**. Without the **Observe DOM changes** option turned on in the trigger,
`article_read` works on the session's first article, and never again. With it
on, GTM watches DOM mutations and re-arms the trigger when the next article's
`#article-end` appears.

## Document before implementing

The rule that ties everything together: **no event is implemented before it is
documented** in `docs/measurement-plan.md`: the event table with name,
parameters, trigger and purpose, the container's configuration recipe and the
validation checklist. The plan is the source; the container and the typed
helper are the implementation. When the three diverge, the plan wins and the
rest is a bug. Without that, six months later nobody knows why there is a
trigger called "scroll 75 old v2" and everyone is afraid to delete it.

It is the same discipline the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs) applies to the rest of the stack: what
matters becomes a versioned artefact (schema derived from the frontmatter,
sitemap derived from the content, events derived from a plan written before the
code).

## How to validate: Tag Assistant, DebugView and the real hit

Three layers, in increasing order of confidence:

1. **Tag Assistant (GTM preview).** Confirm the sequence: on the initial load,
   the consent default appears **before** the container; on SPA navigations,
   History Change fires once per route, and no tag fires twice.
2. **GA4 DebugView.** Check the events arriving with the measurement plan's
   parameters, navigation by navigation.
3. **The real requests.** The layer that doesn't lie: DevTools → Network,
   `collect` filter. One `page_view` per navigation, a `gcs` parameter matching
   the consent state, and, in the refusal scenario, no `_ga` cookie under
   Application → Cookies. That is how this site's implementation was validated,
   and it is the only method that tests what the real user experiences.

An honest practical note, which I found while validating this site: triggers
based on `IntersectionObserver` and `requestAnimationFrame` (such as
`article_read` and `scroll_depth`) **cannot be exercised in a headless or hidden
tab**; browsers suspend that work in tabs that are not visible. Validating
those events had to be manual, in Tag Assistant, with the tab in the
foreground. If your automated QA script says the scroll event "doesn't work",
maybe it is just running in a tab that was never visible.
