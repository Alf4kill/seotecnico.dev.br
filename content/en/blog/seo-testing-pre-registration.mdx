SEO testing proves something only when the hypothesis, the prediction, the
measurement window, and what counts as failure are written down **before**
the data exists. That's pre-registration. Without that record, any result
turns into confirmation. Traffic went up, so the change worked. Traffic went
down, so it's seasonality. On this site, every deliberate change gets an
entry in a
[public
log](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/experiment-log.md)
before its result comes in, and I publish the verdicts, negative ones
included.

Science has a name for this. Pre-registration means specifying in advance
how you'll collect and analyze the data, in a dated record that can't be
altered. Its purpose is to
[separate research that tests hypotheses from research that generates
them](https://rdm.vu.nl/tools/osf/preregistration.html).
You can't use the same data both to invent a hypothesis and to confirm it.
SEO makes the temptation stronger. Search Console hands you new data every
day without being asked, and some curve is always going up.

This article lays out my method. Each section is a rule, and each rule comes
with an experiment from this site that either applied it or showed what
skipping it costs.

## What goes into a registration

A useful entry has four columns, and the last one stays blank until the
window closes.

```markdown
<!-- illustrative: the format of one row of this site's log -->
| Date | Change | Hypothesis | Result |
|---|---|---|---|
| YYYY-MM-DD | what changes, on which URL, in which commit | prediction with a number, window, failure criterion and the smallest effect the window can detect | blank until the window closes |
```

Hypothesis, the third column, is the one that matters. "Improve LCP" isn't a
hypothesis, because no result can contradict it. "Render delay drops to
1.0 s or less" is one. A result of 1.1 s falsifies it.

Here's an excerpt of H17's entry, verbatim, as I logged it on September 28,
2026, before the battery it predicted:

> **ChatGPT, Claude, Gemini** (baseline: server text only, `LD-` 0/15,
> `JS-` 0/15): (C1) condition 1 changes nothing, `LD-` and `JS-` 0/3 each and
> no `/c` request, because their tools extract text and drop `<script>` and a
> hint does not change the tool; falsified by any correct `LD-` or `JS-`, or
> any `/c` request, in condition 1. [...] **Power statement:** 3 rounds per
> cell is a capability check: 3/3 bounds the per-round rate at ≥ 37% and 0/3
> at ≤ 63% (one-sided 95%, exact). Against a 0/5 baseline, only a 3/3 shift
> reaches p < 0.05 (Fisher, one-sided, p = 0.018); a 2/3 shift does not
> (p = 0.11).

It has the three things a registration needs: a prediction with a number
("0/3 each"), what falsifies it ("any correct `LD-` or `JS-`"), and what the
window can detect (only a 3-of-3 shift reaches p < 0.05). Later, I added the
result to the same entry.
[My test of which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript)
confirmed the prediction in 9 of 9 rounds.

## Hypothesis and prediction before the deploy

In July 2026, this site's home page had an LCP of 4.9 s in PageSpeed
Insights on mobile. Its LCP element was text, the hero paragraph, so none of
the image advice applied. Render delay accounted for 1,280 ms of it, held up
by the stylesheet and a font on the critical path. I wrote up the diagnosis
in [how to improve LCP in Next.js](/en/blog/improve-lcp-nextjs).

Before I deployed the fix, I put the prediction in the log. Render delay
would drop to 1.0 s or less, and lab LCP would come in under 2.0 s, the
budget this site's CI enforces on itself. That isn't Google's "good"
threshold, which is 2.5 s in field data. It's a stricter lab yardstick I
chose for the site.

In production, LCP came in at 0.9 s, and render delay fell from 1,280 ms to
530 ms.

A good number isn't the point. If render delay had stopped at 1.1 s, the
entry would say "failed," even with LCP far better than before. I set the
criterion before anyone saw the chart. You'll find the full case, with the
pull request, in my [case studies](/en/case-studies).

All of these numbers are lab data. Field data, which is what Google uses,
comes from CrUX, and when I made the fix the site didn't have enough traffic
to show up there. You can only pre-register a prediction about field data
once your domain has field data. To check whether yours does, use the
[Core Web Vitals checker](/en/tools/cwv-checker), which queries CrUX by
origin.

## Power before the window

Even a well-written hypothesis can end up in a test that never had a chance
of working.

H5, from the detection pilot, predicted that updating an article's
`dateModified` would bring more fetches from search agents over the next 14
days. Its analysis rule required at least 5 fetches of that article in the
window before any verdict.

This site gets 0.47 agent fetches per article every 14 days. That left the
test underpowered by about 10×, and no reasonable window would have saved
it. Worse, that volume was already sitting in the GA4 property when I
pre-registered the hypothesis. I could have known beforehand.

H5 taught a second lesson, because its first attempt never even ran. Its
stimulus was a new field-data section in the target article itself,
[the article on INP in Next.js](/en/blog/nextjs-inp), and that section
wasn't written in time. Without it, no update happened at all. So any entry
that depends on work from another workstream now needs an explicit check
that its precondition was met. Otherwise, a change that never happened looks
the same in the log as a change that happened and had no effect.

Since then, every hypothesis I pre-register declares, next to its window,
the smallest effect or smallest count that window can detect given the
traffic already observed. That changes the kind of question a small site
asks:

- **Rate questions**, like "did CTR go up?" or "do agents come back more?",
  need volume a new site doesn't have.
- **Existence questions**, like "did anyone request this at least once?",
  work with little volume. H14, open until December 24, 2026, asks whether
  any client requests Markdown from this site with `Accept: text/markdown`.
  Its decision rule is already published. I'll build Markdown serving only if
  the request comes from at least five distinct networks or from two
  verified agents.

## Positive control: a zero only counts if the instrument can see

Two honeypots in the detection pilot, URLs that each existed in only one
channel, ended with zero real hits. A zero like that has two explanations
the data can't tell apart. Either nothing came, or the instrument can't see
what comes. Without a control, they're the same observation.

I ran the control in September 2026. A page at a secret URL, kept only in an
environment variable, got new codes every round, and each code existed only
on this server. Over 15 rounds on September 25, I asked ChatGPT (Go plan),
Claude (Pro plan), and Perplexity (free plan) to open the page and report
the codes. No assistant could answer correctly without sending a request to
this server.

Every visit from ChatGPT and Claude showed up in the instrument, **10 of 10**,
each with its identity verified against the IP ranges OpenAI and Anthropic
publish. Perplexity's free plan never fetched the page and reported no
correct code, so its zero is a real zero, not a recording failure. I
describe the test in
[what ChatGPT reads from a Next.js
page](/en/blog/does-chatgpt-read-javascript).

From that control on, a zero in the instrument meant something. Before it, a
zero didn't.

## Bugs in the instrument are results too

The detection pilot had six silent bugs. None of them raised an error. I
found each one by reading an export by hand or by noticing a number that
looked strange:

1. **Signer not recorded.** A valid Web Bot Auth signature proves that a
   domain's owner signed the request. That domain is the identity, and it
   never reached GA4.
2. **New signature format rejected.** The verifier accepted only the old
   form of the `Signature-Agent` header.
3. **Human browsing counted as automation.** Next.js prefetches visible
   links with requests that don't ask for HTML. Those prefetches made up 994
   of the 1,041 events from my own network.
4. **Public repository became a discovery channel.** Honeypot addresses sat
   in versioned files, and Git history is permanent. You can bound that
   confound but never remove it.
5. **One connection produced several network identifiers.** The
   identifier's salt changes every month, and my own-traffic exclusion
   caught only one of them.
6. **Social sharing images counted as page fetches.** They inflated the
   fetch counts, which is why H5's 0.47 is an overestimate.

That list didn't close with the pilot. On October 7, 2026, while checking an
article draft, I found one more. Node's native `fetch` sends
`Sec-Fetch-Mode` without `Sec-Fetch-Dest`, and the instrument counted those
clients as browsers. I logged it before the fix, with the cutoff date and the
rule for reading earlier data. It's written up in
[the article on the `Sec-Fetch-Mode` header](/en/blog/sec-fetch-mode-header).

The same goes for the instrument that measures the site's own code. My CI
gate is supposed to run the SEO suite on every pull request, but a branch
filter made stacked pull requests run zero tests. One of them changed
budgets and tests without a single run. I fixed it in #61, and the gap is
published, not hidden, in [the CI gate case study](/en/case-studies#ci-gate).

And for the tool I read the data with. In the September control, the Explore
export I made the same day showed 3 and 2 visits instead of 5 and 5, because
GA4 hadn't processed the day yet. Taken literally, that table would have
reported five instrument failures that never happened. Since then, I don't
analyze any export until the day has closed and another 24 hours have
passed.

Every published bug comes with a cutoff date. I read data from before the
fix by a rule written **before** the re-reading, so the fix can't become a
second chance to find the result I wanted.

## Deviations recorded, not hidden

A deviation is any point where the protocol wasn't followed. On its own, it
doesn't invalidate a test. Hiding it does, because then nobody can assess
what it affects.

In
[the test of which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript),
the hint battery recorded its deviations, each with its scope:

- **Paid plans on two assistants.** The protocol called for free plans on
  all five, but ChatGPT and Claude ran on Go and Pro plans. Each kept the
  same plan in every block, so the conditions are still comparable with one
  another. The free-plan conclusion applies only to the other three.
- **Cross-conversation memory on** in ChatGPT, Claude, and Gemini during the
  first two blocks, against the protocol. I turned it off before the third.
- **Grok in private mode** from the third block on, because it doesn't show
  a memory setting.

Here's the memory deviation as the repository records it:

> 2. **Memory was on in blocks 1–2** for ChatGPT, Claude and Gemini, against
>    setup step 3. It was found after block 2 and turned off before block 3.
>    - Block 1 came before any H17 hint, so no H17 hint could have been
>      remembered in it.
>    - Block 2 gave the `/c` address in the prompt itself, so memory adds
>      nothing there.

It isn't hidden, and it isn't thrown out. The record says why it doesn't
change the two blocks it touched.

Changing the instrument between batteries is a different thing, and it goes
into the record too. I only started recording the `Sec-Fetch-Mode` value
and a per-request key on September 29, after the neutral battery of
September 27 and before the hint battery. I analyzed the September 27 rounds
as recorded, and anything they can't measure is marked as not measured.

## Counts and bounds, not percentages

With five rounds, "100%" is a false statement. Five of five tells you, with
95% confidence, that the behavior happens in **at least 55%** of cases.
That's the exact one-sided Clopper-Pearson bound, from
[an interval for binomial proportions published in
1934](https://doi.org/10.2307/2331986)
that guarantees its stated coverage even with a tiny sample.

Zero works the same way. In the pilot, H6 predicted that no agent would
follow the `llms.txt` links to the honeypot. None did, but the file was
fetched only 9 times in 57 days. Zero of 9 puts the rate at **at most
28%**, so H6 was supported but underpowered. With that little exposure,
"nobody follows" and "almost nobody reads" can't be told apart.

To compare two small groups, I use Fisher's exact test. It computes the
exact probability of every 2×2 table with the same totals and doesn't rely
on an approximation, which is why
[it works for small samples](https://library.soton.ac.uk/fishers-exact-test).

Two results from the same battery say different things:

| Comparison | Before | After | p (Fisher, one-sided) | What it means |
|---|---|---|---|---|
| ChatGPT and Claude, value loaded by JavaScript, with the address in the prompt | 0 of 5 | 3 of 3 | 0.018 each | The hint changed the result |
| Grok, the JSON-LD code | 2 of 5 | 6 of 6 | 0.06 | It shows capability, not that the hint changed anything |

These calculations fit in four lines:

```python
# illustrative: bounds and p-value with SciPy
from scipy.stats import beta, fisher_exact

print(beta.ppf(0.05, 5, 1))  # 5 of 5: lower bound ≈ 0.549
print(beta.ppf(0.95, 1, 9))  # 0 of 9: upper bound ≈ 0.283
print(fisher_exact([[3, 0], [0, 5]], alternative="greater").pvalue)  # ≈ 0.018
```

## Publishing the negative

I pre-registered the detection pilot's six hypotheses before the first data
point and published all six verdicts: two confirmed, two falsified, one
inconclusive, and one supported but underpowered. You can read all six in
[how to tell whether AI is using your content](/en/blog/detect-ai-crawlers).

- **H1, falsified.** No crawler fell into the robots.txt honeypot. The two
  hits in that period were the lab's own tests.
- **H4, falsified.** Conditional requests didn't point to AI search agents.
  Requests identifying themselves as Claude-SearchBot and OAI-SearchBot sent
  none, and the biggest sender was unidentified traffic.
- **H5, inconclusive**, for the reason in the power section.

H2 is the most delicate confirmation, so the wording has to be exact. It
predicted that a verified training agent would fetch a disallowed page. On
July 30, 2026, GPTBot, from an IP inside the range OpenAI publishes, fetched
three paths that this site's robots.txt disallowed for it. OpenAI documents
GPTBot as a training crawler. But GPTBot didn't fetch `/robots.txt` even
once in the window. This data supports "**fetched without having read the
directive here**" and not "ignored robots.txt." Those two sentences differ
the way a measurement differs from an accusation.

Publishing the negative isn't humility. It's what makes the method
checkable. A site that publishes only its successes gives no one a way to
know how many hypotheses failed for each one that worked.

## When you can't pre-register

In the client accounts I follow in Search Console, Core Web Vitals work
almost never ships alone. It goes out together with content, internal
links, and indexing fixes. When traffic rises, there's no way to attribute
the rise to CWV, and I don't publish a client's gain as a CWV result.

In those cases, the method shrinks, but it doesn't disappear:

- **Record the change and the date anyway.** Without a record, three months
  later nobody remembers what changed in which week.
- **Write the prediction at the mechanism level.** "If render delay drops,
  lab LCP drops with it" is verifiable. "Traffic will rise because of LCP"
  isn't, when three things changed at once.
- **Keep a control.** Pages that didn't get the change, compared over the
  same window, separate the change from seasonality better than any
  before-and-after comparison. H5 used that design, with four control
  articles.
- **Say what can't be attributed.** A sentence like "CWV came together with
  new content, so the gain isn't attributable" is worth more than a chart
  with no caveat.

## How to check an SEO test

Whether the test is yours or someone else's, ask six questions:

1. Is the prediction dated before the data, somewhere it can't be edited
   without leaving a trace?
2. Was the failure criterion written down, with a number?
3. Did the window have the power to detect the predicted effect, given the
   site's real volume?
4. Was there a positive control before anyone interpreted a zero?
5. Are instrument bugs and protocol deviations listed, with what each one
   affects?
6. Are failed hypotheses published alongside the ones that worked?

A "no" to any of them doesn't make the result false. It makes it impossible
to tell apart from luck.

## In Next.js

Bug 3 is the one most worth knowing if you measure traffic on a Next.js
site. Every browser that opens a page prefetches its visible links with RSC
requests. They carry the header `rsc: 1` (or `next-router-prefetch`) and
don't ask for HTML, so a proxy that classifies clients by `Accept` counts
each one as a non-browser client. In the pilot, the six pages that
unidentified clients from my network "accessed" most were exactly the header
and footer links.

My fix leaves the classification alone. It removes those requests from the
proxy before any counting happens, in the matcher itself:

```ts
// src/proxy.ts
export const config = {
  matcher: [
    {
      source:
        '/((?!api/|_next/static|_next/image|images/|favicon.ico|icon.svg|opengraph-image|.*/opengraph-image$|.*\\.(?:png|jpg|jpeg|webp|avif|svg|ico|woff2?)$).*)',
      missing: [
        { type: 'header', key: 'rsc' },
        { type: 'header', key: 'next-router-prefetch' },
      ],
    },
  ],
}
```

With `missing`, the proxy doesn't run when a request carries either of the
two headers. The `.*/opengraph-image$` segment fixes the sixth bug. Before
it, only the root sharing card was excluded.

For the method, the date is what matters. Both lines changed what gets
counted, so each one is a cutoff date in the log, and numbers from before
and after it don't get added together. If you measure traffic in a Next.js
proxy without `missing`, your "non-browser" numbers include your visitors'
navigation.
