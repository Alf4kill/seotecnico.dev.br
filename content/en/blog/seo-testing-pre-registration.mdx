An SEO test only proves something if the hypothesis, the prediction, the
measurement window and what would count as failure are written down
**before** the data exists. That's pre-registration. Without it, every result
turns into confirmation: traffic went up, so the change worked; traffic went
down, so it was seasonality. On this site, every deliberate change gets an
entry in a [public
log](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/experiment-log.md)
before the result is in, and the verdicts are published, negative ones
included.

In science, pre-registration means specifying in advance how data will be
collected and analyzed, in a time-stamped record that can't be altered. It
exists to [separate hypothesis-testing research from hypothesis-generating
research](https://rdm.vu.nl/tools/osf/preregistration.html): you can't use
the same data both to come up with a hypothesis and to confirm it. In SEO, the
temptation is even stronger, because new data shows up in Search Console every
day on its own, and some line is always going up.

This article lays out this site's method. Each section is a rule, and each
rule comes with an experiment that either applied it or showed the cost of
skipping it.

## What goes into a registration

A useful entry has four columns, and the last one stays empty until the
window closes:

```markdown
<!-- illustrative: the format of one row of this site's log -->
| Date | Change | Hypothesis | Result |
|---|---|---|---|
| YYYY-MM-DD | what changes, on which URL, in which commit | prediction with a number, window, failure criterion and the smallest effect the window can detect | blank until the window closes |
```

The column that matters is the third. "Improve LCP" isn't a hypothesis,
because no result can contradict it. "Render delay drops to 1.0 s or less" is,
because 1.1 s would falsify it. Here's a verbatim excerpt from H17's entry,
registered on September 28, 2026, before the battery it made predictions
about:

> **ChatGPT, Claude, Gemini** (baseline: server text only, `LD-` 0/15,
> `JS-` 0/15): (C1) condition 1 changes nothing, `LD-` and `JS-` 0/3 each and
> no `/c` request, because their tools extract text and drop `<script>` and a
> hint does not change the tool; falsified by any correct `LD-` or `JS-`, or
> any `/c` request, in condition 1. [...] **Power statement:** 3 rounds per
> cell is a capability check: 3/3 bounds the per-round rate at ≥ 37% and 0/3
> at ≤ 63% (one-sided 95%, exact). Against a 0/5 baseline, only a 3/3 shift
> reaches p < 0.05 (Fisher, one-sided, p = 0.018); a 2/3 shift does not
> (p = 0.11).

It has the three things a registration needs: a prediction with a number
("0/3 each"), what would falsify it ("any correct `LD-` or `JS-`") and what
the window can detect (only a 3-of-3 shift reaches p < 0.05). The result came
later, in the same entry: the prediction held in 9 of 9 rounds, as written up
in [which AI assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript).

## Hypothesis and prediction before the deploy

In July 2026, this site's home page had an LCP of 4.9 s in PageSpeed Insights
on mobile. The LCP element was text, the hero paragraph, so none of the usual
image advice applied: 1,280 ms of it was render delay, held up by the
stylesheet and a font on the critical path. The diagnosis is in the [article
on improving LCP in Next.js](/en/blog/improve-lcp-nextjs).

Before the fix was deployed, the prediction went into the log: render delay
of 1.0 s or less, and lab LCP under 2.0 s, the budget this site's CI holds
itself to. That isn't Google's "good" threshold, which is 2.5 s in field data;
it's a stricter lab yardstick the site chose for itself.

The production result was an LCP of 0.9 s, with render delay down from
1,280 ms to 530 ms. The nice number isn't the point. The point is that if
render delay had stopped at 1.1 s, the entry would say "failed", even with
LCP far better than before. The criterion was locked in before anyone saw the
chart. The full case, with the pull request, is in the [case
studies](/en/case-studies).

Those are lab numbers. Field data, which is what Google uses, comes from
CrUX, and at the time of the fix this site didn't have enough traffic to show
up in it. You can only register a prediction about field data once the domain
has field data. To check whether yours does, the [Core Web Vitals
checker](/en/tools/cwv-checker) queries CrUX by origin.

## Power before the window

A well-written hypothesis can still be a test that never had a chance. H5 in
the detection pilot predicted that updating an article's `dateModified` would
draw more fetches from search agents over the following 14 days. The analysis
rule required at least 5 fetches of the article within the window to reach a
verdict.

This site gets 0.47 agent fetches per article every 14 days. The test was
underpowered by roughly 10×, and no reasonable window would have saved it.
Worse, that volume was already visible in the GA4 property when the
hypothesis was registered. It could have been known in advance.

H5 has a second lesson. Its first attempt never ran: the stimulus was
supposed to be a new field-data section in the target article itself, the one
on [INP in Next.js](/en/blog/nextjs-inp), and that section wasn't written in
time. Without it, there was no update at all. An entry that depends on someone
else's deliverable needs an explicit precondition check; otherwise a change
that never happened looks exactly like a change that happened and had no
effect.

Since then, every hypothesis registered here states, next to its window, the
smallest effect or count that window can detect given the traffic already
observed. That changes the kind of question a small site asks:

- **Rate questions** ("did CTR go up?", "do agents come back more often?")
  need volume a new site doesn't have.
- **Existence questions** ("did anyone request this at least once?") work
  with very little volume. H14, open until December 24, 2026, asks whether any
  client requests Markdown from this site with `Accept: text/markdown`. The
  decision rule is already published: Markdown serving will only be built if
  the requests come from at least five distinct networks or two verified
  agents.

## Positive control: a zero only counts if the instrument can see

The detection pilot had two honeypots, URLs that each existed in only one
channel, and both ended with zero genuine hits. A zero like that has two
explanations the data can't separate: nothing came, or the instrument can't
see what comes. Without a control, the two look identical.

The control came in September 2026. A page at a secret URL, stored only in an
environment variable, showed new codes each round, and each code existed only
on this server. In 15 rounds on September 25, I asked ChatGPT (Go plan),
Claude (Pro plan) and Perplexity (free plan) to open the page and report the
codes. Every correct answer required a request to this server.

The instrument recorded **10 of 10** visits from ChatGPT and Claude, all with
identity verified against the IP ranges OpenAI and Anthropic publish.
Perplexity's free plan never fetched the page and reported no correct codes,
so its zero is a real zero, not a recording failure. The test is written up in
the [AI crawler detection case study](/en/case-studies/ai-crawler-detection).

From that control on, a zero from the instrument meant something. Before it,
it didn't.

## Bugs in the instrument are results too

None of the bugs below threw an error. Each one was found by reading an
export by hand or noticing a number that looked off. These are the detection
pilot's six silent bugs:

1. **The signer was never recorded.** A valid Web Bot Auth signature proves
   that a domain's owner signed; the domain is the identity, and it never made
   it into GA4.
2. **The current signature format was rejected.** The verifier only accepted
   the older form of the `Signature-Agent` header.
3. **Human browsing was counted as automation.** Next.js prefetches visible
   links with requests that don't ask for HTML. Of the events from the
   author's own network, 994 of 1,041 were those prefetches.
4. **The public repository became a discovery channel.** The honeypot
   addresses were in versioned files, and Git history is permanent: the
   confound can be bounded, but never removed.
5. **One connection produced several network identifiers.** The identifier's
   salt rotates every month, and the exclusion of the author's traffic only
   caught one of them.
6. **Social sharing images were counted as page fetches.** That inflated the
   fetch counts, which is why H5's 0.47 is an upper-bound estimate.

The list didn't end with the pilot. On October 7, 2026, while checking a
draft, I found another one: Node's native `fetch` sends `Sec-Fetch-Mode`
without `Sec-Fetch-Dest`, and the instrument counted those clients as
browsers. The bug was logged before the fix, with a cutoff date and a rule for
reading the earlier data. The case is covered in the [Sec-Fetch-Mode
article](/en/blog/sec-fetch-mode-header).

The same applies to the instrument that checks the site's own code. This
site's CI gate was supposed to run the SEO suite on every pull request, but a
branch filter meant stacked pull requests ran zero tests. One of them changed
the budgets and the tests without a single run. It was fixed in #61, and the
gap is published in the [CI gate case study](/en/case-studies#ci-gate), not
hidden.

And it applies to the analysis tool, too. In the September control, the
Explore export pulled the same day showed 3 and 2 visits, not 5 and 5,
because GA4 hadn't finished processing the day. Taken at face value, that
table would have reported five instrument failures that never happened. The
rule since then: no export gets analyzed until the day has ended and another
24 hours have passed.

A published bug comes with a cutoff date. Data from before the fix is read
according to a rule written **before** anyone re-reads it, so the fix can't
turn into a second chance to find the result someone was hoping for.

## Deviations recorded, not hidden

A deviation is a part of the protocol that wasn't followed. It doesn't
invalidate a test on its own; it does when it's hidden, because then nobody
can judge what it affects. The hint battery in the [test of which AI
assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript)
recorded its own deviations, each with its scope:

- **Paid plans for two assistants.** The protocol assumed free plans for all
  five, but ChatGPT and Claude ran on Go and Pro. They stayed on the same plan
  in every block, so their conditions remain comparable with each other, and
  the free-plan conclusion only applies to the other three.
- **Cross-chat memory left on** for ChatGPT, Claude and Gemini in the first
  two blocks, against the protocol. It was turned off before the third.
- **Grok in private mode** from the third block on, because it has no memory
  setting.

Here's the memory deviation as recorded in the repository:

> 2. **Memory was on in blocks 1–2** for ChatGPT, Claude and Gemini, against
>    setup step 3. It was found after block 2 and turned off before block 3.
>    - Block 1 came before any H17 hint, so no H17 hint could have been
>      remembered in it.
>    - Block 2 gave the `/c` address in the prompt itself, so memory adds
>      nothing there.

The deviation is neither hidden nor thrown out: the record explains why it
doesn't change the two blocks it affected.

A change to the instrument between batteries is a different matter, and it
goes into the record too. The `Sec-Fetch-Mode` value and a per-request key
were only recorded from September 29 on, after the neutral battery of
September 27 and before the hint battery. The September 27 rounds were
analyzed as recorded, and whatever they can't measure is stated as not
measured.

## Counts and bounds, not percentages

With five rounds, "100%" is a false statement. What five out of five tells
you, at 95% confidence, is that the behavior happens **at least 55%** of the
time. That's the exact one-sided Clopper-Pearson bound, the [interval for
binomial proportions](https://doi.org/10.2307/2331986) published in 1934,
which keeps its stated coverage even with tiny samples.

The same goes for zero. The pilot's H6 predicted that no agent would follow
the `llms.txt` links to the honeypot. None did, but the file was only fetched
9 times in 57 days. Zero out of 9 tells you the rate is **at most 28%**. The
hypothesis held, but without much strength: with so little exposure, "nobody
follows it" and "almost nobody reads it" can't be told apart.

To compare two small groups, this site uses Fisher's exact test, which
calculates the exact probability of every 2×2 table with the same totals
instead of relying on an approximation, which is why it [works well for small
samples](https://library.soton.ac.uk/fishers-exact-test). The two results
below come from the same battery and say different things:

| Comparison | Before | After | p (Fisher, one-sided) | What it means |
|---|---|---|---|---|
| ChatGPT and Claude, value loaded by JavaScript, with the address in the prompt | 0 of 5 | 3 of 3 | 0.018 each | the hint changed the result |
| Grok, the JSON-LD code | 2 of 5 | 6 of 6 | 0.06 | shows capability, not that the hint changed anything |

The math fits in four lines:

```python
# illustrative: bounds and p-value with SciPy
from scipy.stats import beta, fisher_exact

print(beta.ppf(0.05, 5, 1))  # 5 of 5: lower bound ≈ 0.549
print(beta.ppf(0.95, 1, 9))  # 0 of 9: upper bound ≈ 0.283
print(fisher_exact([[3, 0], [0, 5]], alternative="greater").pvalue)  # ≈ 0.018
```

## Publishing the negative

The detection pilot registered six hypotheses before the first data point and
published all six in the [AI crawler detection case
study](/en/case-studies/ai-crawler-detection): two confirmed, two falsified,
one inconclusive and one supported but underpowered.

- **H1, falsified.** No crawler fell into the robots.txt honeypot. The two
  hits during the period were the lab's own tests.
- **H4, falsified.** Conditional requests didn't point to AI search agents:
  requests identifying themselves as Claude-SearchBot and OAI-SearchBot sent
  none, and the heaviest senders were unidentified traffic.
- **H5, inconclusive**, for the reason given in the section on power.

And the most sensitive confirmation needs exactly the right wording. H2
predicted that a verified training agent would fetch a disallowed page. On
July 30, 2026, GPTBot, from an IP inside the range OpenAI publishes, fetched
three paths this site's robots.txt disallowed for it. OpenAI documents GPTBot
as a training crawler. But GPTBot didn't fetch `/robots.txt` even once during
the window. The data supports "**fetched without having read the directive
here**". It doesn't support "ignored robots.txt". The gap between those two
sentences is the gap between a measurement and an accusation.

Publishing negative results isn't modesty. It's what lets anyone check the
method: a site that only publishes wins leaves nobody able to tell how many
hypotheses failed for each one that worked.

## When you can't pre-register

In the client accounts I monitor in Search Console, Core Web Vitals work
almost never ships on its own: it goes out alongside content, internal links
and indexing fixes. When traffic goes up, there's no way to attribute the rise
to CWV, so I don't report a client's gains as a CWV result. If you report to
clients, you know the pressure to do exactly that.

In those cases the method gets smaller, but it doesn't disappear:

- **Log the change and the date anyway.** Without a record, three months from
  now nobody will remember what changed in which week.
- **Write the prediction at the level of mechanism.** "If render delay drops,
  lab LCP drops with it" can be checked. "Traffic will rise because of LCP"
  can't, when three things changed at once.
- **Keep a control group.** Pages that didn't get the change, compared over
  the same window, separate the change from seasonality better than any
  before-and-after comparison. That's the design H5 used, with four control
  articles.
- **Say what can't be attributed.** A sentence like "CWV shipped together
  with new content, so the gain can't be attributed to it" is worth more than
  a chart without a caveat.

## How to check an SEO test

Whether it's your test or someone else's, ask six questions:

1. Is the prediction dated before the data, somewhere it can't be edited
   without leaving a trace?
2. Was the failure criterion written down, with a number?
3. Did the window have enough power to detect the predicted effect, at the
   site's actual volume?
4. Was there a positive control before anyone interpreted a zero?
5. Are the instrument's bugs and the protocol's deviations listed, along with
   what each one affects?
6. Are the hypotheses that failed published alongside the ones that worked?

A "no" on any of them doesn't make the result false. It makes the result
impossible to tell apart from luck.

## In Next.js

The third bug on the list is the one most worth knowing about if you measure
traffic on a Next.js site. Every browser that opens a page prefetches the
visible links with RSC requests, which carry an `rsc: 1` (or
`next-router-prefetch`) header and don't ask for HTML. A proxy that
classifies clients by their `Accept` header counts every one of them as a
non-browser client. In the pilot, the six pages most "visited" by
unidentified clients from the author's own network were exactly the header
and footer links.

The fix doesn't touch the classification. It keeps those requests out of the
proxy before anything gets counted, right in the matcher:

```ts
// src/proxy.ts
export const config = {
  matcher: [
    {
      source:
        '/((?!api/|_next/static|_next/image|images/|favicon.ico|icon.svg|opengraph-image|.*/opengraph-image$|.*\\.(?:png|jpg|jpeg|webp|avif|svg|ico|woff2?)$).*)',
      missing: [
        { type: 'header', key: 'rsc' },
        { type: 'header', key: 'next-router-prefetch' },
      ],
    },
  ],
}
```

`missing` keeps the proxy from running when the request carries either
header. The `.*/opengraph-image$` part is the fix for the sixth bug: before
it, only the root social sharing card was excluded.

The methodological point is the date. Both lines changed what gets counted,
so each one is a cutoff in the log, and the numbers before and after are never
added together. If you measure traffic in a Next.js proxy without `missing`,
your "non-browser" numbers include your visitors' own navigation.
