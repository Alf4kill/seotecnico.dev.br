The Metadata API is the App Router's mechanism for emitting `<title>`, meta
description, canonical and Open Graph: a `metadata` object exported from the
route (static) or a `generateMetadata()` function (dynamic); `next/head` no
longer exists here. What the tutorials don't tell you is that inheritance
between layout and page is a **shallow merge**: if the page defines any field
inside `openGraph`, the parent layout's whole object is dropped, silently.
That is why your WhatsApp card comes out blank even with `og:image`
configured "site-wide". In this article I show the two behaviours that broke
this site's Open Graph in production, and the helper that now keeps it from
happening again.

## What the Metadata API replaces (and why next/head no longer works)

In the Pages Router, meta tags were JSX: you imported `next/head` and wrote
`<meta>` by hand, in any component. In the App Router that is over. The
`<head>` is assembled by the framework from data, the `metadata` object, and
`next/head` is simply not supported inside `app/`.

The change is better than it looks: metadata became structured data, typed
(Next's own `Metadata`), evaluated per route and checkable at build time. The
whole [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) starts
from that premise: what is data can be derived, validated and tested.

The problem is that the same change created an inheritance semantics almost
nobody read to the end, and it does not work like a CSS cascade.

## Static object vs generateMetadata: when to use each

The rule I use is a single one: **`generateMetadata()` only when the value
depends on the route**. If the metadata is known without looking at
`params` (home, the tools page, the blog listing), it is a static object:

```ts
// app/ferramentas/page.tsx
export const metadata: Metadata = {
  title: "Ferramentas de SEO técnico",
  description: "…",
};
```

If the value comes from `params` or from loaded content (the classic case is
a post's frontmatter in `/blog/[slug]`), it is a function:

```ts
// app/blog/[slug]/page.tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const post = getPost(params.slug);
  return buildMetadata({ title: post.title, /* … */ });
}
```

On this site, the post route uses exactly that shape; the real
`generateMetadata` is in `src/app/(pt)/blog/[slug]/page.tsx` and appears in
full in the helper section. What matters now: **both paths go through the
same merge pipeline**. Nothing that follows changes between static and
dynamic.

## metadataBase: the piece that makes every relative path absolute

Open Graph requires absolute URLs. Canonical, in practice, does too.
`metadataBase` is the base URL, defined once in the root layout, that Next
uses to resolve every relative path in the Metadata API:

```ts
// app/layout.tsx
export const metadata: Metadata = {
  metadataBase: new URL("https://seotecnico.dev.br"),
  // …
};
```

With it, `alternates.canonical: "/blog/my-post"` becomes
`https://seotecnico.dev.br/blog/my-post` in the emitted HTML. Without
`metadataBase`, relative paths do not resolve to the production domain, and a
relative `og:image` is useless to the WhatsApp or LinkedIn scraper, which has
no base context.

## A self-referencing canonical on every page

This site's rule is that **every indexable route emits a canonical pointing
to itself**; it is one of the canonicalization signals that must tell the
same story as the [sitemap derived from the content](/en/blog/nextjs-dynamic-sitemap).
In the App Router, the field is `alternates.canonical`:

```ts
export const metadata: Metadata = {
  alternates: { canonical: "/blog/my-post" },
};
```

It looks too simple to go wrong. And this is where the detail that justifies
the article comes in: `alternates`, like `openGraph`, **is not merged between
layout and page**. A strategic canonical defined in the layout disappears on
the first route that declares its own `alternates`, together with anything
else that lived there.

## The merge that isn't

The official `generateMetadata` documentation describes the behaviour
precisely: the metadata objects of a route's segments are merged
**shallowly**, and nested fields such as `openGraph` and `robots` defined in an
earlier segment are **overwritten entirely** by the last segment that defines
them. It is documented, but none of the "SEO in Next.js" tutorials I found in
the pt-BR SERP mentions the practical consequence.

### openGraph: defining one field erases the rest

The practical consequence is this. A root layout with the full set:

```ts
// app/layout.tsx
export const metadata: Metadata = {
  openGraph: {
    siteName: "SEO Técnico",
    locale: "pt_BR",
    type: "website",
    images: ["/og-default.png"],
  },
};
```

A page that only wants to change the card's title:

```ts
// app/guia/page.tsx
export const metadata: Metadata = {
  openGraph: { title: "Guia de SEO técnico para Next.js" },
};
```

Result emitted on the page: `og:title`, **and nothing else**. No
`og:site_name`, no `og:locale`, no `og:image`. The layout's object was
replaced, not extended. Verified empirically on this site on Next.js 16.2.6;
if you are on another version, check before assuming, but the behaviour is the
one documented since the start of the App Router.

### alternates: the same behaviour, and why the RSS feed disappears

`alternates` follows the same rule. And it holds more than it seems: besides
the canonical, `alternates.types` is where RSS feed autodiscovery lives
(`application/rss+xml`). If autodiscovery is declared in the root layout and a
page defines `alternates: { canonical: "…" }`, that page **loses the feed
tag**, with no warning, no build error, nothing.

That is why, on this site, RSS autodiscovery was moved into the metadata
helper (the helper section shows where): it is the only place that guarantees
it is re-emitted on every route, since relying on the layout's inheritance
means relying on an inheritance that does not exist.

### The real case: og:url pointing to the home across the site

On 2026-07-14, an external review of this site's production build reported
seven findings. Three of them (`og:image` missing site-wide, `og:url` pointing
to the home on every subpage, and the guide page without `og:locale` and
`og:site_name`) had **the same root cause**: I had treated inheritance as a
cascade.

`og:url` is the most instructive case. It was defined only once, in the root
layout's `openGraph`, pointing to the home. On routes that did not customize
`openGraph`, the root's object was inherited whole, which means every subpage
announced the home as its card URL. On routes that did customize `openGraph`,
the opposite happened: the root's object was dropped and the page lost locale,
site_name and image. Both symptoms, opposite in appearance, were the same
behaviour.

The fix was not "add the missing fields" page by page; it was architectural,
and it is this article's thesis: **per-page metadata cannot be assembled ad
hoc**. The comment that now sits in this site's root layout metadata,
explaining why `openGraph.url` is deliberately **not** there, is that bug's
scar preserved in the code. Since the site has one root layout per language,
that metadata comes from a function, `rootMetadata(lang)`, which both layouts
call (the repository's comments are in Portuguese; this one says that og:url
is always set per page through `buildMetadata`, because a static url in the
root was inherited and pointed every subpage to the home):

```ts
// src/lib/metadata.ts — rootMetadata(lang)
    // Sem `url` aqui: og:url é sempre definido por página via buildMetadata
    // (um url estático no root era herdado e apontava toda subpágina à home).
    openGraph: {
      type: 'website',
      locale: OG_BY_LANG[lang].locale,
      siteName: site.name,
    },
```

The full history of the seven findings is documented in the repository's
`docs/seo-metadata-hardening.md`.

## OG image: file convention and config don't talk to each other

The App Router has a second path for the Open Graph image: the file
convention. An `opengraph-image.tsx` (or `.png`) next to `page.tsx` generates
and emits that segment's `og:image` tag. Two behaviours, both verified on this
site on Next.js 16.2.6, deserve attention, and since this behaviour has
changed between Next versions, it is worth checking yours with a view-source
before assuming.

### opengraph-image.tsx does not cascade

On 16.2.6, the file applies the image to **the segment where it lives**; it
did not flow down to nested routes the way a layout does. An
`app/opengraph-image.tsx` did not guarantee `og:image` on `/blog/my-post`; for
the post route to have an image, the `app/blog/[slug]/` segment needed its own
`opengraph-image.tsx`. If you were counting on "I put one file in the root and
the whole site gets a card", check the HTML emitted on deep routes.

### Page config beats the sibling file

When the same segment has an `opengraph-image.tsx` **and** the page defines
`openGraph.images` in its config, the config wins and the file is ignored. On
this site that mattered for months: the helper always emits the full
`openGraph` set, which would suppress the per-post image generated by the
segment's file. The first fix was a flag in the helper (`fileOgImage: true`)
that left `openGraph.images` out of the config so the sibling file could win.
The flag no longer exists, and the section right below the diagram explains
why.

In words, the order of precedence is: `openGraph.images` defined in the page
config wins over everything; without it, the segment's own
`opengraph-image.tsx` applies; and a parent segment's file does **not** apply
to child routes.

### A route group changes the image URL

In September 2026 this site moved to one root layout per language, with the
routes moved into two route groups, `(pt)` and `(en)`; the reason is in the
[hreflang in Next.js article](/en/blog/nextjs-hreflang). The build passed and
the whole SEO suite stayed green. Even so, the default `og:image` the helper
writes (`/opengraph-image`) and the `image` in the `Article` JSON-LD of the 11
articles started pointing to 404.

The cause: inside a route group, Next.js adds a hashed suffix to the URL of
metadata images generated by file convention. The brand card, in
`app/(pt)/opengraph-image.tsx`, started being served at
`/opengraph-image-35ziq1`; each post's, at
`/blog/<slug>/opengraph-image-18vth1`. On Next.js 16.2.12, the function that
builds the suffix is `getMetadataRouteSuffix`. The file name stays the same;
what breaks is every place that wrote the URL by hand, counting on that name.

The fix was to abandon the file convention for images. Each card became a
route handler, which is served exactly at the folder's path, with no suffix
(the card's text is the Portuguese brand card: "live laboratory", "technical
SEO for people who build modern sites"):

```tsx
// src/app/(pt)/opengraph-image/route.tsx
export const dynamic = 'force-static'

export function GET() {
  return new ImageResponse(
    (
      <OgCard
        kicker="Laboratório vivo"
        title="SEO técnico para quem desenvolve"
        highlight="sites modernos"
        subtitle="Guias práticos, ferramentas gratuitas e experimentos medidos com dados reais."
        art={{ kind: 'mark', variant: 'beam' }}
      />
    ),
    { ...OG_SIZE, fonts: ogFonts() }
  )
}
```

Without the file convention, nothing injects `og:image` on its own. The
`fileOgImage` flag lost its reason to exist, and the helper now emits the
image on every route, receiving the post's card as a parameter. The SEO suite
gained the assertion it was missing: on every route, it downloads the
`og:image` and every image cited in the JSON-LD and requires a 200 response
with `image/png`. Checking that the tag exists is not enough; you have to
check that the URL responds.

If you use route groups and write the URL of a metadata image anywhere
(JSON-LD, a helper, a share link), check the served URL in the build, not the
file name.

## The fix: a single metadata helper

If `openGraph` and `alternates` are replaced wholesale, the only safe
architecture is: **no route assembles metadata by hand; every route calls a
helper that always emits the full set.** It is the opposite of what the
tutorials teach (scattering partial `export const metadata` across routes),
and it is the same philosophy this site already applies to [JSON-LD derived
from the frontmatter](/en/blog/nextjs-json-ld): one source, one format, zero
ad hoc assembly.

The helper's contract: the file's real header, with the reason it exists and
the input signature. The comments are in Portuguese; in short, they say that
when a page defines its own `openGraph` it replaces the root layout's
entirely, so every page must build its metadata here and never write
`openGraph` by hand, and that the title (≤60 with the template suffix) and
description (≤155) limits are validated here and fail the build:

```ts
// src/lib/metadata.ts
// ─────────────────────────────────────────────────────────────────────────────
// buildMetadata — helper único de metadados por página (CLAUDE.md §6).
//
// Motivo de existir: no Metadata API do Next.js, quando uma página define seu
// próprio objeto `openGraph`, ele SUBSTITUI o do root layout por inteiro (não
// há merge profundo). Foi assim que /guia perdeu og:url/og:locale/og:site_name
// e as demais páginas herdaram og:url apontando para a home. Toda página deve
// montar seus metadados por aqui — nunca escrever `openGraph` à mão.
//
// Limites de title (≤60, já com o sufixo do template) e description (≤155)
// são validados aqui e estouram no build — mesma política de /lib/content.ts.
// ─────────────────────────────────────────────────────────────────────────────

const TITLE_MAX = 60
const DESCRIPTION_MAX = 155

/**
 * O que muda no Open Graph de uma página conforme o idioma dela. Uma página em
 * inglês herdando `og:locale pt_BR` e o card da marca escrito em português
 * contradiz o próprio hreflang que ela emite — daí as três coisas andarem
 * juntas, derivadas de um único `lang`, em vez de três opções independentes que
 * alguém pode esquecer de passar.
 */
const OG_BY_LANG: Record<Lang, { locale: string; image: string; alt: string }> = {
  'pt-BR': { locale: site.locale, image: '/opengraph-image', alt: OG_BRAND_ALT },
  en: { locale: 'en_US', image: '/en/opengraph-image', alt: OG_BRAND_ALT_EN },
}

export interface BuildMetadataInput {
  /** Título da página. Com `absoluteTitle`, ignora o template "%s | SEO Técnico". */
  title: string
  description: string
  /** Caminho canônico da rota, começando com '/' (ex.: '/blog/meu-post'). */
  path: string
  absoluteTitle?: boolean
  /** Presente ⇒ og:type article com published/modified time (datas do frontmatter). */
  article?: {
    publishedTime: string
    modifiedTime: string
  }
  /** Para rotas utilitárias (ex.: /busca) que não devem ser indexadas. */
  noindex?: boolean
  /**
   * Idioma da página. Só as rotas em inglês passam este campo; o padrão é o do
   * site (§10, português-primeiro). Define `og:locale` e o card OG da marca.
   */
  lang?: Lang
  /**
   * Card OG próprio da página (ex.: /blog/<slug>/opengraph-image), no lugar do
   * card da marca do idioma. As imagens são route handlers, não a file
   * convention — dentro de route groups a convenção ganha hash na URL (ver
   * app/(pt)/opengraph-image/route.tsx) —, então nada injeta og:image sozinho:
   * toda página o recebe daqui.
   */
  ogImage?: { path: string; alt: string }
}
```

And the body, where each decision in this article becomes a line of code:

```ts
// src/lib/metadata.ts (continuação)
export function buildMetadata(input: BuildMetadataInput): Metadata {
  const { title, description, path, absoluteTitle, article, noindex, ogImage } = input
  const og = OG_BY_LANG[input.lang ?? 'pt-BR']

  if (!path.startsWith('/')) {
    throw new Error(`buildMetadata: path deve começar com '/' (recebido: "${path}")`)
  }

  const renderedTitle = absoluteTitle ? title : `${title} | ${site.name}`
  if (renderedTitle.length > TITLE_MAX) {
    throw new Error(
      `buildMetadata: title renderizado com ${renderedTitle.length} chars (máx ${TITLE_MAX}) em "${path}": "${renderedTitle}"`
    )
  }
  if (description.length > DESCRIPTION_MAX) {
    throw new Error(
      `buildMetadata: description com ${description.length} chars (máx ${DESCRIPTION_MAX}) em "${path}"`
    )
  }

  // hreflang derivado do caminho, nunca declarado à mão na página: é assim que
  // a reciprocidade fica garantida por construção (ver lib/hreflang.ts). Rotas
  // sem tradução não emitem nada — um cluster de um item só é ruído.
  const languagePaths = languageAlternatePaths(path)

  return {
    title: absoluteTitle ? { absolute: title } : title,
    description,
    alternates: {
      canonical: path,
      ...(languagePaths
        ? {
            languages: Object.fromEntries(
              Object.entries(languagePaths).map(([lang, target]) => [
                lang,
                absoluteUrl(target),
              ])
            ),
          }
        : {}),
      // Autodiscovery do feed em toda página. Precisa estar aqui (e não no
      // root layout) porque `alternates` da página substitui o herdado.
      types: {
        'application/rss+xml': [{ url: '/feed.xml', title: site.name }],
      },
    },
    // og:title/og:description/twitter:* são preenchidos pelo Next.js a partir
    // de title/description — aqui só entra o que a herança não cobre.
    openGraph: {
      url: absoluteUrl(path),
      siteName: site.name,
      locale: og.locale,
      // og:image: o card da página, ou o da marca no idioma dela. Precisa estar
      // aqui: como este objeto substitui o openGraph herdado, nenhuma imagem
      // cascateia do layout para as subpáginas.
      images: [
        {
          url: ogImage?.path ?? og.image,
          width: OG_SIZE.width,
          height: OG_SIZE.height,
          type: OG_CONTENT_TYPE,
          alt: ogImage?.alt ?? og.alt,
        },
      ],
      ...(article
        ? {
            type: 'article',
            publishedTime: article.publishedTime,
            modifiedTime: article.modifiedTime,
          }
        : { type: 'website' }),
    },
    // Fail-safe de indexação (site.ts): fora de produção, noindex em tudo. Ver
    // `rootMetadata` sobre por que isto é por página e não do layout.
    robots: {
      index: indexable && !noindex,
      follow: indexable,
    },
  }
}
```

```ts
// src/app/(en)/en/blog/[slug]/page.tsx
export async function generateMetadata({ params }: PageProps): Promise<Metadata> {
  const { slug } = await params
  const post = getEnglishPostBySlug(slug)
  if (!post) return {}

  const { frontmatter } = post
  const path = `/en/blog/${frontmatter.slug}`
  return buildMetadata({
    title: frontmatter.title,
    absoluteTitle: true,
    description: frontmatter.description,
    path,
    lang: 'en',
    article: {
      publishedTime: frontmatter.datePublished,
      modifiedTime: frontmatter.dateModified,
    },
    ogImage: { path: `${path}/opengraph-image`, alt: frontmatter.title },
  })
}
```

The helper's contract matters more than its implementation: every call emits
title, description, a self-referencing canonical, the **complete** `openGraph`
object (locale, site_name, type, image and a url matching the canonical), the
complete `alternates` (canonical, hreflang when the route has a translation,
and RSS autodiscovery in `types`) and the `robots` directive. A route cannot
emit a half `openGraph`, because no route writes `openGraph`: all of them
receive the finished set.

A detail worth recording: the Search Console verification token
(`verification.google`) comes in through the root layout via an environment
variable, never hardcoded; a configuration key is not content.

## Validate at build time, not in production

The 2026-07-14 incident was discovered by an external review, which means
late. The response was to move validation to the only place where it does not
depend on discipline: the build.

On this site, the frontmatter schema validates title and description with
limits that **throw**, not warn:

```ts
// src/lib/content.ts
const TITLE_MAX = 60
const DESCRIPTION_MAX = 155

function parseFrontmatter(data: Record<string, unknown>, file: string): PostFrontmatter {
  const required = [
    'title',
    'description',
    'slug',
    'datePublished',
    'dateModified',
    'primaryQuery',
    'lang',
  ] as const

  for (const field of required) {
    if (!data[field]) {
      throw new Error(`[content] "${file}": missing required frontmatter field "${field}"`)
    }
  }

  const title = String(data.title)
  const description = String(data.description)

  if (title.length > TITLE_MAX) {
    throw new Error(
      `[content] "${file}": title has ${title.length} chars (max ${TITLE_MAX})`
    )
  }
  if (description.length > DESCRIPTION_MAX) {
    throw new Error(
      `[content] "${file}": description has ${description.length} chars (max ${DESCRIPTION_MAX})`
    )
  }
  // …
}
```

A 61-character title does not produce a deploy with a truncated title in the
SERP; it produces a red build. It is the embodiment of a rule I repeat in the
[guide](/en/guide/technical-seo-nextjs): CI is the only reviewer that does not
forget. Together with the Playwright assertions that check canonical, `og:url`
and the H1 count per page, metadata stopped being something you eyeball after
the deploy.

## How to check it is correct

Close the loop, as always, with verification, in this order:

1. **View-source on a subpage, not the home.** The home is almost always
   right; the shallow merge breaks the inner routes. Look for `og:url` (it
   must be the page's own URL), `og:locale`, `og:site_name` and `og:image`
   with an absolute URL. If you would rather not dig through raw HTML, this
   site's [meta tag validator](/ferramentas/validador-meta-tags) reads that
   same response and returns title, description, canonical and Open Graph
   with a verdict for each (its interface is in Portuguese); it is step 1
   automated, including the 60 and 155 limits.
2. **Compare two routes: one that customizes `openGraph` and one that
   doesn't.** If the set of emitted tags differs between them, you have ad hoc
   assembly somewhere, and the helper has a hole.
3. **The platform's debugger.** LinkedIn's and Facebook's scrapers keep a
   cache; after fixing, force a re-scrape in each one's inspection tool before
   concluding that "it didn't work".
4. **Rich Results Test for the JSON-LD** that comes from the same
   frontmatter; if you still assemble the block by hand, this site's [JSON-LD
   generator](/ferramentas/gerador-json-ld) produces the format I use in
   production (its interface is in Portuguese).
5. **Lock it in CI.** A test that opens every route and checks a
   self-referencing canonical plus a matching `og:url` takes minutes to write
   and eliminates the whole class of regression. It was the difference between
   finding the bug through an external review and never reintroducing it.
