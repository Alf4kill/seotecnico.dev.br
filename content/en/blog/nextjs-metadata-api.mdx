The Metadata API is how the App Router emits the `<title>`, meta
description, canonical and Open Graph tags: a `metadata` object exported from
the route (static) or a `generateMetadata()` function (dynamic); `next/head`
no longer exists here. What tutorials don't tell you is that inheritance
between layout and page is a **shallow merge**: if the page sets any field
inside `openGraph`, the parent layout's entire object is silently dropped.
That's why your WhatsApp card comes out blank even with `og:image` set
"site-wide". In this article I'll show the two behaviors that broke this
site's Open Graph in production, and the helper that now keeps it from
happening again.

## What the Metadata API replaces (and why next/head no longer works)

In the Pages Router, meta tags were JSX: you imported `next/head` and wrote
`<meta>` tags by hand, in any component. The App Router does away with that.
The framework assembles the `<head>` from data, the `metadata` object, and
`next/head` simply isn't supported inside `app/`.

The change is better than it looks: metadata became structured, typed data
(Next's own `Metadata` type), evaluated per route and checkable at build time.
The whole [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs)
starts from that premise: anything that's data can be derived, validated and
tested.

The problem is that the same change introduced inheritance rules almost
nobody reads all the way through, and they don't work like a CSS cascade.

## Static object vs generateMetadata: when to use each

I follow one rule: **use `generateMetadata()` only when the value depends on
the route**. If the metadata is known without looking at `params` (the home
page, the tools page, the blog listing), it's a static object:

```ts
// app/ferramentas/page.tsx
export const metadata: Metadata = {
  title: "Ferramentas de SEO técnico",
  description: "…",
};
```

If the value comes from `params` or from loaded content (the classic case is
a post's frontmatter in `/blog/[slug]`), it's a function:

```ts
// app/blog/[slug]/page.tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const post = getPost(params.slug);
  return buildMetadata({ title: post.title, /* … */ });
}
```

On this site, the post route uses exactly that shape; the real
`generateMetadata` lives in `src/app/(pt)/blog/[slug]/page.tsx` and appears
in full in the helper section. What matters for now: **both approaches go
through the same merge pipeline**. Nothing below changes between static and
dynamic.

## metadataBase: the piece that makes every relative path absolute

Open Graph requires absolute URLs, and in practice so does the canonical.
`metadataBase` is the base URL, set once in the root layout, that Next uses to
resolve every relative path in the Metadata API:

```ts
// app/layout.tsx
export const metadata: Metadata = {
  metadataBase: new URL("https://seotecnico.dev.br"),
  // …
};
```

With it, `alternates.canonical: "/blog/my-post"` becomes
`https://seotecnico.dev.br/blog/my-post` in the emitted HTML. Without
`metadataBase`, relative paths don't resolve to the production domain, and a
relative `og:image` is useless to WhatsApp's or LinkedIn's scraper, which has
no base URL to resolve it against.

## A self-referencing canonical on every page

This site's rule is that **every indexable route emits a canonical pointing
to itself**; it's one of the canonicalization signals that has to tell the
same story as the [sitemap derived from the content](/en/blog/nextjs-dynamic-sitemap).
In the App Router, the field is `alternates.canonical`:

```ts
export const metadata: Metadata = {
  alternates: { canonical: "/blog/my-post" },
};
```

It looks too simple to get wrong. And that's where the detail that justifies
this article comes in: `alternates`, like `openGraph`, **isn't merged between
layout and page**. A carefully planned canonical set in the layout disappears
on the first route that declares its own `alternates`, along with everything
else that lived there.

## The merge that isn't

The official `generateMetadata` documentation describes the behavior
precisely: the metadata objects from a route's segments are merged
**shallowly**, and nested fields like `openGraph` and `robots` defined in an
earlier segment are **completely overwritten** by the last segment that
defines them. It's documented, but none of the "SEO in Next.js" tutorials I
found in Brazilian search results mention the practical consequence.

### openGraph: defining one field erases the rest

Here's what that means in practice. Take a root layout with the full set:

```ts
// app/layout.tsx
export const metadata: Metadata = {
  openGraph: {
    siteName: "SEO Técnico",
    locale: "pt_BR",
    type: "website",
    images: ["/og-default.png"],
  },
};
```

And a page that only wants to change the card's title:

```ts
// app/guia/page.tsx
export const metadata: Metadata = {
  openGraph: { title: "Guia de SEO técnico para Next.js" },
};
```

What the page emits: `og:title`, **and nothing else**. No `og:site_name`, no
`og:locale`, no `og:image`. The layout's object was replaced, not extended.
Verified empirically on this site with Next.js 16.2.6; if you're on another
version, check before assuming, but this behavior has been documented since
the App Router launched.

### alternates: the same behavior, and why the RSS feed disappears

`alternates` follows the same rule, and it holds more than you might think:
besides the canonical, `alternates.types` is where RSS feed autodiscovery
lives (`application/rss+xml`). If autodiscovery is declared in the root layout
and a page sets `alternates: { canonical: "…" }`, that page **loses the feed
tag**, with no warning, no build error, nothing.

That's why, on this site, RSS autodiscovery moved into the metadata helper
(the helper section shows where): it's the only place that guarantees it gets
emitted on every route, since relying on the layout's inheritance means
relying on inheritance that doesn't exist.

### The real case: og:url pointing to the home page across the site

On 2026-07-14, an external review of this site's production build reported
seven findings. Three of them (`og:image` missing site-wide, `og:url` pointing
to the home page on every subpage, and the guide page missing `og:locale` and
`og:site_name`) had **the same root cause**: I had treated inheritance as a
cascade.

`og:url` is the most instructive case. It was set only once, in the root
layout's `openGraph`, pointing to the home page. On routes that didn't
customize `openGraph`, the root's object was inherited whole, so every subpage
announced the home page as its card URL. On routes that did customize
`openGraph`, the opposite happened: the root's object was dropped and the page
lost its locale, site_name and image. Two symptoms that looked like opposites
were the same behavior.

The fix wasn't to "add the missing fields" page by page. It was
architectural, and it's the thesis of this article: **per-page metadata can't
be assembled ad hoc**. The comment that now sits in this site's root layout
metadata, explaining why `openGraph.url` is deliberately **not** there, is
that bug's scar preserved in the code. Since the site has one root layout per
language, that metadata comes from a function, `rootMetadata(lang)`, which
both layouts call (the repository's comments are in Portuguese; this one says
og:url is always set per page through `buildMetadata`, because a static url in
the root was inherited and pointed every subpage to the home page):

```ts
// src/lib/metadata.ts — rootMetadata(lang)
    // Sem `url` aqui: og:url é sempre definido por página via buildMetadata
    // (um url estático no root era herdado e apontava toda subpágina à home).
    openGraph: {
      type: 'website',
      locale: OG_BY_LANG[lang].locale,
      siteName: site.name,
    },
```

The full history of the seven findings is documented in the repository, in
`docs/seo-metadata-hardening.md`.

## OG images: the file convention and the config don't talk to each other

The App Router has a second way to set the Open Graph image: the file
convention. An `opengraph-image.tsx` (or `.png`) next to `page.tsx` generates
and emits that segment's `og:image` tag. Two behaviors, both verified on this
site with Next.js 16.2.6, deserve attention, and since this has changed
between Next versions, it's worth checking yours with view-source before
assuming anything.

### opengraph-image.tsx does not cascade

On 16.2.6, the file sets the image for **the segment it lives in**; it didn't
flow down to nested routes the way a layout does. An `app/opengraph-image.tsx`
didn't guarantee an `og:image` on `/blog/my-post`; for the post route to have
an image, the `app/blog/[slug]/` segment needed its own `opengraph-image.tsx`.
If you were counting on "one file in the root and the whole site gets a card",
check the HTML emitted on deeper routes.

### Page config beats the sibling file

When a segment has an `opengraph-image.tsx` **and** the page sets
`openGraph.images` in its config, the config wins and the file is ignored. On
this site that mattered for months: the helper always emits the full
`openGraph` set, which would override the per-post image generated by the
segment's file. The first fix was a flag in the helper (`fileOgImage: true`)
that left `openGraph.images` out of the config so the sibling file could win.
The flag no longer exists, and the section just after the diagram explains
why.

Spelled out, the order of precedence is: `openGraph.images` set in the page
config beats everything; without it, the segment's own `opengraph-image.tsx`
applies; and a parent segment's file does **not** apply to child routes.

### A route group changes the image URL

In September 2026 this site switched to one root layout per language, moving
the routes into two route groups, `(pt)` and `(en)`; the reason is in the
[hreflang in Next.js article](/en/blog/nextjs-hreflang). The build passed and
the whole SEO suite stayed green. Even so, the default `og:image` the helper
writes (`/opengraph-image`) and the `image` in the `Article` JSON-LD of all 11
articles started pointing to a 404.

The cause: inside a route group, Next.js adds a hashed suffix to the URL of
metadata images generated by file convention. The brand card, in
`app/(pt)/opengraph-image.tsx`, started being served at
`/opengraph-image-35ziq1`, and each post's card at
`/blog/<slug>/opengraph-image-18vth1`. In Next.js 16.2.12, the function that
builds the suffix is `getMetadataRouteSuffix`. The file name doesn't change;
what breaks is every place that hardcoded the URL based on that name.

The fix was to drop the file convention for images. Each card became a route
handler, which is served exactly at the folder's path, with no suffix (the
text is the Portuguese brand card: "live lab", "technical SEO for developers
who build modern websites"):

```tsx
// src/app/(pt)/opengraph-image/route.tsx
export const dynamic = 'force-static'

export function GET() {
  return new ImageResponse(
    (
      <OgCard
        kicker="Laboratório vivo"
        title="SEO técnico para quem desenvolve"
        highlight="sites modernos"
        subtitle="Guias práticos, ferramentas gratuitas e experimentos medidos com dados reais."
        art={{ kind: 'mark', variant: 'beam' }}
      />
    ),
    { ...OG_SIZE, fonts: ogFonts() }
  )
}
```

Without the file convention, nothing injects `og:image` automatically. The
`fileOgImage` flag no longer had a reason to exist, and the helper now emits
the image on every route, taking the post's card as a parameter. The SEO suite
got the assertion it had been missing: on every route, it downloads the
`og:image` and every image referenced in the JSON-LD, and requires a 200
response with `image/png`. Checking that the tag exists isn't enough; you have
to check that the URL actually responds.

If you use route groups and write a metadata image's URL anywhere (JSON-LD, a
helper, a share link), check the URL the build actually serves, not the file
name.

## The fix: a single metadata helper

If `openGraph` and `alternates` get replaced wholesale, the only safe
architecture is this: **no route assembles metadata by hand; every route calls
a helper that always emits the full set.** It's the opposite of what tutorials
teach (scattering partial `export const metadata` objects across routes), and
it's the same philosophy this site already applies to [JSON-LD derived from
the frontmatter](/en/blog/nextjs-json-ld): one source, one format, nothing
assembled ad hoc.

Here's the helper's contract: the file's actual header, with why it exists
and its input signature. The comments are in Portuguese; in short, they say
that when a page sets its own `openGraph` it completely replaces the root
layout's, so every page must build its metadata here and never write
`openGraph` by hand, and that the title (≤60 including the template suffix)
and description (≤155) limits are validated here and fail the build:

```ts
// src/lib/metadata.ts
// ─────────────────────────────────────────────────────────────────────────────
// buildMetadata — helper único de metadados por página (CLAUDE.md §6).
//
// Motivo de existir: no Metadata API do Next.js, quando uma página define seu
// próprio objeto `openGraph`, ele SUBSTITUI o do root layout por inteiro (não
// há merge profundo). Foi assim que /guia perdeu og:url/og:locale/og:site_name
// e as demais páginas herdaram og:url apontando para a home. Toda página deve
// montar seus metadados por aqui — nunca escrever `openGraph` à mão.
//
// Limites de title (≤60, já com o sufixo do template) e description (≤155)
// são validados aqui e estouram no build — mesma política de /lib/content.ts.
// ─────────────────────────────────────────────────────────────────────────────

const TITLE_MAX = 60
const DESCRIPTION_MAX = 155

/**
 * O que muda no Open Graph de uma página conforme o idioma dela. Uma página em
 * inglês herdando `og:locale pt_BR` e o card da marca escrito em português
 * contradiz o próprio hreflang que ela emite — daí as três coisas andarem
 * juntas, derivadas de um único `lang`, em vez de três opções independentes que
 * alguém pode esquecer de passar.
 */
const OG_BY_LANG: Record<Lang, { locale: string; image: string; alt: string }> = {
  'pt-BR': { locale: site.locale, image: '/opengraph-image', alt: OG_BRAND_ALT },
  en: { locale: 'en_US', image: '/en/opengraph-image', alt: OG_BRAND_ALT_EN },
}

export interface BuildMetadataInput {
  /** Título da página. Com `absoluteTitle`, ignora o template "%s | SEO Técnico". */
  title: string
  description: string
  /** Caminho canônico da rota, começando com '/' (ex.: '/blog/meu-post'). */
  path: string
  absoluteTitle?: boolean
  /** Presente ⇒ og:type article com published/modified time (datas do frontmatter). */
  article?: {
    publishedTime: string
    modifiedTime: string
  }
  /** Para rotas utilitárias (ex.: /busca) que não devem ser indexadas. */
  noindex?: boolean
  /**
   * Idioma da página. Só as rotas em inglês passam este campo; o padrão é o do
   * site (§10, português-primeiro). Define `og:locale` e o card OG da marca.
   */
  lang?: Lang
  /**
   * Card OG próprio da página (ex.: /blog/<slug>/opengraph-image), no lugar do
   * card da marca do idioma. As imagens são route handlers, não a file
   * convention — dentro de route groups a convenção ganha hash na URL (ver
   * app/(pt)/opengraph-image/route.tsx) —, então nada injeta og:image sozinho:
   * toda página o recebe daqui.
   */
  ogImage?: { path: string; alt: string }
}
```

And the body, where each decision in this article turns into a line of code:

```ts
// src/lib/metadata.ts (continuação)
export function buildMetadata(input: BuildMetadataInput): Metadata {
  const { title, description, path, absoluteTitle, article, noindex, ogImage } = input
  const og = OG_BY_LANG[input.lang ?? 'pt-BR']

  if (!path.startsWith('/')) {
    throw new Error(`buildMetadata: path deve começar com '/' (recebido: "${path}")`)
  }

  const renderedTitle = absoluteTitle ? title : `${title} | ${site.name}`
  if (renderedTitle.length > TITLE_MAX) {
    throw new Error(
      `buildMetadata: title renderizado com ${renderedTitle.length} chars (máx ${TITLE_MAX}) em "${path}": "${renderedTitle}"`
    )
  }
  if (description.length > DESCRIPTION_MAX) {
    throw new Error(
      `buildMetadata: description com ${description.length} chars (máx ${DESCRIPTION_MAX}) em "${path}"`
    )
  }

  // hreflang derivado do caminho, nunca declarado à mão na página: é assim que
  // a reciprocidade fica garantida por construção (ver lib/hreflang.ts). Rotas
  // sem tradução não emitem nada — um cluster de um item só é ruído.
  const languagePaths = languageAlternatePaths(path)

  return {
    title: absoluteTitle ? { absolute: title } : title,
    description,
    alternates: {
      canonical: path,
      ...(languagePaths
        ? {
            languages: Object.fromEntries(
              Object.entries(languagePaths).map(([lang, target]) => [
                lang,
                absoluteUrl(target),
              ])
            ),
          }
        : {}),
      // Autodiscovery do feed em toda página. Precisa estar aqui (e não no
      // root layout) porque `alternates` da página substitui o herdado.
      types: {
        'application/rss+xml': [{ url: '/feed.xml', title: site.name }],
      },
    },
    // og:title/og:description/twitter:* são preenchidos pelo Next.js a partir
    // de title/description — aqui só entra o que a herança não cobre.
    openGraph: {
      url: absoluteUrl(path),
      siteName: site.name,
      locale: og.locale,
      // og:image: o card da página, ou o da marca no idioma dela. Precisa estar
      // aqui: como este objeto substitui o openGraph herdado, nenhuma imagem
      // cascateia do layout para as subpáginas.
      images: [
        {
          url: ogImage?.path ?? og.image,
          width: OG_SIZE.width,
          height: OG_SIZE.height,
          type: OG_CONTENT_TYPE,
          alt: ogImage?.alt ?? og.alt,
        },
      ],
      ...(article
        ? {
            type: 'article',
            publishedTime: article.publishedTime,
            modifiedTime: article.modifiedTime,
          }
        : { type: 'website' }),
    },
    // Fail-safe de indexação (site.ts): fora de produção, noindex em tudo. Ver
    // `rootMetadata` sobre por que isto é por página e não do layout.
    robots: {
      index: indexable && !noindex,
      follow: indexable,
    },
  }
}
```

feeding the helper:

```ts
// src/app/(en)/en/blog/[slug]/page.tsx
export async function generateMetadata({ params }: PageProps): Promise<Metadata> {
  const { slug } = await params
  const post = getEnglishPostBySlug(slug)
  if (!post) return {}

  const { frontmatter } = post
  const path = `/en/blog/${frontmatter.slug}`
  return buildMetadata({
    title: frontmatter.title,
    absoluteTitle: true,
    description: frontmatter.description,
    path,
    lang: 'en',
    article: {
      publishedTime: frontmatter.datePublished,
      modifiedTime: frontmatter.dateModified,
    },
    ogImage: { path: `${path}/opengraph-image`, alt: frontmatter.title },
  })
}
```

The helper's contract matters more than its implementation: every call emits
the title, the description, a self-referencing canonical, the **complete**
`openGraph` object (locale, site_name, type, image and a url matching the
canonical), the complete `alternates` (canonical, hreflang when the route has a
translation, and RSS autodiscovery in `types`) and the `robots` directive. A
route can't emit half an `openGraph`, because no route writes `openGraph`:
they all get the finished set.

One detail worth noting: the Search Console verification token
(`verification.google`) comes in through the root layout from an environment
variable, never hardcoded; a configuration key isn't content.

## Validate at build time, not in production

The 2026-07-14 incident was caught by an external review, which means it was
caught late. The response was to move validation to the one place where it
doesn't depend on discipline: the build.

On this site, frontmatter validation checks the title and description
against limits that **throw**, not warn:

```ts
// src/lib/content.ts
const TITLE_MAX = 60
const DESCRIPTION_MAX = 155

function parseFrontmatter(data: Record<string, unknown>, file: string): PostFrontmatter {
  const required = [
    'title',
    'description',
    'slug',
    'datePublished',
    'dateModified',
    'primaryQuery',
    'lang',
  ] as const

  for (const field of required) {
    if (!data[field]) {
      throw new Error(`[content] "${file}": missing required frontmatter field "${field}"`)
    }
  }

  const title = String(data.title)
  const description = String(data.description)

  if (title.length > TITLE_MAX) {
    throw new Error(
      `[content] "${file}": title has ${title.length} chars (max ${TITLE_MAX})`
    )
  }
  if (description.length > DESCRIPTION_MAX) {
    throw new Error(
      `[content] "${file}": description has ${description.length} chars (max ${DESCRIPTION_MAX})`
    )
  }
  // …
}
```

A 61-character title doesn't produce a deploy with a truncated title in
search results; it produces a red build. It puts into practice a rule I keep
coming back to in the [guide](/en/guide/technical-seo-nextjs): CI is the only
reviewer that never forgets. Together with the Playwright assertions that check
the canonical, `og:url` and the H1 count on each page, metadata is no longer
something you eyeball after the deploy.

## How to check that it's correct

As always, close the loop with verification, in this order:

1. **View the source of a subpage, not the home page.** The home page is
   almost always right; the shallow merge breaks inner routes. Look for
   `og:url` (it has to be the page's own URL), `og:locale`, `og:site_name` and
   `og:image` with an absolute URL. If you'd rather not dig through raw HTML,
   this site's [meta tag validator](/en/tools/meta-tag-validator) reads that
   same response and returns the title, description, canonical and Open Graph
   tags with a verdict for each; it's step 1 automated, including the 60 and
   155 limits.
2. **Compare two routes: one that customizes `openGraph` and one that
   doesn't.** If the set of emitted tags differs between them, something is
   being assembled ad hoc, and the helper has a hole.
3. **The platform's debugger.** LinkedIn's and Facebook's scrapers cache what
   they fetch; after a fix, force a re-scrape in each one's inspection tool
   before concluding that "it didn't work".
4. **Rich Results Test for the JSON-LD** that comes from the same
   frontmatter; if you still put the block together by hand, this site's
   [JSON-LD generator](/en/tools/json-ld-generator) produces the format I use
   in production.
5. **Lock it in with CI.** A test that opens every route and checks for a
   self-referencing canonical plus a matching `og:url` takes minutes to write
   and wipes out this whole class of regression. It made the difference
   between finding the bug through an external review and never
   reintroducing it.
