The Next.js Metadata API is how the App Router emits `<title>`, the meta
description, the canonical, and Open Graph tags. You export either a
`metadata` object from the route (static) or a `generateMetadata()` function
(dynamic), and `next/head` no longer exists here. What tutorials leave out
is how a page inherits from its layout. It's a **shallow merge**. If a page
sets any field inside `openGraph`, Next.js silently drops the parent
layout's entire object. That's how your WhatsApp card comes up blank even
with `og:image` configured "site-wide." Below I show the two behaviors that
broke this site's Open Graph in production, and the helper that now keeps
it from happening again.

## What the Metadata API replaces (and why next/head no longer works)

In the Pages Router, meta tags were JSX. You imported `next/head` and wrote
each `<meta>` by hand, in any component.

The App Router ends that. Next builds `<head>` from data in the `metadata`
object, and `next/head` simply isn't supported inside `app/`.

I think the change is better than it looks. Metadata became structured
data. It's typed with Next's own `Metadata` type, evaluated per route, and
checkable at build time. My
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs) builds on
that premise. If something is data, you can derive it, validate it, and test
it.

But the change also came with inheritance rules almost nobody has read to
the end, and they don't work like a CSS cascade.

## Static object vs generateMetadata: when to use each

I follow one rule. Use **`generateMetadata()` only when the value depends on
the route**.

If you know the value without looking at `params`, as on the home page, the
tools page, or the blog listing, export a static object.

```ts
// app/ferramentas/page.tsx
export const metadata: Metadata = {
  title: "Ferramentas de SEO técnico",
  description: "…",
};
```

If the value comes from `params` or from loaded content, use the function.
The classic case is a post's frontmatter in `/blog/[slug]`.

```ts
// app/blog/[slug]/page.tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const post = getPost(params.slug);
  return buildMetadata({ title: post.title, /* … */ });
}
```

This site's post route has exactly this shape. Its real `generateMetadata`
lives in `src/app/(pt)/blog/[slug]/page.tsx`, and you'll see it in full in
the helper section.

What matters is that **both paths go through the same merge pipeline**.
Nothing in the rest of this article differs between static and dynamic
metadata.

## metadataBase: the piece that makes every relative path absolute

Open Graph requires absolute URLs, and in practice so does the canonical.
You define `metadataBase` once, in the root layout, and Next uses it as the
base URL to resolve every relative path in the Metadata API.

```ts
// app/layout.tsx
export const metadata: Metadata = {
  metadataBase: new URL("https://seotecnico.dev.br"),
  // …
};
```

With it in place, `alternates.canonical: "/blog/my-post"` becomes
`https://seotecnico.dev.br/blog/my-post` in the emitted HTML.

Without it, relative paths don't resolve to your production domain. A
relative `og:image` is useless to WhatsApp's or LinkedIn's scraper, which has
no base to resolve it against.

## A self-referencing canonical on every page

On this site, **every indexable route emits a canonical pointing to
itself**. It's one of the canonicalization signals that have to tell the
same story as the
[sitemap derived from the content](/en/blog/nextjs-dynamic-sitemap). In the
App Router, you set it in `alternates.canonical`.

```ts
export const metadata: Metadata = {
  alternates: { canonical: "/blog/my-post" },
};
```

It looks too simple to go wrong, and this is where the detail behind this
whole article comes in. Like `openGraph`, `alternates` **isn't merged between
layout and page**. A canonical you deliberately set in the layout disappears
on the first route that declares its own `alternates`, along with everything
else that lives there.

## The merge that isn't

Next.js documents this precisely in the official `generateMetadata`
reference. It merges the metadata objects of a route's segments
**shallowly**. When an earlier segment defines a nested field like
`openGraph` or `robots`, the last segment that defines it **overwrites it
entirely**.

So it's documented. Yet none of the "SEO in Next.js" tutorials I found in
Google's Brazilian Portuguese results (this site's home market) mention the
practical consequence.

### openGraph: defining one field erases the rest

Take a root layout with the full set:

```ts
// app/layout.tsx
export const metadata: Metadata = {
  openGraph: {
    siteName: "SEO Técnico",
    locale: "pt_BR",
    type: "website",
    images: ["/og-default.png"],
  },
};
```

And a page that only wants to change the card's title:

```ts
// app/guia/page.tsx
export const metadata: Metadata = {
  openGraph: { title: "Guia de SEO técnico para Next.js" },
};
```

On that page, Next emits `og:title` **and nothing else**. There's no
`og:site_name`, no `og:locale`, no `og:image`. Instead of extending the
layout's object, the page's object replaced it.

I verified this empirically on this site with Next.js 16.2.6. If you're on
another version, check before assuming, although this has been the
documented behavior since the App Router came out.

### alternates: the same behavior, and why the RSS feed disappears

`alternates` follows the same rule, and it holds more than it seems to.
Besides the canonical, `alternates.types` is where RSS feed autodiscovery
(`application/rss+xml`) lives.

If you declare autodiscovery in the root layout and a page defines
`alternates: { canonical: "…" }`, that page **loses the feed tag**. You get
no warning, no build error, nothing.

That's why I moved this site's RSS autodiscovery into the metadata helper
(the helper section shows where). It's the only place that guarantees every
route emits the tag again. Leaving it to the layout means trusting an
inheritance that doesn't exist.

### The real case: og:url pointing to the home page across the site

On July 14, 2026, an external review of this site in production reported
seven findings. Three of them had **the same root cause**. `og:image` was
missing site-wide, `og:url` pointed to the home page on every subpage, and
the guide page had no `og:locale` or `og:site_name`, all because I had
treated inheritance as a cascade.

`og:url` is the most instructive case. I'd defined it once, in the root
layout's `openGraph`, pointing to the home page. Routes that didn't
customize `openGraph` inherited the root object whole, so every subpage
announced the home page as its card URL. Routes that did customize
`openGraph` got the opposite. Next dropped the root object, and those pages
lost their locale, site name, and image. Two symptoms that look like
opposites come from one behavior.

The fix wasn't to "add the missing fields" page by page. It was
architectural, and it's this article's thesis. **Per-page metadata can't be
assembled ad hoc.**

On this site, the root layout's metadata now carries a comment explaining
why `openGraph.url` is deliberately **not** there. It's a scar from the bug,
preserved in code. Because the site has one root layout per language, both
layouts call a function, `rootMetadata(lang)`, that returns this metadata.
Its comments are in Portuguese. They say og:url is always set per page
through `buildMetadata`, because a static url in the root was inherited and
pointed every subpage to the home page.

```ts
// src/lib/metadata.ts — rootMetadata(lang)
    // Sem `url` aqui: og:url é sempre definido por página via buildMetadata
    // (um url estático no root era herdado e apontava toda subpágina à home).
    openGraph: {
      type: 'website',
      locale: OG_BY_LANG[lang].locale,
      siteName: site.name,
    },
```

You'll find the full history of the seven findings in
`docs/seo-metadata-hardening.md`, in the repository.

## OG images: the file convention and the config don't talk to each other

You can also set the OG image through the App Router's file convention. Put
an `opengraph-image.tsx` (or `.png`) next to `page.tsx`, and Next generates
the image and emits that segment's `og:image` tag.

Two behaviors deserve attention. I verified both on this site with Next.js
16.2.6, but they've already varied between Next versions, so check yours
with view-source before assuming.

### opengraph-image.tsx does not cascade

On 16.2.6, an `opengraph-image.tsx` applies its image to **the segment where
it lives**. On this site, it didn't flow down to nested routes the way a
layout does. A file at `app/opengraph-image.tsx` didn't guarantee an
`og:image` on `/blog/my-post`. For the post route to get one, the
`app/blog/[slug]/` segment needed its own `opengraph-image.tsx`.

If you were counting on "one file in the root and the whole site gets a
card," check the emitted HTML on deep routes.

### Page config beats the sibling file

If the same segment has an `opengraph-image.tsx` **and** the page defines
`openGraph.images` in its config, the config wins and the file is ignored.

On this site, that mattered for months. My helper always emits a full
`openGraph` set, so it would suppress the image that each post's segment
file generates. My first fix was a helper flag, `fileOgImage: true`, that
left `openGraph.images` out of the config so the sibling file would win.

That flag no longer exists. The section after the diagram explains why.

In order of precedence:

1. `openGraph.images` in the page config beats everything.
2. Without it, the segment's own `opengraph-image.tsx` applies.
3. A parent segment's file does **not** apply to child routes.

### A route group changes the image URL

In September 2026, I moved this site to one root layout per language, which
put the routes into two route groups, `(pt)` and `(en)`. My
[article on hreflang in Next.js](/en/blog/nextjs-hreflang) explains why.

The build passed, and the whole SEO suite stayed green. Even so, two kinds
of URL started pointing to a 404: the default `og:image` the helper writes
(`/opengraph-image`) and the `image` in the `Article` JSON-LD of the 11
articles.

Inside a route group, Next.js appends a hash suffix to the URL of any
metadata image the file convention generates. This site's brand card, then in
`app/(pt)/opengraph-image.tsx`, was served at `/opengraph-image-35ziq1`.
Each post's card was served at `/blog/<slug>/opengraph-image-18vth1`. In
Next.js 16.2.12, `getMetadataRouteSuffix` builds that suffix. The file name
doesn't change. What breaks is every URL written by hand that counted on
that name.

I fixed it by dropping the file convention for images. Each card became a
route handler, served exactly at its folder's path, with no suffix. The code
below renders the Portuguese brand card. Its kicker and title translate to
"live lab" and "technical SEO for developers who build modern websites."

```tsx
// src/app/(pt)/opengraph-image/route.tsx
export const dynamic = 'force-static'

export function GET() {
  return new ImageResponse(
    (
      <OgCard
        kicker="Laboratório vivo"
        title="SEO técnico para quem desenvolve"
        highlight="sites modernos"
        subtitle="Guias práticos, ferramentas gratuitas e experimentos medidos com dados reais."
        art={{ kind: 'mark', variant: 'beam' }}
      />
    ),
    { ...OG_SIZE, fonts: ogFonts() }
  )
}
```

Without the file convention, nothing injects `og:image` on its own. That
left the `fileOgImage` flag with no reason to exist, and the helper now
emits the image on every route, taking the post's card as a parameter.

My SEO suite also gained the assertion it was missing. On every route, it
downloads `og:image` and every image cited in the JSON-LD, and it requires a
200 response with `image/png`. Checking that a tag exists isn't enough. You
have to check that its URL responds.

If you use route groups and write a metadata image's URL anywhere (JSON-LD,
a helper, a share link), check the URL the build actually serves, not the
file name.

## The fix: a single metadata helper

If `openGraph` and `alternates` get replaced wholesale, only one
architecture is safe. **No route assembles metadata by hand. Every route
calls a helper that always emits the complete set.**

Tutorials teach the opposite. They scatter partial `export const metadata`
declarations across routes. A single helper is the same approach this site
already takes with
[JSON-LD derived from the frontmatter](/en/blog/nextjs-json-ld): one source,
one format, zero ad hoc assembly.

Here's the helper's contract, taken from the real file header. It says why
the helper exists and what it takes as input. The comments are in
Portuguese. They explain that a page that sets its own `openGraph` replaces
the root layout's entirely, so every page has to build its metadata here and
never write `openGraph` by hand. They also note that the helper checks the
title limit (≤60, including the template suffix) and the description limit
(≤155), and that a violation fails the build.

```ts
// src/lib/metadata.ts
// ─────────────────────────────────────────────────────────────────────────────
// buildMetadata — helper único de metadados por página (CLAUDE.md §6).
//
// Motivo de existir: no Metadata API do Next.js, quando uma página define seu
// próprio objeto `openGraph`, ele SUBSTITUI o do root layout por inteiro (não
// há merge profundo). Foi assim que /guia perdeu og:url/og:locale/og:site_name
// e as demais páginas herdaram og:url apontando para a home. Toda página deve
// montar seus metadados por aqui — nunca escrever `openGraph` à mão.
//
// Limites de title (≤60, já com o sufixo do template) e description (≤155)
// são validados aqui e estouram no build — mesma política de /lib/content.ts.
// ─────────────────────────────────────────────────────────────────────────────

const TITLE_MAX = 60
const DESCRIPTION_MAX = 155

/**
 * O que muda no Open Graph de uma página conforme o idioma dela. Uma página em
 * inglês herdando `og:locale pt_BR` e o card da marca escrito em português
 * contradiz o próprio hreflang que ela emite — daí as três coisas andarem
 * juntas, derivadas de um único `lang`, em vez de três opções independentes que
 * alguém pode esquecer de passar.
 */
const OG_BY_LANG: Record<Lang, { locale: string; image: string; alt: string }> = {
  'pt-BR': { locale: site.locale, image: '/opengraph-image', alt: OG_BRAND_ALT },
  en: { locale: 'en_US', image: '/en/opengraph-image', alt: OG_BRAND_ALT_EN },
}

export interface BuildMetadataInput {
  /** Título da página. Com `absoluteTitle`, ignora o template "%s | SEO Técnico". */
  title: string
  description: string
  /** Caminho canônico da rota, começando com '/' (ex.: '/blog/meu-post'). */
  path: string
  absoluteTitle?: boolean
  /** Presente ⇒ og:type article com published/modified time (datas do frontmatter). */
  article?: {
    publishedTime: string
    modifiedTime: string
  }
  /** Para rotas utilitárias (ex.: /busca) que não devem ser indexadas. */
  noindex?: boolean
  /**
   * Idioma da página. Só as rotas em inglês passam este campo; o padrão é o do
   * site (§10, português-primeiro). Define `og:locale` e o card OG da marca.
   */
  lang?: Lang
  /**
   * Card OG próprio da página (ex.: /blog/<slug>/opengraph-image), no lugar do
   * card da marca do idioma. As imagens são route handlers, não a file
   * convention — dentro de route groups a convenção ganha hash na URL (ver
   * app/(pt)/opengraph-image/route.tsx) —, então nada injeta og:image sozinho:
   * toda página o recebe daqui.
   */
  ogImage?: { path: string; alt: string }
}
```

Next comes the body, where each decision in this article turns into a line
of code.

```ts
// src/lib/metadata.ts (continuação)
export function buildMetadata(input: BuildMetadataInput): Metadata {
  const { title, description, path, absoluteTitle, article, noindex, ogImage } = input
  const og = OG_BY_LANG[input.lang ?? 'pt-BR']

  if (!path.startsWith('/')) {
    throw new Error(`buildMetadata: path deve começar com '/' (recebido: "${path}")`)
  }

  const renderedTitle = absoluteTitle ? title : `${title} | ${site.name}`
  if (renderedTitle.length > TITLE_MAX) {
    throw new Error(
      `buildMetadata: title renderizado com ${renderedTitle.length} chars (máx ${TITLE_MAX}) em "${path}": "${renderedTitle}"`
    )
  }
  if (description.length > DESCRIPTION_MAX) {
    throw new Error(
      `buildMetadata: description com ${description.length} chars (máx ${DESCRIPTION_MAX}) em "${path}"`
    )
  }

  // hreflang derivado do caminho, nunca declarado à mão na página: é assim que
  // a reciprocidade fica garantida por construção (ver lib/hreflang.ts). Rotas
  // sem tradução não emitem nada — um cluster de um item só é ruído.
  const languagePaths = languageAlternatePaths(path)

  return {
    title: absoluteTitle ? { absolute: title } : title,
    description,
    alternates: {
      canonical: path,
      ...(languagePaths
        ? {
            languages: Object.fromEntries(
              Object.entries(languagePaths).map(([lang, target]) => [
                lang,
                absoluteUrl(target),
              ])
            ),
          }
        : {}),
      // Autodiscovery do feed em toda página. Precisa estar aqui (e não no
      // root layout) porque `alternates` da página substitui o herdado.
      types: {
        'application/rss+xml': [{ url: '/feed.xml', title: site.name }],
      },
    },
    // og:title/og:description/twitter:* são preenchidos pelo Next.js a partir
    // de title/description — aqui só entra o que a herança não cobre.
    openGraph: {
      url: absoluteUrl(path),
      siteName: site.name,
      locale: og.locale,
      // og:image: o card da página, ou o da marca no idioma dela. Precisa estar
      // aqui: como este objeto substitui o openGraph herdado, nenhuma imagem
      // cascateia do layout para as subpáginas.
      images: [
        {
          url: ogImage?.path ?? og.image,
          width: OG_SIZE.width,
          height: OG_SIZE.height,
          type: OG_CONTENT_TYPE,
          alt: ogImage?.alt ?? og.alt,
        },
      ],
      ...(article
        ? {
            type: 'article',
            publishedTime: article.publishedTime,
            modifiedTime: article.modifiedTime,
          }
        : { type: 'website' }),
    },
    // Fail-safe de indexação (site.ts): fora de produção, noindex em tudo. Ver
    // `rootMetadata` sobre por que isto é por página e não do layout.
    robots: {
      index: indexable && !noindex,
      follow: indexable,
    },
  }
}
```

```ts
// src/app/(en)/en/blog/[slug]/page.tsx
export async function generateMetadata({ params }: PageProps): Promise<Metadata> {
  const { slug } = await params
  const post = getEnglishPostBySlug(slug)
  if (!post) return {}

  const { frontmatter } = post
  const path = `/en/blog/${frontmatter.slug}`
  return buildMetadata({
    title: frontmatter.title,
    absoluteTitle: true,
    description: frontmatter.description,
    path,
    lang: 'en',
    article: {
      publishedTime: frontmatter.datePublished,
      modifiedTime: frontmatter.dateModified,
    },
    ogImage: { path: `${path}/opengraph-image`, alt: frontmatter.title },
  })
}
```

What matters is the contract, more than the implementation. Every call
emits a title, a description, a self-referencing canonical, a **complete**
`openGraph` object (locale, site_name, type, image, and a url that matches
the canonical), complete `alternates` (canonical, hreflang when the route
has a translation, and RSS autodiscovery in `types`), and a `robots`
directive. A route can't emit half an `openGraph`, because no route
writes `openGraph`. They all receive the finished set.

One more detail. The root layout reads the Search Console verification
token (`verification.google`) from an environment variable. It's never
hardcoded. A configuration key isn't content.

## Validate at build time, not in production

An external review found the July 14 incident, which means I found out
late. I responded by moving validation to the only place where it doesn't depend on
discipline, the build.

On this site, the frontmatter schema checks title and description against
limits that **throw**, not warn.

```ts
// src/lib/content.ts
const TITLE_MAX = 60
const DESCRIPTION_MAX = 155

function parseFrontmatter(data: Record<string, unknown>, file: string): PostFrontmatter {
  const required = [
    'title',
    'description',
    'slug',
    'datePublished',
    'dateModified',
    'primaryQuery',
    'lang',
  ] as const

  for (const field of required) {
    if (!data[field]) {
      throw new Error(`[content] "${file}": missing required frontmatter field "${field}"`)
    }
  }

  const title = String(data.title)
  const description = String(data.description)

  if (title.length > TITLE_MAX) {
    throw new Error(
      `[content] "${file}": title has ${title.length} chars (max ${TITLE_MAX})`
    )
  }
  if (description.length > DESCRIPTION_MAX) {
    throw new Error(
      `[content] "${file}": description has ${description.length} chars (max ${DESCRIPTION_MAX})`
    )
  }
  // …
}
```

A 61-character title doesn't reach production and get truncated in the
SERP. It turns the build red. I keep repeating this rule in the
[guide](/en/guide/technical-seo-nextjs): CI is the only reviewer that
doesn't forget.

Add the Playwright assertions that check canonical, `og:url`, and H1 count
on every page, and metadata is no longer something you eyeball after a
deploy.

## How to check that it's correct

As always, close the loop by verifying, in this order:

1. **View-source on a subpage, not the home page.** The home page is almost
   always fine. It's the inner routes that the shallow merge breaks. Look for
   `og:url` (it must be the page's own URL), `og:locale`, `og:site_name`,
   and an `og:image` with an absolute URL. If you'd rather not dig through
   raw HTML, this site's [meta tag validator](/en/tools/meta-tag-validator)
   reads that same response and returns the title, description, canonical,
   and Open Graph tags with a verdict for each. That's step 1 automated,
   including the 60 and 155 limits.
2. **Compare two routes, one that customizes `openGraph` and one that
   doesn't.** If the emitted tag sets differ, something is being assembled
   ad hoc, and the helper has a hole.
3. **Use the platform's debugger.** LinkedIn's and Facebook's scrapers keep
   a cache. After a fix, force a re-scrape in each one's inspection tool
   before you conclude "it didn't work."
4. **Run the Rich Results Test on the JSON-LD** that comes from the same
   frontmatter. If you still assemble that block by hand, this site's
   [JSON-LD generator](/en/tools/json-ld-generator) produces the format I
   use in production.
5. **Lock it in CI.** A test that opens every route and checks for a
   self-referencing canonical with a matching `og:url` takes minutes to
   write and eliminates the whole class of regression. It made the
   difference between finding the bug through an external review and never
   reintroducing it.
