To add JSON-LD in Next.js with the App Router, render a
`<script type="application/ld+json">` tag inside a Server Component (in the
route's `page.tsx` or in `layout.tsx`, depending on the schema's scope) and
put the data object inside it with `JSON.stringify`. It doesn't go in
`<Head>`, and it doesn't need `next/script`. That's Next.js's own official
recommendation. The rest of this article covers where each schema type should
live, how to derive it from your source of truth instead of writing it by
hand, and how to keep it from silently breaking later on.

This is the second track of the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs): not "how to paste a script", but
what a structured data implementation looks like as production code, derived
from the content and locked in by an automated test. Each section below is an
architecture decision: where the schema comes from, what feeds it, and what
happens when it stops making sense.

One caveat has to come before any code, because half of what's written about
this in Portuguese gets it wrong: **structured data is not a direct ranking
factor.** JSON-LD won't push your position up. What it does is make the page
eligible for rich results (a breadcrumb trail instead of the URL, the
article's author and dates) and help search engines understand how the page is
structured. The gain is in eligibility and presentation, not rankings.

## Where JSON-LD lives in the App Router

JSON-LD has to be in the HTML Googlebot reads on its first visit. That one
rule drives the whole architecture. In the App Router, the natural way to do
that is to render the script in a Server Component, which is the default for
any `page.tsx` or `layout.tsx` without `"use client"` at the top.

Here's the mechanism. Googlebot reads pages in two waves. In the first, it
processes the HTML that comes from the server. Only later, in a separate
rendering queue, does it run the JavaScript and look at the final DOM. If your
JSON-LD block only comes into existence after React hydrates on the client,
there's a window where the crawler sees the initial HTML with no schema at
all, and the second-wave render can take a while.

There's a subtlety here that almost every article on the topic gets wrong.
The problem is **not** a file having `"use client"` at the top. A client
component is still rendered on the server: its HTML ships in the initial
response, schema script included. What breaks is schema that only gets
**created** after hydration, assembled inside a `useEffect` or derived from
state that only exists in the browser. That schema isn't in the initial HTML,
because it didn't exist yet when the server responded.

components are pure Server Components; the `FAQPage` block lives inside the
FAQ component, which is a client component because of the accordion, and the
script still ships in the initial HTML, because the questions come from the
frontmatter, not from state. It's the case that proves the rule: what matters
is where the data comes from.

## The base component: a `<script>` and nothing else

The component that emits the schema is deliberately dumb: it takes an object,
serializes it with `JSON.stringify` and injects the result into a `<script>`
tag. No state, no effects, no `next/script`. That last point is intentional,
and the Next.js documentation explains why: `next/script` is for loading and
running JavaScript, and JSON-LD is data, not executable code, so the native
`<script type="application/ld+json">` tag is the right choice.

This is the pattern running in production on this site; every schema on the
site goes through these few lines:

```tsx
// src/components/seo/JsonLd.tsx
function JsonLdScript({ schema }: { schema: Record<string, unknown> }) {
  return (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: JSON.stringify(schema).replace(/</g, '\\u003c') }}
    />
  )
}
```

`dangerouslySetInnerHTML` sounds scary, but here it's the right tool. It's
how you inject the schema text without React escaping the quotes in the JSON.
The "dangerous" in the name is a legitimate reminder, though, and worth
taking seriously: the Next.js documentation warns that `JSON.stringify`
doesn't sanitize strings used in XSS attacks, and recommends replacing the
less-than character with its Unicode escape before injecting. That's exactly
what the `.replace()` does: inside a JSON string, `\u003c` is the escaped form
of the `<` character. The parser reads the same data, but no text in the
schema can ever write a literal `</script>` that closes the tag in the middle
of the HTML.

The question that tells you how big the risk is: where does the schema's data
come from? If it comes from user input, this sanitization isn't optional. On
this site, every object is built from the content's own frontmatter and from
repository constants, sources I control, never text typed by a third party.
In other words, here the escape doesn't fix a vulnerability; it removes the
need for editorial discipline. Without it, the day an FAQ answer mentions an
HTML tag becomes a broken-HTML bug. It's one line of code so I never have to
remember that, which is why it lives in the component rather than in a code
review checklist.

With that component in place, the work for each schema type comes down to
building the right object and passing it in. The next sections do exactly
that, one type at a time.

## `Article`: schema that comes from the frontmatter, not your keyboard

The most common mistake with `Article` is writing the object by hand in every
post. That guarantees that sooner or later the schema's `headline` will drift
from the page's `<title>`, or `dateModified` will be stuck on a date that no
longer matches the last edit. Hand-written schema rots.

The solution is to derive `Article` from the same source that generates the
page. On this site, every blog post and the guide have a frontmatter block at
the top of the MDX file, and the `Article` component takes that whole
frontmatter instead of individually typed values (the comments are in
Portuguese: they say `abstract` is the frontmatter's short answer, the same
sentence the reader sees at the top of the page, and that the page's single
target query is also its subject, so both are declared from the same source):

```tsx
// src/components/seo/JsonLd.tsx
export function ArticleJsonLd({
  frontmatter,
  path,
  imagePath,
}: {
  frontmatter: PostFrontmatter
  /** Path da página. Default: /blog/{slug}. */
  path?: string
  /** Rota da imagem OG da página. Default: o card da marca. */
  imagePath?: string
}) {
  const url = `${site.url}${path ?? `/blog/${frontmatter.slug}`}`

  const schema = {
    '@context': 'https://schema.org',
    '@type': 'Article',
    '@id': `${url}#article`,
    headline: frontmatter.title,
    description: frontmatter.description,
    // `abstract` é a resposta curta do frontmatter: a mesma frase que o leitor
    // vê no topo da página, disponível como dado para quem extrai.
    ...(frontmatter.tldr ? { abstract: frontmatter.tldr } : {}),
    datePublished: frontmatter.datePublished,
    dateModified: frontmatter.dateModified,
    inLanguage: frontmatter.lang,
    url,
    mainEntityOfPage: { '@type': 'WebPage', '@id': url },
    isPartOf: { '@id': WEBSITE_ID },
    image: `${site.url}${imagePath ?? '/opengraph-image'}`,
    // A ÚNICA query que a página persegue (CLAUDE.md §10) é também o assunto
    // dela — declarar as duas coisas pela mesma fonte impede que divirjam.
    keywords: frontmatter.primaryQuery,
    about: { '@type': 'Thing', name: frontmatter.primaryQuery },
    author: personSchema(),
    publisher: organizationSchema(),
  }
  return <JsonLdScript schema={schema} />
}
```

The mapping is direct, and that's the whole point: `headline` comes from the
frontmatter's `title`, `description` from `description`, `abstract` from the
short answer (`tldr`) when there is one, the dates from the dates,
`inLanguage` from `lang`, and `keywords` and `about` from `primaryQuery`. The
`url`, the `@id` and `mainEntityOfPage` come from the canonical URL, built
from the site's base URL plus the route's path. `author` and `publisher` are
never typed in: they come from shared functions that other pages use too. I
wrote the frontmatter once, and the schema is derived from it. There's no
second place for the date to drift, because there's only one place it's
written.

That principle runs through the rest of the article: **schema isn't written
per page; it's derived from the source of truth.** If you have to update the
content in one place and the schema in another, it's only a matter of time
before they disagree, and a schema that disagrees with the page is worse than
no schema, because it describes a page that doesn't exist.

Note that `Article` still produces a rich result: with a `headline`, dates and
author and publisher entities, it makes the page eligible to show the author
and the publication and modification dates in search results. Unlike FAQ,
which comes up below, here the effort still pays off visually in search.

## `BreadcrumbList`: the schema almost everyone forgets

`BreadcrumbList` is the best value-for-effort schema that most sites ignore.
It describes the navigation trail to the page (Home › Blog › post title), and
it's one of the rich results that's still fully active: in search results, it
replaces the raw URL with that readable path. It's a small amount of work with
a concrete visual payoff, which is why it's worth doing systematically.

"Systematically" here means not writing the breadcrumb page by page. It's
built from the route's hierarchy, the same way `Article` is derived from the
frontmatter:

```tsx
// src/components/seo/JsonLd.tsx
export function BreadcrumbJsonLd({ items }: { items: BreadcrumbItem[] }) {
  const schema = {
    '@context': 'https://schema.org',
    '@type': 'BreadcrumbList',
    itemListElement: items.map((item, i) => ({
      '@type': 'ListItem',
      position: i + 1,
      name: item.name,
      item: `${site.url}${item.path}`,
    })),
  }
  return <JsonLdScript schema={schema} />
}
```

Google requires two things, and the mapping above handles both: each
`ListItem` needs a sequential `position` starting at 1, and it needs a `name`.
The `item` (the URL for that level) is what makes each step in the trail
clickable. A `BreadcrumbList` needs at least two levels to make sense; a
single item isn't a trail. That's the same rule this site's [JSON-LD
generator](/en/tools/json-ld-generator) enforces before it lets you generate a
breadcrumb: with fewer than two levels, it refuses.

## `FAQPage`: what changed in May 2026 and why I still use it

This is where most Portuguese-language content is out of date, so I'll be
blunt: **since May 7, 2026, Google no longer shows the FAQ rich result.** The
dropdown of questions and answers that used to expand under your search
result doesn't appear anymore, for any site. This isn't a restriction to
certain categories, like in 2023, when the feature was limited to government
and health sites. This time the feature is gone entirely, and on June 15, 2026
Google removed the feature's documentation as well.

That has an awkward practical consequence: much of what you'll find searching
for "FAQPage schema" today describes a feature that no longer exists, and the
official page that would set the record straight isn't there anymore. In
structured data, checking a source's date has stopped being pedantic.

Two wrong reactions went around when the announcement came out, and both are
worth debunking. The first: "schema is dead". It isn't. `FAQPage` is still a
valid schema.org type, the markup doesn't cause errors or harm the page, and
other types like `Article` and `BreadcrumbList` still produce rich results as
usual. The second: "so FAQPage is now essential for AI". Not that either. In
its official guide to optimizing for generative AI search, published in May
2026, Google says no special markup or schema.org is required to appear in AI
Overviews or AI Mode. Schema is still useful for traditional rich results
(which in turn feed AI answers indirectly), but it isn't a direct lever for
getting cited by AI. Anyone who traded "it'll become a rich result" for "it'll
get cited by AI" just swapped one unfounded promise for another.

So why do I keep `FAQPage` on this site if the rich result is gone? For an
architectural reason: here, the FAQ visible on the page and the structured
FAQPage come from the same source. There's no hand-written `FAQPage`
component. There's a `faq` array in the article's frontmatter (the same
questions and answers you'll see at the end of this page) and a single
component that reads that array to render two things at once: the visible
accordion and the matching JSON-LD.

```tsx
// src/components/sections/FaqSection.tsx
<script
  type="application/ld+json"
  dangerouslySetInnerHTML={{
    __html: JSON.stringify({
      '@context': 'https://schema.org',
      '@type': 'FAQPage',
      mainEntity: items.map(({ question, answer }) => ({
        '@type': 'Question',
        name: question,
        acceptedAnswer: { '@type': 'Answer', text: answer },
      })),
    }).replace(/</g, '\\u003c'),
  }}
/>
```

The `items` in that snippet is exactly the same array the accordion loops
over to draw the questions on screen, a few lines up in the same file. Since
there's a single source, the marginal cost of keeping `FAQPage` is
practically zero: I write the FAQ for readers anyway, and the schema comes
from the same array with no extra work. It also satisfies, by design, the
requirement Google always had for FAQPage: the schema's content has to be
visible on the page. It can't drift, because it's literally the same data.

That matters more than it seems, because automated validation doesn't catch
drift. The Rich Results Test, back when it still validated FAQ, never compared
the JSON-LD with the visible text: it checked syntax and properties, not
whether the schema matched what users see. A schema that declares one answer
on a page that shows another passes validation and still violates the policy.
Deriving both from the same source eliminates that kind of error before it can
happen.

So the recommendation isn't "add FAQPage to get the rich result"; that advice
died in May. It's this: if you have a genuine FAQ on the page, answering real
questions, marking it up with FAQPage costs little and keeps the page well
described for the engines that still read the markup. If your FAQ only
existed to chase the dropdown in search results, now's the time to rethink it.

## `Person` and `Organization`: the author entity and E-E-A-T

The `author` in the `Article` above isn't just a name in a string. It's a
reference to a single `Person` entity, built once from the site's central
config and reused by every article:

```tsx
// src/components/seo/JsonLd.tsx
function personSchema() {
  const sameAs = [site.author.github, site.author.linkedin].filter(Boolean)
  return {
    '@type': 'Person',
    name: site.author.name,
    jobTitle: site.author.jobTitle,
    url: site.url,
    ...(sameAs.length > 0 ? { sameAs } : {}),
  }
}
```

The field doing the heavy lifting is `sameAs`: it links the site's `Person`
entity to the external profiles (GitHub, LinkedIn) that corroborate who the
author is. It's not a claim that the person exists; it's a set of anchors to
other verifiable places the same person shows up online. That's how
structured data plays into E-E-A-T: not by claiming expertise, but by tying
authorship to a traceable identity.

Notice the `filter(Boolean)` and the conditional spread: if a profile isn't
filled in, the field simply doesn't make it into the schema. That rule applies
to every type. An empty field is worse than a missing one, because it
describes the page with information that doesn't exist. The site's generator
follows the same policy: blank fields are left out of the output instead of
becoming empty strings.

## `SoftwareApplication` and tool pages

Not every page is an article. A page that offers an interactive tool is
described by the `SoftwareApplication` type, not `Article`. On this site, tool
pages emit that schema with the fields that describe what the tool is:

```json
{
  "@context": "https://schema.org",
  "@type": "SoftwareApplication",
  "applicationCategory": "DeveloperApplication",
  "operatingSystem": "Web",
  "isAccessibleForFree": true,
  "offers": { "@type": "Offer", "price": "0", "priceCurrency": "BRL" }
}
```

The values aren't decoration: `applicationCategory` says it's a developer
tool, `operatingSystem` says it runs in the browser, and `isAccessibleForFree`
plus an `offers` with a price of zero declare that it's free. It's an honest
description of a tool that runs entirely on the client and costs nothing. The
general principle applies to every type: the `@type` you choose has to match
what the page actually is. Marking a tool page as `Article`, or an article as
`SoftwareApplication`, is the kind of inconsistency Google treats as a bad
signal.

## Page vs. layout: where each schema should be rendered

With the types defined, one architecture decision remains that trips up a lot
of people: does the schema go in the route's `page.tsx` or in `layout.tsx`?
The answer isn't a matter of style; it follows directly from asking "where
does this schema's data come from?".

Schema that depends on a route's specific content goes in `page.tsx`. A
post's `Article` and `BreadcrumbList` are like that: the data behind them
(title, dates, trail) only exists at that page's level. You can't build them
in the layout, because the layout doesn't know about the post.

Schema that's stable across a whole section can live in the corresponding
`layout.tsx`. A `WebSite` or an `Organization` that applies to the entire site
doesn't need to be rebuilt on every route. The rule that settles every case:
**render each schema at the level where the data behind it actually lives.**
If the data belongs to the page, the schema belongs to the page. If the data
belongs to the section, the schema belongs to the layout.

The same applies to the most dynamic case of all, a route with a parameter
like `/blog/[slug]`. The schema isn't written for each slug; it's derived,
inside the route's async function, from the same data that generates the
page. You fetch the content using the parameter, build the schema object from
those fields, and render the script component in the return. A dynamic
route's schema is dynamic for the same reason the page is: both come from the
same fetch.

## How to validate: which tool for which schema

Validating structured data now requires a distinction that's new this year:
not every tool validates every schema type, because FAQ is no longer in
Google's rich results catalog. Your routine depends on which `@type` you're
checking.

For the types that still produce rich results (`Article`, `BreadcrumbList`,
`SoftwareApplication`), Google's [Rich Results
Test](https://search.google.com/test/rich-results) is still the right tool.
Paste the URL, not the code: with the URL, the tool renders the page the way
Google sees it, which matters precisely when anything in your schema depends
on rendering. Then check two things. Errors block eligibility: a missing
required property, an `@type` Google doesn't recognize, JSON that doesn't
parse. Warnings don't. They point to missing recommended properties, and the
rich result still works without them, just with less detail. Fix every error;
treat warnings as optional improvements.

For `FAQPage`, the routine has changed. With no FAQ rich result, there's no
eligibility to test; what still makes sense is validating the schema's
**syntax**, and for that the tool is the [schema.org
validator](https://validator.schema.org/), which checks whether the markup
follows the vocabulary regardless of whether Google produces any visual
feature from it.

Once you've published, Search Console handles ongoing monitoring. The
enhancement reports show, at site scale, when a schema type breaks on many
pages at once: a template change that knocks out `Article` on two hundred
posts shows up there as a spike in invalid items that no single-URL test
would catch. It's the tool for monitoring over time, complementing the
one-off test before publishing. One honest caveat: this site is new, so I
don't have enhancement report history to show yet. What I'm describing is the
tool's role, not a result of mine.

## How to keep it from breaking: the test that runs in my CI

Validating before publishing takes care of launch day. It doesn't take care
of month three, when someone (maybe you) touches a template and knocks out the
schema on every page without noticing. The way to make sure that doesn't slip
by is to turn validation into an automated test that blocks deploys.

The suite runs on every pull request in GitHub Actions and blocks the merge
if it fails. What makes it robust is that the routes it tests aren't listed
by hand: they come from `sitemap.ts`, which in turn derives from every post in
`/content`. In practice, **a new article joins the suite the moment its file is
committed**, including the one you're reading now. I don't have to remember
to add the post to the test; the test finds the post on its own.

For each route, the suite checks a set of invariants. There's exactly one
non-empty `<h1>`. The `<title>` is present and at most 60 characters. The meta
description is present and at most 155. The canonical is self-referencing.
And, most relevant here: **every `application/ld+json` block on the page
passes through `JSON.parse` without errors**, and the set of `@type` values
expected for that kind of route is present.

```ts
// tests/seo/seo.spec.ts — trecho da suíte de regressão de SEO
const jsonLdBlocks = await page
  .locator('script[type="application/ld+json"]')
  .allTextContents()

const foundTypes: string[] = []
for (const raw of jsonLdBlocks) {
  let parsed: unknown
  try {
    parsed = JSON.parse(raw)
  } catch {
    throw new Error(`JSON-LD block on ${route} is not valid JSON:\n${raw}`)
  }
  for (const node of Array.isArray(parsed) ? parsed : [parsed]) {
    const type = (node as { '@type'?: string })['@type']
    if (type) foundTypes.push(type)
  }
}

for (const type of expectedJsonLdTypes(route)) {
  expect.soft(foundTypes, `JSON-LD @type "${type}" on ${route}`).toContain(type)
}
```

`expectedJsonLdTypes` is the map from the diagram above, written as a
function: a blog route must have `Article` and `BreadcrumbList`, plus
`FAQPage` if and only if that post's frontmatter has a `faq` array; a tool
route must have `SoftwareApplication` and `BreadcrumbList`, and so on. Which
leads to the sentence that sums up why the test exists: **if a JSON-LD block
stops parsing, or an `@type` disappears from a template, the test fails and
the merge is blocked.**

There's a second layer, in the build itself. The frontmatter is validated when
the page is built: if a required field is missing, or the `title` goes over 60
characters, or the `description` over 155, the build breaks. It's not a
warning you can ignore; it's a failure that stops generation. Between a build
that rejects invalid frontmatter and a suite that rejects invalid schema, the
two places where these errors usually sneak in are both closed off.

## What not to chase

I'll close with an honest reality check, because half the value of a
technical article is saying what not to do. Don't chase rankings with
JSON-LD: it isn't a ranking factor, and no amount of schema will change that.
Don't add `FAQPage` expecting the dropdown in search results; it was
discontinued in May 2026 and won't come back, however well-intentioned your
markup is. Don't treat schema as a shortcut to getting cited by AI; Google
itself says no special markup is required for that. And don't write schema by
hand page by page: what's derived from the source of truth doesn't drift,
while what's typed twice does.

What structured data actually delivers is more modest and more real: it
makes the page eligible for the rich results that still exist, describes the
content's structure for whatever reads the markup, and, if you lock it in with
a test, stays correct over time without anyone having to watch it. That wraps
up the second track of the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs); the other topics follow the same
logic of deriving from content instead of writing by hand. When you need to
generate a quick schema for a specific case, the [JSON-LD
generator](/en/tools/json-ld-generator) produces the object and the Next.js
component ready to use, following the same Server Component pattern described
here. This article is the architecture; the tool is the shortcut for when you
already understand the architecture and just want the result.
