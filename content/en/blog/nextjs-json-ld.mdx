To add JSON-LD in Next.js with the App Router, you render a
`<script type="application/ld+json">` tag inside a Server Component (in the
route's `page.tsx` or in `layout.tsx`, depending on the schema's scope) and put
the data object inside it with `JSON.stringify`. It does not go in `<Head>` and
does not need `next/script`. That is Next.js's own official recommendation, and
the rest of this article is about where each schema type should live, how to
derive it from your source of truth instead of writing it by hand, and how to
keep it from breaking silently later.

This is the second path in the [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs):
not "how to paste a script", but what the structured data implementation looks
like when it is production code, derived from the content and locked by an
automated test. Each section below is an architecture decision: where the
schema is born, what feeds it, and what happens when it stops making sense.

A caveat that has to come before any code, because half the content in
Portuguese gets this wrong: **structured data is not a direct ranking
factor.** JSON-LD does not push your position up. What it does is make the page
eligible for rich results (the breadcrumb path instead of the URL, the
article's author and dates) and help engines understand the page's structure.
The gain is in eligibility and presentation, not in ranking.

## Where JSON-LD lives in the App Router

The JSON-LD must be in the HTML that Googlebot reads on its first visit. That
is the one rule that decides the whole architecture. In the App Router, the
natural way to do it is to render the script in a Server Component, the
default for any `page.tsx` or `layout.tsx` without `"use client"` at the top.

The mechanism is this. Googlebot reads the page in two waves. In the first, it
processes the HTML that arrives from the server. Only later, in a separate
rendering queue, does it run the JavaScript and look at the final DOM. If your
JSON-LD block only comes into existence after React hydrates on the client,
there is a window in which the crawler sees the initial HTML with no schema at
all, and the second-wave rendering can take a while.

There is a precision here that almost every article on the subject gets wrong.
The problem is **not** the file having `"use client"` at the top. A client
component is also rendered on the server: its HTML ships in the initial
response, schema script included. What breaks is schema that is only **born**
after hydration, assembled inside a `useEffect` or derived from state that
only exists in the browser. That is the schema that is not in the initial
HTML, because when the server responded it did not exist yet.

On this site the rule is followed from both sides. The page-level schema
components are pure Server Components; the `FAQPage` block lives inside the FAQ
component, which is a client component because of the accordion, and even so
the script ships in the initial HTML, because the questions come from the
frontmatter, not from state. It is the case that confirms the rule: what
matters is where the data comes from.

## The base component: a `<script>` and nothing else

The component that emits the schema is deliberately dumb: it receives an
object, serializes it with `JSON.stringify` and injects the result inside a
`<script>` tag. No state, no effect, no `next/script`. That last point is
intentional, and the Next.js documentation itself explains why: `next/script`
is for loading and running JavaScript, and JSON-LD is data, not executable code;
the native `<script type="application/ld+json">` tag is the right choice.

This is the pattern running in production on this site; every schema on the
site goes through these few lines:

```tsx
// src/components/seo/JsonLd.tsx
function JsonLdScript({ schema }: { schema: Record<string, unknown> }) {
  return (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: JSON.stringify(schema).replace(/</g, '\\u003c') }}
    />
  )
}
```

`dangerouslySetInnerHTML` is scary by name, but here it is the correct path:
it is how you inject the schema text without React escaping the JSON's quotes.
The name "dangerous" is a legitimate reminder, and worth taking seriously: the
Next.js documentation warns that `JSON.stringify` does not sanitize strings
used in XSS injection, and recommends replacing the less-than character with
its unicode equivalent before injecting. That is exactly what that `.replace()`
does: inside a JSON string, `<` is the escaped form of the `<` character.
The parser reads the same data, but no text in the schema can write a literal
`</script>` that closes the tag in the middle of the HTML any more.

The question that sizes the risk is: where does the schema's data come from? If
it comes from user input, this sanitization is not optional. On this site each
object is built from the content's own frontmatter and from repository
constants, sources I control, never text typed by a third party. In other
words: here the escape does not fix a vulnerability, it removes the dependency
on editorial discipline. Without it, the day an FAQ answer mentions an HTML tag
becomes a broken-HTML bug. It is one line of code so I never have to remember
that, and that is why it lives in the component and not in a review rule.

With that component ready, the work for each schema type is just building the
right object and passing it on. The next sections are exactly that, type by
type.

## `Article`: the schema that comes from the frontmatter, not from your hands

The most common mistake with `Article` is writing the object by hand in every
post. That guarantees that, at some point, the schema's `headline` will drift
from the page's `<title>`, or the `dateModified` will be frozen on a date that
no longer matches the last edit. Hand-written schema rots.

The way out is to derive `Article` from the same source that generates the
page. On this site, every blog post and the guide have a frontmatter block at
the top of the MDX file, and the `Article` component receives that whole
frontmatter instead of typed values (the comments are in Portuguese; they say
that `abstract` is the frontmatter's short answer, the same sentence the reader
sees at the top of the page, and that the page's single target query is also
its subject, so both are declared from the same source):

```tsx
// src/components/seo/JsonLd.tsx
export function ArticleJsonLd({
  frontmatter,
  path,
  imagePath,
}: {
  frontmatter: PostFrontmatter
  /** Path da página. Default: /blog/{slug}. */
  path?: string
  /** Rota da imagem OG da página. Default: o card da marca. */
  imagePath?: string
}) {
  const url = `${site.url}${path ?? `/blog/${frontmatter.slug}`}`

  const schema = {
    '@context': 'https://schema.org',
    '@type': 'Article',
    '@id': `${url}#article`,
    headline: frontmatter.title,
    description: frontmatter.description,
    // `abstract` é a resposta curta do frontmatter: a mesma frase que o leitor
    // vê no topo da página, disponível como dado para quem extrai.
    ...(frontmatter.tldr ? { abstract: frontmatter.tldr } : {}),
    datePublished: frontmatter.datePublished,
    dateModified: frontmatter.dateModified,
    inLanguage: frontmatter.lang,
    url,
    mainEntityOfPage: { '@type': 'WebPage', '@id': url },
    isPartOf: { '@id': WEBSITE_ID },
    image: `${site.url}${imagePath ?? '/opengraph-image'}`,
    // A ÚNICA query que a página persegue (CLAUDE.md §10) é também o assunto
    // dela — declarar as duas coisas pela mesma fonte impede que divirjam.
    keywords: frontmatter.primaryQuery,
    about: { '@type': 'Thing', name: frontmatter.primaryQuery },
    author: personSchema(),
    publisher: organizationSchema(),
  }
  return <JsonLdScript schema={schema} />
}
```

The mapping is direct, and that is the whole point: `headline` comes from the
frontmatter's `title`, `description` from `description`, `abstract` from the
short answer (`tldr`) when it exists, the dates from the dates, `inLanguage`
from `lang`, and `keywords` and `about` from `primaryQuery`. The `url`, the
`@id` and `mainEntityOfPage` come from the canonical URL, built from the site's
base plus the route's path. `author` and `publisher` are never typed: they come
from central functions, the same ones other pages use. I wrote the frontmatter
once; the schema is derived from it. There is no second place where the date
can drift, because there is only one place where it is written.

That is the principle that repeats through the rest of the article: **schema is
not written per page, it is derived from the source of truth.** If you have to
update the content in one place and the schema in another, it is only a matter
of time before the two disagree, and a schema that disagrees with the page is
worse than no schema, because it describes a page that does not exist.

Note that `Article` still produces a rich result: implemented with `headline`,
dates and the author and publisher entities, it enables showing the author and
the publication and modification dates in the result. Unlike FAQ, which we will
see below, here the effort still has a visual payoff in search.

## `BreadcrumbList`: the schema almost everyone forgets

`BreadcrumbList` is the best value-for-effort schema that most sites ignore. It
describes the navigation trail to the page (Home › Blog › post title) and is
one of the rich results that remain fully active: in the search result, it
replaces the raw URL with that readable path. It is small work with a concrete
visual return, and that is why it is worth being systematic about.

"Systematic" here means not writing the breadcrumb per page. It is built from
the route's hierarchy, the same way `Article` is derived from the frontmatter:

```tsx
// src/components/seo/JsonLd.tsx
export function BreadcrumbJsonLd({ items }: { items: BreadcrumbItem[] }) {
  const schema = {
    '@context': 'https://schema.org',
    '@type': 'BreadcrumbList',
    itemListElement: items.map((item, i) => ({
      '@type': 'ListItem',
      position: i + 1,
      name: item.name,
      item: `${site.url}${item.path}`,
    })),
  }
  return <JsonLdScript schema={schema} />
}
```

Two details Google requires, both respected by the mapping above: each
`ListItem` needs a sequential `position` starting at 1, and it needs a `name`.
The `item` (the level's URL) is what makes each step of the trail clickable. A
`BreadcrumbList` needs at least two levels to make sense; a single item is not
a trail. It is the same rule this site's [JSON-LD
generator](/en/tools/json-ld-generator) applies before letting you generate a
breadcrumb: without two levels, it refuses.

## `FAQPage`: what changed in May 2026 and why I still keep it

This is the section where most of the Portuguese-language content is out of
date, so I will be direct: **since 7 May 2026, Google no longer shows the FAQ
rich result.** That dropdown of questions and answers that expanded below your
search result no longer appears, for any site. It is not a restriction to
certain categories, as it was in 2023, when the feature was limited to
government and health sites. This time the feature went away entirely, and on
15 June 2026 Google removed the feature's documentation itself.

That has an awkward practical consequence: much of what you find searching
"FAQPage schema" today describes a feature that no longer exists, and the
official page that would serve as a reference is no longer there to correct
it. In structured data, checking the date of a source stopped being pedantry.

Two wrong reactions circulated when the notice came out, and both are worth
defusing. The first: "schema is dead". It is not: `FAQPage` remains a valid
schema.org type, the markup produces no error and does not harm the page, and
other types such as `Article` and `BreadcrumbList` keep producing rich results
normally. The second: "so FAQPage is now essential for AI". Not that either. In
the official guide to optimizing for generative AI search, published in May
2026, Google states that no special markup or schema.org is required to appear
in AI Overviews or AI Mode. Schema remains useful for traditional rich results
(which, in turn, feed AI answers indirectly), but it is not a direct lever for
AI citation. Anyone who swapped "it will become a rich result" for "it will be
cited by AI" just swapped one unfounded promise for another.

So why do I keep `FAQPage` on this site, if the rich result is gone? For an
architectural reason: here, the visible FAQ on the page and the structured
FAQPage come from the same source. There is no hand-written `FAQPage`
component. What exists is a `faq` array in the article's frontmatter (the same
questions and answers that appear at the end of this page for you) and a single
component that reads that array to render two things at once: the visual
accordion and the matching JSON-LD.

```tsx
// src/components/sections/FaqSection.tsx
<script
  type="application/ld+json"
  dangerouslySetInnerHTML={{
    __html: JSON.stringify({
      '@context': 'https://schema.org',
      '@type': 'FAQPage',
      mainEntity: items.map(({ question, answer }) => ({
        '@type': 'Question',
        name: question,
        acceptedAnswer: { '@type': 'Answer', text: answer },
      })),
    }).replace(/</g, '\\u003c'),
  }}
/>
```

The `items` in that snippet is exactly the same array the accordion walks to
draw the questions on screen, a few lines above in the same file. Since the
source is single, the marginal cost of keeping `FAQPage` is practically zero: I
write the FAQ for the reader anyway, and the schema comes from the same array
with no extra work. And it solves by construction the requirement Google always
made of FAQPage: the schema's content has to be visible on the page. It cannot
drift, because it is literally the same data.

That detail matters more than it seems, because automated validation does not
catch drift. The Rich Results Test, when it still validated FAQ, never compared
the JSON-LD with the visible text: it checks syntax and properties, not whether
the schema matches what the user sees. A schema that declares one answer and a
page that shows another passes validation and still violates the policy.
Deriving both from the same source eliminates that class of error before it
exists.

The recommendation, then, is not "add FAQPage to get the rich result"; that
advice died in May. It is: if you have a genuine FAQ on the page, answering real
questions, marking it up with FAQPage costs little and keeps the page well
described for the engines that still read the markup. If your FAQ only existed
to hunt for the dropdown in the SERP, now is the time to rethink it.

## `Person` and `Organization`: the author entity and E-E-A-T

The `author` in the `Article` above is not a loose name in a string. It is a
reference to a single `Person` entity, built once from the site's central
module and reused by every article:

```tsx
// src/components/seo/JsonLd.tsx
function personSchema() {
  const sameAs = [site.author.github, site.author.linkedin].filter(Boolean)
  return {
    '@type': 'Person',
    name: site.author.name,
    jobTitle: site.author.jobTitle,
    url: site.url,
    ...(sameAs.length > 0 ? { sameAs } : {}),
  }
}
```

The field that does the heavy lifting is `sameAs`: it links the site's `Person`
entity to the external profiles (GitHub, LinkedIn) that corroborate who the
author is. It is not a statement that the person exists; it is a set of anchors
to other verifiable presences of the same person on the web. That is how
structured data takes part in E-E-A-T: not by claiming expertise, but by
connecting authorship to a traceable identity.

Note the `filter(Boolean)` and the conditional spread: if a profile is not
filled in, the field simply does not enter the schema. It is a rule that holds
for every type: an empty field is worse than a missing field, because it
describes the page with information that does not exist. The site's generator
follows the same policy: blank fields are left out of the output instead of
becoming empty strings.

## `SoftwareApplication` and the case of tool pages

Not every page is an article. A page that delivers an interactive tool is
described by the `SoftwareApplication` type, not by `Article`. On this site, the
tool pages emit that schema with the fields that describe what the tool is:

```json
{
  "@context": "https://schema.org",
  "@type": "SoftwareApplication",
  "applicationCategory": "DeveloperApplication",
  "operatingSystem": "Web",
  "isAccessibleForFree": true,
  "offers": { "@type": "Offer", "price": "0", "priceCurrency": "BRL" }
}
```

The values are not decorative: `applicationCategory` says it is a tool for
developers, `operatingSystem` that it runs in the browser,
`isAccessibleForFree` plus the `offers` with a zero price declare that it is
free. It is the honest description of a tool that runs entirely on the client
and charges nothing. The general principle runs through every type: the
`@type` you choose has to match what the page really is. Marking a tool page as
`Article`, or an article as `SoftwareApplication`, is the kind of inconsistency
Google treats as a bad signal.

## Page vs. layout: where each schema should be rendered

With the types defined, there is one architecture decision left that confuses
a lot of people: does the schema go in the route's `page.tsx` or in
`layout.tsx`? The answer is not a style preference; it falls straight out of
the question "where does this schema's data come from?".

Schema that depends on the route's specific content goes in `page.tsx`. A
post's `Article` and `BreadcrumbList` are like that: the data that feeds them
(title, dates, trail) only exists at that page's level. There is no way to
build them in the layout, because the layout does not know the post.

Schema that is stable for a whole section can live in the corresponding
`layout.tsx`. A `WebSite` or an `Organization` that applies to the whole site
does not need to be rebuilt on every route. The rule that settles every case:
**render each schema at the level where the data that feeds it actually
lives.** If the data belongs to the page, the schema belongs to the page. If the
data belongs to the section, the schema belongs to the layout.

That also holds for the most dynamic case of all, a route with a parameter
such as `/blog/[slug]`. The schema is not written for each slug; it is derived,
inside the route's async function, from the same data that generates the page.
You fetch the content by the parameter, build the schema object from those
fields, and render the script component in the return. A dynamic route's schema
is dynamic for the same reason the page is: both come from the same fetch.

## How to validate: which tool for which schema

Validating structured data today requires a distinction that is new this year:
not every tool validates every schema type, because FAQ left Google's rich
results catalogue. The routine depends on which `@type` you are checking.

For the types that still produce rich results (`Article`, `BreadcrumbList`,
`SoftwareApplication`), Google's
[Rich Results Test](https://search.google.com/test/rich-results)
is still the right tool. Paste the URL, not the code: with the URL, the tool
renders the page the way Google sees it, which matters precisely if anything in
your schema depends on rendering. Then check two things. Errors block
eligibility: a missing required property, an `@type` Google does not
recognize, JSON that does not parse. Warnings do not: they point to missing
recommended properties, and the rich result still works without them, just
with less detail. Fix every error; treat warnings as optional improvements.

For `FAQPage`, the routine changed. With no FAQ rich result, there is no
eligibility to test; what still makes sense is validating the schema's
**syntax**, and for that the path is the [schema.org
validator](https://validator.schema.org/), which checks whether the markup
follows the vocabulary regardless of whether Google produces any visual feature
from it.

After publishing, continuous monitoring is Search Console. The enhancement
reports show, at site scale, when a schema type breaks on many pages at once: a
template change that knocks out `Article` on two hundred posts shows up there as
a spike of invalid items that no single-URL test would catch. It is the tool
for monitoring over time, complementary to the one-off test before publishing.
An honest caveat applies: this site is new, so I do not yet have enhancement
report history to show. What I describe is the tool's role, not a result of
mine.

## How to keep it from breaking: the test that runs in my CI

Validating before publishing solves launch day. It does not solve the third
month, when someone (maybe you) touches a template and knocks out the schema on
every page without noticing. The way to make sure that does not go unnoticed is
to turn the validation into an automated test that blocks the deploy.

The suite runs on every pull request, in GitHub Actions, and blocks the merge
if it fails. The detail that makes it robust is that the tested routes are not
written by hand in a list: they come from `sitemap.ts`, which in turn derives
from every post in `/content`. In practice, **a new article joins the suite the
moment its file is committed**, including the one you are reading. I do not
need to remember to add the post to the test; the test discovers the post on
its own.

Per route, the suite asserts a set of invariants. There is exactly one non-empty
`<h1>`. The `<title>` is present and at most 60 characters. The meta
description is present and at most 155. The canonical is self-referencing.
And, what matters here: **every `application/ld+json` block on the page goes
through `JSON.parse` without error**, and the set of `@type` expected for that
route type is present.

```ts
// tests/seo/seo.spec.ts — trecho da suíte de regressão de SEO
const jsonLdBlocks = await page
  .locator('script[type="application/ld+json"]')
  .allTextContents()

const foundTypes: string[] = []
for (const raw of jsonLdBlocks) {
  let parsed: unknown
  try {
    parsed = JSON.parse(raw)
  } catch {
    throw new Error(`JSON-LD block on ${route} is not valid JSON:\n${raw}`)
  }
  for (const node of Array.isArray(parsed) ? parsed : [parsed]) {
    const type = (node as { '@type'?: string })['@type']
    if (type) foundTypes.push(type)
  }
}

for (const type of expectedJsonLdTypes(route)) {
  expect.soft(foundTypes, `JSON-LD @type "${type}" on ${route}`).toContain(type)
}
```

`expectedJsonLdTypes` is the map you already saw in the diagram, written as a
function: a blog route must contain `Article` and `BreadcrumbList`, plus
`FAQPage` if, and only if, that post's frontmatter has a `faq` array; a tool
route must contain `SoftwareApplication` and `BreadcrumbList`, and so on. The
consequence is the sentence that sums up why the test exists: **if a JSON-LD
block stops parsing, or an `@type` disappears from a template, the test fails
and the merge is blocked.**

There is a second layer, in the build itself. The frontmatter is validated when
the page is assembled: if a required field is missing, or the `title` goes over
60 characters, or the `description` over 155, the build breaks. It is not a
warning you can ignore; it is a failure that stops generation. Between the build
that rejects invalid frontmatter and the suite that rejects invalid schema, the
path to publishing a page with broken structured data is closed at the two
points where the error usually gets in.

## What not to chase

I close with the honest calibration, because half the value of a technical
article lies in saying what not to do. Do not chase rankings with JSON-LD: it
is not a ranking factor and no amount of schema will change that. Do not add
`FAQPage` expecting the dropdown in the SERP; it was discontinued in May 2026
and will not come back no matter how well-intentioned your markup is. Do not
treat schema as a shortcut to being cited by AI; Google itself says no special
markup is required for that. And do not write schema by hand per page: what is
derived from the source of truth does not drift, what is typed twice does.

What structured data actually delivers is more modest and more real: it makes
the page eligible for the rich results that still exist, describes the
content's structure for whoever reads the markup, and (if you lock it with a
test) stays correct over time without manual vigilance. That closes the second
path of the [technical SEO guide for Next.js](/en/guide/technical-seo-nextjs);
the other topics follow the same logic of deriving from the content instead of
writing by hand. When you need to generate a quick schema for a specific case,
the [JSON-LD generator](/en/tools/json-ld-generator) produces the object and
the Next.js component ready to use, in the same Server Component pattern I
described here. This article is the
architecture; the tool is the shortcut for when you already understand the
architecture and just want the result.
