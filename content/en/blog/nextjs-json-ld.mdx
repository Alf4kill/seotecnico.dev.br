To add JSON-LD to a Next.js site that uses the App Router, render a
`<script type="application/ld+json">` tag inside a Server Component, in the
route's `page.tsx` or in `layout.tsx` depending on the schema's scope, and
put the data object inside it with `JSON.stringify`. It doesn't go in
`<Head>`, and it doesn't need `next/script`. This is what Next.js itself
recommends. The rest of this article covers where each schema type should
live, how to derive it from your source of truth instead of writing it by
hand, and how to keep it from breaking silently later on.

This article is the second track of the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs). It isn't
about how to paste a script. It's about what structured data looks like as
production code, derived from the content and locked by an automated test.
Each section below is an architecture decision: where the schema is born,
what feeds it, and what happens when it stops making sense.

One caveat comes before any code, because half of what's written about this
in Portuguese gets it wrong. **Structured data is not a direct ranking
factor.** JSON-LD won't push your
position up. What it does is make the page eligible for rich results, such
as the breadcrumb trail shown in place of the URL or an article's author
and dates, and help search engines understand how the page is structured.
You gain eligibility and presentation, not rankings.

## Where JSON-LD lives in the App Router

One rule decides the whole architecture. JSON-LD has to be in the HTML that
Googlebot reads on its first visit. In the App Router, the natural way to
get it there is to render the script in a Server Component, which is what
any `page.tsx` or `layout.tsx` is by default when it has no `"use client"`
at the top.

This matters because Googlebot reads a page in two waves. First it
processes the HTML the server sends. Later, in a separate rendering queue,
it runs the JavaScript and looks at the final DOM. If your JSON-LD block
only comes into existence after React hydrates on the client, there's a
window in which the crawler sees the initial HTML with no schema at all,
and the second-wave render may take a while.

Almost every article on the subject gets the next part wrong. The problem
is **not** that the file has `"use client"` at the top. A client component
is also rendered on the server, so its HTML ships in the initial response,
schema script included. What breaks is schema that's only **created** after
hydration, built inside a `useEffect` or derived from state that exists
only in the browser. That schema isn't in the initial HTML because it
didn't exist yet when the server responded.

where the data comes from.

## The base component: a `<script>` and nothing else

Start with the component that emits the schema. It's deliberately dumb. It
takes an object, serializes it with `JSON.stringify`, and injects the
result into a `<script>` tag. It has no state, no effect, and no
`next/script`. Leaving out `next/script` is intentional, and the Next.js
documentation explains why. `next/script` is for loading and running
JavaScript. JSON-LD is data, not executable code, so the native
`<script type="application/ld+json">` tag is the right choice. This pattern
runs in production on this site, and every schema the site emits goes
through these few lines.

```tsx
// src/components/seo/JsonLd.tsx
function JsonLdScript({ schema }: { schema: Record<string, unknown> }) {
  return (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: JSON.stringify(schema).replace(/</g, '\\u003c') }}
    />
  )
}
```

`dangerouslySetInnerHTML` sounds alarming, but here it's the correct path.
It lets you inject schema text without React escaping the JSON's quotes.
Still, "dangerous" in its name is a legitimate reminder, and you should
take it seriously. Next.js documentation warns that `JSON.stringify`
doesn't sanitize strings used in XSS injection, and it recommends
replacing the less-than character with its Unicode equivalent before you
inject anything. That's exactly what `.replace()` does here.
Inside a JSON string, `\u003c` is the escaped form of the `<` character.
A parser reads the same data, but no text in the schema can produce a
literal `</script>` and close the tag in the middle of the HTML.

How big is the risk? It depends on where the schema's data comes from. If
it comes from user input, this sanitization isn't optional. On this site,
every object is built from the content's own frontmatter and from
repository constants, sources I control and never text typed by a third
party. So here the escape doesn't fix a vulnerability. It removes a
dependency on editorial discipline. Without it, the first FAQ answer that
mentions an HTML tag would break the page's HTML. One line of code
means I never have to remember this, which is why it sits in the component
and not in a code review checklist.

With this component in place, each schema type comes down to building the
right object and passing it on. The next sections do exactly that, type by
type.

## `Article`: schema that comes from the frontmatter, not your keyboard

The most common mistake with `Article` is writing the object by hand in
each post. Sooner or later, that guarantees the schema's `headline` drifts
away from the page's `<title>`, or `dateModified` stays frozen on a date
that no longer matches the last edit. Hand-written schema rots.

Instead, derive `Article` from the same source that generates the page.
Every blog post on this site, and the guide, starts its MDX file with a
frontmatter block, and the `Article` component receives that whole block
instead of typed values. The comments in the code below are in Portuguese.
The first says `abstract` is the frontmatter's short answer, the sentence
readers see at the top of the page, available as data for anyone who extracts it. The
second says a page's single target query is also its subject, so both are
declared from one source, which keeps them from diverging.

```tsx
// src/components/seo/JsonLd.tsx
export function ArticleJsonLd({
  frontmatter,
  path,
  imagePath,
}: {
  frontmatter: PostFrontmatter
  /** Path da página. Default: /blog/{slug}. */
  path?: string
  /** Rota da imagem OG da página. Default: o card da marca. */
  imagePath?: string
}) {
  const url = `${site.url}${path ?? `/blog/${frontmatter.slug}`}`

  const schema = {
    '@context': 'https://schema.org',
    '@type': 'Article',
    '@id': `${url}#article`,
    headline: frontmatter.title,
    description: frontmatter.description,
    // `abstract` é a resposta curta do frontmatter: a mesma frase que o leitor
    // vê no topo da página, disponível como dado para quem extrai.
    ...(frontmatter.tldr ? { abstract: frontmatter.tldr } : {}),
    datePublished: frontmatter.datePublished,
    dateModified: frontmatter.dateModified,
    inLanguage: frontmatter.lang,
    url,
    mainEntityOfPage: { '@type': 'WebPage', '@id': url },
    isPartOf: { '@id': WEBSITE_ID },
    image: `${site.url}${imagePath ?? '/opengraph-image'}`,
    // A ÚNICA query que a página persegue (CLAUDE.md §10) é também o assunto
    // dela — declarar as duas coisas pela mesma fonte impede que divirjam.
    keywords: frontmatter.primaryQuery,
    about: { '@type': 'Thing', name: frontmatter.primaryQuery },
    author: personSchema(),
    publisher: organizationSchema(),
  }
  return <JsonLdScript schema={schema} />
}
```

The mapping is direct, and that's the whole point:

- `headline` comes from the frontmatter's `title`.
- `description` comes from `description`.
- `abstract` comes from the short answer (`tldr`), when there is one.
- The dates come from the dates.
- `inLanguage` comes from `lang`.
- `keywords` and `about` come from `primaryQuery`.
- `url`, `@id`, and `mainEntityOfPage` come from the canonical URL, built
  from the site's base URL plus the route's path.
- `author` and `publisher` are never typed. They come from central
  functions, the same ones other pages use.

I wrote the frontmatter once, and the schema derives from it. Since the
date is written in only one place, there's no second copy to drift. That's
the principle behind the rest of this article. **Schema is not written per
page. It is derived from the source of truth.**

If you update content in one place and schema in another, it's only a
matter of time before they disagree. A schema that disagrees with the page
is worse than no schema, because it describes a page that doesn't exist.

`Article` still produces a rich result. With `headline`, the dates, and the
author and publisher entities in place, it makes the page eligible to show
its author and its publication and modification dates in search results.
Unlike FAQ, covered below, this is effort that still pays off visually in
search.

## `BreadcrumbList`: the schema almost everyone forgets

`BreadcrumbList` is the best-value schema that most sites ignore. It
describes the navigation trail to the page, as in Home › Blog › post title.
It's also one of the rich results that are still fully active, and in
search results it replaces the raw URL with that readable path. It takes
little work and the visual return is concrete, so it's worth being
systematic about it.

Systematic here means you don't write the breadcrumb per page. You build it
from the route's hierarchy, the same way `Article` is derived from the
frontmatter.

```tsx
// src/components/seo/JsonLd.tsx
export function BreadcrumbJsonLd({ items }: { items: BreadcrumbItem[] }) {
  const schema = {
    '@context': 'https://schema.org',
    '@type': 'BreadcrumbList',
    itemListElement: items.map((item, i) => ({
      '@type': 'ListItem',
      position: i + 1,
      name: item.name,
      item: `${site.url}${item.path}`,
    })),
  }
  return <JsonLdScript schema={schema} />
}
```

This mapping covers two details Google requires. Each `ListItem` needs a
sequential `position` starting at 1, and it needs a `name`. Its `item`, the
URL of that level, makes each step of the trail clickable. A
`BreadcrumbList` also needs at least two levels to make sense, since a
single item isn't a trail. This site's
[JSON-LD generator](/en/tools/json-ld-generator) applies the same rule and
refuses to generate a breadcrumb with fewer than two levels.

## `FAQPage`: what changed in May 2026 and why I still use it

Most of the Portuguese-language content on this topic is out of date, so
here's the blunt version. **Since May 7, 2026, Google no longer shows the
FAQ rich result.** The dropdown of questions and answers that used to
expand under your search result doesn't appear anymore, for any site. This
isn't a restriction to certain categories, as in 2023, when the feature was
limited to government and health sites. This time Google took the feature
down entirely, and on June 15, 2026, it removed the feature's own
documentation.

That has an uncomfortable consequence. Much of what you find when you
search for "FAQPage schema" today describes a feature that no longer
exists, and the official page that would serve as a reference isn't there
to contradict it. With structured data, checking a source's date isn't
pedantry anymore.

Two wrong reactions circulated when the notice came out. Neither holds up.

The first was "schema is dead." It isn't. `FAQPage` is still a valid
schema.org type, the markup doesn't generate errors or harm the page, and
other types such as `Article` and `BreadcrumbList` still produce rich
results normally.

The second was "so FAQPage is now essential for AI." That's wrong too. In
its official guide to optimizing for generative AI search, published in May
2026, Google says you don't need any special markup or schema.org to appear
in AI Overviews or AI Mode. Schema stays useful for traditional rich
results, which in turn feed AI answers indirectly, but it isn't a direct
lever for getting cited by AI. Anyone who swapped "it'll become a rich
result" for "it'll get cited by AI" just traded one baseless promise for
another.

So why do I keep `FAQPage` here, with the rich result gone? The reason is
architectural. The FAQ you see on this page and its `FAQPage` markup come
from one source. There's no hand-written `FAQPage` component. There's
a `faq` array in this article's frontmatter, holding the questions and
answers you'll find at the end of the page, and a single component reads
that array to render two things at once: a visual accordion and its
matching JSON-LD.

```tsx
// src/components/sections/FaqSection.tsx
<script
  type="application/ld+json"
  dangerouslySetInnerHTML={{
    __html: JSON.stringify({
      '@context': 'https://schema.org',
      '@type': 'FAQPage',
      mainEntity: items.map(({ question, answer }) => ({
        '@type': 'Question',
        name: question,
        acceptedAnswer: { '@type': 'Answer', text: answer },
      })),
    }).replace(/</g, '\\u003c'),
  }}
/>
```

Here, `items` is the same array the accordion loops over, a few lines
higher in this file, to draw the questions on screen. With one source, keeping
`FAQPage` costs practically nothing. I write the FAQ for readers anyway,
and the schema comes out of that array with no extra work.

It also meets, by construction, the requirement Google always had for
FAQPage, that the schema's content be visible on the page. The two can't
diverge, because they're literally the same data.

This matters more than it seems, because automated validation doesn't
catch divergence. Back when the Rich Results Test still validated FAQ, it
never compared the JSON-LD with the visible text. It checks syntax and
properties, not whether the schema matches what the user sees. A schema
that declares one answer on a page that shows another passes validation
and still violates the policy. Deriving both from the same source rules out
this class of error before it can exist.

So my recommendation isn't "add FAQPage to win the rich result." That
advice died in May. If you have a genuine FAQ on the page that answers real
questions, marking it up with `FAQPage` costs little and keeps the page
well described for the engines that still read the markup. If your FAQ
existed only to chase the dropdown in search results, now is the time to
rethink it.

## `Person` and `Organization`: the author entity and E-E-A-T

The `author` in the `Article` above isn't a bare name in a string. It's a
reference to a single `Person` entity, built once from the site's central
config and reused by every article.

```tsx
// src/components/seo/JsonLd.tsx
function personSchema() {
  const sameAs = [site.author.github, site.author.linkedin].filter(Boolean)
  return {
    '@type': 'Person',
    name: site.author.name,
    jobTitle: site.author.jobTitle,
    url: site.url,
    ...(sameAs.length > 0 ? { sameAs } : {}),
  }
}
```

`sameAs` does the heavy lifting. It links the site's `Person` entity to
external profiles (GitHub, LinkedIn) that corroborate who the author is.
Rather than state that the person exists, it anchors the entity to other
verifiable places where that same person appears on the web. That's how
structured data takes part in E-E-A-T, not by asserting expertise but by
connecting authorship to a traceable identity.

Notice the `filter(Boolean)` and the conditional spread. If a profile isn't
filled in, the field stays out of the schema. That rule holds for every
type. An empty field is worse than an absent one, because it describes the
page with information that doesn't exist. The site's generator follows the
same policy and omits blank fields from its output instead of turning them
into empty strings.

## `SoftwareApplication` and tool pages

Not every page is an article. You describe a page that delivers an
interactive tool with `SoftwareApplication`, not `Article`. Tool pages on
this site emit this schema, with fields that describe what the tool is.

```json
{
  "@context": "https://schema.org",
  "@type": "SoftwareApplication",
  "applicationCategory": "DeveloperApplication",
  "operatingSystem": "Web",
  "isAccessibleForFree": true,
  "offers": { "@type": "Offer", "price": "0", "priceCurrency": "BRL" }
}
```

None of these values are decorative. `applicationCategory` says it's a tool
for developers, `operatingSystem` says it runs in the browser, and
`isAccessibleForFree` plus `offers` with a price of zero declare that it's
free. Together they honestly describe a tool that runs entirely on the
client and charges nothing.

Across all types, the `@type` you choose has to match what the page really
is. Marking a tool page as `Article`, or an article as
`SoftwareApplication`, is the kind of inconsistency Google treats as a bad
signal.

## Page vs. layout: where each schema should be rendered

With the types defined, one architecture decision is left, and it confuses
a lot of people. Does the schema go in the route's `page.tsx` or in
`layout.tsx`? The answer isn't a matter of style. It falls straight out of
one question: where does this schema's data come from?

Schema that depends on the route's specific content goes in `page.tsx`. A
post's `Article` and `BreadcrumbList` are fed by its title, dates, and
trail, and that data exists only at the page's level. You can't build them
in the layout, because the layout doesn't know about the post.

Schema that's stable for a whole section can live in the matching
`layout.tsx`. A `WebSite` or `Organization` that's valid for the whole site
doesn't need to be rebuilt on every route.

One rule settles every case: **render each schema at the level where the
data feeding it actually lives.** Page data means page schema. Section data
means layout schema.

It works the same way even in the most dynamic case, a route with a
parameter like `/blog/[slug]`. You don't write a schema per slug. You
derive it inside the route's async function, from the data that also
generates the page. Fetch content by the parameter, build a schema object
from its fields, and render the script component in what the function
returns. A dynamic route's schema is dynamic for the same reason its page
is, because both come from one fetch.

## How to validate: which tool for which schema

Validating structured data now takes a distinction that's new in 2026.
Because FAQ left Google's rich results catalog, not every tool validates
every schema type, and your routine depends on which `@type` you're
checking.

For the types that still produce rich results, `Article`, `BreadcrumbList`,
and `SoftwareApplication`, Google's
[Rich Results Test](https://search.google.com/test/rich-results) is still
the right tool. Paste the URL, not the code. With a URL, the tool renders
the page the way Google sees it, which matters if anything in your schema
depends on rendering. Then check two things:

- Errors block eligibility. Examples are a missing required property, an
  `@type` Google doesn't recognize, or JSON that doesn't parse.
- Warnings don't. They point to missing recommended properties, and the
  rich result still works without them, just with less detail.

Fix every error, and treat warnings as optional improvements.

For `FAQPage`, the routine has changed. With no FAQ rich result, there's no
eligibility to test. What still makes sense is validating the schema's
**syntax**, and the tool for that is the
[schema.org validator](https://validator.schema.org/). It checks whether
the markup conforms to the vocabulary, whether or not Google builds any
visual feature from it.

After you publish, Search Console handles continuous monitoring. Its
enhancement reports show, at site scale, when a schema type breaks on many
pages at once. A template change that knocks out `Article` on two hundred
posts, for example, shows up there as a spike of invalid items that no
single-URL test would catch. It's the tool for monitoring over time, and it
complements the one-off test before publishing.

One honest caveat. This site is new, so I don't have enhancement report
history to show yet. What I'm describing is the tool's role, not one of my
results.

## How to keep it from breaking: the test that runs in my CI

Validating before you publish takes care of launch day. It doesn't take
care of month three, when someone, maybe you, touches a template and knocks
out the schema on every page without noticing. To catch that, turn
validation into an automated test that blocks the deploy.

On this site the suite runs on every pull request, in GitHub Actions, and
blocks the merge if it fails. What makes it robust is that the tested
routes aren't a hand-written list. They come from `sitemap.ts`, which in
turn derives from every post in `/content`. In practice,
**a new article enters the suite the moment its file is committed**,
including the one you're reading. I don't have to remember to add a post to
the test, because the test finds the post on its own.

For each route, the suite asserts a set of invariants:

- exactly one non-empty `<h1>`
- a `<title>` that's present and at most 60 characters
- a meta description that's present and at most 155
- a self-referencing canonical
- and, what matters here, **every `application/ld+json` block on the page
  passes `JSON.parse` without error**, and the set of `@type` expected for
  that route type is present

```ts
// tests/seo/seo.spec.ts — trecho da suíte de regressão de SEO
const jsonLdBlocks = await page
  .locator('script[type="application/ld+json"]')
  .allTextContents()

const foundTypes: string[] = []
for (const raw of jsonLdBlocks) {
  let parsed: unknown
  try {
    parsed = JSON.parse(raw)
  } catch {
    throw new Error(`JSON-LD block on ${route} is not valid JSON:\n${raw}`)
  }
  for (const node of Array.isArray(parsed) ? parsed : [parsed]) {
    const type = (node as { '@type'?: string })['@type']
    if (type) foundTypes.push(type)
  }
}

for (const type of expectedJsonLdTypes(route)) {
  expect.soft(foundTypes, `JSON-LD @type "${type}" on ${route}`).toContain(type)
}
```

`expectedJsonLdTypes` is the map you already saw in the diagram, written as
a function. A blog route must contain `Article` and `BreadcrumbList`, plus
`FAQPage` if, and only if, that post's frontmatter has a `faq` array. A
tool route must contain `SoftwareApplication` and `BreadcrumbList`. And so
on. The test exists for one reason. **If a JSON-LD block stops parsing, or
an `@type` disappears from a template, the test fails and the merge is
blocked.**

A second layer sits in the build itself, which validates the frontmatter
of every page it generates. If a required field is missing, or `title` runs
over 60 characters, or `description` over 155, the build breaks. That
isn't a warning you can ignore. It's a failure that stops the page from
being generated. Between a build that refuses invalid frontmatter and a
suite that refuses invalid schema, the path to publishing a page with
broken structured data is closed at the two points where the error usually
gets in.

## What not to chase

I'll close with an honest calibration, because half the value of a
technical article is in saying what not to do.

- Don't chase rankings with JSON-LD. It isn't a ranking factor, and no
  amount of schema will change that.
- Don't add `FAQPage` expecting the dropdown in search results. Google
  discontinued it in May 2026, and it won't come back, however
  well-intentioned your markup is.
- Don't treat schema as a shortcut to getting cited by AI. Google itself
  says no special markup is required for that.
- Don't write schema by hand for each page. What's derived from the source
  of truth doesn't diverge, and what's typed twice does.

What structured data actually delivers is more modest and more real. It
makes the page eligible for the rich results that still exist, describes
the content's structure for whoever reads the markup, and, if you lock it
with a test, stays correct over time without anyone watching it by hand.
