There's no way to prove that AI does **not** use your content. What you can
measure with your own server logs comes down to three things: **which agents
fetch your pages**, **whether the identity they claim is true**, and
**whether they respect robots.txt**. This site has measured all three in
production since July 2026. It uses a robots.txt honeypot, checks identity
by IP range, reverse DNS, and cryptographic signature, and runs telemetry
that separates browsers from automated clients. Here you'll find the
method, the code, numbers from the first 28 days, and three bugs that my
first look at the data turned up in the instrument itself.

## What can and can't be measured

"Is AI using my content?" is really four questions, and a web server can
answer only some of them.

| Question | Answerable? | With what |
|---|---|---|
| Did this request come from an automated client? | **Yes**, with good confidence | Header shape, compared with visits that run JavaScript |
| Which agent made the request? | **Partly** | Published IP ranges, reverse DNS, or a Web Bot Auth signature, and only for vendors that publish at least one of the three |
| Was it to train a model? | **No** | Only the vendor knows. At most, you can cite the vendor's documentation on the agent's purpose |
| Did robots.txt authorize it? | **Yes**, exactly | What the file said for that agent when the request arrived |

That asymmetry shapes everything else here. **Authorization is a fact** the
site controls. **Purpose is a citation**, never an inference. **Absence
can't be proven**. An unidentified crawler, a copy of your article on
another domain, or a dataset that's already published is out of reach of
any server. Any text that promises to "find out whether AI trained on your
site" is selling the fourth answer, and that answer doesn't exist.

## A user agent is a claim, not an identity

A `User-Agent` header is text the client chooses. A `curl` with
`-A "GPTBot"` sends exactly the same header as the real GPTBot.

So this site's telemetry treats the user agent as a **claim**. It talks
about identity only when a request passes a check against a source the
vendor itself publishes. There are three such sources, from strongest to
weakest:

1. **Web Bot Auth signature** (HTTP Message Signatures, RFC 9421). A client
   signs the request with an Ed25519 key published on the domain it declares
   in the `Signature-Agent` header. This is cryptography, and it doesn't
   depend on the user agent. Strictly speaking, it proves that **whoever
   controls that domain signed**. Anyone can publish keys on their own
   domain, so the domain *is* the identity. Google signs some `Google-Agent`
   requests this way, experimentally, according to documentation dated
   May 4, 2026. Web Bot Auth itself is still an Internet-Draft.
2. **Published IP ranges.** OpenAI, Perplexity, Microsoft, Apple, Anthropic,
   and Common Crawl publish JSON lists of their crawlers' addresses. If a
   request's IP falls inside one of those ranges, its identity is verified.
3. **Confirmed reverse DNS.** Here the IP's reverse name has to end in the
   vendor's documented domain (`.search.msn.com` for Bingbot,
   `.crawl.commoncrawl.org` for CCBot), **and** that name has to resolve back
   to the same IP. Without the forward lookup, whoever owns the IP controls
   the reverse name.

These checks produce the verdicts the telemetry records. Here's the type,
copied from the production code:

```ts
// src/lib/crawler-verification.ts
export type Verdict =
  | 'verified-ip'
  | 'verified-signature'
  | 'verified-rdns'
  | 'impersonated'
  | 'unverifiable'
  | 'unknown-agent'

export interface VerificationResult {
  agent: string | null
  verdict: Verdict
  /** Which published source produced the verdict, for the log record. */
  evidence: string | null
}
```

Two of these verdicts are findings, not failures. Mixing them up is the
worst mistake you can make in this kind of measurement.

- **`impersonated`** exists only when there was a source to check and the
  request failed it. A request from an IP outside OpenAI's ranges that
  claims to be GPTBot is a request **that claims to be GPTBot and didn't
  come from OpenAI**, never "GPTBot did X."
- **`unverifiable`** means the vendor publishes nothing. Bytespider
  (ByteDance) and meta-externalagent (Meta) fall in this group. Calling
  their traffic fake would invent a proof that doesn't exist.

There's also a neat shortcut. `Google-Extended` and `Applebot-Extended` are
**robots.txt tokens**, not crawlers, and their vendors document that no
request carries those names. A user agent claiming to be either one is fake
by definition.

Who publishes what changes over time, and that's data too. Anthropic
publishes the ranges of its three agents in a single list, linked from a
page dated April 7, 2026. Common Crawl publishes both ranges and reverse
DNS. **This site only added the two vendors on September 13, 2026.** Until
then, requests claiming their agents came out `unverifiable`. A
verification list ages silently, so checking the sources before publishing
any number is part of the method.

## The honeypot: a URL that only exists in robots.txt

This site's robots.txt has a `Disallow` line for a lab route with a random
name. That URL isn't in the sitemap, the on-site search, or a link on any
page, and this article leaves it out for the same reason. To reach it, a
client has to **read robots.txt and choose to fetch what it forbids**.

I declare the blocked paths like this (the Portuguese comment says the trap
exists only in this line, and that the llms.txt trap stays out of the list on
purpose so it can't muddy channel attribution):

```ts
// src/app/robots.ts
// O trap de robots (docs/detection-experiment.md §4) existe APENAS nesta
// linha de Disallow: fora do sitemap, fora do llms.txt, sem link de lugar
// nenhum. Quem chega lá parseou este arquivo e escolheu buscar o que ele
// proíbe. O trap de llms.txt (TRAP_LLMS_PATH) fica fora daqui de propósito —
// listá-lo contaminaria a atribuição de canal.
const DISALLOWED_PATHS = ['/api/', TRAP_ROBOTS_PATH]
```

Three limits come with it:

- **The honeypot only catches clients that read robots.txt.** A client that
  never opens the file never finds the URL. It detects deliberate disregard,
  not ignorance, which is a narrower and stronger claim.
- **It doesn't identify anyone.** Every client gets the same robots.txt, so
  one URL per agent would prove nothing. Attribution comes from verifying
  the identity behind the hit itself.
- **It's not a punitive trap.** It generates no junk, doesn't trap the
  client in a maze of links, and doesn't try to poison anything. It explains
  itself to whoever lands on it and sends `noindex` in the header. That
  combination, `Disallow` plus `noindex`, is what my
  [article on redirects and canonicals](/en/blog/nextjs-redirects-canonicals)
  advises against on a real page. Here it's on purpose. Whoever obeys
  robots.txt never arrives, and whoever disobeys can't index the page.

A second honeypot applies the same logic to another channel. It's a URL
that exists only as a link inside `llms.txt`. A hit proves that the client
reads `llms.txt` **and follows** its links, which is the strong form of the
question "does any agent use llms.txt?"

## Telling browsers from automated clients

Crawlers don't execute JavaScript, so you can tell whether a request came
from a browser without trusting any header. Ask one question: **was there a
matching visit with JavaScript?**

My server logs every page request to its own analytics property. Human
visits go to a different property, which only receives an event when
JavaScript runs in the browser. So a document request with no matching visit
comes from a client that doesn't run JavaScript.

Visitors who refuse cookies are the obvious confound, and an earlier
decision already removed it. This site runs Consent Mode in advanced mode,
so someone who declines the banner still generates a cookieless
measurement.

For each request, the classifier looks at headers a browser always sends
and a raw HTTP client almost never does (the comment notes that Node's
`fetch` sends only the Mode):

```ts
// src/proxy.ts
function classifyUa(request: NextRequest, crawler: AiCrawler | undefined): UaClass {
  if (crawler) return 'declared-ai'
  // Mode + Dest: o `fetch` do Node manda só o Mode (lib/fetch-metadata.ts).
  const hasSecFetch = hasBrowserFetchMetadata(request.headers)
  const acceptsHtml = request.headers.get('accept')?.includes('text/html') ?? false
  return hasSecFetch && acceptsHtml ? 'browser-like' : 'unknown'
}
```

Until October 7, 2026, `Sec-Fetch-Mode` by itself counted as a browser
signal. Node's native `fetch` sends that header without
`Sec-Fetch-Dest`, so any client built on it that asked for HTML passed.
Since the fix, both headers are required, and the log records the cutoff
date. I wrote up the case in the
[article on the Sec-Fetch-Mode header](/en/blog/sec-fetch-mode-header).

No IP address, raw header, or full user agent leaves the server. To
correlate requests from the same network without identifying anyone, the
telemetry records a truncated hash of the subnet, salted with a value that
changes every month.

## Why most automated traffic doesn't identify itself

A bot gains from identifying itself only if it **wants to be recognized**.
Search engines want robots.txt to allow them. Bots that build link previews
on WhatsApp or LinkedIn declare themselves so they get the Open Graph tags.
SEO tools publish how to verify their own crawlers so they don't get
blocked.

On the other side, anyone afraid of blocks, rate limits, or being charged
has every incentive to look like an ordinary browser. That includes
scrapers going through residential proxies, headless browsers driven by
scripts, vulnerability scanners, and AI agents that open pages at a user's
request with a browser user agent.

This traffic is large and hard to size from the outside. Imperva's bot
report, published April 29, 2026, estimates that automated traffic made up
53% of web traffic in 2025, against 47% human. Those numbers come from a
company that sells bot protection, using its own definitions.

Cloudflare only treats a client as a "verified bot" if it passes Web Bot
Auth or IP validation. Everything else is unverified by definition,
whatever its user agent says.

Attribution needs care, and the most-cited public case shows why. On
August 4, 2025, Cloudflare accused Perplexity of using undeclared crawlers,
with a Chrome user agent and changing networks, to get around blocks.
Perplexity soon replied publicly that Cloudflare had mistaken traffic from
a third-party cloud browser service for Perplexity's. Both versions are
still disputed, and neither is an established fact. That's exactly the
point. Without verified identity, browser-like traffic has no owner.

## What the first look revealed: three bugs in the instrument itself

A lab that only publishes what worked isn't a lab. The whole point of that
first look was to catch collection errors early, and it did.

**1. Human browsing counted as unidentified traffic.** Every browser visit
makes Next.js prefetch the page's visible links with RSC requests, which
carry the header `rsc: 1` and don't ask for HTML. My classification above
marked them `unknown`. The data held a clue. The six pages that
unidentified clients from my network "accessed" most were exactly the links
in the header and footer. In a local production build, a single visit to
an article prefetched those same six routes. Now the proxy drops those
requests before anything is counted:

```ts
// src/proxy.ts
  matcher: [
    {
      source:
        '/((?!api/|_next/static|_next/image|images/|favicon.ico|icon.svg|opengraph-image|.*/opengraph-image$|.*\\.(?:png|jpg|jpeg|webp|avif|svg|ico|woff2?)$).*)',
      missing: [
        { type: 'header', key: 'rsc' },
        { type: 'header', key: 'next-router-prefetch' },
      ],
    },
  ],
```

For data from before the fix, I wrote down the rule before looking at the
data again. The "non-browser" group is requests **without** `Sec-Fetch-*`
headers, which browsers send even on RSC requests.

**2. Verified signature without the signer's name.** A Web Bot Auth
signature only proves that a domain's owner signed, so the domain is the
whole identity. My telemetry recorded the verdict but not the domain.
That's why the 64 signed requests in the period say "someone signed" and
nothing more. Since September 13, it records the signer's domain too.

**3. The current Web Bot Auth format was rejected.** In its March 2026
version, the spec changed the `Signature-Agent` header to a dictionary
(`agent1="https://…"`), which is the format Google uses. My verifier only
accepted the earlier format, so a valid signature in the new one would
never have been verified here. I fixed this on September 13 too.

**And one process error.** The only hit on the robots.txt honeypot in the
period was a `curl` the lab sent itself during an indexing audit on
September 11, 2026. No crawler fell into the trap. It was me. I identified
the hit and excluded it along with all traffic from my network, and the
episode became a rule. Any test request sent to production goes into the
measurement plan, with its time, before the work session ends.

## What this site won't publish

I set these rules before any data came in. They apply to this whole
article, including the next section's results.

1. An agent is **named** as the author of a behavior only with three proofs
   together: verified identity, a dated observation on this domain, and the
   purpose the vendor itself declares.
2. Traffic that **claims** to be an agent and fails verification is
   reported as a claim, never under the vendor's name.
3. Counts, dates, and definitions. Not adjectives.
4. Every inferred classification is called inferred, in the text, not in a
   footnote.
5. When the vendor has a public position on the observed behavior, it
   appears next to the observation.
6. Hypotheses that fail get published too.
7. Before publishing any impersonation case, I redo the verification
   against the vendor's list downloaded that day, and the sentence says
   "outside the ranges published on [date]."

Ignoring robots.txt isn't a crime. The file is a voluntary request. This
site measures who honors it and makes no legal claim of any kind.

## What the pilot showed

I closed the measurement round on **September 20, 2026**, at 57 of 90
planned days, and reclassified it as a **pilot**. The bugs above turned up
while it was running, and an instrument fixed midway doesn't measure the
same thing from start to finish. The close also coincided with the site's
visual redesign, which changed every page served.

These verdicts cover **5,480 events** from July 25 to September 20, after I
excluded 1,728 of my own (24% of everything recorded).

| Hypothesis, pre-registered | Verdict | What supports it |
|---|---|---|
| Some crawler falls into the robots.txt honeypot | **Falsified** | Zero real hits. Both hits in the period were the lab's own tests. With 1,191 fetches of robots.txt, following the forbidden line happens in at most 1 of every 398 fetches |
| A verified training agent fetches a forbidden page | **Confirmed** | On July 30, GPTBot, from an IP inside the list OpenAI publishes, fetched three forbidden paths: `/`, `/feed.xml`, and `/politica-de-privacidade` |
| Unidentified traffic exceeds traffic from declared, blocked agents | **Confirmed, by a wide margin** | Unidentified, without browser headers: 1,326 events from 436 networks. Declared and blocked: 425 events from 7 networks. **62 times as many networks** |
| Conditional requests point to a search agent | **Falsified** | Claude-SearchBot and OAI-SearchBot sent none (0 of 939 and 0 of 182). They come from Bingbot (52 of 96) and, above all, unidentified traffic (762 of the 814) |
| Updating an article draws more fetches from search agents | **Inconclusive** | The test needed at least 5 fetches of the article in 14 days. The real rate was 0.47 per article per 14 days, ten times lower |
| No agent follows `llms.txt` to the honeypot | **Supported, but underpowered** | Zero hits, but `llms.txt` was fetched only 9 times in 57 days. With so little exposure, "nobody follows" can't be told apart from "almost nobody reads" |

**The caveat that goes with the only confirmed case.** GPTBot didn't fetch
`/robots.txt` once in the period. This data supports "fetched forbidden
paths without having read the rule in the observed period." It doesn't
support "ignored robots.txt." Those two sentences differ the way a
measurement differs from an accusation. OpenAI documents GPTBot as a
training agent and advises blocking it through robots.txt, and the
`Disallow: /` rule for it had been live since July 25. Three requests on
one date prove the case exists, not how often it happens.

**Two observations outside the hypotheses:**

- **Requests that declare themselves ClaudeBot** fetched `/robots.txt` 424
  times in the period and **no page**. Until September 13, Anthropic's IP
  list wasn't consulted, so some of them are claims, not verified identity.
  Anthropic documents that ClaudeBot respects robots.txt, and what I
  observed is consistent with that.
- **Requests that declare themselves Claude-SearchBot** spent almost
  everything on the sitemap and robots.txt (648 and 250 of 939), leaving 41
  page fetches in 58 days. Before September 13, the same verification
  caveat applies.

**Why the overall share stays out.** By design, the network identifier
changes every month, so no history builds up. That makes excluding my own
traffic a month-by-month job. A VPN exit I used was also identified only
for September. The exclusion ended up larger than in the first look and
still isn't complete, so any overall percentage would carry an error of
unknown size. That's not true of the third hypothesis's comparison. All of
my traffic identified later had browser headers, and the compared group is
the one without them, so its numbers didn't change with the correction.

**The lesson that changed everything that came next** is that a zero
without a positive control isn't a measurement. A honeypot with no hits and
an `llms.txt` with no followers didn't show whether the instrument would
see an agent that did come. So the next step was to provoke visits on
purpose, at a scheduled time:

- [what ChatGPT and Claude read from a Next.js page](/en/blog/does-chatgpt-read-javascript)
- [which AI assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript),
  with Gemini, DeepSeek, and Grok, three agents that don't always identify
  themselves

Every provoked visit showed up in the instrument. For a one-page summary of
the pilot and positive control, see
[the case study](/en/case-studies/ai-crawler-detection).

**What isn't in progress.** I logged a second version of the instrument on
September 20, with seven new hypotheses covering automation signals in the
browser, discovery channels, and a canary that only exists in the
repository. Its instruments haven't been built yet, no window is open, and
this article promises no date. You'll find the full record, with limits and
corrections, in
[`docs/experiment-log.md`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/experiment-log.md).
