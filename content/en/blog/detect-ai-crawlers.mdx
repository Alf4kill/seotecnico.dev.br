There is no way to prove that AI does **not** use your content. What exists are
three things you can measure with your own server's logs: **which agents fetch
your pages**, **whether the identity they claim is true** and **whether they
respect robots.txt**. This site has measured all three in production since July
2026, with a honeypot in robots.txt, identity verification by IP range, reverse
DNS and cryptographic signature, and telemetry that separates browsers from
automated clients. This article shows the method, the code, the first 28 days
of numbers, and three defects the first reading found in the instrument itself.

## What can and can't be measured

The question "does AI use my content?" is four different questions, and only
some of them have an answer on a web server:

| Question | Does it have an answer? | With what |
|---|---|---|
| Did this request come from an automated client? | **Yes**, with good confidence | The shape of the headers and the comparison with the visits that run JavaScript |
| Which agent made the request? | **Partly** | Published IP ranges, reverse DNS and Web Bot Auth signatures, and only for vendors that publish one of those three |
| Was it for training a model? | **No** | Only the vendor knows. The most you can do is cite its documentation on the agent's purpose |
| Did robots.txt allow it? | **Yes**, exactly | What the file said for that agent at the time of the request |

The asymmetry organizes everything else. **Authorization is a fact** the site
controls. **Purpose is a citation**, never an inference. And **absence can't be
proven**: a crawler that doesn't identify itself, a copy of your article on
another domain or a dataset already published are out of reach of any server.
Any text that promises to "find out whether AI trained on your site" is selling
the fourth answer, which doesn't exist.

## A user agent is a claim, not an identity

The `User-Agent` header is text the client chooses. A `curl` with `-A "GPTBot"`
sends exactly the same header as the real GPTBot. That is why this site's
telemetry treats the user agent as a **claim** and only speaks of identity when
the request passes a source published by the vendor itself. There are three,
from strongest to weakest:

1. **Web Bot Auth signature** (HTTP Message Signatures, RFC 9421). The client
   signs the request with an Ed25519 key published on the domain it declares in
   the `Signature-Agent` header. It is cryptography, and it doesn't depend on the
   user agent. What it proves is precisely this: **whoever controls that domain
   signed**; anyone can publish keys on their own domain, so the domain *is* the
   identity. Google signs some `Google-Agent` requests this way, on an
   experimental basis (documentation of 2026-05-04), and the specification is
   still an Internet-Draft.
2. **Published IP ranges.** OpenAI, Perplexity, Microsoft, Apple, Anthropic and
   Common Crawl publish JSON lists of their crawlers' addresses. The request's IP
   inside a range is verified identity.
3. **Confirmed reverse DNS.** The IP's reverse name ends in the domain documented
   by the vendor (`.search.msn.com` for Bingbot, `.crawl.commoncrawl.org` for
   CCBot) **and** that name resolves back to the same IP. Without the return
   trip, the reverse name is controlled by whoever owns the IP.

Out of that process come the verdicts the telemetry records. The type is this,
copied from the production code:

```ts
// src/lib/crawler-verification.ts
export type Verdict =
  | 'verified-ip'
  | 'verified-signature'
  | 'verified-rdns'
  | 'impersonated'
  | 'unverifiable'
  | 'unknown-agent'

export interface VerificationResult {
  agent: string | null
  verdict: Verdict
  /** Which published source produced the verdict, for the log record. */
  evidence: string | null
}
```

Two of those verdicts are findings, not failures, and confusing them would be the
worst possible mistake in this kind of measurement:

- **`impersonated`** only exists when there was a source to check and the
  request failed it. An IP outside OpenAI's ranges claiming to be GPTBot is a
  request **that claims to be GPTBot and didn't come from OpenAI**, never "GPTBot
  did such and such".
- **`unverifiable`** is the vendor that publishes nothing. Bytespider
  (ByteDance) and meta-externalagent (Meta) are in that group. Calling that
  traffic fake would be inventing a proof that doesn't exist.

There is also an elegant shortcut: `Google-Extended` and `Applebot-Extended` are
**robots.txt tokens**, not crawlers; the vendors document that no request
carries those names. A user agent claiming to be one of them is fake by
construction.

The list of who publishes what changes, and that is data too. Anthropic
publishes the ranges of its three agents in a single list, linked from a page
of 2026-04-07; Common Crawl publishes ranges and reverse DNS. **This site only
incorporated both on 2026-09-13**; until then, requests claiming to be those
agents came out as `unverifiable`. A verification list ages silently; checking
the sources before publishing any number is part of the method.

## The honeypot: a URL that only exists in robots.txt

This site's robots.txt has a `Disallow` line for a lab route with a random name.
That URL is not in the sitemap, doesn't appear in the internal search, has no
link on any page, and doesn't appear in this article, for the same reason. The
only way to get to it is to **read robots.txt and choose to fetch what it
forbids**. The list of blocked paths is declared like this (the Portuguese
comment says the robots trap exists ONLY in this Disallow line, outside the
sitemap, outside llms.txt, linked from nowhere; whoever gets there parsed this
file and chose to fetch what it forbids; and that the llms.txt trap is kept out
of here on purpose, since listing it would contaminate channel attribution):

```ts
// src/app/robots.ts
// O trap de robots (docs/detection-experiment.md §4) existe APENAS nesta
// linha de Disallow: fora do sitemap, fora do llms.txt, sem link de lugar
// nenhum. Quem chega lá parseou este arquivo e escolheu buscar o que ele
// proíbe. O trap de llms.txt (TRAP_LLMS_PATH) fica fora daqui de propósito —
// listá-lo contaminaria a atribuição de canal.
const DISALLOWED_PATHS = ['/api/', TRAP_ROBOTS_PATH]
```

Three limits have to be stated alongside:

- **The honeypot only catches those who read robots.txt.** A client that never
  opens the file never discovers the URL. It detects deliberate disregard, not
  ignorance, which is a narrower and stronger claim.
- **It doesn't identify anyone.** robots.txt is the same file for everyone, so
  creating one URL per agent would prove nothing. Attribution comes from
  verifying the identity of the access itself.
- **It isn't a punitive trap.** It generates no junk, doesn't lock the client in
  a maze of links, doesn't try to poison anything. The page explains what it is to
  whoever lands on it, and sends `noindex` in the header. It is the combination the
  [article on redirects and canonicals](/en/blog/nextjs-redirects-canonicals)
  advises against on a real page (`Disallow` plus `noindex`), used here on
  purpose: whoever obeys robots.txt never arrives, and whoever disobeys can't
  index it.

A second honeypot follows the same logic for another channel: a URL that only
exists as a link inside `llms.txt`. An access to it proves the client reads
`llms.txt` **and follows** the file's links, the strong form of the question
"does any agent use llms.txt?".

## The two-pipeline delta

Crawlers don't run JavaScript. So the question "is this request from a
browser?" has an answer that doesn't depend on any header: **was there a
matching visit with JavaScript?**

The server records every page request in a separate analytics property. The
property for human visits only receives an event when JavaScript runs in the
browser. A document request with no matching visit is a client that doesn't run
JavaScript. The obvious confusion (the visitor who declines cookies) had
already been ruled out by an earlier decision: this site's Consent Mode is the
advanced kind, so whoever declines the banner still generates a cookieless
measurement.

Per request, the classification uses what a browser always sends and a raw HTTP
client almost never sends (the comment says: Mode + Dest, because Node's `fetch`
sends only the Mode):

```ts
// src/proxy.ts
function classifyUa(request: NextRequest, crawler: AiCrawler | undefined): UaClass {
  if (crawler) return 'declared-ai'
  // Mode + Dest: o `fetch` do Node manda só o Mode (lib/fetch-metadata.ts).
  const hasSecFetch = hasBrowserFetchMetadata(request.headers)
  const acceptsHtml = request.headers.get('accept')?.includes('text/html') ?? false
  return hasSecFetch && acceptsHtml ? 'browser-like' : 'unknown'
}
```

Until 7 October 2026, the signal was just the presence of `Sec-Fetch-Mode`.
Node's native `fetch` sends that header without `Sec-Fetch-Dest`, so a client
built with it that asked for HTML was counted as a browser. The fix started
requiring the pair, and the cut-off date is in the log. The case is in the
[article on Sec-Fetch-Mode](/en/blog/sec-fetch-mode-header).

No IP address, raw header or full user agent leaves the server. To correlate
requests from the same network without identifying anyone, the telemetry
records a truncated hash of the subnet, with a salt that changes every month.

In words, the figure's sequence:

| # | Question | If the answer is… | Result |
|---|---|---|---|
| 1 | Is it a Next.js RSC request? | yes | Not counted: it is browser navigation |
| 2 | Does it carry a valid Web Bot Auth signature? | yes | `verified-signature`, with the domain of whoever signed |
| 3 | Does the user agent declare a known agent? | no | No identity; behaviour signals remain |
| 4 | Does the vendor publish IPs or reverse DNS? | no | `unverifiable`, never `impersonated` |
| 5 | Is the IP on the list or does reverse DNS confirm? | yes / no | `verified-ip` or `verified-rdns` / `impersonated` |

## Why most automated traffic doesn't identify itself

Identifying yourself only pays off for those who **want to be recognized**.
Search engines want to be allowed in robots.txt. The bots that build a link
preview on WhatsApp or LinkedIn declare themselves to receive the Open Graph
tags. SEO tools publish how to verify their own crawlers so they don't get
blocked. On the other side, those who fear blocking, rate limits or charges have
every incentive to look like an ordinary browser: scrapers going through
residential proxies, headless browsers driven by scripts, vulnerability
scanners, and AI agents that open pages at a user's request with a browser user
agent.

The size of the phenomenon is large and hard to measure from outside. Imperva's
bot report published on 2026-04-29 estimates automated traffic at 53% of 2025
web traffic, against 47% human, numbers from a company that sells bot
protection, with its own definitions. Cloudflare only considers a "verified bot"
whoever passes Web Bot Auth or IP validation: everything else is, by definition,
unverified, whatever the user agent says.

The most cited public case shows why care is needed in attributing. On
2025-08-04 Cloudflare accused Perplexity of using undeclared crawlers, with a
Chrome user agent and a switched network, to get around blocks. Perplexity
replied publicly soon after that Cloudflare had confused its traffic with that of
a third-party cloud browser service. The two versions are still in dispute, and
neither is an established fact, which is exactly the point: without verified
identity, browser-like traffic has no owner.

## What the first reading revealed: three defects in the instrument itself

A lab that only publishes what worked is not a lab. The interim reading existed
precisely to find collection errors in time, and it found them.

**1. Human browsing counted as unidentified traffic.** Every visit in a browser
makes Next.js prefetch the page's visible links with RSC requests, which carry
the `rsc: 1` header and don't ask for HTML. The classification above marked them
as `unknown`. The clue was in the data: the six pages most "accessed" by
unidentified clients from the author's network were exactly the header and
footer links. In a local production build, a single visit to an article
prefetched those same six routes. The fix takes those requests out of the proxy
before any counting:

```ts
// src/proxy.ts
  matcher: [
    {
      source:
        '/((?!api/|_next/static|_next/image|images/|favicon.ico|icon.svg|opengraph-image|.*/opengraph-image$|.*\\.(?:png|jpg|jpeg|webp|avif|svg|ico|woff2?)$).*)',
      missing: [
        { type: 'header', key: 'rsc' },
        { type: 'header', key: 'next-router-prefetch' },
      ],
    },
  ],
```

For data before the fix, the rule was recorded before any new reading: the
"non-browser" group is the requests **without** `Sec-Fetch-*` headers, which the
browser sends even on RSC requests.

**2. A verified signature without the name of who signed.** Since a Web Bot Auth
signature only proves that a domain's owner signed, the domain is the whole
identity. The verdict was recorded; the domain wasn't. The period's 64 signed
requests say "someone signed" and nothing more. Since 13 September the signer's
domain is recorded along with it.

**3. The current Web Bot Auth format was rejected.** The March 2026 version of
the specification changed the `Signature-Agent` header to a dictionary
(`agent1="https://…"`), which is the format Google uses. The verifier only
accepted the previous format, so a valid signature in the new format would never
be verified here. Also fixed on 13 September.

**And a process error.** The only access to the robots.txt honeypot in the period
was a `curl` sent by the lab itself during an indexing audit, on 2026-09-11. No
crawler fell into the trap: it was us. The access was identified, excluded along
with all the traffic from the author's network, and it became a rule: any test
request sent to production is recorded in the measurement plan, with its time,
before the end of the work session.

## What this site forbids itself to publish

The rules came before the data, and they apply to this whole article, including
the results in the next section:

1. An agent is only **named** as the author of a behaviour with three proofs
   together: verified identity, a dated observation on this domain and the
   purpose declared by the vendor itself.
2. Traffic that **claims** to be an agent and fails verification is reported as
   a claim, never under the vendor's name.
3. Counts, dates and definitions. Not adjectives.
4. Every inferred classification is called inferred, in the text and not in a
   footnote.
5. When the vendor has a public position on the observed behaviour, it appears
   next to the observation.
6. Hypotheses that fail are published too.
7. Before publishing any case of forgery, the verification is redone against the
   vendor's list downloaded that day, and the sentence says "outside the ranges
   published on such a date".

Ignoring robots.txt is not a crime: the file is a voluntary request. This site
measures who honours the request, and makes no legal claim at all.

## What the pilot showed

The measurement round was closed on **20 September 2026**, with 57 of the 90
planned days, and reclassified as a **pilot**. The defects described above were
found with it in progress, and an instrument fixed halfway through doesn't
measure the same thing from start to finish. The closing coincided with the
site's visual redesign, which changed every page served.

The verdicts cover 25 July to 20 September: **5,480 events**, after excluding
1,728 from the author's own network (24% of everything recorded).

| Hypothesis, registered before the data | Verdict | What supports it |
|---|---|---|
| Some crawler falls into the robots.txt honeypot | **Falsified** | Zero real accesses; the period's two were the lab's own tests. With 1,191 readings of robots.txt, following the forbidden line happens at most once in every 398 readings |
| A verified training agent fetches a forbidden page | **Confirmed** | On 30 July, GPTBot, with an IP inside the list OpenAI publishes, fetched three forbidden paths: `/`, `/feed.xml` and `/politica-de-privacidade` |
| Unidentified traffic exceeds that of declared, blocked agents | **Confirmed, comfortably** | Unidentified and with no browser headers: 1,326 events from 436 networks. Declared and blocked: 425 events from 7 networks. That is **62 times more networks** |
| Conditional requests indicate a search agent | **Falsified** | Claude-SearchBot and OAI-SearchBot sent none (0 of 939 and 0 of 182). The ones that send them are Bingbot (52 of 96) and, above all, unidentified traffic: 762 of the 814 |
| Updating an article attracts more readings by search agents | **Inconclusive** | The test needed at least 5 readings of the article in 14 days; the real pace was 0.47 per article every 14 days, ten times less |
| No agent follows `llms.txt` to the honeypot | **Supported, but without power** | Zero accesses, but `llms.txt` was read only 9 times in 57 days. With so little exposure, "nobody follows" can't be told apart from "almost nobody reads" |

**The caveat that comes with the only confirmed case.** GPTBot didn't fetch
`/robots.txt` once in the period. The data supports "fetched forbidden paths
without having read the rule in the observed period". It doesn't support
"ignored robots.txt", and the difference between those two sentences is the
difference between a measurement and an accusation. OpenAI documents GPTBot as a
training agent and advises blocking it through robots.txt; the `Disallow: /`
rule for it had been live since 25 July. Three requests on one date prove that
the case exists, not how often it happens.

**Two observations outside the hypotheses:**

- **Requests declaring themselves ClaudeBot** fetched `/robots.txt` 424 times in
  the period and **no page**. Until 13 September, Anthropic's IP list wasn't
  consulted, so part of them is a claim, not verified identity. Anthropic
  documents that ClaudeBot respects robots.txt, and what was observed is
  compatible with that.
- **Requests declaring themselves Claude-SearchBot** spent almost everything on
  the sitemap and robots.txt: 648 and 250 of 939, leaving 41 page readings in 58
  days. The same caveat about verification before 13 September applies.

**Why the share over the total stays out.** The network identifier changes every
month, by design, so as not to accumulate history. That is why excluding the
author's traffic is a month-by-month operation. On top of that, a VPN exit the
author used was only identified for September. The exclusion became larger than in the
first reading and is still not complete. A percentage over the total would carry
an error of unknown size. The third hypothesis's comparison doesn't: all the
author's traffic identified later had browser headers, and the compared group is
the one without them. Its numbers didn't change with the correction.

**The lesson that changed the rest of the work:** a zero without a positive
control is not a measurement. The honeypot with no accesses and the `llms.txt`
with no followers didn't say whether the instrument would see an agent that came.
That is why the next step was visits provoked on purpose, at a set time:

- [what ChatGPT and Claude read from a Next.js page](/en/blog/does-chatgpt-read-javascript);
- [which AI assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript),
  with Gemini, DeepSeek and Grok, three agents that don't always identify
  themselves.

The instrument recorded every provoked visit.

promises no date. The full record, with the limits and the corrections, is in
