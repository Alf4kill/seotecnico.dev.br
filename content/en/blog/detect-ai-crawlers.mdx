There's no way to prove that AI is **not** using your content. What you can
do is measure three things with your own server logs: **which agents fetch
your pages**, **whether they are who they say they are** and **whether they
obey robots.txt**. This site has measured all three in production since July
2026, using a robots.txt honeypot, identity checks by IP range, reverse DNS
and cryptographic signature, and telemetry that separates browsers from
automated clients. This article covers the method, the code, the first 28
days of numbers, and three bugs that first look at the data turned up in the
instrument itself.

## What can and can't be measured

"Is AI using my content?" is really four separate questions, and only some
of them can be answered from a web server:

| Question | Can it be answered? | How |
|---|---|---|
| Did this request come from an automated client? | **Yes**, with good confidence | The shape of the headers, compared with visits that run JavaScript |
| Which agent made the request? | **Partly** | Published IP ranges, reverse DNS and Web Bot Auth signatures, and only for vendors that publish at least one of the three |
| Was it for training a model? | **No** | Only the vendor knows. The best you can do is cite its documentation on what the agent is for |
| Did robots.txt allow it? | **Yes**, precisely | What the file said for that agent at the time of the request |

That asymmetry shapes everything else. **Authorization is a fact** the site
controls. **Purpose is something you cite**, never something you infer. And
**absence can't be proven**: a crawler that doesn't identify itself, a copy
of your article on another domain or a dataset that's already been published
are all beyond the reach of any server. Anything that promises to "find out
whether AI trained on your site" is selling that fourth answer, and it
doesn't exist.

## A user agent is a claim, not an identity

The `User-Agent` header is whatever text the client decides to send. A
`curl` with `-A "GPTBot"` sends exactly the same header as the real GPTBot.
That's why this site's telemetry treats the user agent as a **claim** and
only talks about identity when the request matches a source the vendor itself
publishes. There are three such sources, from strongest to weakest:

1. **Web Bot Auth signature** (HTTP Message Signatures, RFC 9421). The client
   signs the request with an Ed25519 key published on the domain it names in
   the `Signature-Agent` header. It's cryptography, and it doesn't rely on the
   user agent. What it proves is exactly this: **whoever controls that domain
   signed the request**. Anyone can publish keys on their own domain, so the
   domain *is* the identity. Google signs some `Google-Agent` requests this way
   on an experimental basis (documented on 2026-05-04), and the specification
   is still an Internet-Draft.
2. **Published IP ranges.** OpenAI, Perplexity, Microsoft, Apple, Anthropic and
   Common Crawl publish JSON lists of their crawlers' addresses. If the
   request's IP falls inside one of those ranges, the identity is verified.
3. **Confirmed reverse DNS.** The IP's reverse name ends in the domain the
   vendor documents (`.search.msn.com` for Bingbot, `.crawl.commoncrawl.org`
   for CCBot) **and** that name resolves back to the same IP. Without the
   forward lookup, the reverse name is whatever the IP's owner wants it to be.

That process produces the verdicts the telemetry records. Here's the type,
copied from the production code:

```ts
// src/lib/crawler-verification.ts
export type Verdict =
  | 'verified-ip'
  | 'verified-signature'
  | 'verified-rdns'
  | 'impersonated'
  | 'unverifiable'
  | 'unknown-agent'

export interface VerificationResult {
  agent: string | null
  verdict: Verdict
  /** Which published source produced the verdict, for the log record. */
  evidence: string | null
}
```

Two of those verdicts are findings, not failures, and mixing them up would be
the worst mistake you could make in this kind of measurement:

- **`impersonated`** only applies when there was a source to check against and
  the request failed it. An IP outside OpenAI's ranges claiming to be GPTBot is
  a request **that claims to be GPTBot and didn't come from OpenAI**, never
  "GPTBot did X".
- **`unverifiable`** means the vendor publishes nothing. Bytespider (ByteDance)
  and meta-externalagent (Meta) fall into this group. Calling that traffic fake
  would mean inventing proof that doesn't exist.

There's also a neat shortcut: `Google-Extended` and `Applebot-Extended` are
**robots.txt tokens**, not crawlers, and the vendors document that no request
ever carries those names. A user agent claiming to be one of them is fake by
definition.

Who publishes what keeps changing, and that's data too. Anthropic publishes
the ranges for all three of its agents in a single list, linked from a page
dated 2026-04-07; Common Crawl publishes both ranges and reverse DNS. **This
site only added both on 2026-09-13**, so until then, requests claiming to be
those agents came out as `unverifiable`. A verification list goes stale
without anyone noticing, which is why checking the sources before publishing
any number is part of the method.

## The honeypot: a URL that only exists in robots.txt

This site's robots.txt has a `Disallow` line for a lab route with a random
name. That URL isn't in the sitemap, doesn't show up in the site search, isn't
linked from any page, and isn't in this article either, for the same reason.
The only way to find it is to **read robots.txt and decide to fetch what it
forbids**. The list of blocked paths is declared like this (the Portuguese
comment says the robots trap exists ONLY in this Disallow line, outside the
sitemap and llms.txt and linked from nowhere, so anyone who reaches it parsed
this file and chose to fetch what it forbids; it also says the llms.txt trap
is deliberately left out, because listing it here would muddy which channel
led a client to it):

```ts
// src/app/robots.ts
// O trap de robots (docs/detection-experiment.md §4) existe APENAS nesta
// linha de Disallow: fora do sitemap, fora do llms.txt, sem link de lugar
// nenhum. Quem chega lá parseou este arquivo e escolheu buscar o que ele
// proíbe. O trap de llms.txt (TRAP_LLMS_PATH) fica fora daqui de propósito —
// listá-lo contaminaria a atribuição de canal.
const DISALLOWED_PATHS = ['/api/', TRAP_ROBOTS_PATH]
```

Three limits come with it:

- **The honeypot only catches clients that read robots.txt.** A client that
  never opens the file never finds the URL. It detects deliberate disregard,
  not ignorance, which is a narrower but stronger claim.
- **It doesn't identify anyone.** robots.txt is the same file for everyone, so
  creating one URL per agent would prove nothing. Attribution comes from
  verifying the identity of the request that hits it.
- **It isn't a punitive trap.** It doesn't generate junk, doesn't lock the
  client in a maze of links and doesn't try to poison anything. The page
  explains what it is to anyone who lands on it and sends `noindex` in the
  header. That's the combination the [article on redirects and
  canonicals](/en/blog/nextjs-redirects-canonicals) warns against on a real
  page (`Disallow` plus `noindex`), used here on purpose: anything that obeys
  robots.txt never arrives, and anything that doesn't can't index it.

A second honeypot applies the same logic to another channel: a URL that
exists only as a link inside `llms.txt`. A hit on it proves the client reads
`llms.txt` **and follows** its links, which is the strongest version of the
question "does any agent use llms.txt?".

## The two-pipeline delta

Crawlers don't run JavaScript. So the question "is this request from a
browser?" has an answer that doesn't depend on any header: **was there a
matching visit that ran JavaScript?**

The server logs every page request to a separate analytics property. The
property for human visits only receives an event when JavaScript runs in the
browser. A document request with no matching visit comes from a client that
doesn't run JavaScript. The obvious objection (visitors who decline cookies)
had already been ruled out by an earlier decision: this site uses advanced
Consent Mode, so a visitor who declines the banner still sends a cookieless
measurement.

For each request, the classification relies on what a browser always sends
and a bare HTTP client almost never does (the comment says: Mode + Dest,
because Node's `fetch` only sends the Mode):

```ts
// src/proxy.ts
function classifyUa(request: NextRequest, crawler: AiCrawler | undefined): UaClass {
  if (crawler) return 'declared-ai'
  // Mode + Dest: o `fetch` do Node manda só o Mode (lib/fetch-metadata.ts).
  const hasSecFetch = hasBrowserFetchMetadata(request.headers)
  const acceptsHtml = request.headers.get('accept')?.includes('text/html') ?? false
  return hasSecFetch && acceptsHtml ? 'browser-like' : 'unknown'
}
```

Until October 7, 2026, the signal was just whether `Sec-Fetch-Mode` was
present. Node's native `fetch` sends that header without `Sec-Fetch-Dest`, so
a client built on it that asked for HTML got counted as a browser. The fix
now requires both headers, and the cutoff date is in the log. The full story
is in the [article on Sec-Fetch-Mode](/en/blog/sec-fetch-mode-header).

No IP address, raw header or full user agent ever leaves the server. To
correlate requests from the same network without identifying anyone, the
telemetry records a truncated hash of the subnet, with a salt that rotates
every month.

## Why most automated traffic doesn't identify itself

Identifying yourself only pays off if you **want to be recognized**. Search
engines want to be allowed in by robots.txt. The bots that build link
previews on WhatsApp or LinkedIn identify themselves so they get served the
Open Graph tags. SEO tools publish instructions for verifying their crawlers
so they don't get blocked. On the other side, anyone worried about being
blocked, rate-limited or charged has every reason to look like an ordinary
browser: scrapers routed through residential proxies, scripted headless
browsers, vulnerability scanners, and AI agents that open pages on a user's
behalf with a browser user agent.

The problem is big, and hard to size from the outside. Imperva's bot report,
published on 2026-04-29, puts automated traffic at 53% of web traffic in
2025, versus 47% human. Those numbers come from a company that sells bot
protection, using its own definitions. Cloudflare only counts something as a
"verified bot" if it passes Web Bot Auth or IP validation; everything else is
unverified by definition, whatever the user agent says.

The most widely cited public case shows why attribution needs care. On
2025-08-04, Cloudflare accused Perplexity of using undeclared crawlers, with
a Chrome user agent and rotating networks, to get around blocks. Perplexity
responded publicly soon after, saying Cloudflare had confused its traffic
with that of a third-party cloud browser service. Both accounts are still
disputed and neither is established fact, which is exactly the point: without
verified identity, browser-like traffic has no owner.

## What the first look revealed: three bugs in the instrument itself

A lab that only publishes what worked isn't a lab. The interim look at the
data existed precisely to catch collection errors in time, and it did.

**1. Human browsing counted as unidentified traffic.** Every browser visit
makes Next.js prefetch the page's visible links with RSC requests, which carry
an `rsc: 1` header and don't ask for HTML. The classification above marked
them as `unknown`. The clue was in the data: the six pages most "visited" by
unidentified clients from the author's network were exactly the header and
footer links. In a local production build, a single visit to an article
prefetched those same six routes. The fix removes those requests in the proxy
before anything is counted:

```ts
// src/proxy.ts
  matcher: [
    {
      source:
        '/((?!api/|_next/static|_next/image|images/|favicon.ico|icon.svg|opengraph-image|.*/opengraph-image$|.*\\.(?:png|jpg|jpeg|webp|avif|svg|ico|woff2?)$).*)',
      missing: [
        { type: 'header', key: 'rsc' },
        { type: 'header', key: 'next-router-prefetch' },
      ],
    },
  ],
```

For data from before the fix, a rule was written down before any new look at
the numbers: the "non-browser" group is the set of requests **without**
`Sec-Fetch-*` headers, which browsers send even on RSC requests.

**2. A verified signature with no record of the signer.** Since a Web Bot Auth
signature only proves that the owner of a domain signed, the domain is the
entire identity. The verdict was recorded, but the domain wasn't, so the
period's 64 signed requests say "someone signed" and nothing more. Since
September 13, the signer's domain is recorded alongside the verdict.

**3. The current Web Bot Auth format was rejected.** The March 2026 version of
the specification changed the `Signature-Agent` header to a dictionary
(`agent1="https://…"`), which is the format Google uses. The verifier only
accepted the older format, so a valid signature in the new format would never
have been verified here. Also fixed on September 13.

**And one process error.** The only hit on the robots.txt honeypot during the
period was a `curl` the lab itself sent during an indexing audit on
2026-09-11. No crawler fell into the trap; it was us. The hit was identified
and excluded along with all traffic from the author's network, and it became a
rule: any test request sent to production gets logged in the measurement plan,
with its time, before the work session ends.

## What this site won't let itself publish

The rules were written before the data came in, and they apply to this entire
article, including the results in the next section:

1. An agent is only **named** as responsible for a behavior when three proofs
   line up: verified identity, a dated observation on this domain and the
   purpose the vendor itself declares.
2. Traffic that **claims** to be an agent and fails verification is reported
   as a claim, never under the vendor's name.
3. Counts, dates and definitions. No adjectives.
4. Every inferred classification is labeled as inferred, in the text itself,
   not in a footnote.
5. When the vendor has a public position on the behavior observed, it's shown
   next to the observation.
6. Hypotheses that fail get published too.
7. Before publishing any case of impersonation, the check is rerun against the
   vendor's list downloaded that same day, and the sentence says "outside the
   ranges published on [date]".

Ignoring robots.txt isn't a crime: the file is a voluntary request. This site
measures who honors that request, and makes no legal claims whatsoever.

## What the pilot showed

The measurement period was closed on **September 20, 2026**, at 57 of the 90
planned days, and reclassified as a **pilot**. The bugs described above were
found while it was running, and an instrument that gets fixed halfway through
isn't measuring the same thing from start to finish. The cutoff also lined up
with the site's visual redesign, which changed every page served.

The verdicts cover July 25 to September 20: **5,480 events**, after excluding
1,728 from the author's own network (24% of everything recorded).

| Hypothesis, registered before the data | Verdict | Evidence |
|---|---|---|
| Some crawler falls into the robots.txt honeypot | **Falsified** | Zero genuine hits; the two in the period were the lab's own tests. Across 1,191 fetches of robots.txt, following the forbidden line happens at most once every 398 fetches |
| A verified training agent fetches a forbidden page | **Confirmed** | On July 30, GPTBot, from an IP inside the list OpenAI publishes, fetched three forbidden paths: `/`, `/feed.xml` and `/politica-de-privacidade` |
| Unidentified traffic exceeds traffic from declared, blocked agents | **Confirmed, by a wide margin** | Unidentified and with no browser headers: 1,326 events from 436 networks. Declared and blocked: 425 events from 7 networks. That's **62 times as many networks** |
| Conditional requests point to a search agent | **Falsified** | Claude-SearchBot and OAI-SearchBot sent none (0 of 939 and 0 of 182). The ones that do send them are Bingbot (52 of 96) and, above all, unidentified traffic: 762 of the 814 |
| Updating an article attracts more fetches from search agents | **Inconclusive** | The test needed at least 5 fetches of the article within 14 days; the actual rate was 0.47 per article every 14 days, a tenth of that |
| No agent follows `llms.txt` to the honeypot | **Supported, but underpowered** | Zero hits, but `llms.txt` was only fetched 9 times in 57 days. With so little exposure, "nobody follows it" can't be told apart from "almost nobody reads it" |

**The caveat that comes with the only confirmed case.** GPTBot didn't fetch
`/robots.txt` even once during the period. The data supports "fetched
forbidden paths without having read the rule during the observed period". It
doesn't support "ignored robots.txt", and the gap between those two sentences
is the gap between a measurement and an accusation. OpenAI documents GPTBot as
a training agent and recommends blocking it in robots.txt; the `Disallow: /`
rule for it had been live since July 25. Three requests on a single date
prove the case exists, not how often it happens.

**Two observations outside the hypotheses:**

- **Requests identifying themselves as ClaudeBot** fetched `/robots.txt` 424
  times during the period and **not a single page**. Until September 13,
  Anthropic's IP list wasn't being checked, so some of these are claims, not
  verified identities. Anthropic documents that ClaudeBot honors robots.txt,
  and what was observed is consistent with that.
- **Requests identifying themselves as Claude-SearchBot** went almost entirely
  to the sitemap and robots.txt: 648 and 250 of 939, leaving 41 page fetches
  in 58 days. The same caveat about verification before September 13 applies.

**Why the share of the total stays out.** The network identifier rotates every
month by design, so that no history builds up. That makes excluding the
author's traffic a month-by-month job. On top of that, a VPN exit node the
author used was only identified for September. The exclusion grew larger than
in the first look and is still incomplete, so a percentage of the total would
carry an error of unknown size. The third hypothesis's comparison doesn't
have that problem: all of the author's traffic identified later had browser
headers, and the group being compared is the one without them. Its numbers
didn't change after the correction.

**The lesson that changed the rest of the work:** a zero without a positive
control isn't a measurement. The honeypot with no hits and the `llms.txt` with
no followers couldn't tell us whether the instrument would have seen an agent
that did show up. So the next step was to trigger visits on purpose, at a
known time:

- [what ChatGPT and Claude read from a Next.js page](/en/blog/does-chatgpt-read-javascript);
- [which AI assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript),
  with Gemini, DeepSeek and Grok, three agents that don't always identify
  themselves.

The instrument recorded every one of those visits.

**What isn't in progress.** A second version of the instrument was registered
on September 20, with seven new hypotheses: automation signals in the browser,
discovery channels and a canary that exists only in the repository. Its
instruments haven't been built, no window is open, and this article doesn't
promise a date. The full record, limits and corrections included, is in
[`docs/experiment-log.md`](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/experiment-log.md).
The [AI crawler detection case study](/en/case-studies/ai-crawler-detection)
sums up the pilot and the positive control on a single page.
