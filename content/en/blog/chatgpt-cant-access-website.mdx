When ChatGPT, Gemini or Claude says it can't access your website, that's a
sentence the model wrote, not an error code. This site's tests produced both
situations: sometimes no request reached the server at all, and sometimes a
request did arrive, got a response, and the assistant still said it hadn't.
So the first place to look is the log, not the answer. Check in this order:
the server log, the HTTP status, robots.txt, the firewall or CDN, and whether
the content is in the first-render HTML, before any JavaScript runs.

## Short answer: five causes and what each looks like in the log

| Cause | What shows up in the log | Seen in the tests? |
|---|---|---|
| The assistant answers from an index and doesn't fetch the page | No request from the on-demand agent when the question was asked | Yes: Perplexity free, Sep 2026 |
| The tool got the file, but the model said it didn't | A request at the time of the question, with a response | Yes: Gemini free, Oct 2026 |
| The assistant's environment can't reach the site | No request | Yes: Claude and Gemini, Oct 2026 |
| The content only exists after JavaScript | The request may be there, but the passage isn't in the served HTML | Yes: ChatGPT, Claude and Gemini, Sep–Oct 2026 |
| A block on your server or CDN | A 403 or a challenge, or nothing at the origin if the block happens at the edge | No |

Three of these causes leave the same trace in the origin log: nothing. A
missing request doesn't tell you whether the assistant used an index, whether
its environment never got out to the internet, or whether a CDN stopped the
request first. To tell them apart, you also have to look at whatever sits in
front of your server.

A note on how I know who requested each page. In [this site's
lab](/en/blog/which-ai-assistants-run-javascript), each assistant gets its
own secret URL, so when that URL shows up in the log, the URL itself
identifies the assistant, not the user agent. Your log won't have that. You
have a profile (user agent, IP, time), and you have to verify identity by
checking the IP against the ranges the vendor publishes. The method is
explained in the [AI crawler detection case
study](/en/case-studies/ai-crawler-detection).

The same decision tree, as text:

1. Did a request from the agent arrive when the question was asked? If
   **not**, it's one of three causes: the assistant answered from an index,
   its environment can't reach the site, or something is blocking it at the
   edge. Look for a 403 or a challenge in the CDN or firewall log.
2. If **yes**, was the status 200? If not, the problem is on the server (a
   403, a redirect loop, a 5xx).
3. If it was 200, is the content in the served HTML? If not, it depends on
   JavaScript.
4. If it is, the server did its job. The problem is in the model's answer,
   as in the Gemini case described below.

## 1. The assistant answers from an index and doesn't fetch the page live

Some assistants answer from their own index, built ahead of time by a
crawler, instead of fetching the page when the question comes in. If the page
isn't in that index, there's nothing to answer from, and your server sees
nothing.

That's what happened with Perplexity on the free plan, over 5 rounds on
September 25, 2026, in the [first control test with ChatGPT, Claude and
Perplexity](/en/case-studies/ai-crawler-detection). In two months of logs up
to that date, not one request identifying itself as Perplexity-User (the
agent Perplexity documents for on-demand fetches) reached the server. Over
the same period, 6 requests from PerplexityBot, the indexer, did arrive, all
from IPs in the ranges Perplexity publishes. When I asked about the home
page, which had already been crawled, the answer came back correct without
any request reaching the server.

That's 5 rounds, on one site, on one plan. It says nothing about how
Perplexity behaves on the paid plan, which I didn't test.

**In the log:** no request from the on-demand agent at the time of the
question. Requests from the indexer, if there are any, show up on other days.
If the indexer has never visited the page, the page can't be in its index,
so the thing to check is that nothing is preventing the crawl: robots.txt and
the firewall, covered below.

## 2. The tool got the file, and the model said it didn't

This is the strongest argument for starting with the log. In the
experiment [Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript), I gave Gemini, on
the free plan, the page's address and the direct address of a JSON file the
page uses, in 3 rounds. Every time, the server logged the page and the JSON
being requested in the same second, and served both. Gemini reported the
page's content, but all three answers said the JSON couldn't be accessed. In
round 47, on October 2, 2026, it said it was "not possible to access the
endpoint" (translated from Portuguese).

The log can't explain why the answer contradicts the record, and I'm not
going to guess. What the log does show is that, in this case, there was
nothing to fix on the server. More cases where an AI's explanation
contradicts the server are covered in [SEO audit with
ChatGPT](/en/blog/seo-audit-with-chatgpt).

**In the log:** a request at the time of the question, with a response. The
next step is to confirm that the passage you want cited is in the served HTML
(section 4). If it is, the server delivered what it should have, and the
problem is on the assistant's side.

## 3. The assistant's environment can't reach the site

For some tasks, some assistants run code in a sandbox with restricted network
access. A failure there never touches your server.

In the same experiment, in the condition where the prompt said where each
piece of data was, Claude on the Pro plan said it couldn't download the raw
HTML from its terminal because the domain wasn't on its environment's network
allowlist (round 41, October 2, 2026). It gave the same explanation in all six
rounds with a hint. In the same condition, Gemini on the free plan wrote and
ran a Python script to fetch the page in rounds 42, 52 and 62, also on
October 2, and all three runs failed with a DNS resolution error. Neither path
sent a single request to the server.

One distinction matters here: the allowlist explanation comes from Claude,
not from my log. The log only confirms the part that fits it, which is the
absence of a request. An assistant's explanation isn't data; I include it only
because the server log is consistent with it.

**In the log:** nothing. On its own, the origin log can't distinguish this
case from the index case (section 1) or from an edge block (section 5).

## 4. The content only exists after JavaScript

If the content is inserted in the browser after JavaScript runs, it isn't in
the HTML the server sends. An assistant that only reads that HTML won't find
the content, even if the request arrives and gets a 200.

In the experiment, with the neutral prompt, three assistants never cited the
code that only existed after JavaScript: ChatGPT (Go plan) 0 of 5, Claude
(Pro plan) 0 of 5 and Gemini (free) 0 of 8, between September 25 and
October 2, 2026. Zero out of five doesn't prove it never happens. It proves
it didn't happen in those rounds.

**In the log:** the request may look perfectly normal, with a 200 status.
The server did its job; what's missing is missing from the HTML. To check,
request the page without running JavaScript and search for the passage:

```bash
curl -s https://your-site.com/your-page | grep -o "the passage that needs to be cited"
```

If the command prints nothing, the passage isn't in the served HTML. For the
title, description and Open Graph tags, the [meta tag
validator](/en/tools/meta-tag-validator) shows what the page actually sends.

## 5. A block on your server or CDN (not observed here)

I **didn't observe** this cause. During the tests, this site had Bot
Protection turned off and the AI Bots rule set to Allow in the Vercel
firewall, a configuration I checked on September 25, 2026 and again on
October 4, 2026. What follows is conditional, not measured.

If a firewall rule, a security plugin or the CDN blocks the agent, you'll see
a 403 or a challenge in the log of whichever layer blocked it. If the block
happens at the edge, the origin server may log nothing, and in the origin log
this case looks exactly like sections 1 and 3. So it's worth opening the
CDN's log and dashboard as well.

One concrete example of a default that changed in 2026: according to
[Cloudflare's July 1, 2026
changelog](https://developers.cloudflare.com/changelog/post/2026-07-01-ai-traffic-options/),
domains added to Cloudflare from September 15, 2026 onward have the Training
and Agent categories blocked by default on pages that show ads. Cloudflare
defines Agent as automated activity acting in real time on a person's behalf,
such as chat fetch bots. If your domain falls into that group and the page
carries ads, a request from an assistant may be stopped before it reaches
your origin. The setting lives in the dashboard's security settings, under
the AI bot policies
([documentation](https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/)).

robots.txt belongs here too, with one wrinkle: the agents that fetch a page
at a user's request don't all treat robots.txt the same way. According to
each vendor's documentation, as of October 4, 2026:

- **OpenAI:** for ChatGPT-User, the [bots
  page](https://developers.openai.com/api/docs/bots) says that because these
  actions are initiated by a user, robots.txt rules may not apply.
- **Perplexity:** the [bots documentation](https://docs.perplexity.ai/docs/resources/perplexity-crawlers)
  says that Perplexity-User generally ignores robots.txt rules, since a user
  requested the fetch.
- **Anthropic:** the [help
  center](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)
  says the company's bots honor robots.txt directives, and that disabling
  Claude-User prevents content from being retrieved in response to a user.

In practice, a `Disallow` might explain why one assistant fails and not
another. I didn't test any of these behaviors; this site's robots.txt allows
all three agents.

**In the log:** a 403 or a challenge in whichever layer did the blocking, or
no request at the origin. Check the bot rules in the dashboard of every layer
in front of your server.

## How to check: a step-by-step checklist

1. **Server log.** Look for the agent's requests around the time the question
   was asked (sample command right after this list).
2. **HTTP status.** A 200 means the server delivered the page. A 403 points
   to a block. A chain of 3xx responses may be a redirect loop. A 5xx is a
   server error.
3. **robots.txt.** Check whether any rule applies to the assistant's agent or
   indexer.
4. **Firewall and CDN.** Open the dashboard and the log of every layer in
   front of the server. No request at the origin doesn't rule out an edge
   block.
5. **Content in the first render.** Run the `curl` from section 4 with the
   passage you want cited.

For step 1, with an access log in the combined format (Nginx or Apache), here
is an illustrative command; adjust the file path:

```bash
grep -E "ChatGPT-User|Claude-User|Perplexity-User" /var/log/nginx/access.log \
  | awk '{print $4, $9, $7}'
```

It lists the date, status and path of requests that identify themselves with
those tokens. A user agent can be spoofed, so to be sure it was really the
agent, verify the IP against the ranges the vendor publishes. Not every
assistant fetches with a token of its own, and the list above doesn't cover
them all: in the experiment, Gemini identified itself only as `Google`.

Only after these five steps does the assistant's answer become a clue. Until
then, it's just a sentence.

## In Next.js (and on Vercel)

On Vercel, the two managed rulesets that matter most here are off by default,
according to the [managed rulesets
documentation](https://vercel.com/docs/vercel-firewall/vercel-waf/managed-rulesets).
Bot Protection, when turned on in challenge mode, serves a JavaScript
challenge to traffic that's unlikely to be a browser. AI Bots can only log or
deny traffic Vercel identifies as an AI bot. If you've enabled either one,
it's the first rule to check under section 5. On this site, as mentioned
above, both were permissive throughout the tests.

In Next.js, the question from section 4 becomes: is the passage rendered on
the server, or fetched in the browser after hydration? Whatever a Server
Component renders ends up in the HTML. Whatever arrives through a fetch fired
in the browser, inside a `useEffect` for example, doesn't. That's exactly how
I built the experiment's neutral condition: the code the assistants had to
cite only appeared after JavaScript ran, on purpose. The same `curl` works
for checking any page in your project, in production or on a preview
deployment.

## What the October check showed

The Perplexity figures above were measured up to September 25, 2026. Going
back over the records through October 11 didn't change any of them. Not one
request identifying itself as Perplexity-User reached the server during the
whole period. PerplexityBot came back once, on October 10: it fetched
`robots.txt` and this article, and none of the experiment's addresses. In the
tests with ChatGPT, Claude, Gemini, DeepSeek and Grok, no assistant made an
unprompted request to the secret addresses used in the second and third
rounds ([full results](/en/blog/which-ai-assistants-run-javascript)).

For the full picture of crawling, rendering and indexing, see the [technical
SEO guide for Next.js](/en/guide/technical-seo-nextjs).
