When ChatGPT, Gemini, or Claude tells you it can't access your site, that's
a sentence the model wrote, not an error code. My tests on this site turned
up both situations. Sometimes no request reached the server. Other times my
server received a request and answered it, and the assistant still said it
couldn't get the page. So start with the log, not the answer. Check in this
order: server log, HTTP status, robots.txt, firewall or CDN, and whether the
content is in the first-render HTML, before any JavaScript runs.

## Short answer: five causes and what each looks like in the log

| Cause | What shows up in the log | Seen in the tests? |
|---|---|---|
| The assistant answers from an index and doesn't fetch the page | No request from the on-demand agent when the question was asked | Yes: Perplexity free, Sep 2026 |
| The tool received the resource, but the model said it didn't | A request when the question was asked, served | Yes: Gemini free, Oct 2026 |
| The assistant's environment can't reach the site | No request | Yes: Claude and Gemini, Oct 2026 |
| The content only exists after JavaScript | The request may be there, but the passage isn't in the served HTML | Yes: ChatGPT, Claude, and Gemini, Sep–Oct 2026 |
| A block on your server or CDN | A 403 or a challenge, or nothing at the origin if the block is at the edge | No |

Three of these causes look identical in your origin log, because none of them
leaves a trace there. A missing request doesn't tell you whether the
assistant used an index, whether its environment never got out to the
internet, or whether a CDN stopped the request first. To tell them apart,
you also need to check whatever layer sits in front of your server.

How do I know who requested each page? In
[this site's lab](/en/blog/which-ai-assistants-run-javascript), each
assistant gets its own secret URL, so when one shows up in my log, it's the
URL that identifies the assistant, not the user agent. Your log won't have
that. You get a profile (user agent, IP, and time), and you verify identity
by comparing the IP with the vendor's published ranges. I explain the method
in [how to detect AI crawlers in your server
log](/en/blog/detect-ai-crawlers).

Here's the same decision tree in text:

1. Did the agent send a request when the question was asked? If **no**,
   it's one of three causes: the assistant answered from an index, its
   environment can't reach the site, or something blocked it at the edge.
   Look for a 403 or a challenge in your CDN or firewall log.
2. If **yes**, was the status 200? If not, the problem is on your server (a
   403, a redirect loop, or a 5xx).
3. If it was 200, does the served HTML contain the content? If not, the
   content depends on JavaScript.
4. If it does, your server did its part, and the problem lies in the model's
   answer, as in the Gemini case below.

## 1. The assistant answers from an index and doesn't fetch the page live

Some assistants answer from their own index, which a crawler built earlier,
instead of fetching the page when you ask. If your page isn't in that index,
the assistant has nothing to answer from, and your server sees nothing.

That's what I saw with Perplexity on the free plan, in 5 rounds on September
25, 2026, during the experiment
[Does ChatGPT read JavaScript?](/en/blog/does-chatgpt-read-javascript). In
two months of logs up to September 25, 2026, no request declaring itself
Perplexity-User reached my server. Perplexity documents that agent as its
on-demand fetcher. Over the same period, 6 requests declared themselves
PerplexityBot, its indexer, and all 6 came from IPs in Perplexity's
published ranges. When I asked about my home page, which had already been
crawled, Perplexity answered correctly without a single request arriving.

That's 5 rounds, on one site, on one plan. It says nothing about how
Perplexity behaves on the paid plan, which I didn't test.

**In the log:** no request from the on-demand agent when the question was
asked. Indexer requests, if any, show up on other days. If the indexer never
visited your page, the page can't be in its index. In that case, make sure
nothing prevents crawling. Check robots.txt and the firewall, both covered
in the sections below.

## 2. The tool got the file, and the model said it didn't

This case is the strongest reason to check your log first. In the experiment
[Which AI assistants run
JavaScript?](/en/blog/which-ai-assistants-run-javascript),
I gave Gemini (free plan) the page's address along with the direct URL of a
JSON file it uses, in 3 rounds. Each time, my server logged requests for
both in the same second and served them. Gemini reported what was on the
page, yet all three answers said the JSON couldn't be accessed. In round 47,
on October 2, 2026, Gemini said it was "not possible to access the endpoint"
(translated from Portuguese).

My log doesn't explain why the answer contradicts it, and I won't guess at a
reason. What it does show is that, in this case, there was nothing to fix on
the server. For other cases where an AI's explanation contradicts what the
server recorded, see
[my article on auditing SEO with ChatGPT](/en/blog/seo-audit-with-chatgpt).

**In the log:** a request when the question was asked, and it was served.
Next, confirm that the passage you want cited is in the served HTML
(section 4). If it is, your server delivered what it should, and the problem
is on the assistant's side.

## 3. The assistant's environment can't reach the site

In some tasks, an assistant runs code in an isolated environment with
restricted network access. When a fetch fails in there, it never touches
your server.

I saw this in the same experiment as section 2, in the "hint" condition,
where the prompt told the assistant where each piece of data was. Claude
(Pro plan) said it couldn't download the raw HTML from its terminal because
my domain wasn't on its environment's network allowlist (round 41, October
2, 2026). It repeated that explanation in all six hint rounds. Gemini (free
plan), in the same condition, wrote and ran a Python script to fetch the
page in rounds 42, 52, and 62, also on October 2. All three runs failed with
a DNS resolution error. Neither path sent a single request to my server.

Keep two things apart here. The allowlist explanation comes from Claude, not
from my log. My log confirms only the consistent part, that no request
arrived. An assistant's explanation isn't data, and I include this one only
because my server's record is consistent with it.

**In the log:** nothing. On its own, your origin log can't tell this case
apart from the index case (section 1) or an edge block (section 5).

## 4. The content only exists after JavaScript

If the browser inserts content after JavaScript runs, that content isn't in
the HTML your server delivers. An assistant that reads only that HTML won't
find it, even when its request arrives and gets a 200.

With the neutral prompt, three assistants in the experiment never cited the
code that only existed after JavaScript, in any round. Between September 25
and October 2, 2026, ChatGPT (Go plan) cited it 0 of 5 times, Claude (Pro
plan) 0 of 5, and Gemini (free plan) 0 of 8. Zero in five doesn't prove it
never happens, only that it didn't happen in those rounds.

**In the log:** the request can look normal, with a 200 status. Your server
did its part, and the gap is in the HTML. To check, request the page
without running JavaScript and search for the passage:

```bash
curl -s https://your-site.com/your-page | grep -o "the passage that needs to be cited"
```

If the command prints nothing, the passage isn't in the served HTML. For
title, description, and Open Graph tags, the
[meta tag validator](/en/tools/meta-tag-validator) shows what your page
delivers.

## 5. A block on your server or CDN (not observed here)

I **didn't observe** this cause. During the tests, this site had Bot
Protection off and the AI Bots rule set to Allow in the Vercel firewall. I
checked that configuration on September 25, 2026, and again on October 4,
2026. What follows is conditional, not a measurement.

If a firewall rule, a security plugin, or your CDN blocks the agent, look
for a 403 or a challenge in that layer's log. When the block happens at the
edge, your origin may log nothing, and this case looks just like sections 1
and 3 there. So open your CDN's log and dashboard too.

Cloudflare changed a default in 2026 that makes a concrete example. Its
[July 1, 2026,
changelog](https://developers.cloudflare.com/changelog/post/2026-07-01-ai-traffic-options/)
says that domains joining Cloudflare starting September 15, 2026, have the
Training and Agent categories blocked by default on pages that show ads.
Cloudflare's own definition of Agent covers automated real-time activity on
behalf of a person, such as chat assistants' search and fetch bots. If your
domain falls into that group and the page has ads, an assistant's request
may be stopped before it reaches your origin. You'll find the setting under
AI bot policies in the dashboard's security options (see the
[documentation](https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/)).

robots.txt belongs here too, but agents that fetch a page at a user's
request don't all treat it the same way. Here's what each vendor's
documentation said when I checked it on October 4, 2026:

- **OpenAI:** for ChatGPT-User, the
  [bots page](https://developers.openai.com/api/docs/bots) says robots.txt
  rules may not apply, because a user initiates the actions.
- **Perplexity:** the
  [bots documentation](https://docs.perplexity.ai/docs/resources/perplexity-crawlers)
  says Perplexity-User generally ignores robots.txt rules, since it fetches
  at a user's request.
- **Anthropic:** the
  [help center](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)
  says Anthropic's bots respect robots.txt directives, and that disabling
  Claude-User prevents content from being fetched in response to a user.

In practice, a `Disallow` can explain why one assistant fails and another
doesn't. I didn't test any of these behaviors, and this site's robots.txt
allows all three agents.

**In the log:** a 403 or a challenge in whichever layer blocked the request,
or no request at the origin. Check the bot rule in each dashboard, for every
layer in front of your server.

## How to check: a step-by-step checklist

1. **Server log.** Look for requests from the agent at the time the question
   was asked. A sample command follows this list.
2. **HTTP status.** A 200 means the server delivered. A 403 points to a
   block. A sequence of 3xx responses may be a redirect loop. A 5xx is a
   server error.
3. **robots.txt.** Check whether any rule matches the assistant's agent or
   its indexer.
4. **Firewall and CDN.** Open the dashboard and log of each layer in front
   of your server. No request at the origin doesn't rule out a block at the
   edge.
5. **Content in the first render.** Run the `curl` from section 4 with the
   passage you need cited.

For step 1, here's an illustrative command for an access log in combined
format (Nginx or Apache). Adjust the file path to match your server.

```bash
grep -E "ChatGPT-User|Claude-User|Perplexity-User" /var/log/nginx/access.log \
  | awk '{print $4, $9, $7}'
```

It lists the date, status, and path of each request that declares itself
with one of those tokens. A user agent can be spoofed, so before you say a
request came from the agent, verify its IP against the vendor's published
ranges. Not every assistant fetches with its own token, and the list above
doesn't cover them all. In the experiment, Gemini identified itself only as
`Google`.

Only after these five steps does the assistant's answer become a clue. Until
then, it's just a sentence.

## In Next.js (and on Vercel)

Vercel's
[managed rulesets
documentation](https://vercel.com/docs/vercel-firewall/vercel-waf/managed-rulesets)
says the two managed rulesets that matter most here are inactive by default.
When Bot Protection is active in challenge mode, it serves a JavaScript
challenge to traffic that probably doesn't come from a browser. You can set
AI Bots to just log the traffic Vercel identifies as AI bots, or to deny it.
If you've enabled either ruleset, check it first for section 5. On this
site, as I mentioned above, both were permissive during the tests.

In Next.js, section 4 comes down to one question. Is the passage rendered on
the server, or fetched in the browser after hydration? Whatever a Server
Component renders goes into the HTML. Anything that arrives through a fetch
fired in the browser, such as one inside a `useEffect`, doesn't. That's how I
built the experiment's neutral condition, where the code the assistants had
to cite appeared only after JavaScript, on purpose. You can run the same
`curl` against any page in your project, in production or on a preview
deployment.

## What the October check showed

I measured the Perplexity numbers above up to September 25, 2026. When I
checked the records through October 11, none of them changed. Over the whole
period, no request declaring itself Perplexity-User reached my server.
PerplexityBot came back once, on October 10. It fetched `robots.txt` and this
article, and it didn't request any of the experiment's addresses.

Across my tests with ChatGPT, Claude, Gemini, DeepSeek, and Grok, no
assistant came back to the second- and third-batch secret addresses outside
the rounds. You'll find the
[full results](/en/blog/which-ai-assistants-run-javascript) in the
experiment's write-up.
