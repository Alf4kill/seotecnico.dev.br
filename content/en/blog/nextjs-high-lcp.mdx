If your Next.js LCP stays high even after switching everything to
`next/image` and marking the hero as priority, the culprit is almost never
what Lighthouse points to. It's usually a pattern that hides the resource
from the preload scanner (a CSS `background-image`, a hero behind `"use
client"`), a render delay you caused yourself with an animation or an A/B
script, or a preload that competes for bandwidth and slows down the very
element it was meant to speed up. This cluster's hub explains [how LCP breaks
down into phases and how to fix each one](/en/blog/improve-lcp-nextjs); this
article covers the other side of the problem: why it **won't improve** after
you've already optimized. Each section below is one mistake: the symptom you
see in PageSpeed Insights or the waterfall, the mechanism behind it, and what
to do about it.

## `next/image` doesn't fix a hero in `background-image`

This one is frustrating precisely because everything looks right: you
switched every image to `next/image`, Lighthouse's image audit is all green,
and LCP is still high. In most diagnoses I run, when the audit passes but LCP
won't budge, the LCP element is a CSS `background-image`, and `next/image`
never touches it.

The mechanism comes down to the preload scanner. Before building the DOM, the
browser runs a secondary parser that skims the raw HTML for resources it can
start downloading early. It sees what's declared in the markup: an `<img>`
with a `src`, a `<link rel="preload">` in the `head`. A `background-image`
lives in CSS, not markup, so the scanner never sees it: the download only
gets queued once the browser has built the DOM, applied the styles and
figured out that element needs an image. Late discovery turns into a high
LCP, and the image audit flags nothing because, as far as it's concerned,
there's no misconfigured `<img>` on the page.

| The scanner sees it (discovered early) | The scanner misses it (discovered late) |
|---|---|
| `<img>` with `src` in the markup | `background-image` in CSS |
| `<link rel="preload">` in the `head` | hero behind `"use client"` |
| downloads with the HTML | only downloads after the DOM/JS |

The fix is to put the hero back in the markup. Replace the
`background-image` with a real `<img>` above the fold; in Next.js, that's a
`next/image` with the image declared in JSX:

```tsx
// app/(marketing)/hero.tsx
import Image from 'next/image'

export function Hero() {
  return (
    <section className="hero">
      <Image
        src="/hero.webp"
        alt="..."
        width={1600}
        height={900}
        preload
      />
    </section>
  )
}
```

Two things changed in Next.js 16 that are worth updating in your head: the
`priority` prop was deprecated in favor of `preload`, and for most cases the
recommendation is now `loading="eager"` or `fetchPriority="high"` rather than
an explicit preload. The practical effect is the same (restoring the early
discovery the `background-image` took away), but much of the material still
ranking for this question teaches `priority`, which no longer exists. If you
really do need a background (a decorative texture behind the content, say),
the workaround is to preload the resource yourself with a
`<link rel="preload" as="image">` in the `head`, but that only makes sense if
that background really is the LCP element.

## Hero behind `"use client"`: discovered too late

The audit passes here too, but for a different reason: the `<img>` is in the
JSX, just inside a component marked `"use client"`. In the trace, the symptom
is a hero that only appears after hydration, with LCP recorded well after what
the filmstrip suggests.

The mechanism is the same as the previous case, arrived at differently. If
the hero only comes into existence once the client component mounts in the
browser, the initial HTML the scanner reads doesn't contain that `<img>`. The
resource is invisible to early discovery, not because it's in CSS, but
because it sits behind JavaScript that hasn't run yet. The component may even
render on the server by default, but if the image depends on client state (a
`useState` value, a viewport calculation, data that only arrives after mount),
the markup SSR produces won't include it.

The fix is to keep the LCP element in a server component. Render the hero on
the server, with its `src` resolved at build or request time, and isolate the
interactive bits in a smaller island (a button, a control) instead of
wrapping the whole hero in `"use client"`. The hub covers how early discovery
works in detail in the section on [the browser needing to find the image
early](/en/blog/improve-lcp-nextjs#resource-load-delay-the-browser-needs-to-discover-the-image-early);
the point here is to recognize the pattern: if the hero depends on the client,
the scanner can't see it.

## An `@import` chain: CSS that downloads one file at a time

The last late-discovery pattern isn't an image at all; it's the CSS itself.
The symptom shows up in the waterfall: stylesheet requests cascading one
after another, each starting only when the previous one finishes, pushing
first paint to the back of the line.

The mechanism is how `@import` works. An `@import` inside a CSS file is only
discovered after the file containing it has finished downloading and been
parsed. Chaining imports (a CSS file that imports a theme, which imports the
fonts) forces the downloads into a sequence: nothing downloads in parallel,
and everything waits its turn. Since the browser needs CSS to paint, that
cascade directly delays rendering of the LCP element, whether it's an image
or text.

The fix is to flatten the chain. Replace the chained `@import`s with parallel
`<link>`s in the `head`, or let your bundler resolve the imports at build time
so the CSS arrives in a single request instead of a sequence. In Next.js,
styles imported in your components already take that optimized path; the
trap is usually third-party or legacy CSS that still uses `@import` to pull in
its dependencies. It's worth opening the waterfall to check: if stylesheets
are waiting on each other, that's where your first paint is stuck.

## A fade-in on the hero: LCP doesn't count until the animation ends

This is the first of the render delays you inflict on yourself. The symptom
is misleading: the element shows up quickly in the filmstrip, but LCP is
recorded much later. Nothing is slow to download; the problem is when the
browser considers the element "painted".

The mechanism is in LCP's definition. The browser doesn't count an element
as painted until it's actually visible, and an element with `opacity: 0` that
fades up to `1` in an entrance animation only becomes visible when the
animation ends. If your hero has a half-second fade-in, you've added half a
second of render delay to LCP, even if the image was on screen, transparent,
the whole time.

The fix is to not animate the LCP element's `opacity`. If the entrance effect
matters to the design, animate something else (a neighboring element, a
secondary detail) and let the hero paint right away. The hub covers [the
render delay phase in
detail](/en/blog/improve-lcp-nextjs#element-render-delay-the-image-has-arrived-but-still-has-to-paint);
the pattern to recognize here is that a beautiful animation on the wrong
element costs you LCP.

## An A/B testing anti-flicker snippet: rendering blocked on purpose

If you run A/B tests with a tool that injects a snippet into the `head`, you
may have imported a render delay without realizing it. The symptom is a high
render delay, with the page body hidden for the first moments of the load.

The mechanism is intentional, and that's the trap. Experimentation tools
hide the page (typically with `opacity: 0` or `visibility: hidden` on the
`<body>`) until the script decides which variant to show, so users don't see
the original version "flicker" before the variant appears. That anti-flicker
snippet blocks painting of everything, the LCP element included, by design.
The longer the script takes, the longer the render delay.

The fix depends on how much control you have over the tool. The safest
approach is to run the experiment on the server, or load it asynchronously as
early as possible with a short anti-flicker timeout, so the page isn't held
hostage by a slow script. Where the test isn't critical to the above-the-fold
area, taking the snippet out of the hero's render path removes the problem.
The principle is the same as with the fade-in: nothing that hides the LCP
element belongs on the critical path.

## Render-blocking CSS plus a font on the critical path: the text LCP

Not every LCP is an image, and when it's text, the conversation changes. The
symptom is a high LCP on an element that has nothing to download: a
paragraph, a heading. Image optimization won't help here, because the
bottleneck is the CSS and the font holding back the text's paint.

This is the case I measured on this very site, and I use it as an example
because the before-and-after is clean. The home page's LCP was a hero
paragraph, with PageSpeed Insights mobile at 78, an LCP of 4.9 s and a render
delay of 1,280 ms. Two fixes solved it: inlining critical CSS (via
`experimental.inlineCss` in the config) and loading the Inter font with
`display: 'optional'` and `preload: false`, which took the woff2 off the
critical path. The result, measured after the deploy: PSI mobile 100, an LCP
of 0.9 s, a render delay of 530 ms and zero CLS.

Both fixes work the same way: they remove obstacles between the page and the
text's first paint. External CSS is render-blocking (the browser won't paint
until it has downloaded and parsed the stylesheet), so inlining critical CSS
into the HTML removes an entire request from in front of the paint. A font on
the critical path holds text back for the same reason. With
`display: 'optional'`, the browser stops waiting for the web font and paints
with a system font, without blocking. In Next.js, `next/font` is how you do
it; the nuance is that `display: 'swap'` still leaves a swap window, and
`'optional'` is what removes the block when the LCP is text. One caveat:
those numbers come from a single measurement of mine, on one specific site;
yours will depend on your CSS and your fonts. What carries over is the
mechanism, not "4.9 s becomes 0.9 s".

## Hydration, sliders and skeletons: LCP recorded again, later

There's a class of mistake where LCP isn't high because anything is slow,
but because it got **recorded again** later. The symptom is an LCP worse than
the filmstrip suggests: the page looks ready, but the reported number is
still late.

The mechanism is that the LCP element can change while the page loads. LCP
isn't locked in at first paint: if something renders a larger element later,
the browser records LCP again at that later moment. A carousel that switches
slides after hydration, a skeleton replaced by bigger content, a block that
only reaches its final size once JavaScript runs: in each case, the "largest
element" shows up late, and LCP follows it.

The fix is to stabilize the LCP element before hydration. Render the hero at
its final size during SSR, so the largest element doesn't change once the
client takes over. If you use a skeleton, size it like the real content; a
skeleton smaller than the content makes the element grow on hydration and
resets LCP. And don't let sliders or carousels promote a larger element after
first paint. The practical rule: whatever the browser sees as the largest
element at the start needs to stay the largest.

## Too many preloads: competing for bandwidth delays LCP itself

The last mistake is the most counterintuitive, because it comes from trying
to optimize. The symptom is simple: you added a preload and LCP got worse.

The mechanism is bandwidth competition. A preload tells the browser "this is
urgent, download it now". If you mark five resources as urgent (the hero, the
font, a script, a CSS file), they fight for bandwidth with each other and
with the critical CSS and JS. When everything is urgent, nothing is: the LCP
resource that actually mattered gets drowned out by the other preloads and
arrives later than it would have on its own.

There's a nuance I measured that shows the "it depends" nicely. In the case
of the home page's text LCP, preloading the woff2 font (about 48 KB) was
**adding** roughly 1.7 s of render delay to Lighthouse's simulated LCP,
because with a text LCP and the font set to `display: optional`, that preload
only competed for bandwidth without speeding up anything that mattered.
Taking it off the critical path was one of the fixes. But the conditions
matter: a font preload isn't always bad. It's bad when the LCP is text and
the font already has a non-blocking `display`. When the font is the
bottleneck, the preload helps.

The fix is to preload only the LCP resource, nothing else. In Next.js 16,
`fetchPriority="high"` on the element itself marks the hero as a priority
without adding a separate hint, and `fetchPriority="low"` does the opposite:
it deprioritizes above-the-fold resources that aren't the LCP, freeing
bandwidth for the one that is. The hub's FAQ covers the same preload trap;
the rule I follow is that I have to be able to explain in one sentence why
each preload is there. If I can't, it goes.

## How to check that LCP really improved

None of these fixes means anything until you've confirmed they worked, and
"PSI went up" isn't enough. My routine goes from lab to field, in this order.

Start with PageSpeed Insights for the lab number and the breakdown of the
four phases, which tell you which phase got shorter. Then open DevTools, record
a trace and confirm two things: which element was recorded as LCP, and which
phase the time is going to. If the element isn't the one you expected (a
background-image, a skeleton), you've found the problem before touching any
code. Next, view the page source: does the initial markup contain the LCP
resource, or is it hidden in CSS or behind a client component? That's the
direct test of "can the scanner see this?".

Lab isn't field, and that's where RUM comes in. This site has been
collecting real users' LCP since mid-2026 (web-vitals with attribution,
sending the four subparts to GA4), though there isn't yet a statistical
window large enough to draw conclusions, and the site is still below CrUX's
traffic threshold. Even so, RUM is what closes the loop: the lab simulates,
the field measures. If your site already has enough traffic, the [Core Web
Vitals checker](/en/tools/cwv-checker) shows field data straight from CrUX,
with no instrumentation needed.

One last note on what **not** to chase. Not every PSI warning is worth
hunting down: Next.js ships about 14 KiB of legacy JavaScript (the
unconditional core-js polyfills in the framework chunk) that PSI flags and you
can't remove; a modern browserslist produces byte-for-byte identical output.
