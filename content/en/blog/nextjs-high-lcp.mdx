If your Next.js LCP is still high after you've moved every image to
`next/image` and marked the hero as priority, the culprit is almost never
what Lighthouse points to. It's usually one of three things: a pattern that
hides the resource from the preload scanner (a CSS `background-image`, a
hero behind `"use client"`), a render delay you created yourself with an
animation or an A/B script, or a preload that competes for bandwidth and
delays the very element it was supposed to speed up.

[How to improve LCP in Next.js](/en/blog/improve-lcp-nextjs) is the cluster
hub. It explains how LCP breaks down into phases and how to fix each one.
This article covers the other side: why LCP **won't improve** once you've
already optimized. Each section below is one mistake, with the symptom you'll
see in PageSpeed Insights or the waterfall, the mechanism behind it, and what
to do about it.

## `next/image` doesn't fix a hero in `background-image`

This one is frustrating because everything looks right. You've switched every
image to `next/image`, Lighthouse's image audit is all green, and LCP is still
high. In most of the cases I diagnose where the audit passes but LCP doesn't
improve, the LCP element is a CSS `background-image`, and `next/image` doesn't
touch it.

It comes down to the preload scanner. Before it builds the DOM, the browser
runs a secondary parser over the raw HTML, looking for resources it can start
downloading early. That parser sees only what's declared in the markup, such
as an `<img>` with `src` or a `<link rel="preload">` in the `head`. A
`background-image` lives in CSS, not in the markup, so the scanner never sees
it. Its download isn't queued until the browser has built the DOM, applied
styles, and worked out that this element needs an image. Discovering it that
late is what keeps LCP high. Lighthouse's image audit flags nothing, because
from its point of view there's no misconfigured `<img>` on the page.

To fix it, move the hero back into the markup. Replace the
`background-image` with a real `<img>` above the fold. In Next.js, that means
a `next/image` with the image declared in JSX:

```tsx
// app/(marketing)/hero.tsx
import Image from 'next/image'

export function Hero() {
  return (
    <section className="hero">
      <Image
        src="/hero.webp"
        alt="..."
        width={1600}
        height={900}
        preload
      />
    </section>
  )
}
```

Next.js 16 changed two things here, so update your mental model. It
deprecated the `priority` prop in favor of `preload`, and for most cases the
recommendation is now `loading="eager"` or `fetchPriority="high"` rather than
an explicit preload. Either way, the practical effect is the same. It restores the early discovery
that `background-image` took away. Much of the material that still ranks for
this question teaches `priority`, though, and that prop no longer exists.

If you do need a background, such as a decorative texture behind the
content, preload it by hand with a `<link rel="preload" as="image">` in the
`head`. Save this for a background that really is the LCP element.

## Hero behind `"use client"`: discovered too late

Here the audit passes too, but for a different reason. Your `<img>` does
exist in JSX, inside a component marked `"use client"`. A trace shows your
hero appearing only after hydration, with LCP recorded well past what the
filmstrip suggests.

It's the same problem as before, by a different route. If your hero exists
only once a client component mounts in the browser, that `<img>` isn't in the
initial HTML the scanner reads. Early discovery misses it, not because it's
in CSS this time, but because it sits behind JavaScript that hasn't run yet.

That component may even render on the server by default. But if the image
depends on client state (a `useState` value, a viewport calculation, data
that only arrives after mount), the server-rendered markup won't include it.

Keep the LCP element in a server component. Render the hero on the server,
with its `src` resolved at build or request time, and isolate the interactive
parts in a smaller island, such as a button or a control, instead of wrapping
the whole hero in `"use client"`.

I cover early discovery in detail in
[the hub's section on why a browser needs to discover an image
early](/en/blog/improve-lcp-nextjs#resource-load-delay-the-browser-needs-to-discover-the-image-early).
For now, learn to recognize the pattern. A hero that depends on the client is
invisible to the scanner.

## An `@import` chain: CSS that downloads one file at a time

This last late-discovery pattern involves the CSS itself, not an image. In
the waterfall, you'll see stylesheet requests in a cascade, each one starting
only when the previous one finishes, which pushes first paint to the end of
the queue.

Blame the way `@import` works. An `@import` inside a CSS file isn't discovered until the file that contains
it has downloaded and been parsed. Chain a few imports together (a stylesheet
that imports a theme, which imports the fonts) and you serialize the
downloads. Nothing happens in parallel, and each file waits its turn. Because
the browser needs CSS before it can paint, this cascade directly delays
rendering of the LCP element, whether it's an image or text.

Flatten the chain. Replace chained `@import`s with parallel `<link>`s in the
`head`, or let the bundler resolve the imports at build time so the CSS
arrives in a single request instead of a sequence.

In Next.js, styles you import in your components already take that optimized
path. The trap usually sits in third-party or legacy CSS that still uses
`@import` to pull in its dependencies. Open the waterfall and check. If your
stylesheets wait on each other, that's where first paint is stuck.

## A fade-in on the hero: LCP doesn't count until the animation ends

This is the first render delay you inflict on yourself, and its
symptom is misleading. Your element shows up quickly in the filmstrip, but
LCP is recorded much later. Nothing is slow to download. What matters is
*when* the browser considers the element "painted."

That follows from how LCP is defined. A browser doesn't count an element as
painted until it's actually visible, and an element that starts at
`opacity: 0` and rises to `1` in an entrance animation becomes visible only
when the animation ends. If your hero has a half-second fade-in, you've added
half a second of render delay to LCP, even if the image was on screen,
transparent, the whole time.

Don't animate the `opacity` of the LCP element. If the entrance effect
matters to the design, animate something else, such as a neighboring element
or a secondary detail, and let the hero paint immediately.

[The hub's section on render
delay](/en/blog/improve-lcp-nextjs#element-render-delay-the-image-has-arrived-but-still-has-to-paint)
covers this phase in detail. What you want to spot here is a nice animation
on the wrong element, because it costs you LCP.

## An A/B testing anti-flicker snippet: rendering blocked on purpose

If you run A/B tests with a tool that injects a snippet into the `head`, you
may have imported a render delay without noticing. It shows up as high render
delay, with the page body hidden during the first moments of the load.

Here the delay is intentional, and that's what makes it a trap. Experiment
tools hide your page until their script decides which variant to show,
typically with `opacity: 0` or `visibility: hidden` on the `<body>`, so users
never see your original version "flicker" before a variant replaces it. By
design, this snippet blocks all painting, your LCP element included. A
slower script means a longer render delay.

How you fix it depends on how much control you have over the tool. Your
safest option is to load experiments on the server, or asynchronously as
early as possible, with a short anti-flicker timeout so a slow script can't
hold your page hostage. Where a test isn't critical above the fold, taking
its snippet out of your hero's render path eliminates the problem.

It's the same principle as the fade-in. Nothing that hides the LCP element
belongs on the critical path.

## Render-blocking CSS plus a font on the critical path: the text LCP

Not every LCP element is an image, and when it's text, the problem lives
somewhere else. You'll see a high LCP on an element with nothing to download,
such as a paragraph or a heading. Optimizing images won't help, because CSS
and the font are what hold back the text's paint.

I measured this case on this site, and I use it as an example because the
before and after are clean. On my home page, the LCP element was a paragraph
in the hero. Before the fixes, PageSpeed Insights scored it 78 on mobile,
with an LCP of 4.9 s and 1,280 ms of render delay. Two changes solved it. I
inlined critical CSS with `experimental.inlineCss` in the config, and I
loaded the Inter font with `display: 'optional'` and `preload: false`, which
took the woff2 off the critical path. Measured after the deploy, mobile PSI
went to 100, LCP to 0.9 s, render delay to 530 ms, and CLS to zero.

Both fixes work the same way. They clear blockers from the path to your
text's first paint. External CSS is render-blocking. A browser won't paint
until it has downloaded and parsed its stylesheets, so inlining critical CSS
in your HTML removes a whole request from in front of the paint.
A font on the critical path holds back text for the same reason. With
`display: 'optional'`, a browser stops waiting for the web font and paints in
a system font, without blocking.

In Next.js, `next/font` is how you do this. Keep in mind that
`display: 'swap'` still leaves a swap window. When LCP is text, `'optional'`
is the setting that removes the block.

These magnitudes come from one measurement of mine, on one specific site.
Your numbers will depend on your CSS and your fonts. What transfers is the
mechanism, not the "4.9 s becomes 0.9 s."

## Hydration, sliders and skeletons: LCP recorded again, later

In this case LCP isn't high because anything is slow. It's high because the
browser **recorded it again**, later. You'll notice it when LCP looks worse
than the filmstrip suggests. The page appears ready, but the reported number
is late.

LCP can switch to a different element during the load. It isn't locked in at
first paint, so if something renders a larger element later, the browser
records LCP again at that later moment. This happens with a carousel that
changes slides after hydration, a skeleton replaced by larger content, or a
block that reaches its final size only once JavaScript runs. In each case,
the "largest element" shows up late, and LCP follows it.

Stabilize the LCP element before hydration. Render the hero at its final size
during SSR so the largest element doesn't change once the client takes over.
If you use a skeleton, give it the same size as the real content. A skeleton
smaller than the content makes the element grow on hydration, and LCP gets
recorded again. Also avoid sliders and carousels that promote a larger
element after first paint.

As a rule, whatever the browser sees as largest at the start has to stay the
largest.

## Too many preloads: competing for bandwidth delays LCP itself

This last mistake is the most counterintuitive, because it comes from trying
to optimize. You add a preload, and LCP gets worse.

It's a matter of bandwidth. A preload tells the browser "this is urgent,
download it now." Mark five resources as urgent (the hero, a font, a script,
a CSS file) and they fight over bandwidth with each other and with the
critical CSS and JS. If everything is urgent, nothing is. Your LCP resource,
the one that really mattered, gets demoted by the noise from the other
preloads and arrives later than it would have on its own.

My own measurement shows why "it depends." In the home page's text-LCP case,
preloading the woff2 font (about 48 KB) was **adding** roughly 1.7 s of
render delay to Lighthouse's simulated LCP. With text as the LCP element and
the font available with `display: optional`, that preload only competed for
bandwidth without speeding up anything that mattered. Taking it off the
critical path was one of the fixes.

A font preload isn't always bad. It's bad when LCP is text and the font
already has a non-blocking `display`. When the font is the bottleneck, the
preload helps.

Preload only your LCP resource, nothing else. In Next.js 16,
`fetchPriority="high"` on the hero element itself marks it as a priority
without adding a separate hint. `fetchPriority="low"` does the opposite. It
deprioritizes above-the-fold resources that aren't your LCP, which frees
bandwidth for the one that is. This same preload trap also comes up in the
hub's FAQ.

My rule is to be able to explain, in one sentence, why each preload is there.
If I can't, it goes.

## How to check that LCP really improved

None of these fixes counts until you've confirmed it worked, and "PSI went
up" isn't enough confirmation. My routine goes from lab to field, in that
order.

1. Run PageSpeed Insights for the lab number and the breakdown of LCP's four
   phases. It tells you which phase shrank.
2. Record a trace in DevTools and confirm two things: which element was
   marked as LCP, and which phase the time is going to. If the element isn't
   the one you expected (a background-image, a skeleton), you've found the
   problem before touching any code.
3. Use view-source to check whether the initial markup contains the LCP
   resource, or whether it's hidden in CSS or behind a client component. It's
   a direct test of "does the scanner see this?"

Lab data isn't field data, though, and for the field you need RUM. This site
has collected LCP from real users since mid-2026, using web-vitals with
attribution to send the four subparts to GA4. It doesn't have a statistical
window large enough for conclusions yet, and it's still outside CrUX because
its traffic is below the threshold. Even so, RUM closes the loop. Lab tests
simulate, and field data measures.

If your site already gets enough traffic, the
[Core Web Vitals checker](/en/tools/cwv-checker) shows field data straight
from CrUX, with no instrumentation.

**Not** every PSI flag is worth hunting down. Next.js ships about 14 KiB of
legacy JavaScript (the unconditional core-js polyfills in the framework
chunk) that PSI flags and you can't remove. A modern browserslist produces
byte-for-byte identical output. Any of the mistakes above will repay your
hours far better than chasing those 14 KiB.

To get started with verification, use
[the cluster's validators and measurement tools that I rely on in this
routine](/en/tools).
