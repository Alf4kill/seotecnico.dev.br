For Googlebot, what matters is not the acronym: it is what comes in the HTML of
the **first response**. SSG and SSR deliver the full content in that HTML and
are equivalent for indexing; ISR delivers full HTML, possibly stale between
revalidations; CSR delivers empty HTML that depends on a second rendering pass,
and it is the only one of the four that creates a real indexing risk. This
article shifts the comparison from "which is fastest" to "what the indexer
receives", and ends with what almost no guide teaches: how to **prove** which
strategy each of your routes is really using.

## The four strategies in one sentence each

- **SSG (static generation):** the HTML is built once, at build time, and
  served ready from a CDN. It is the App Router's default when the route uses
  no dynamic APIs.
- **ISR (incremental static regeneration):** SSG with an expiry date; the
  static HTML is regenerated in the background after a revalidation interval.
- **SSR (server-side rendering):** the HTML is built on every request, on the
  server, with that moment's data.
- **CSR (client-side rendering):** the server sends a skeleton and the content
  is built in the browser, by JavaScript, after load.

Notice the criterion of the list: **when the HTML gets its content**. It is the
only axis that matters for the rest of the article.

## What Googlebot actually does with your HTML

The reference here is Google Search Central's JavaScript SEO documentation, not
SERP guesswork. The process has two queues.

### The two waves: crawl and render

In the first pass, Googlebot makes the HTTP request, checks robots.txt,
receives the HTML and processes it: it extracts the links from `href`s, feeds
the crawl queue and indexes what is there. If your content is in that HTML, the
essential work is done here.

Every page with a 200 status also enters a **rendering queue**. Google's
documentation is explicit about timing: the page may stay in that queue a few
seconds, but **it can take longer**, and there is no published or guaranteed
deadline. When Google's resources allow, a headless Chromium renders the page,
runs the JavaScript, and the rendered HTML is used to (re)index and to discover
links that only exist after execution.

### Why "Google runs JavaScript" is not the end of the conversation

It is true that Google renders JavaScript, and it is the standard defence of
people who build SPAs. But the sentence hides three things. First, rendering is
**deferred and has no SLA**: critical content hanging in a queue of variable
capacity is a risk that ready HTML does not run. Second, rendering can **fail
partially** (a blocked script, a runtime error, an API timeout) and what did not
render does not exist for the index. Third, and increasingly relevant:
**Googlebot is practically the only crawler that renders**. Other search
engines' crawlers and those of AI search systems read the HTML of the first
response and stop there. On a site competing for citation in generated answers,
content that only exists after hydration is content invisible to half of its
machine readers.

## SSG: the App Router's default (and the right default for content)

In the App Router, a route with no dynamic APIs (`cookies()`, `headers()`,
`searchParams`) is static by default. For dynamic routes such as
`/blog/[slug]`, `generateStaticParams()` enumerates the paths at build time.

On this site, the slugs are derived from the content itself (the pipeline reads
the filesystem at build time), and that is the physical reason the route is
static. The Portuguese comment says that only slugs that exist in
`/content/blog` are generated, and the rest is 404:

```tsx
// src/app/(pt)/blog/[slug]/page.tsx
// Somente slugs existentes em /content/blog são gerados; o resto é 404.
export const dynamicParams = false

export function generateStaticParams() {
  return getAllPosts().map(({ frontmatter }) => ({ slug: frontmatter.slug }))
}
```

```ts
// src/lib/content.ts
/** All blog posts, newest first. Returns [] while content/blog is empty. */
export function getAllPosts(): Post[] {
  const dir = path.join(CONTENT_DIR, 'blog')
  if (!fs.existsSync(dir)) return []

  const posts = fs
    .readdirSync(dir)
    .filter((f) => f.endsWith('.mdx'))
    .map((f) => {
      const post = readMdxFile(path.join(dir, f))
      if (!post.frontmatter.category) {
        throw new Error(`[content] "blog/${f}": missing required frontmatter field "category"`)
      }
      return post
    })
    .sort((a, b) =>
      b.frontmatter.datePublished.localeCompare(a.frontmatter.datePublished)
    )
  assertBasedOn(posts, 'blog')
  return posts
}
```

`dynamicParams = false` closes the door: a slug that does not exist in the
content is a 404 at build time, not a render attempt at runtime. And the SEO
by-products follow the same logic: the [sitemap derived from the
content](/en/blog/nextjs-dynamic-sitemap) and the RSS feed are static routes
generated in the same build, so page, sitemap and feed never tell different
stories.

## SSR: when the data can't wait for the build

SSR solves a specific problem: the data changes per request or depends on who
is asking (real-time prices, per-session content). The HTML still arrives
complete in the first response, and that is what matters to the indexer.

### SSR doesn't index better than SSG: it indexes the same, more slowly

It is worth saying plainly, because the SERP treats SSR as Next.js's "SEO
mode": **for indexing, SSR and SSG are equivalent**. Googlebot receives the same
kind of artefact (HTML with content) in both cases. The differences are
operational: SSR pays the cost of building the page on every request (higher
TTFB, a server that has to be up and withstand the crawler) in exchange for
absolute freshness. If the page's data does not change between deploys, SSR is
paying rent on a property you could have bought at build time.

## ISR: static with an expiry date

An honesty caveat first: **this site does not use ISR in production**. It is
100% static, and I have no ISR measurement of my own to show. What follows is
mechanism analysis, not field experience.

ISR is SSG with `revalidate`: the static HTML is served normally and, once the
interval has passed, the next visit triggers regeneration in the background.
For Googlebot, the contract is the same as SSG: full HTML in the first
response, indexing with no rendering queue.

### The SEO cost: the first visit after revalidation

The trade-off is freshness. Between revalidations, any visitor, Googlebot
included, may receive a stale version. And the stale-while-revalidate model
means that the first visit **after** expiry still gets the old version while
the new one is built in the background. For a blog, irrelevant. For a page
whose content needs to show up quickly in the index (price, stock, a corrected
news story), it is a structural delay you accepted when you chose the strategy;
I would use ISR exactly where the data changes at a known frequency and a lag of
one interval is tolerable.

## CSR: the only one that really risks indexing

CSR is the skeleton HTML: the first response brings an empty `<div>` and a
JavaScript bundle, and the content is born in the browser. All the weight of
indexing falls on the second wave (the rendering queue, with no deadline,
subject to execution failure), and for crawlers that do not render, the content
simply does not exist.

## How this site is rendered (and why TTFB came out at 0 ms)

This site is the lab for its own articles, so: every page route is static,
generated at build time from the content on disk; the only exception on the
whole site was the route that generates each post's Open Graph image, rendered
on demand, which no crawler needs to index (the update further down tells how
that changed). A performance decision that only makes sense in that scenario
sits in the config. The comment says the site's CSS is small (~22 KB raw, ~5 KB
compressed), and inlining it in the `<head>` removes the only render-blocking
request PSI pointed out, at the cost of losing the `.css` cache between pages, a
favourable trade at this size:

```ts
// next.config.ts
  // ── CSS inline (LCP) ───────────────────────────────────────────────────────
  // O CSS do site é pequeno (~22KB brutos / ~5KB comprimidos); inlinado no
  // <head> elimina o único request render-blocking apontado pelo PSI, ao custo
  // de perder o cache do .css entre páginas — troca favorável neste tamanho.
  experimental: {
    inlineCss: true,
  },
```

Two real numbers from that setup:

- In the production mobile PSI run of 2026-07-18, the LCP's **TTFB subpart
  read 0 ms**, the signature of static HTML served from the edge. It is a
  number SSR, by definition, cannot deliver, because there is always a server
  building the page between the request and the first byte. TTFB's role inside
  LCP is broken down in the [guide to improving LCP](/en/blog/improve-lcp-nextjs).
- In the 2026-07-20 baseline, the site's 10 URLs were indexable, with a 200
  status, exactly one `<h1>` each, valid JSON-LD on all of them, zero orphan
  pages and a maximum depth of 2 clicks.

## How to prove which strategy your route uses

The part the guides leave out. Three proofs, from cheapest to most definitive.

### The next build symbol map

At the end of every `next build`, Next prints the list of routes with a symbol
per route indicating how each one was generated, and a legend right below
explaining each symbol. **Read the legend of your own build**, not a
tutorial's: it has changed between Next versions, and the symbol that meant
"static" in one version may have another glyph in yours. This site's real
output, on Next.js 16.2.6:

```
Route (app)
┌ ○ /
├ ○ /_not-found
├ ○ /blog
├ ● /blog/[slug]
│ ├ /blog/gtm-nextjs
│ ├ /blog/inp-nextjs
│ ├ /blog/metadata-api-nextjs
│ └ [+7 more paths]
├ ƒ /blog/-/opengraph-image
├ ○ /busca
├ ○ /feed.xml
├ ○ /ferramentas
├ ○ /ferramentas/gerador-json-ld
├ ○ /guia/seo-tecnico-nextjs
├ ○ /icon.svg
├ ○ /opengraph-image
├ ○ /politica-de-privacidade
├ ○ /robots.txt
├ ○ /sitemap.xml
└ ○ /sobre

○  (Static)   prerendered as static content
●  (SSG)      prerendered as static HTML (uses generateStaticParams)
ƒ  (Dynamic)  server-rendered on demand
```

Three symbols, three strategies, and notice that the legend distinguishes `○`
from `●`: both are static, but `●` marks the routes that needed
`generateStaticParams()` to enumerate their paths. The blog articles are those.

And here comes the honesty of someone writing about their own site: **I
expected to see no `ƒ` in this list.** The `/blog/-/opengraph-image` route (the
Open Graph image generated per post) shows up as dynamic, because it is the only
route with a parameter that does not declare `generateStaticParams()`. It is not
an indexing problem (no crawler needs to index a card image, and it is served
with caching), but it is exactly the kind of thing only reading your own build
output reveals. That is why this is the first of the three proofs.

**Update (September 2026):** reading the build turned into a fix. The card
route now declares `generateStaticParams()` and `dynamicParams = false`, the
same two declarations as the article route, and in the current build (Next.js
16.2.12) it shows up as `● /blog/-/opengraph-image`, with one pre-rendered path
per post. The `ƒ` routes still on the list are routes that have to respond to
every request, such as the tools' APIs.

If a route you expected to be static shows up as dynamic, the build has just
told you that some dynamic API leaked into it, or that enumerating the paths was
missed, before any crawler found out.

### curl vs. the rendered DOM

The build tells you the intent; `curl` tells you the fact. Request the
production URL without running JavaScript:

```bash
curl -s https://seotecnico.dev.br/en/blog/nextjs-ssr-ssg-isr | grep -o "<h1[^>]*>[^<]*</h1>"
```

If the `<h1>` (and the article text, and the internal links) is in that
response, Googlebot indexes them in the first wave. Then compare with the
rendered DOM (DevTools → Elements): what exists in the DOM but **not** in the
`curl` output is exactly the content hanging in the rendering queue.

This site's [meta tag validator](/en/tools/meta-tag-validator) reads from
the same side of the comparison: it reads the
server's response, not the DOM. A tag that only exists after hydration simply
does not appear in the report, and that is not a limitation of the tool, it is
the diagnosis this whole article describes.

### URL Inspection in Search Console: the tested HTML

The definitive proof, because it comes from Google itself: Search Console →
URL Inspection → "View tested page". There is the HTML Google actually got when
it tested the page. Check that the critical content is present, and use the
inspection to validate the route's JSON-LD too, which also has to be in the HTML
of the first response; if you still assemble the block by hand, the [JSON-LD
generator](/en/tools/json-ld-generator) produces the format this site uses.

## The most common mistake: the component that only exists after hydration

The pattern that brings down well-meaning Next.js pages is not "I chose SSR
instead of SSG": it is the component that fetches its own content in a
`useEffect`. The route is technically static, the build smiles, but the
important paragraph is born in the browser: smuggled CSR inside an "SSG" page.

The empirical proof that this site carries no such contraband is in the
2026-07-20 baseline: on all 10 pages, **LCP = FCP**; the largest visible element
paints together with the first, because no content appears after hydration.
When LCP and FCP diverge a lot on a content site, that is a hint that something
important is being born late, and what is born late for the user is born late
(or never) for the indexer. AI assistants are even more radical: in a controlled
test, [ChatGPT and Claude did not run JavaScript a single
time](/en/blog/which-ai-assistants-run-javascript), and what was born in a
`useEffect` simply did not exist for them. As always in the [technical SEO
guide for Next.js](/en/guide/technical-seo-nextjs): you declare the rendering
strategy in code, but measurement is what confirms it.
