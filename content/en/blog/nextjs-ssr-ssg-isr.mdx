For Googlebot, the acronym doesn't matter. What matters is what's in the HTML
of the **first response**. SSG and SSR both send the full content in that
HTML, so they're equivalent for indexing. ISR also sends full HTML, though it
can be stale between revalidations. CSR sends empty HTML that depends on a
second rendering pass, and it's the only one of the four with a real
indexing risk. This article moves the comparison from "which is fastest" to
"what does the indexer receive," and it ends with a step almost no guide
teaches: how to **prove** which strategy each of your routes actually uses.

## The four strategies in one sentence each

- **SSG (static site generation):** the HTML is built once, at build time,
  and a CDN serves it as is. It's the App Router default when a route uses
  no dynamic APIs.
- **ISR (incremental static regeneration):** SSG with an expiry. Next.js
  regenerates the static HTML in the background after a revalidation
  interval.
- **SSR (server-side rendering):** the server builds the HTML on every
  request, with whatever the data is at that moment.
- **CSR (client-side rendering):** the server sends a skeleton, and
  JavaScript fills it in after the page loads in the browser.

All four definitions turn on one question, **when the HTML gets its
content**. For the rest of this article, that's the only axis that matters.

## What Googlebot actually does with your HTML

This section follows Google Search Central's JavaScript SEO documentation,
not guesses pieced together from search results. Google describes a process
with two queues.

### The two waves: crawl and render

In the first pass, Googlebot requests the page over HTTP, checks
robots.txt, receives the HTML, and processes it. It extracts links from
`href`s, adds them to its crawl queue, and indexes whatever that HTML
contains. If your content is already there, this pass does the essential
work.

Every page that returns status 200 also enters a **rendering queue**.
Google's documentation is explicit about timing. A page may sit there for a
few seconds, but **it can take longer**, and Google publishes no deadline or
guarantee. When its resources allow, a headless Chromium renders the page
and runs the JavaScript. Google then uses the rendered HTML to (re)index the
page and to discover links that only exist after execution.

### Why "Google runs JavaScript" is not the end of the conversation

Google does render JavaScript, and that's the standard defense from people
who build SPAs. That sentence hides three things, though:

1. Rendering is **deferred and has no SLA**. Critical content waiting in a
   queue of variable capacity carries a risk that ready-made HTML doesn't.
2. Rendering can **partially fail**. A blocked script, a runtime error, or an
   API timeout is enough, and whatever didn't render doesn't exist for the
   index.
3. The one that matters more and more is that **Googlebot is practically
   the only crawler that renders**. Crawlers from other search engines and
   from AI search systems read the first-response HTML and stop there. If
   your site competes to be cited in generated answers, content that only
   exists after hydration is invisible to half the machine readers.

## SSG: the App Router's default (and the right one for content)

In the App Router, a route that uses no dynamic APIs (`cookies()`,
`headers()`, `searchParams`) is static by default. For dynamic routes like
`/blog/[slug]`, `generateStaticParams()` enumerates the paths at build time.

On this site, slugs come from the content itself. My pipeline reads the
filesystem at build time, and that's the concrete reason the route is
static. In the code below, a comment in Portuguese says that only slugs that
exist in `/content/blog` get generated and everything else is a 404.

```tsx
// src/app/(pt)/blog/[slug]/page.tsx
// Somente slugs existentes em /content/blog são gerados; o resto é 404.
export const dynamicParams = false

export function generateStaticParams() {
  return getAllPosts().map(({ frontmatter }) => ({ slug: frontmatter.slug }))
}
```

```ts
// src/lib/content.ts
/** All blog posts, newest first. Returns [] while content/blog is empty. */
export function getAllPosts(): Post[] {
  const dir = path.join(CONTENT_DIR, 'blog')
  if (!fs.existsSync(dir)) return []

  const posts = fs
    .readdirSync(dir)
    .filter((f) => f.endsWith('.mdx'))
    .map((f) => {
      const post = readMdxFile(path.join(dir, f))
      if (!post.frontmatter.category) {
        throw new Error(`[content] "blog/${f}": missing required frontmatter field "category"`)
      }
      return post
    })
    .sort((a, b) =>
      b.frontmatter.datePublished.localeCompare(a.frontmatter.datePublished)
    )
  assertBasedOn(posts, 'blog')
  return posts
}
```

Setting `dynamicParams = false` closes the door. A slug that isn't in the
content is a 404 at build time, not a render attempt at runtime. SEO
by-products follow the same logic. Both the
[sitemap derived from the content](/en/blog/nextjs-dynamic-sitemap) and the
RSS feed are static routes generated in the same build, so page, sitemap,
and feed never tell different stories.

## SSR: when the data can't wait for the build

SSR is for a specific problem, data that changes per request or depends on
who's asking (a real-time price, per-session content). Its HTML still
arrives complete in the first response, which is what matters to the
indexer.

### SSR doesn't index better than SSG: it indexes the same way, just more slowly

Search results treat SSR as Next.js's "SEO mode," so I'll say it outright.
**For indexing, SSR and SSG are equivalent.** In both cases Googlebot
receives the same kind of artifact, HTML with content.

They differ operationally. SSR pays to build the page on every request,
which means a higher TTFB and a server that has to stay up and withstand
the crawler. In exchange, it gets absolute freshness. If your data doesn't
change between deploys, SSR means paying rent on a property you could have
bought at build time.

## ISR: static with an expiry date

A disclaimer first. **This site doesn't use ISR in production.** It's 100%
static, and I have no ISR measurements of my own to show you. What follows
analyzes how the mechanism works. It isn't field experience.

ISR is SSG with `revalidate`. It serves static HTML as usual, and once the
interval passes, the next visit triggers a background regeneration.
Googlebot gets the same contract it gets from SSG, full HTML in the first
response, so indexing skips the rendering queue.

### The SEO cost: the first visit after revalidation

You trade away freshness. Between revalidations, any visitor, Googlebot
included, may receive a stale version. ISR follows a stale-while-revalidate
model, so the first visit **after** expiry still gets the old version while
a new one is built in the background.

For a blog, that doesn't matter. For a page whose content has to reach the
index fast (a price, stock levels, a corrected news story), it's a
structural delay you accepted when you chose the strategy. I'd use ISR
exactly where data changes at a known frequency and a one-interval lag is
tolerable.

## CSR: the only one that really risks indexing

With CSR, the HTML is a skeleton. Its first response carries an empty
`<div>` and a JavaScript bundle, and the content only comes into existence
in the browser.
That puts the whole weight of indexing on the second wave, the rendering
queue, which has no deadline and can fail during execution. For crawlers
that don't render, the content simply doesn't exist.

## How this site is rendered (and why TTFB came out at 0 ms)

This site is the lab for its own articles. Every page route is static,
generated at build time from the content on disk. Across the whole site, the
only exception was the route that generates each post's Open Graph image. It
was rendered on demand, and no crawler needs to index it (the update further
down explains how that changed).

One performance decision that only makes sense in this setup lives in the
config. Its comment, in Portuguese, explains the trade. This site's CSS is
small (about 22 KB raw, about 5 KB compressed), so inlining it in the
`<head>` removes the only render-blocking request PSI flagged. It costs you
`.css` caching between pages, which is a favorable trade at this size.

```ts
// next.config.ts
  // ── CSS inline (LCP) ───────────────────────────────────────────────────────
  // O CSS do site é pequeno (~22KB brutos / ~5KB comprimidos); inlinado no
  // <head> elimina o único request render-blocking apontado pelo PSI, ao custo
  // de perder o cache do .css entre páginas — troca favorável neste tamanho.
  experimental: {
    inlineCss: true,
  },
```

Two real numbers come out of this setup:

- In the PSI mobile run on production on July 18, 2026, the LCP's **TTFB
  subpart came in at 0 ms**, the signature of static HTML served from the
  edge. SSR can't deliver that number by definition, because a server always
  builds the page between request and first byte. For how TTFB fits
  inside LCP, see the [guide to improving LCP](/en/blog/improve-lcp-nextjs).
- In the July 20, 2026, baseline, all 10 of the site's URLs were indexable
  and returned status 200, each with exactly one `<h1>` and valid JSON-LD.
  There were zero orphan pages, and the maximum depth was 2 clicks.

## How to prove which strategy your route uses

This is the part the guides leave out. Here are three checks, from cheapest
to most definitive.

### The symbols in the next build output

At the end of every `next build`, Next prints each route with a symbol
showing how it was generated, and a legend right below explains the
symbols. **Read your own build's legend**, not a tutorial's. It changed
between Next versions, and the symbol that meant
"static" in one version may be a different glyph in yours.

Here's this site's real output on Next.js 16.2.6 (the routes are the
Portuguese site's paths):

```
Route (app)
┌ ○ /
├ ○ /_not-found
├ ○ /blog
├ ● /blog/[slug]
│ ├ /blog/gtm-nextjs
│ ├ /blog/inp-nextjs
│ ├ /blog/metadata-api-nextjs
│ └ [+7 more paths]
├ ƒ /blog/-/opengraph-image
├ ○ /busca
├ ○ /feed.xml
├ ○ /ferramentas
├ ○ /ferramentas/gerador-json-ld
├ ○ /guia/seo-tecnico-nextjs
├ ○ /icon.svg
├ ○ /opengraph-image
├ ○ /politica-de-privacidade
├ ○ /robots.txt
├ ○ /sitemap.xml
└ ○ /sobre

○  (Static)   prerendered as static content
●  (SSG)      prerendered as static HTML (uses generateStaticParams)
ƒ  (Dynamic)  server-rendered on demand
```

Three symbols, three strategies. In the legend, `○` and `●` are both static,
but `●` marks routes that needed `generateStaticParams()` to enumerate their
paths. Those are the blog articles.

Here's an honest admission about my own site. **I expected no `ƒ` in
this list.** Yet `/blog/-/opengraph-image`,
the route that generates the Open Graph image for each post, shows up as
dynamic, because it's the only route with a parameter that doesn't declare
`generateStaticParams()`. That isn't an indexing problem, since no crawler
needs to index the card image and it's served with caching. It's exactly
the kind of thing only your own build output reveals, though, which is why
this check comes first.

**Update (September 2026):** reading the build led to a fix. Now the card
route declares `generateStaticParams()` and `dynamicParams = false`, the
same two declarations as the article route. In the current build (Next.js
16.2.12) it shows as `● /blog/-/opengraph-image`, with one pre-rendered path
per post. What's still marked `ƒ` are routes that must respond to every
request, such as the tools' APIs.

If a route you expected to be static shows up as dynamic, your build has
just told you that a dynamic API leaked into it, or that its paths weren't
enumerated, before any crawler found out.

### curl vs. the rendered DOM

Your build states the intent. `curl` states the fact. Request the production
URL without running JavaScript:

```bash
curl -s https://seotecnico.dev.br/en/blog/nextjs-ssr-ssg-isr | grep -o "<h1[^>]*>[^<]*</h1>"
```

If your `<h1>`, article text, and internal links are in that response,
Googlebot indexes them in the first wave. Then compare it with the rendered
DOM (DevTools → Elements). Anything in the DOM but **not** in your `curl`
output is exactly what's waiting in the rendering queue.

This site's [meta tag validator](/en/tools/meta-tag-validator) sits on the
same side of that comparison. It reads the server response, not the DOM,
so a tag that only exists after hydration simply doesn't appear in its
report. That's not a limitation of the tool. It's the diagnosis this whole
article describes.

### URL Inspection in Search Console: the tested HTML

Google itself provides the definitive check. Go to Search Console → URL
Inspection → "View tested page" to see the HTML Google actually got when it
tested the page. Make sure the critical content is there, and use the same
inspection to validate the route's JSON-LD, which also has to be in the
first-response HTML. If you still put that block together by hand, the
[JSON-LD generator](/en/tools/json-ld-generator) produces the format this
site uses.

## The most common mistake: the component that only exists after hydration

Well-intentioned Next.js pages don't sink because someone picked SSR
instead of SSG. They sink because of a component that fetches its own
content in a `useEffect`. Technically the route is static, and the build
looks happy, but the important paragraph only comes into existence in the
browser. It's CSR smuggled inside an "SSG" page.

Here's empirical proof that this site carries none of that contraband. In
my July 20, 2026, baseline, **LCP = FCP** on all 10 pages. On each one, the
largest visible element paints at the same time as the first, because no
content appears after hydration.

On a content site, a large gap between LCP and FCP is a clue that something
important shows up late. And whatever shows up late for the user shows up
late, or never, for the indexer.

AI assistants are stricter still. In a controlled test,
[ChatGPT and Claude didn't run JavaScript a single
time](/en/blog/does-chatgpt-read-javascript),
and anything created in a `useEffect` simply didn't exist for them.

As throughout the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs), you
declare the rendering strategy in code, but it takes a measurement to
confirm it.
