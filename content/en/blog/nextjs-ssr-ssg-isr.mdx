For Googlebot, the acronym doesn't matter; what matters is what's in the HTML
of the **first response**. SSG and SSR both send the full content in that HTML
and are equivalent for indexing; ISR sends full HTML that may be stale between
revalidations; CSR sends empty HTML that depends on a second rendering pass,
and it's the only one of the four that creates a real indexing risk. This
article shifts the comparison from "which is fastest" to "what the indexer
receives", and ends with something almost no guide covers: how to **prove**
which strategy each of your routes is actually using.

## The four strategies in one sentence each

- **SSG (static site generation):** the HTML is built once, at build time,
  and served ready-made from a CDN. It's the App Router's default when a route
  uses no dynamic APIs.
- **ISR (incremental static regeneration):** SSG with an expiry date; the
  static HTML is regenerated in the background after a revalidation interval.
- **SSR (server-side rendering):** the HTML is built on the server for every
  request, with the data as it stands at that moment.
- **CSR (client-side rendering):** the server sends a skeleton, and JavaScript
  builds the content in the browser after the page loads.

Notice what that list is sorted by: **when the HTML gets its content**. That's
the only dimension that matters for the rest of this article.

## What Googlebot actually does with your HTML

The reference here is Google Search Central's JavaScript SEO documentation,
not guesswork from search results. The process has two queues.

### The two waves: crawl and render

In the first pass, Googlebot makes the HTTP request, checks robots.txt,
receives the HTML and processes it: it extracts the links from `href`s, adds
them to the crawl queue and indexes whatever is there. If your content is in
that HTML, the essential work is done at this stage.

Every page with a 200 status also goes into a **rendering queue**. Google's
documentation is explicit about timing: a page may sit in that queue for a few
seconds, but **it can take longer**, and there's no published or guaranteed
deadline. When Google's resources allow, a headless Chromium renders the page
and runs the JavaScript, and the rendered HTML is used to (re)index the page
and discover links that only exist after the scripts run.

### Why "Google runs JavaScript" is not the end of the conversation

It's true that Google renders JavaScript, and that's the standard defense
from people who build SPAs. But the sentence hides three things. First,
rendering is **deferred and has no SLA**: critical content stuck in a queue
with variable capacity is a risk that ready-made HTML doesn't carry. Second,
rendering can **partially fail** (a blocked script, a runtime error, an API
timeout), and whatever didn't render doesn't exist as far as the index is
concerned. Third, and increasingly relevant: **Googlebot is practically the
only crawler that renders**. Other search engines' crawlers and AI search
systems read the HTML of the first response and stop there. On a site
competing to be cited in generated answers, content that only exists after
hydration is invisible to half of its machine readers.

## SSG: the App Router's default (and the right one for content)

In the App Router, a route that uses no dynamic APIs (`cookies()`,
`headers()`, `searchParams`) is static by default. For dynamic routes like
`/blog/[slug]`, `generateStaticParams()` lists the paths at build time.

On this site, the slugs are derived from the content itself (the pipeline
reads the filesystem at build time), which is the concrete reason the route is
static. The Portuguese comment says only slugs that exist in `/content/blog`
get generated, and everything else is a 404:

```tsx
// src/app/(pt)/blog/[slug]/page.tsx
// Somente slugs existentes em /content/blog são gerados; o resto é 404.
export const dynamicParams = false

export function generateStaticParams() {
  return getAllPosts().map(({ frontmatter }) => ({ slug: frontmatter.slug }))
}
```

```ts
// src/lib/content.ts
/** All blog posts, newest first. Returns [] while content/blog is empty. */
export function getAllPosts(): Post[] {
  const dir = path.join(CONTENT_DIR, 'blog')
  if (!fs.existsSync(dir)) return []

  const posts = fs
    .readdirSync(dir)
    .filter((f) => f.endsWith('.mdx'))
    .map((f) => {
      const post = readMdxFile(path.join(dir, f))
      if (!post.frontmatter.category) {
        throw new Error(`[content] "blog/${f}": missing required frontmatter field "category"`)
      }
      return post
    })
    .sort((a, b) =>
      b.frontmatter.datePublished.localeCompare(a.frontmatter.datePublished)
    )
  assertBasedOn(posts, 'blog')
  return posts
}
```

`dynamicParams = false` shuts the door: a slug that doesn't exist in the
content is a 404 decided at build time, not a rendering attempt at runtime.
And the SEO by-products follow the same logic: the [sitemap derived from the
content](/en/blog/nextjs-dynamic-sitemap) and the RSS feed are static routes
generated in the same build, so the page, the sitemap and the feed never tell
different stories.

## SSR: when the data can't wait for the build

SSR solves a specific problem: data that changes per request or depends on
who's asking (real-time prices, per-session content). The HTML still arrives
complete in the first response, and that's what matters to the indexer.

### SSR doesn't index better than SSG: it indexes the same way, just more slowly

It's worth saying plainly, because search results treat SSR as Next.js's "SEO
mode": **for indexing, SSR and SSG are equivalent**. Googlebot gets the same
kind of artifact (HTML with content) either way. The differences are
operational: SSR pays the cost of building the page on every request (higher
TTFB, a server that has to stay up and handle crawler load) in exchange for
always-fresh data. If the page's data doesn't change between deploys, SSR is
paying rent on a house you could have bought outright at build time.

## ISR: static with an expiry date

A disclaimer first: **this site doesn't use ISR in production**. It's 100%
static, and I have no ISR measurements of my own to show. What follows is an
analysis of the mechanism, not field experience.

ISR is SSG with `revalidate`: the static HTML is served as usual, and once the
interval has passed, the next visit triggers regeneration in the background.
For Googlebot, the deal is the same as with SSG: full HTML in the first
response, indexed with no rendering queue.

### The SEO cost: the first visit after revalidation

The trade-off is freshness. Between revalidations, any visitor, Googlebot
included, may get a stale version. And the stale-while-revalidate model means
the first visit **after** expiry still gets the old version while the new one
is built in the background. For a blog, that doesn't matter. For a page whose
content needs to reach the index quickly (prices, stock levels, a corrected
news story), it's a built-in delay you accepted when you chose the strategy.
I'd use ISR precisely where data changes at a known frequency and a lag of one
interval is acceptable.

## CSR: the only one that really risks indexing

CSR means skeleton HTML: the first response contains an empty `<div>` and a
JavaScript bundle, and the content is created in the browser. The entire
burden of indexing falls on the second wave (the rendering queue, with no
deadline and subject to execution failures), and for crawlers that don't
render, the content simply doesn't exist.

## How this site is rendered (and why TTFB came out at 0 ms)

This site is the test bed for its own articles, so here's how it works: every
page route is static, generated at build time from the content on disk. The
only exception on the entire site was the route that generates each post's
Open Graph image, rendered on demand, which no crawler needs to index (the
update further down explains how that changed). There's also a performance
decision in the config that only makes sense in this setup. The comment says
the site's CSS is small (~22 KB raw, ~5 KB compressed), and inlining it in the
`<head>` removes the only render-blocking request PSI flagged, at the cost of
losing `.css` caching between pages, which is a good trade at this size:

```ts
// next.config.ts
  // ── CSS inline (LCP) ───────────────────────────────────────────────────────
  // O CSS do site é pequeno (~22KB brutos / ~5KB comprimidos); inlinado no
  // <head> elimina o único request render-blocking apontado pelo PSI, ao custo
  // de perder o cache do .css entre páginas — troca favorável neste tamanho.
  experimental: {
    inlineCss: true,
  },
```

Two real numbers from that setup:

- In the 2026-07-18 production PSI run on mobile, the LCP's **TTFB subpart
  came in at 0 ms**, the signature of static HTML served from the edge. SSR can't
  produce that number by definition, because there's always a server building
  the page between the request and the first byte. TTFB's role within LCP is
  covered in the [guide to improving LCP](/en/blog/improve-lcp-nextjs).
- In the 2026-07-20 baseline, all 10 of the site's URLs were indexable, with a
  200 status, exactly one `<h1>` each, valid JSON-LD on every one, zero orphan
  pages and a maximum depth of 2 clicks.

## How to prove which strategy your route uses

This is the part guides leave out. Three checks, from cheapest to most
definitive.

### The symbols in the next build output

At the end of every `next build`, Next prints the list of routes with a symbol
next to each one showing how it was generated, plus a legend just below
explaining the symbols. **Read the legend in your own build**, not a
tutorial's: it has changed between Next versions, and the symbol that meant
"static" in one version may be a different glyph in yours. Here's this site's
actual output, on Next.js 16.2.6:

```
Route (app)
┌ ○ /
├ ○ /_not-found
├ ○ /blog
├ ● /blog/[slug]
│ ├ /blog/gtm-nextjs
│ ├ /blog/inp-nextjs
│ ├ /blog/metadata-api-nextjs
│ └ [+7 more paths]
├ ƒ /blog/-/opengraph-image
├ ○ /busca
├ ○ /feed.xml
├ ○ /ferramentas
├ ○ /ferramentas/gerador-json-ld
├ ○ /guia/seo-tecnico-nextjs
├ ○ /icon.svg
├ ○ /opengraph-image
├ ○ /politica-de-privacidade
├ ○ /robots.txt
├ ○ /sitemap.xml
└ ○ /sobre

○  (Static)   prerendered as static content
●  (SSG)      prerendered as static HTML (uses generateStaticParams)
ƒ  (Dynamic)  server-rendered on demand
```

Three symbols, three strategies. Notice that the legend distinguishes `○` from
`●`: both are static, but `●` marks the routes that needed
`generateStaticParams()` to list their paths. Those are the blog articles.

And here's an honest admission from someone writing about their own site: **I
expected no `ƒ` in this list.** The `/blog/-/opengraph-image` route (the Open
Graph image generated for each post) shows up as dynamic, because it's the
only route with a parameter that doesn't declare `generateStaticParams()`. It
isn't an indexing problem (no crawler needs to index a card image, and it's
served with caching), but it's exactly the kind of thing you only discover by
reading your own build output. That's why this is the first of the three
checks.

**Update (September 2026):** reading the build led to a fix. The card route
now declares `generateStaticParams()` and `dynamicParams = false`, the same two
declarations as the article route, and in the current build (Next.js 16.2.12)
it shows up as `● /blog/-/opengraph-image`, with one pre-rendered path per
post. The `ƒ` routes still on the list are ones that genuinely have to respond
to every request, like the tools' APIs.

If a route you expected to be static shows up as dynamic, the build has just
told you that a dynamic API slipped into it, or that you forgot to list its
paths, before any crawler found out.

### curl vs. the rendered DOM

The build tells you the intent; `curl` tells you what actually happens.
Request the production URL without running JavaScript:

```bash
curl -s https://seotecnico.dev.br/en/blog/nextjs-ssr-ssg-isr | grep -o "<h1[^>]*>[^<]*</h1>"
```

If the `<h1>` (along with the article text and the internal links) is in that
response, Googlebot indexes it in the first wave. Then compare it with the
rendered DOM (DevTools → Elements): whatever exists in the DOM but **not** in
the `curl` output is exactly the content waiting in the rendering queue.

This site's [meta tag validator](/en/tools/meta-tag-validator) reads from the
same side of that comparison: the server's response, not the DOM. A tag that
only exists after hydration simply doesn't show up in its report, and that's
not a limitation of the tool; it's the very diagnosis this article describes.

### URL Inspection in Search Console: the tested HTML

The definitive check, because it comes from Google itself: Search Console →
URL Inspection → "View tested page". That's the HTML Google actually received
when it tested the page. Make sure the critical content is there, and use the
inspection to validate the route's JSON-LD too, which also has to be in the
HTML of the first response; if you still put that block together by hand, the
[JSON-LD generator](/en/tools/json-ld-generator) produces the format this site
uses.

## The most common mistake: the component that only exists after hydration

The pattern that sinks well-intentioned Next.js pages isn't "I chose SSR
instead of SSG"; it's a component that fetches its own content in a
`useEffect`. The route is technically static and the build looks happy, but
the important paragraph is created in the browser: CSR smuggled into an "SSG"
page.

The empirical proof that this site isn't smuggling anything is in the
2026-07-20 baseline: on all 10 pages, **LCP = FCP**. The largest visible
element paints at the same time as the first one, because no content appears
after hydration. When LCP and FCP are far apart on a content site, it's a sign
that something important is showing up late, and whatever shows up late for
users shows up late (or never) for the indexer. AI assistants are even
stricter. In a controlled test, [ChatGPT and Claude didn't run JavaScript a
single time](/en/blog/which-ai-assistants-run-javascript), and anything
created in a `useEffect` simply didn't exist for them. As always in the
[technical SEO guide for Next.js](/en/guide/technical-seo-nextjs): you declare
the rendering strategy in code, but measurement is what confirms it.
