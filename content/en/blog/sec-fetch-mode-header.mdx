`Sec-Fetch-Mode` is a header the browser sends with each request to say how
it made that request. A value of `cors` with `Sec-Fetch-Dest: empty` means a
script inside a browser fired a `fetch()`. A value of `navigate` with
`document` means a page is being opened. If a request doesn't carry the Mode
and Dest pair, it doesn't have a browser's shape. Put these headers next to
the time of each request, and they show whether a visit ran JavaScript.

In my test of
[which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript),
these headers took the evidence from "the assistant's answer contained the
value" to "the server saw the script run." That article gives the signal one
section. This one covers all of it: what each header means, what it was
designed for, how I used it as a measuring instrument, where it stops
holding, and the bug that reviewing this article turned up in the instrument
itself.

## What Fetch Metadata headers are

Fetch Metadata is a group of four request headers, all prefixed with
`Sec-Fetch-`. They're defined in a
[W3C specification](https://www.w3.org/TR/fetch-metadata/), currently a
Working Draft. Browsers fill in each one themselves, from the context the
request came from.

| Header | What it tells you | Most common values |
|---|---|---|
| `Sec-Fetch-Mode` | The request's mode | `navigate`, `cors`, `no-cors`, `same-origin`, `websocket` |
| `Sec-Fetch-Dest` | Where the response will be used | `document`, `empty`, `script`, `style`, `image`, `iframe` |
| `Sec-Fetch-Site` | How the requester relates to the responder | `same-origin`, `same-site`, `cross-site`, `none` |
| `Sec-Fetch-User` | Whether the user activated the navigation | `?1`, or absent |

If you want to know whether JavaScript ran, Mode and Dest are the two that
matter. Read together, they separate three situations:

| Mode / Dest | What happened in the browser |
|---|---|
| `navigate` / `document` | A page opened as the main document |
| `no-cors` / `script`, `style`, `image` | The browser loaded a resource referenced in the HTML |
| `cors` / `empty` | Code running in the page made a call, such as `fetch()` or `XMLHttpRequest` |

Calls made by code have no destination of their own, so they get `empty`.
`fetch()` uses `cors` by default, even for a same-origin target. That's why
a `fetch('/api/something')` on the page itself reaches the server as
`cors/empty`, with `Sec-Fetch-Site: same-origin`.

Two details from the
[MDN
reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Mode)
underpin the rest of this article. Browsers send these headers only to
potentially trustworthy URLs, which means HTTPS or localhost. They're also
forbidden headers for page code, so a script in the browser can't create or
change them.

Every modern engine sends Mode and Dest together: Chrome since version 76,
Firefox since 90, and Safari since 16.4 (March 2023).

## The original use: security

These headers exist so a server can tell where a request came from before it
processes it.
[web.dev's article on Fetch Metadata](https://web.dev/articles/fetch-metadata)
describes a pattern for this, called Resource Isolation Policy, with four
rules and one optional exception:

1. Allow requests without the headers. They come from browsers that don't
   send them.
2. Allow requests whose `Sec-Fetch-Site` is `same-origin`, `same-site`, or
   `none`.
3. Allow simple navigations (`navigate` with `GET`), except those to `object`
   and `embed`.
4. Optionally, exempt endpoints built to receive traffic from other sites.
5. Reject everything else, which is cross-site traffic that isn't a
   navigation.

This policy blocks attacks such as CSRF and cross-site script inclusion
without touching legitimate traffic. web.dev also says the server should list
`Sec-Fetch-Dest`, `Sec-Fetch-Mode`, and `Sec-Fetch-Site` in the response's
`Vary` header so the protection holds for `GET` requests. Since the response
depends on those headers, a cache needs to know it.

This site doesn't block anything with them. It only records them.

## The use here: measurement

Inside a browser, only code can produce `cors/empty`. An HTTP client that
downloads HTML without running it doesn't send that pair. curl sends no
`Sec-Fetch` header at all, and Node's `fetch` sends Mode without Dest (more
on that below).

So if a page has a script that calls an endpoint with `fetch()`, and the
endpoint receives `cors/empty` seconds after the page was requested, that's
evidence that a browser opened the page and ran the script.

In the lab, each assistant gets its own secret URL. That URL, not the user
agent, identifies the visit, as the
[write-up of the AI crawler detection pilot](/en/blog/detect-ai-crawlers)
explains. On the lab page, the value the test looks for appears only after
the page has loaded and a script fetches it from a separate JSON file. If an
assistant answers with that value, it either read the page after the script
ran or opened the JSON some other way. The server tells you which of the two
happened.

`fetchMode()` in `src/lib/lab-probes.ts` turns the two headers into a value
you can log:

```ts
// src/lib/lab-probes.ts
function fetchMode(headers: Headers): string {
  const mode = headers.get('sec-fetch-mode')
  const dest = headers.get('sec-fetch-dest')
  if (!mode && !dest) return '(none)'
  return clip(`${mode || '-'}/${dest || '-'}`)
}
```

It returns one of three shapes. You get `(none)` when neither header
arrived, `mode/dest` when both did, and a hyphen in place of the missing one
when only one arrived. `clip()` cuts the value at 100 characters, GA4's
limit for an event parameter, and returns `(none)` if what's left is an
empty string. Storing the pair as one string makes it easier to count and
compare later.

The proxy computes this value only when the request is a lab probe:

```ts
// src/proxy.ts
  // Sondas do controle positivo (H16, §4.7): quem buscou, pelo formato da
  // requisição e pela lista pública em que o IP está, diga o UA o que disser.
  // Só aqui: fora das sondas, nada disto é coletado (§2.3).
  const probe = controlProbeForPath(pathname)
  const lab =
    probe &&
    labHitParams(
      probe,
      request.nextUrl,
      request.headers,
      await ipOwner(clientIp).catch(() => 'unknown'),
      hitId

```

These comments are in Portuguese, as in the repository. They say that
positive-control probes record who fetched the URL, from the request's shape
and from whichever public IP list the address is on, whatever the user agent
claims. Outside these probes, the proxy collects none of it.

In Next.js 16, what used to be Middleware is now called Proxy. It lives in
`proxy.ts`, exports a function named `proxy`, and runs on the Node.js runtime
with no option to switch to Edge, according to the
[Next.js
docs](https://nextjs.org/docs/app/api-reference/file-conventions/proxy).
If you still have a `middleware.ts`, you can migrate it with the official codemod.

### What the server recorded

Every statement below holds for the date and plan shown, not for the
assistant in general. You'll find the full rounds in my tests of
[which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript)
and of
[what ChatGPT reads from a Next.js
page](/en/blog/does-chatgpt-read-javascript).

| Visit | What the server recorded | What it means |
|---|---|---|
| Grok (free, 2026-10-02) | The renderer requested the page, then the JSON with `cors/empty`, in the 6 rounds of the hint battery | The script ran |
| ChatGPT (Go) and Claude (Pro), 2026-10-02 | One request for the page, with no `Sec-Fetch` header at all. With the address in the prompt, a second request, to the JSON, also without one | An HTTP client. It opened the JSON directly, and no script called it |
| DeepSeek (free, 2026-10-02), "the address" condition | The JSON arrived twice per round, once as `navigate/document` and once as `cors/empty` | The headers separate the two paths |

**Grok.** It follows a full browser's pattern, requesting the document first
and then making the script's call. Its renderer is a `HeadlessChrome`, and
the JSON arrived with `cors/empty` in every round.

**ChatGPT and Claude.** Neither sent a `Sec-Fetch` header on any request.
That's the profile of an HTTP client that downloads the HTML and runs
nothing. When the prompt gave them the JSON's address, they opened it, and
that request arrived like the others, with no header. So no page script
called the JSON.

**DeepSeek.** This case shows what the header settles and what it doesn't.
In the "the address" condition (rounds 48, 58, and 68), the JSON arrived
twice per round. One request, `navigate/document`, opened it directly as a
document. The other, `cors/empty`, came from the page's script. Here the
headers keep the two paths clearly apart. On their own, though, they can't
tell you which of the two responses reached the model.

You get that answer by comparing it with the other condition. In the
location-only condition (rounds 43, 53, and 63), the script called the JSON
with `cors/empty` in all three rounds, and all three answers read
"carregando…" ("loading…"). The value arrived only when the JSON was also
opened directly.
DeepSeek's own explanation of what it did doesn't count as data. It said it
didn't run the page's JavaScript, and the server recorded the opposite.

## When the instrument changed mid-test

I didn't record the full value from the start. For the rounds on September
27, 2026, the site logged only `has_sec_fetch`, a field that said whether a
`Sec-Fetch-Mode` header was present, not what its value was.

So in those rounds, "the script ran" was an inference. There was a
`Sec-Fetch` header on the JSON request, and its `Accept` was `*/*`, which is
what `fetch()` sends by default, while a navigation asks for `text/html`
first. It was a reasonable inference, but still an inference, and I now know
of a client that meets both conditions without a browser. Node's `fetch`
sends `Sec-Fetch-Mode: cors` and `Accept: */*`. Beyond the header, though,
the rest of each visit backed the inference up: browser user agents, each
with its own `Accept-Language` and, on the page request, its own navigation
`Accept`.

On September 29, 2026, at 01:13:22 UTC, PR #75 added two fields at once:

- `lab_fetch_mode`, the `mode/dest` pair that the function above produces.
- `lab_hit`, one key per request, made of the UTC time to the second plus
  four random hex characters.

This key identifies the request, never who made it. It's what makes it
possible to join GA4 tables row by row and measure intervals to the second.

The hint battery came after that change, and the server recorded
`cors/empty`, destination included, in all 6 Grok rounds and all 6 DeepSeek
rounds. Node's `fetch` doesn't produce that pair, so the September 27
inference is confirmed for those two assistants.

I'm going through this timeline because it changes how much weight the
September 27 rounds carry. They're still valid, but they were measured with
a weaker instrument, and the article that cites them says so. There are two
lessons here. Record the value, not just whether it's present. And date
every change to the instrument, so you can tell later which rounds were
measured with which version.

## The bug this article uncovered

While checking this text against the code, I tested what Node's native
`fetch` (the undici library) sends on an ordinary request. In Node 22.16, it
adds `Sec-Fetch-Mode: cors` to every request and sends no `Sec-Fetch-Dest`,
even when you set an HTML `Accept` by hand.

This site's proxy sends two fields on every page, and both treated the
presence of `Sec-Fetch-Mode` alone as the browser signal:

- `has_sec_fetch`
- `ua_class`, which marks a request `browser-like` when that header is
  present and the `Accept` asks for HTML

So the proxy counted any client built on Node's `fetch` that asked for HTML
as a browser. That includes this site's own
[meta tag validator](/en/tools/meta-tag-validator). It fetches the URL you
paste with Node's `fetch` and an HTML `Accept`, so when the URL was on this
site, the request reached the proxy shaped like a browser.

`lab_fetch_mode` wasn't affected. It records the pair as a string, so Node's
`fetch` always showed up there as `cors/-`, never as a page script's
`cors/empty`. None of the assistants' verdicts change.

Fixing it means requiring the pair, in a single helper that both fields use:

```ts
// src/lib/fetch-metadata.ts
/** A requisição traz o par Mode + Dest que um navegador sempre manda junto. */
export function hasBrowserFetchMetadata(headers: Headers): boolean {
  return headers.has('sec-fetch-mode') && headers.has('sec-fetch-dest')
}
```

Its doc comment, in Portuguese, says the request carries the Mode and Dest
pair that a browser always sends together.

I fixed it in the order
[this site's pre-registration method](/en/blog/seo-testing-pre-registration)
calls for. I logged the bug before fixing it, with its cutoff date (the
deploy of October 7, 2026, at 23:56:38 UTC) and the rule for reading earlier
data, written before I re-read any of it. No closed verdict changes
direction. A unit test pins the exact set of headers undici sends, so the
presence-only rule doesn't come back.

## Limits of the signal

**Any client can send these headers.** The "forbidden header" protection
holds only inside the browser, against page code. Outside it, any HTTP
client can send `Sec-Fetch-Mode` with any value, and Node sends it without
anyone asking. On its own, `cors/empty` is evidence, not proof. In the lab,
the evidence gets its strength from the combination: a secret URL per
assistant, the page-then-JSON order, and an interval consistent with a
browser running the page.

**Missing headers don't prove it isn't a browser.** Browsers don't send them
without HTTPS, and neither do browsers older than the support listed above
(Safari before 16.4, Firefox before 90). On an HTTPS site with current
traffic, this counts for little, but it's there.

**`cors/empty` shows that a script called the endpoint, not what happened
next.** DeepSeek is the example. The server knows the call happened, but on
its own it can't tell whether the result reached the model.

**The signal is per request.** It tells you how that request was made. It
doesn't tell you whether the whole page was rendered or how much of the
content was read.

**In your ordinary log, you only have a profile.** In the lab, the secret
URL identifies who visited. A normal site log has nothing like that, only a
declared user agent and a header pattern. Write "requests that declare
themselves X ran the script" there, not "X runs JavaScript." To name an
agent, you need verified identity, which is separate work, covered in the
[write-up of the AI crawler detection pilot](/en/blog/detect-ai-crawlers).

## How to record it on your server

### In Next.js

This site's implementation is in the snippets above. `fetchMode()` in
`src/lib/lab-probes.ts` turns the headers into a string, and `proxy.ts`
decides when to record it.

One part worth copying is how it separates data by level of detail. Only lab
URLs record the full `mode/dest` pair, along with the user agent, `Accept`,
and country. On every other page, the proxy records just a boolean,
`has_sec_fetch`, next to a truncated network hash and the client class. It
never records the IP.

That's a privacy choice, not a performance one. `Sec-Fetch` headers say
little about a person on their own. Recorded with the IP, user agent, and
time on every page, they become a browsing history. If you record them
site-wide, decide beforehand what you store alongside them and for how long.

### In PHP

On shared hosting, you get the same data from the variables PHP exposes in
`$_SERVER`. PHP uppercases the header name, replaces hyphens with
underscores, and adds the `HTTP_` prefix:

```php
<?php
// illustrative: logs the mode/dest pair to PHP's error log
$mode = $_SERVER['HTTP_SEC_FETCH_MODE'] ?? '';
$dest = $_SERVER['HTTP_SEC_FETCH_DEST'] ?? '';

if ($mode === '' && $dest === '') {
    $fetchMode = '(none)';
} else {
    $fetchMode = ($mode !== '' ? $mode : '-') . '/' . ($dest !== '' ? $dest : '-');
}

error_log(date('c') . ' ' . $_SERVER['REQUEST_URI'] . ' ' . $fetchMode);
```

Add it only to the endpoint and page you want to measure, for the same
privacy reason. Read `cors/-` for what it is, a client outside the browser,
not a page script.

## How to check

**1. Look at the headers in your browser.** Open your site over HTTPS, go to
the Network tab in DevTools, and reload. In the document request's Request
Headers, you should see `Sec-Fetch-Mode: navigate` and
`Sec-Fetch-Dest: document`.

**2. Fire a call from the console.** In the same page's console, run:

```js
// illustrative: run in the DevTools console, on your site's page
fetch('/', { cache: 'no-store' })
```

In the Network tab, the new row should show `Sec-Fetch-Mode: cors`,
`Sec-Fetch-Dest: empty`, and `Sec-Fetch-Site: same-origin`. That's exactly
the pattern a page script produces.

**3. Make two requests without a browser.**

```bash
# illustrative: use your own domain
curl -s -o /dev/null https://your-domain.com/
node -e "fetch('https://your-domain.com/')"
```

curl sends no `Sec-Fetch` headers, so your log should record `(none)`. Node
sends only the Mode, so it should record `cors/-`.

**4. Check the log.** If the cases show up as `navigate/document`,
`cors/empty`, `(none)`, and `cors/-`, recording works. If everything shows
`(none)`, make sure the site is on HTTPS and that no proxy or CDN in front
of your server strips the headers before they reach the application.
