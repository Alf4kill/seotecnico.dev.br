`Sec-Fetch-Mode` is a header the browser sends with every request to say how
the request was made. The value `cors`, paired with `Sec-Fetch-Dest: empty`,
means a `fetch()` fired by a script inside a browser; `navigate` with
`document` means a page being opened. Without both Mode and Dest, a request
doesn't look like it came from a browser. Combined with the request's timing,
these headers show whether a visit ran JavaScript.

These headers are what took this site from "the assistant's answer contained
the value" to "the server saw the script run", in the [test of which AI
assistants run JavaScript](/en/blog/which-ai-assistants-run-javascript).
There, the signal gets one section. Here's the full explanation: what each
header means, what it was designed for, how I used it as a measurement tool,
where it stops being reliable, and the bug that reviewing this article turned
up in the instrument itself.

## What Fetch Metadata headers are

Fetch Metadata is a group of four request headers prefixed with `Sec-Fetch-`,
defined in a [W3C specification](https://www.w3.org/TR/fetch-metadata/) that's
currently a Working Draft. The browser fills in each one itself, based on the
context the request came from.

| Header | What it tells you | Most common values |
|---|---|---|
| `Sec-Fetch-Mode` | the request's mode | `navigate`, `cors`, `no-cors`, `same-origin`, `websocket` |
| `Sec-Fetch-Dest` | where the response will be used | `document`, `empty`, `script`, `style`, `image`, `iframe` |
| `Sec-Fetch-Site` | the relationship between requester and responder | `same-origin`, `same-site`, `cross-site`, `none` |
| `Sec-Fetch-User` | whether a navigation was user-activated | `?1`, or absent |

For measuring JavaScript execution, Mode and Dest are the ones that matter.
Read together, they distinguish three situations:

| Mode / Dest | What happened in the browser |
|---|---|
| `navigate` / `document` | a page was opened as the main document |
| `no-cors` / `script`, `style`, `image` | the browser loaded a resource referenced in the HTML |
| `cors` / `empty` | code running in the page made a call, such as `fetch()` or `XMLHttpRequest` |

The `empty` destination is used for calls made by code, which have no
destination of their own. And `cors` is `fetch()`'s default mode, even for the
same origin. That's why a `fetch('/api/something')` on the page itself
reaches the server as `cors/empty`, with `Sec-Fetch-Site: same-origin`.

Two details from the [MDN
reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Mode)
underpin the rest of this article. First, the headers are only sent to
potentially trustworthy URLs (HTTPS or localhost). Second, they're forbidden
headers as far as page code is concerned, so a script running in the browser
can't create or change them. As for support, every modern engine sends Mode
and Dest together: Chrome since version 76, Firefox since 90 and Safari since
16.4, released in March 2023.

## The original use: security

The headers were created so a server can tell where a request came from
before processing it. The pattern described in [web.dev's article on Fetch
Metadata](https://web.dev/articles/fetch-metadata), called a Resource
Isolation Policy, has four rules and one optional exception:

1. allow requests without the headers, because they come from browsers that
   don't send them;
2. allow a `Sec-Fetch-Site` of `same-origin`, `same-site` or `none`;
3. allow simple navigations (`navigate` with `GET`), except those to `object`
   and `embed`;
4. optionally, exempt endpoints that are meant to serve other sites;
5. reject everything else, which is cross-site traffic that isn't a
   navigation.

The policy blocks attacks like CSRF and cross-site script inclusion without
affecting legitimate traffic. The same article asks servers to include
`Sec-Fetch-Dest`, `Sec-Fetch-Mode` and `Sec-Fetch-Site` in the response's
`Vary` header so the protection holds on `GET` requests: the response depends
on those headers, and caches need to know that.

This site doesn't block anything with them. It just records them.

## The use here: measurement

The reasoning is simple. Inside a browser, only code can produce
`cors/empty`. An HTTP client that downloads the HTML without running it
doesn't send that pair: curl sends no `Sec-Fetch` headers at all, and Node's
`fetch` sends the Mode without the Dest (more on that below). So if a page has
a script that calls an endpoint with `fetch()`, and the endpoint receives
`cors/empty` a few seconds after the page was requested, that's evidence a
browser opened the page and ran the script.

In this site's lab, each assistant gets its own secret URL, so the visit is
identified by the URL rather than the user agent, as described in the [AI
crawler detection case study](/en/case-studies/ai-crawler-detection). The lab
page only shows the value being tested after a script fetches it from a
separate JSON file, once the page has loaded. If the assistant answers with
the value, it either read the page after its scripts ran or opened the JSON
some other way, and the server is what tells you which.

The function that turns the two headers into a value that can be recorded
lives in `src/lib/lab-probes.ts`:

```ts
// src/lib/lab-probes.ts
function fetchMode(headers: Headers): string {
  const mode = headers.get('sec-fetch-mode')
  const dest = headers.get('sec-fetch-dest')
  if (!mode && !dest) return '(none)'
  return clip(`${mode || '-'}/${dest || '-'}`)
}
```

It produces three kinds of output: `(none)` when neither header was sent,
`mode/dest` when both were, and a hyphen in place of whichever one is missing
when only one was sent. `clip()` truncates the value at 100 characters, GA4's
limit for an event parameter, and returns `(none)` if it's left with an empty
string. Recording the pair as a single string makes counting and comparing
easier later on.

The value is computed in the proxy and only put together when the request
hits a lab probe:

```ts
// src/proxy.ts
  // Sondas do controle positivo (H16, §4.7): quem buscou, pelo formato da
  // requisição e pela lista pública em que o IP está, diga o UA o que disser.
  // Só aqui: fora das sondas, nada disto é coletado (§2.3).
  const probe = controlProbeForPath(pathname)
  const lab =
    probe &&
    labHitParams(
      probe,
      request.nextUrl,
      request.headers,
      await ipOwner(clientIp).catch(() => 'unknown'),
      hitId
    )
```

The comments are in Portuguese, as they are in the repository. They say the
positive control probes record who fetched the page based on the request's
shape and which public IP list the address appears on, whatever the user
agent claims, and that this happens only here: none of it is collected
outside the probes.

In Next.js 16, what used to be Middleware is now called Proxy: the file is
`proxy.ts`, the exported function is `proxy`, and it runs on the Node.js
runtime with no option to switch to Edge, according to the [Next.js
documentation](https://nextjs.org/docs/app/api-reference/file-conventions/proxy).
If you still have a `middleware.ts`, the official codemod will migrate it.

### What the server recorded

Everything below holds for the date and plan listed, not for the assistant in
general. The full rounds are in the [test of which AI assistants run
JavaScript](/en/blog/which-ai-assistants-run-javascript) and in the [AI
crawler detection case study](/en/case-studies/ai-crawler-detection).

| Visit | What the server recorded | What it means |
|---|---|---|
| Grok (free, Oct 2, 2026) | the renderer requested the page and then the JSON with `cors/empty`, in all 6 rounds of the hint battery | the script ran |
| ChatGPT (Go) and Claude (Pro), Oct 2, 2026 | one request for the page, with no `Sec-Fetch` headers; with the address in the prompt, a second request, for the JSON, also with none | an HTTP client; the JSON was opened directly, not called by a script |
| DeepSeek (free, Oct 2, 2026), "the address" condition | the JSON was requested twice per round: once with `navigate/document`, once with `cors/empty` | the headers tell the two paths apart |

**Grok.** This is what a full browser looks like: the document first, then the
script's call. The renderer is a `HeadlessChrome`, and the JSON came in with
`cors/empty` in every round.

**ChatGPT and Claude.** No `Sec-Fetch` headers on any request. That's the
profile of an HTTP client that downloads the HTML and runs nothing. When given
the JSON's address, they opened the JSON, and the request looked like all the
others: no headers, so it wasn't a page script calling the JSON.

**DeepSeek.** This case shows what the header can and can't tell you. In "the
address" condition (rounds 48, 58 and 68), the JSON was requested twice per
round: once with `navigate/document`, opened directly as a document, and once
with `cors/empty`, called by the page's script. The headers cleanly separate
the two paths. What they can't tell you on their own is which of the two
responses reached the model. Comparing with the other condition can: with only
the location hint (rounds 43, 53 and 63), the script called the JSON with
`cors/empty` in all three rounds, and all three answers said "carregando…"
("loading…"). The value only came through when the JSON was opened directly.
The assistant's own account of what it did doesn't count as data: it said it
didn't run the page's JavaScript, and the server recorded the opposite.

## When the instrument changed mid-test

The full value wasn't recorded from the start. In the September 27, 2026
rounds, the site only recorded `has_sec_fetch`, a field that said whether a
`Sec-Fetch-Mode` header was present without saying what its value was.

In those rounds, the conclusion "the script ran" was an inference. There was a
`Sec-Fetch` header and the `Accept` was `*/*`, which is `fetch()`'s default,
whereas a navigation asks for `text/html` first. It was a reasonable
inference, but it was still an inference, and I now know of a client that
matches it without being a browser: Node's `fetch` sends `Sec-Fetch-Mode:
cors` and `Accept: */*`. What backed it up, beyond the header, was the rest
of the request: browser user agents with each browser's own `Accept-Language`
and navigation `Accept`.

On September 29, 2026, at 01:13:22 UTC, PR #75 added two fields at once:
`lab_fetch_mode`, with the `mode/dest` pair the function above produces, and
`lab_hit`, a per-request key made of the UTC time to the second plus four
random hex characters. The key identifies the request, never the person who
made it, and it's what allows the GA4 tables to be joined row by row and
intervals to be measured to the second. The hint battery, run afterward,
recorded `cors/empty` with the destination in all 6 Grok rounds and all 6
DeepSeek rounds. Node's `fetch` doesn't produce that pair, so the September 27
inference was confirmed for those two.

I'm laying out the timeline because it affects how much weight the September
27 rounds carry. They're still valid, but they were measured with a weaker
instrument, and the article that cites them says so. There are two lessons:
record the value, not just whether it's present, and date every change to the
instrument so you know later which rounds were measured with which version.

## The bug this article uncovered

While checking this article against the code, I tested what Node's native
`fetch` (the undici library) sends on an ordinary request. On Node 22.16, it
adds `Sec-Fetch-Mode: cors` to every request and sends no `Sec-Fetch-Dest`,
even when you set an HTML `Accept` by hand.

This site's proxy treated the presence of `Sec-Fetch-Mode` alone as the
browser signal in two fields recorded on every page: `has_sec_fetch`, and
`ua_class`, which marks a request `browser-like` when that header is present
and the `Accept` asks for HTML. Any client built on Node's `fetch` that asked
for HTML got counted as a browser. That includes this site's own tool: the
[meta tag validator](/en/tools/meta-tag-validator) fetches the URL you paste
using Node's `fetch` with an HTML `Accept`, so when the URL was on this site,
the request reached the proxy looking like a browser.

`lab_fetch_mode` wasn't affected: it records the pair as a string, so a Node
`fetch` always showed up there as `cors/-`, never as a page script's
`cors/empty`. None of the assistants' verdicts change.

The fix requires both headers, in a single helper used by both fields:

```ts
// src/lib/fetch-metadata.ts
/** A requisição traz o par Mode + Dest que um navegador sempre manda junto. */
export function hasBrowserFetchMetadata(headers: Headers): boolean {
  return headers.has('sec-fetch-mode') && headers.has('sec-fetch-dest')
}
```

(The comment reads: "the request carries the Mode + Dest pair a browser
always sends together".)

The order followed [this site's method](/en/blog/seo-testing-pre-registration):
the bug was logged before the fix, with the cutoff date (the October 7, 2026
deploy, at 23:56:38 UTC) and the rule for reading earlier data written down
before any of it was re-read. No closed verdict changes direction. The unit
test pins down the exact set of headers undici sends, so the old rule can't
sneak back in.

## Limits of the signal

**Any client can send the headers.** The "forbidden header" protection only
applies inside the browser, against page code. Outside the browser, any HTTP
client can send `Sec-Fetch-Mode` with whatever value it likes, and Node sends
it without even being asked. That's why `cors/empty` on its own is evidence,
not proof. In the lab, the signal gets its strength from the combination: a
secret URL per assistant, the page → JSON order, and an interval consistent
with a browser running the page.

**Missing headers don't prove it isn't a browser.** Without HTTPS, browsers
don't send them. Neither do browsers older than the versions that added
support (Safari before 16.4, Firefox before 90). On an HTTPS site with modern
traffic that's a small factor, but it exists.

**`cors/empty` shows a script called the endpoint, not what happened next.**
DeepSeek is the example: the server knows the call happened, but on its own it
can't tell whether the result reached the model.

**The signal is per request.** It tells you how that one request was made. It
doesn't tell you whether the whole page was rendered, or how much of the
content was read.

**In an ordinary log, all you have is a profile.** In the lab, the secret URL
identifies the visitor. A normal site's log has nothing like that, just a
declared user agent and a pattern of headers. The accurate sentence in that
case is "requests identifying themselves as X ran the script", not "X runs
JavaScript". Naming an agent requires verified identity, which is a separate
job, described in the [AI crawler detection case
study](/en/case-studies/ai-crawler-detection).

## How to record it on your server

### In Next.js

This site's implementation is in the snippets above: `fetchMode()` in
`src/lib/lab-probes.ts` turns the headers into a string, and `proxy.ts`
decides when to record it. The design decision worth copying is how the level
of detail is split. The full `mode/dest` pair, along with the user agent,
`Accept` and country, is only recorded on lab URLs. On every other page, the
proxy records just a boolean, `has_sec_fetch`, alongside a truncated network
hash and the client class, and never the IP.

That's a privacy decision, not a performance one. `Sec-Fetch` headers alone say
little about a person, but recorded together with the IP, user agent and time
on every page, they add up to a browsing history. If you record them
site-wide, decide first what you'll store alongside them and for how long.

### In PHP

On shared hosting, the equivalent is reading the variables PHP exposes in
`$_SERVER`. PHP uppercases the header name, replaces hyphens with underscores
and adds an `HTTP_` prefix.

```php
<?php
// illustrative: logs the mode/dest pair to PHP's error log
$mode = $_SERVER['HTTP_SEC_FETCH_MODE'] ?? '';
$dest = $_SERVER['HTTP_SEC_FETCH_DEST'] ?? '';

if ($mode === '' && $dest === '') {
    $fetchMode = '(none)';
} else {
    $fetchMode = ($mode !== '' ? $mode : '-') . '/' . ($dest !== '' ? $dest : '-');
}

error_log(date('c') . ' ' . $_SERVER['REQUEST_URI'] . ' ' . $fetchMode);
```

Only add it to the endpoint and page you want to measure, for the same
privacy reason. And read `cors/-` for what it is: a client outside a browser,
not a page script.

## How to check

**1. Look at the headers in your browser.** Open your site over HTTPS, open
DevTools to the Network tab and reload. On the document request, under
Request Headers, you should see `Sec-Fetch-Mode: navigate` and
`Sec-Fetch-Dest: document`.

**2. Make a call from the console.** In the same page's console:

```js
// illustrative: run in the DevTools console, on your site's page
fetch('/', { cache: 'no-store' })
```

The new row in the Network tab should show `Sec-Fetch-Mode: cors`,
`Sec-Fetch-Dest: empty` and `Sec-Fetch-Site: same-origin`. That's exactly the
pattern a page script produces.

**3. Make two requests without a browser.**

```bash
# illustrative: use your own domain
curl -s -o /dev/null https://your-domain.com/
node -e "fetch('https://your-domain.com/')"
```

curl sends no `Sec-Fetch` headers, so your log should record `(none)`. Node
sends only the Mode, so your log should record `cors/-`.

**4. Check the log.** If the four cases show up as `navigate/document`,
`cors/empty`, `(none)` and `cors/-`, your recording works. If everything shows
up as `(none)`, make sure the site is on HTTPS and that no proxy or CDN in
front of your server is stripping the headers before they reach the
application.

## What comes next

The next version of the detection instrument, with hypotheses H7 to H13
pre-registered, stops looking at headers one at a time and measures whether
the whole set is consistent: whether the headers a request sends agree with
each other and with the client it claims to be. The Node bug shows why that
matters: a single header, read as a signal, fooled the very instrument that
was built not to be fooled. The pilot's method is in the [AI crawler
detection case study](/en/case-studies/ai-crawler-detection), and the rest of
this site's reference implementation is in the [technical SEO guide for
Next.js](/en/guide/technical-seo-nextjs).
