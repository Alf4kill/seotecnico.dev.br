Writing is the smallest part of making a page here. Every page goes through
the same chain: a dated research note, a brief I approve, a draft, a
verification pass against sources and code, an English version, registration,
check scripts, and a pull request I merge. Verification matters most. So far,
every published draft, wherever it came from, had something wrong that only
verification found.

This page is part of the [Project section](/en/project). How Claude and I
split the work is covered in [how AI is used in this
project](/en/project/how-ai-is-used). This one covers the process itself. It's
based on my [pipeline
doc](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/content-pipeline.md),
and the [content-page
skill](https://github.com/Alf4kill/seotecnico.dev.br/tree/main/.claude/skills/content-page)
packages the procedure so any session with repository access can follow it
step by step.

## How the pipeline works

This table lists every step, where it runs, what it produces, and whether that
output stays in the repository.

| Step | Runs in | Output | Kept in the repository |
|---|---|---|---|
| Gates: first-hand evidence, scope, no query overlap | Session with the repository | Go or stop, with the reason | No |
| Research note | Session with the repository and web access | `docs/research/YYYY-MM-DD-<topic>.md` | Yes |
| Brief | Session with the repository, or an editorial session | The page plan, which I approve before any prose is written | No, the brief is deleted after use |
| Draft | Writing session, me, or the session with the repository | Portuguese MDX | Only after verification |
| Verification | Session with the repository, always | Corrected MDX, with the corrections listed in the commit body | Yes |
| English version | Session with the repository, using the `english-version` skill | The pair in `content/en/`, plus the list of judgment calls in the PR | Yes |
| Registration | Session with the repository | Hreflang pair and a row in the experiment log | Yes |
| Checks | Session with the repository and CI | Script and test output | In the PR |
| Merge, indexing request, distribution | Me | The date in the log row | Yes |

Three gates stop a page that shouldn't exist. First, it needs first-hand
evidence, such as a measurement, an audit, an incident, or a file in this
repository. Second, its topic has to fit the blog's scope, which is how
machines fetch, render, read, and index pages. Third, a search of published
content must not turn up an equivalent `primaryQuery`. On an exact-match
domain, filler is the main risk, and it's cheaper to stop before the research
note than after the draft.

A page is only as well informed as its research note. Every external fact in
the note comes from the original page, read on the day, along with the
last-updated date that page prints. Each fact gets a certainty label, verbatim
and in bold: **[documented]**, **[inference]**, **[third-party]**, or
**[observation]**. The note ends with a list of what the article may and may
not claim.

## One page traced: scaled content abuse

My [article on scaled content abuse](/en/blog/scaled-content-abuse), published
October 18, 2026, went through every step, and each one left a record.

| Step | What happened | Record |
|---|---|---|
| Research note | Every Google page read that day from its HTML, with its last-updated date. A label for each claim, a list of claims to avoid, and a proposed angle. | Commit `5adfded` |
| Brief | Approved with changes the same day: structure, FAQ, links, banned framings, and a length cap | Outside the repository |
| Writing session | Without the research note, the session researched every Google source again from scratch. It delivered a self-check table and a list of open items. | Outside the repository |
| Verification | Aligned the manual-action sentence with the help text. Cut a "most visible sign" claim back to the mechanism. Corrected a timeline row against the changelog. Added a source for the live-test claim. Trimmed the short answer to the 300-character limit the build enforces. | Body of commit `7e73fc1` |
| English version | Interface labels taken from the English help pages, and the English route's real code | Commit `ed4adb4` |
| Links | English pages pointed at the new article. Later, the rule that English text links only to English pages. | `9742f18`, `62b32b7`, `8aba089` |

In its self-check, the writing session got every mechanical check right, and
verification still had four factual corrections to make. Leaving the research
note behind cost a whole extra round of research. Since then, the note always
travels with the brief.

## What verification has corrected

This table lists every correction on record.

| Page | Draft from | Correction | Record |
|---|---|---|---|
| `melhorar-lcp-nextjs` | Writing session | A placeholder for a lab measurement with nothing to fill it. A sentence about RUM while RUM was still only a plan. | PR #7 |
| `json-ld-nextjs` | Writing session | Made-up component files, props, and author object. An argument resting on a Google page removed on 2026-06-15. The wrong mechanism for client components. | PR #17 |
| `inp-nextjs` | Writing session | An H1 in the body. SVG colors outside the palette. An internal document cited in reader-facing text. | `0b95d3c` |
| Five spokes | Writing session, with placeholders | A "100% static" claim the build output contradicted. A missing link to the pillar guide. | PR #27 |
| `pre-registro-seo` | My draft | A title missing the query. A stimulus attributed to the wrong article. A list of deviations that did not match the log. | `0d997fb` |
| `sec-fetch-mode` | My draft | A false claim about HTTP clients. Testing it exposed a bug in the site's own classifier, fixed in PR #95. | `4de2df3` |
| `scaled-content-abuse` | Writing session | Four factual fixes to match the sources. A short answer over the limit. | `7e73fc1` |

`[CODE-n]` placeholders put an end to made-up code. A writing session can't
see the repository, so it leaves the slot empty, and the session with the
repository copies the excerpt from the file.

Nothing has done the same for a fact that sounds right. So verification
re-reads every source on the day and tests whichever claim looks most
testable, when it can be tested here. That's how the `sec-fetch-mode` draft
led to a real bug in the code.

## What is automated, and what is not

This table splits what scripts check from what only reading can.

| Check | Done by | When |
|---|---|---|
| Frontmatter fields, title ≤60, description ≤155, short answer ≤300, topic, `basedOn` | `src/lib/content.ts` | Every build |
| A cited repository path exists | `content-code-paths.test.ts` | CI |
| Translation pair declared on both sides | `hreflang.test.ts` | CI |
| One H1, title, description, canonical, JSON-LD, hreflang, contrast, accessibility | The Playwright suite | CI |
| Leftover placeholder, H1 in the body, double braces, unmapped component, SVG color outside the tokens, banned framing, quote length, required links, lead paragraph | `check-draft.mjs` | When the draft arrives and before the PR |
| Both sides exist, same facts and dates, links stay within their language, translation note, log row | `check-pair.mjs` | Before the PR |
| British spelling, day-month dates, translation note not on the last line, known calques from Portuguese, register compared with native technical English | `check-english.mjs` | After the native read and before the PR |
| Whether the topic deserves a page, whether a fact is still true, whether the code shown matches the repository's lines, whether the English reads as written in English | **No script**: verification, the native read, and me | Every page |

Look at the last row. A script catches a mistake that has already happened
once. Deciding whether a page should exist, or whether a sentence is still
true today, still takes reading.

## Packaging the process as a skill

My process used to be scattered across `CLAUDE.md`, the tests, two research
notes, and commit messages. The `content-page` skill pulls it together into
nine phases, and each phase says where it runs and what it delivers. It also
holds templates for research notes and briefs, the kit that goes to a writing
session, a verification walkthrough listing every correction on record, and
both scripts. Rather than copy sections of `CLAUDE.md`, it points to them. If
they ever disagree, `CLAUDE.md` wins and the skill is what changes.

`check-draft.mjs` grew out of the mistakes in the table above, and I didn't
trust it until it had run against every published article. Its first run
failed six correct files, all false positives, from four causes:

- The `<Image>` component, which the skill's own draft said didn't exist in MDX.
- A table of date formats, read as a placeholder.
- `aria-label` text, counted as a long quote.
- Windows line endings, which hid the lead paragraph.

With those four fixed, all 48 articles passed with no errors, and a draft
broken on purpose in ten places failed on all ten.

This page ran through both scripts before its PR, using the `project` type.
That type drops the requirement to link the pillar guide and a tool, and
requires a link to a versioned file instead.

## Writing the English version

In October 2026, I got feedback that the site's English pages read like a
literal translation of the Portuguese. That was true, and my method was to
blame. My English step was a single paragraph listing what had to stay the
same (facts, dates, H2s, FAQ, links). It said nothing about how the English
should sound.

Each English page had been written sentence by sentence from its Portuguese
original, so Portuguese structure survived inside correct English words:
clauses chained with colons, "it is worth" for "vale a pena", "readings" for
"leituras", day-month dates, and British spelling mixed with American.

On October 27, a revision rewrote all 28 English pages, and its method became
a second skill,
[english-version](https://github.com/Alf4kill/seotecnico.dev.br/tree/main/.claude/skills/english-version),
which `content-page` now calls for its English phase. This skill never
translates in one pass. It works in steps instead.

| Step | What it does |
|---|---|
| Fact sheet | Records, per section, what the Portuguese claims, at what level, and with what hedge, in a file saved before any English sentence is written |
| English draft | Written from the fact sheet by someone who does not read the Portuguese prose. Code and diagrams are added afterward, copied from the original. |
| Native read | The English alone, ideally read by a reviewer who has not seen the Portuguese |
| Fidelity check | The English against the Portuguese: facts, hedges, links, code, and H2 and FAQ counts |
| Report | The judgment calls go in the PR, so I can review meaning without diffing prose |

The skill came with a style guide (American English, US dates in prose and ISO
dates in tables, contractions in explanatory text, and a glossary of the
site's terms) and a script, `check-english.mjs`, that looks for the calques
the revision cataloged. On the commit before the revision, it found 263
occurrences, with errors in 28 of 28 pages. After the revision, it reported 0
errors and 1 warning. My [research note on English
quality](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/research/2026-10-27-english-translation-quality.md)
has the details.

That pass also turned up two problems that had nothing to do with language.
In the JSON-LD article, the sentence explaining the escape showed `<` where
the code has `\u003c`, and one article had a paragraph after its translation
note.

A clean script run doesn't prove the English is native. It proves no known
calque is left. Reading still decides.

Reading proved that the same day. When I reviewed this page's English version,
written during the revision, it had no calque from the list and was still
built like Portuguese: a definite article on every noun, sentences opening
with "The", and colons joining clauses.

To make sure this wasn't just an impression, I measured the register of all
28 English pages against 26 pages of native technical English (Google and
web.dev documentation, and first-person write-ups by US companies and
engineers). Every one of the 28 used more colons than 90% of the native pages,
and 23 crossed that same threshold for "the". This page crossed it on four of
the five measures.

Again, the method was to blame. Whoever wrote the English had the Portuguese
open, and its sentence structure came along. So I changed three things:

1. The intent map became a fact sheet saved to a file, and someone who doesn't see the Portuguese prose writes the English draft from it.
2. The style guide now builds on the Google developer documentation style guide, which brought back the serial comma that Portuguese doesn't use.
3. `check-english.mjs` now compares each page with thresholds measured on native English and ranks the pages by distance.

My [research note on
register](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/research/2026-10-27-english-register-profile.md)
has the corpus, the thresholds, and the false-positive rate. About 4 in 10
flagged paragraphs were fine as they stood.

This page's English version was the first one written that way.

reported 48 files and 0 errors. If you run it on a newer commit, expect the
file count to grow with every article published since.

with the new method. The last three lines of the block redo the measurement at
