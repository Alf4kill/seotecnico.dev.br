Making a page here isn't a writing task. It's the end of a chain: a dated
research note, a brief I approve, a draft, a verification pass against
sources and code, an English version, registration, check scripts, and a
pull request I merge. Verification carries the most weight. Every draft
published so far, wherever it came from, arrived with something wrong that
only verification found.

This page is part of the [Project section](/en/project). How Claude and I
split the work is covered in
[how AI is used in this project](/en/project/how-ai-is-used), and this one
covers the process itself. It's based on my
[pipeline
doc](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/content-pipeline.md),
and the procedure became the
[content-page
skill](https://github.com/Alf4kill/seotecnico.dev.br/tree/main/.claude/skills/content-page),
which a session with access to the repository follows step by step.

## How the pipeline works

This table lists every step, where it runs, what it produces, and whether
the repository keeps it.

| Step | Runs in | Output | Kept in the repository |
|---|---|---|---|
| Gates: first-hand evidence, scope, no query overlap | Session with the repository | Go or stop, with the reason | No |
| Research note | Session with the repository and web access | `docs/research/YYYY-MM-DD-<topic>.md` | Yes |
| Brief | Session with the repository, or an editorial session | The page plan, which I approve before any prose | No, the brief is deleted after use |
| Draft | Writing session, me, or the session with the repository | Portuguese MDX | Only after verification |
| Verification | Session with the repository, always | Corrected MDX, with each correction listed in the commit body | Yes |
| English version | Session with the repository, with the `english-version` skill | The pair in `content/en/`, plus the list of judgment calls in the PR | Yes |
| Registration | Session with the repository | Hreflang pair and a row in the experiment log | Yes |
| Checks | Session with the repository and CI | Script and test output | In the PR |
| Merge, indexing request, distribution | Me | The log row's date | Yes |

Three gates exist to stop a page that shouldn't exist. A page needs
first-hand evidence, meaning a measurement, an audit, an incident, or a file
in this repository. It has to fit the blog's scope, which is how machines
fetch, render, read, and index pages. And a search of published content
must turn up no equivalent `primaryQuery`. On an exact-match domain, a
filler page is the main risk, and stopping one before the research note
costs less than stopping it after the draft.

What makes a page well informed is the research note. Every external fact
in it comes from its original page, read on the day the note is written,
along with the last-updated date that page prints. Each fact gets a certainty
label: **[documented]**, **[inference]**, **[third-party]**, or
**[observation]**.
At the end, the note lists what the article may claim and what it may not.

## One page traced: scaled content abuse

I published the article on
[scaled content abuse](/en/blog/scaled-content-abuse) on October 18, 2026.
It went through every step, and each one left a trace.

| Step | What happened | Record |
|---|---|---|
| Research note | Each Google page was read that day from its HTML, with the last-updated date it prints. Each claim got a label, and the note added a list of claims to avoid and the proposed angle. | Commit `5adfded` |
| Brief | Approved with changes the same day: structure, FAQ, links, banned framings, and a length cap | Outside the repository |
| Writing session | The research note was not sent along, so every Google source was re-read from scratch. The session delivered a self-check table and a list of open items. | Outside the repository |
| Verification | The manual-action sentence aligned with the help text. A "most visible sign" scaled down to the mechanism. A timeline row corrected against the changelog. A source added for the live-test claim. The short answer cut to the 300-character limit the build enforces. | Body of commit `7e73fc1` |
| English version | Interface labels taken from the English help pages, and the English route's real code | Commit `ed4adb4` |
| Links | English pages pointed at the new articles. Later, the rule that English text links only to English pages. | `9742f18`, `62b32b7`, `8aba089` |

Every mechanical check in the writing session's self-check was right, and
verification still had four facts to correct. Leaving the note behind meant
redoing its research from scratch. Since then, the note
travels with the brief.

## What verification has corrected

Here's what verification corrected in real drafts, page by page, with a
record for each one.

| Page | Draft from | Correction | Record |
|---|---|---|---|
| `melhorar-lcp-nextjs` | Writing session | A slot for a lab measurement with nothing to fill it, and a sentence about RUM when RUM was still a plan | PR #7 |
| `json-ld-nextjs` | Writing session | Invented component files, props, and author object. An argument resting on a Google page removed on 2026-06-15. The wrong mechanism for client components. | PR #17 |
| `inp-nextjs` | Writing session | An H1 in the body, SVG colors outside the palette, and an internal document cited in reader-facing text | `0b95d3c` |
| Five spokes | Writing session, with placeholders | A "100% static" claim the build output contradicted, and a missing link to the pillar guide | PR #27 |
| `pre-registro-seo` | My draft | A title without the query, a stimulus attributed to the wrong article, and a list of deviations different from the log's | `0d997fb` |
| `sec-fetch-mode` | My draft | A false claim about HTTP clients. Testing it revealed a bug in the site's own classifier, fixed in PR #95. | `4de2df3` |
| `scaled-content-abuse` | Writing session | Four factual alignments with the sources, and a short answer over the limit | `7e73fc1` |

Placeholders like `[CODE-n]` put an end to invented code. A writing session
can't see the repository, so it leaves a slot empty, and a session that can
see it copies the excerpt from the file. Nothing has done that for "a fact
that sounded right." So verification re-reads each source on the day and,
when a claim can be tested here, tests whichever one looks most testable.
That's how the `sec-fetch-mode` draft led to a real bug in the code.

## What is automated, and what is not

Some checks run as scripts and tests. Others only happen when someone reads
the page.

| Check | Done by | When |
|---|---|---|
| Frontmatter fields, title ≤60, description ≤155, short answer ≤300, topic, `basedOn` | `src/lib/content.ts` | Every build |
| A cited repository path exists | `content-code-paths.test.ts` | CI |
| Translation pair declared on both sides | `hreflang.test.ts` | CI |
| One H1, title, description, canonical, JSON-LD, hreflang, contrast, accessibility | The Playwright suite | CI |
| Leftover placeholder, H1 in the body, double braces, unmapped component, SVG color outside the tokens, banned framing, quote length, required links, lead paragraph | `check-draft.mjs` | When the draft arrives and before the PR |
| Both sides exist, same facts and dates, links within their own language, translation note, log row | `check-pair.mjs` | Before the PR |
| British spelling, day-month dates, translation note not on the last line, known calques from Portuguese, and register compared with native technical English | `check-english.mjs` | After the native read and before the PR |
| Whether the subject deserves a page, whether a fact is still true, whether the code shown matches the repository's lines, whether the English reads as written in English | **No script**: verification, the native read, and me | Every page |

That last row is the one that matters. Scripts catch a problem that has
already happened once. Deciding whether a page should exist, and whether a
sentence is still true today, still takes someone reading.

## Packaging the process as a skill

Before the skill existed, the process was scattered across `CLAUDE.md`,
tests, two research notes, and commit messages. Today, `content-page`
gathers it into nine phases, and each one says where it runs and what it
delivers. It also holds templates for the research note and brief, the
kit a writing session receives, a verification walkthrough with every
correction made so far, and the two scripts. Instead of copying sections of
`CLAUDE.md`, it points to them. When the two disagree, `CLAUDE.md` wins and
the skill gets corrected.

`check-draft.mjs` grew out of the corrections listed earlier on this page,
and it ran against every published article before I trusted it. Its first
run failed six correct files, all of them false positives from four causes:

- the `<Image>` component, which the skill's draft said didn't exist in MDX
- a table of date formats, read as a placeholder
- `aria-label` text, counted as a long quote
- Windows line endings, which hid the first paragraph

With those four fixed, all 48 articles passed with no errors, and a draft
broken on purpose in ten places failed on all ten. This page went through
both scripts before its PR, as the `project` type, which requires a link to
a versioned file instead of links to the pillar guide and a tool.

## Writing the English version

In October 2026, I got feedback that the site's English version read like
a literal translation of the Portuguese. That feedback was right, and the
method was to blame. Its English step was a single paragraph listing what
had to stay the same (facts, dates, H2s, FAQ, links), and it said nothing
about how the English should sound. Each English page had been written
sentence by sentence from its Portuguese counterpart, so Portuguese
structure survived in correct English words. You could see it in colons
chaining clauses, "it is worth" for "vale a pena", "readings" for
"leituras", day-month dates, and British spelling mixed with American.

On October 27, 2026, a revision rewrote the 28 English pages and became a
second skill,
[english-version](https://github.com/Alf4kill/seotecnico.dev.br/tree/main/.claude/skills/english-version),
which the English phase of `content-page` now calls. This skill doesn't
translate in a single pass.

| Step | What it does |
|---|---|
| Fact sheet | Per section, what the Portuguese claims, at what level, and with what hedge, saved to a file before any English sentence is written |
| English draft | Written from the fact sheet by someone who does not read the Portuguese prose. Code and diagrams go in afterward, copied from the original. |
| Native read | The English, read alone, preferably by a reviewer who has not seen the Portuguese |
| Fidelity check | The English checked against the Portuguese: facts, hedges, links, code, and H2 and FAQ counts |
| Report | The judgment calls go in the PR, so I review meaning without comparing prose |

It also comes with a style guide (American English, US dates in prose and
ISO in tables, contractions in explanatory text, and a glossary of the
site's terms) and a script, `check-english.mjs`, that looks for the calques
the revision cataloged. Run on the commit before the revision, it found 263
occurrences, with errors in 28 of 28 pages. Afterward, it reported 0 errors
and 1 warning. You'll find the research, with the count, in the
[research note on English
quality](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/research/2026-10-27-english-translation-quality.md).

That same pass found two problems that had nothing to do with language. In
the JSON-LD article, the sentence explaining the escape showed `<` where the
code has `\u003c`. And one article had a paragraph after the translation
note. A clean run doesn't prove the English is native, only
that no known calque is left. Reading still decides.

Reading proved the point that same day. I reviewed this page's English
version, written during the revision, and found English that had none of the listed calques and was
still built like Portuguese. Every noun had a definite article, sentences
opened with "The", and colons joined clauses. To find out whether that was
just an impression, I measured register on the 28 English pages and on 26
pages of native technical English (Google and web.dev documentation, plus
first-person write-ups by US companies and engineers). All 28 used more
colons than 90% of the native pages, and 23 crossed that same threshold
for "the". This page crossed it on four of the five measures.

Once again, the cause was the method. Whoever wrote the English had the
Portuguese open, and each sentence brought its structure along. Three
things changed:

1. What used to be an intent map is now a fact sheet saved to a file, and
   someone who doesn't see the Portuguese prose writes the English draft
   from it.
2. The style guide is now based on Google's developer documentation style
   guide, which brought back the serial comma that Portuguese doesn't use.
3. `check-english.mjs` now compares each page with thresholds measured on
   native English and ranks pages by distance.

You'll find the corpus, thresholds, and false-positive rate (about 4 in 10
flagged paragraphs were fine) in the
[research note on
register](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/research/2026-10-27-english-register-profile.md).
This page's English version was the first one written that way.

## How to check

```bash
git clone https://github.com/Alf4kill/seotecnico.dev.br && cd seotecnico.dev.br
git show -s 5adfded 7e73fc1 ed4adb4
wc -l docs/research/2026-10-18-scaled-content-research.md
node .claude/skills/content-page/scripts/check-draft.mjs --published
node .claude/skills/content-page/scripts/check-pair.mjs --all
node .claude/skills/content-page/scripts/check-pair.mjs como-uma-pagina-nasce --type project
node .claude/skills/english-version/scripts/check-english.mjs --published --summary
git checkout 4a1f512 -- content/en
node .claude/skills/english-version/scripts/calibrate-register.mjs
git checkout HEAD -- content/en
```

When the skill landed in the repository in PR #115,
`check-draft.mjs --published` reported 48 files and 0 errors. Run it on a
newer commit and you'll see the number grow with each article published.
I took the register counts from commit `4a1f512`, before any page was
rewritten with the new method. To rerun that measurement at that commit,
you can use the block's last three lines. They need network access, and
the native pages may have changed since October 27, 2026.
