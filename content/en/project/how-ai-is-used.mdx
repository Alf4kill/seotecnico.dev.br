This site is built by one person working with Claude, Anthropic's model. I
decide what gets built, supply the data only I can access (Search Console and
GA4), review every change and merge every pull request. Claude writes most of
the code, tests, documentation and article drafts, within rules the
repository enforces on its own. The model isn't what makes that output
usable. What does is that almost every rule a model could break is checked by
a test.

This page is part of the [Project](/en/project) section, which documents how
the site is built. Everything here comes from the
[AI workflow document in the repository](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/ai-workflow.md),
and every number below comes with the command that reproduces it.

## Who does what

| Step | Me | Claude |
|---|---|---|
| Decide what to work on next | yes | proposes it, in research notes and proposals |
| Search Console and GA4 data | exported by hand from the project's properties | reads the exports; never has the credentials |
| Research | review | writes dated notes, with an evidence label on every claim |
| Code, tests, documentation, drafts | review and correct | writes them, in a session with repository access |
| Pull request | review and merge | opens it; never merges |
| After merge | request indexing and share | — |

Editorial work (briefs, draft review) happens in a session without repository
access; implementation happens in one with it. Since the first session can't
see the code, it leaves `[CODE-n]` placeholders wherever the site's code
belongs, and the second fills them in by copying from the file. Before that
rule, drafts came back with made-up code: component files and prop shapes
that don't exist in the repository, as PR #17 shows.

## The contract: CLAUDE.md

`CLAUDE.md` is read at the start of every session and describes itself as the
project's single source of truth. A few things make it a contract a model can
follow rather than a wish list:

- **Numbered sections.** A commit, a review comment or a skill cites "§10"
  instead of paraphrasing a rule.
- **Dated decisions.** "owner rule, 2026-10-23", "rule since 2026-09-25":
  the rule itself records when it was made and by whom, so a later session
  knows which rule is newer and why it exists.
- **The claims policy** (§10). Every claim is a mechanism, a condition or a
  magnitude, and a magnitude needs a measurement with a declared method. This
  is the rule that stops generated text from making up numbers.
- **An out-of-scope list** (§13), which matters as much to a model as the
  scope does.

## Rules that are tests

CI (`.github/workflows/ci.yml`) blocks a merge if anything fails:

| Check | What a model might get wrong that it catches |
|---|---|
| Lint, type-check, 33 Vitest files | broken code, schema builders, content parsing |
| Content loader (`src/lib/content.ts`) | a title over 60 characters, a description over 155, a short answer over 300, an unknown axis |
| `content-code-paths.test.ts` | an article citing a repository path that doesn't exist |
| `hreflang.test.ts` | a translation pair declared on only one side |
| `design-rules.test.ts`, `design-tokens.test.ts` | a hardcoded color, a forbidden utility, tokens drifting apart |
| 8 Playwright specs | one H1, title and description, canonical, JSON-LD types, hreflang in both directions, contrast, accessibility |
| Lighthouse CI | performance budgets |

A rule that matters but isn't a test yet tends to get broken. The closing
translation note on English articles was a convention, not a check, and the
two pairs published on October 23 shipped without it. Nobody noticed until
the page-creation skill's pair script started checking for it.

## Scaling a claim down

Several commits exist only to make a sentence smaller and true. One example:
during the October crawl audit, the apex domain refused connections from my
network and from an external fetcher. The first interpretation was an
outage. Commit `e376922` scaled that down to what the evidence supported: a
TCP-only check reached the address from 17 of 18 nodes worldwide and from a
node in São Paulo, so the server was up; what failed was the route to it from
some networks. The research notes follow the same habit, labeling every claim
**[documented]**, **[inference]** or **[observation]**.

## What stays with me

- **Merging.** No session merges its own pull request.
- **Secrets.** API keys live in Vercel environment variables. The project's
  Search Console and GA4 properties live in my personal Google account.
- **Search Console data, by hand.** No API pulls it. The monitoring toolkits
  listed in `CLAUDE.md` (`gsc-monitor`, `nextjs-cwv-toolkit`,
  `ai-search-monitor`) have never run against this site. Every Search Console
  number in the repository comes from a manual export, dated in the file that
  records it.
- **The decision to publish.** Whether a topic deserves a page, and whether a
  page is ready.
- **Distribution.** Indexing requests and posts happen by hand, after merge.

Google takes the same view of AI use: as the article on
[scaled content abuse](/en/blog/scaled-content-abuse) shows, the problem its
spam policy describes is scale without value, not the tool. The method of
registering a hypothesis before seeing the data, used in this site's
experiments, is explained in
[SEO testing with pre-registration](/en/blog/seo-testing-pre-registration).
And the other page that explains a site decision from the inside is the
[design colophon](/en/design).

## Reproducing the numbers

```bash
git clone https://github.com/Alf4kill/seotecnico.dev.br && cd seotecnico.dev.br
git rev-list --count b141722
git log --merges --oneline b141722 | wc -l
git rev-list --no-merges --count b141722
git log --no-merges --format='%(trailers:key=Co-Authored-By,valueonly)' b141722 \
  | grep -i claude | sed 's/<.*//' | sort | uniq -c
git log --no-merges --format='%s' b141722 \
  | sed -E 's/^([a-z]+)(\([^)]*\))?:.*/\1/' | sort | uniq -c | sort -rn
```

On a later commit the numbers will be higher: the tables above are a dated
snapshot, not a live counter.
