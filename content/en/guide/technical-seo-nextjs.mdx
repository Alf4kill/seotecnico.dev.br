**Technical SEO for Next.js** is everything you implement in code (metadata,
structured data, sitemaps, rendering and performance) so Google can crawl,
index and rank a site built with the App Router. Unlike content SEO, it gets
solved in the repository: the `Metadata API`, `sitemap.ts`, `robots.ts`,
JSON-LD and Core Web Vitals. This guide walks through each piece in the order
it comes up in a real project, with the code and measurements from this very
site.

## What the App Router changed

The change everything else follows from: in the App Router, a meta tag is no
longer JSX; it's **data**. `next/head` isn't supported inside `app/`; the
framework builds the `<head>` from a `metadata` object exported by the route,
or from a `generateMetadata()` function when the value depends on `params`.
The sitemap and robots file went the same way: they're no longer static files
in `public/` but code in `app/sitemap.ts` and `app/robots.ts`.

That's good news and a trap at the same time. The good news is that everything
can be derived from the content: publishing an MDX file can be the only step
needed for a page to enter the sitemap, get JSON-LD and be covered by tests.
The trap is that the way those objects are inherited between layout and page
isn't what you'd intuitively expect, and that's where the most expensive
problems start.

## Metadata: canonicals, Open Graph and the merge that doesn't happen

Every page needs a unique `<title>`, a meta description and a self-referencing
canonical. In the App Router, those come from the Metadata API. The detail
that breaks sites in production is that inheritance between layout and page
is a **shallow merge**: if the page declares any field inside `openGraph`, the
parent layout's entire object gets silently thrown away, including `og:image`,
`og:site_name` and `og:locale`. The same goes for `alternates`, so a canonical
set only in the layout disappears on any route that customizes its
alternates.

That's exactly how this site's Open Graph broke in July 2026. The fix isn't
remembering to repeat the fields on every page; it's removing the possibility
of forgetting: a single metadata helper every route goes through, which builds
the complete `openGraph` object every time and enforces the length limits at
build time. A title over 60 characters or a description over 155 breaks the
build, not your search results.

It's also worth checking `metadataBase` (it's what turns a relative path into
an absolute URL, which Open Graph requires) and how `opengraph-image.tsx`
behaves: in Next.js 16.2.6, it does **not** cascade to nested routes.

To audit a published route against the checks in this section, this site has
a [meta tag validator](/en/tools/meta-tag-validator): it reads the HTML the
server returns and grades the title, description, canonical, robots, H1 and
Open Graph tags, the same checks this site's CI runs on every deploy.

## A sitemap and robots file derived from your content

`app/sitemap.ts` exports a function that returns an array of URLs, and the
version worth writing is the one that **derives that array from your
content**, not one that lists routes by hand. A hand-written list goes stale
the first time you publish an article.

Of the four fields Next.js accepts per entry, Google only cares about two:
`url` and `lastModified`. The official documentation says `priority` and
`changeFrequency` are ignored. And `lastmod` is only used when it's consistent
and verifiable. A `new Date()` on every build produces a date that never
matches a real change, which teaches Google to ignore the field. The rule that
holds up: only emit `lastmod` when you can derive it from the content.

`app/robots.ts` is the counterpart, and its right default is **not to index**:
a preview environment inheriting production's robots rules is a common
accident. One last trap, which this site fell into and measured: `noindex` and
`Disallow` do **not** add up. A URL blocked in robots.txt is never crawled, so
its `noindex` is never read; the two cancel each other out.

→ Full chapter: [Dynamic sitemap in Next.js with sitemap.ts and robots.ts](/en/blog/nextjs-dynamic-sitemap)

## Redirects, canonicals and noindex: choosing the right tool

Before choosing between `redirects()` in `next.config` and middleware, there's
an earlier question almost nobody asks: does this problem actually call for a
redirect?

There are three tools for three different problems. A permanent redirect
(301/308) when the old URL should stop existing. A canonical when both URLs
exist but one should consolidate the signals, keeping in mind that it's a
strong hint, not a directive. `noindex` when the page exists for users but not
for the index. And when the content is genuinely different, there's no problem
to solve. Getting this choice wrong doesn't produce a build error; it produces
a symptom months later, in Search Console's indexing report.

Once you've made the choice, the implementation is simple: `redirects()` in the
config is static, evaluated before routing and free per request; middleware
runs on **every** request and is the only option that can decide based on a
cookie, a header or the visitor's location. If the rule is already known at
build time, it doesn't belong in middleware.

→ Full chapter: [Redirects and canonicals in Next.js: config or middleware](/en/blog/nextjs-redirects-canonicals)

## JSON-LD in the App Router

Structured data in the App Router doesn't need a library: a
`<script type="application/ld+json">` rendered in a Server Component arrives
ready-made in the initial HTML, which is exactly where Googlebot wants to find
it.

The architectural decision is **where** each schema lives, and the practical
rule is to render it at the level where the data behind it actually exists.
A schema that changes per route (`Article`, `BreadcrumbList`) goes in
`page.tsx`. A schema that's stable across the whole site (`WebSite`,
`Organization`) can live in the layout. Multiple blocks on the same page are
read without trouble; what you mustn't do is let the same type contradict
itself across blocks.

The real gain comes from deriving the schema from the frontmatter instead of
writing it by hand: the `Article` for every post on this site comes from the
same fields that generate the `<title>` and the sitemap, so the two can never
disagree. As for `FAQPage`: Google stopped showing the rich result on May 7,
2026 and removed its documentation on June 15, 2026, but the type is still
valid in schema.org, and keeping it costs almost nothing when it comes from
the same source as the visible FAQ.

To put together a one-off schema quickly, this site has a [JSON-LD
generator](/en/tools/json-ld-generator) that gives you both the object and a
ready-to-use Next.js component.

## Hreflang and the bilingual site

The page you're reading is this chapter's own proof: it's the English version
of a Portuguese guide, and the two declare each other.

Three rules cover almost everything about hreflang. **Reciprocity**: if A
declares B as its alternate, B has to declare A back, or Google throws out the
cluster, a silent failure that raises no error anywhere. **Self-reference**:
each page lists itself among the alternates, which is what lets the same block
of tags be valid on both sides. **`x-default`**: the version served to anyone
who doesn't match a declared language; on a Portuguese-first site, it points
to the Portuguese original, not the translation.

In the App Router, the tags come from `alternates.languages` in the Metadata
API, and the implementation detail that matters is where that object gets
built. Declaring the pair by hand on each page is what breaks reciprocity at
the first refactor: someone renames a route and only one side finds out. On
this site, the pairs live in a single module, both sides of each pair are
generated from the same object, and a test checks reciprocity in the served
HTML rather than in the source code. That's the difference between hreflang
that works and hreflang that merely exists.

There's one trap I found while writing that test, and it applies to anyone
auditing hreflang with a script: Next.js serializes the attribute as
`hrefLang`, in camelCase, in the HTML it serves. That's valid, since HTML
attribute names are case-insensitive, and both the browser and Google read it
as `hreflang`. But a script that reads the raw HTTP response with a
case-sensitive regex finds nothing and concludes the site has no hreflang at
all. That's exactly what happened here: the DOM-based check passed while the
same check over HTTP came back empty.

Two decisions are worth spelling out because they aren't obvious. An English
page's URL carries its query in English (this one is
`/en/guide/technical-seo-nextjs`, not a mirror of the Portuguese path), since
the URL is part of what the page is about. And `<html lang>` matches each
page's language: `en` here, `pt-BR` on the Portuguese original. The site has
one root layout per language, using route groups, so the navigation, footer
and cookie banner around this guide are in English too. The first version of
this page lived inside the Portuguese frame, and only the article carried
`lang="en"`, because only the article was in English. Google ignores the
attribute for language detection either way (it reads the content), but
assistive technology doesn't.

The dedicated chapter followed this implementation rather than coming before
it. Nothing here gets published before it's implemented and measured.

## Rendering: what Googlebot actually receives

For the indexer, the acronym doesn't matter; what matters is what arrives in
the HTML of the **first response**.

By that measure, SSG and SSR are equivalent: both deliver the complete content
in that HTML. ISR also delivers complete HTML, though it may be stale between
revalidations. CSR delivers a skeleton and depends on a second rendering pass
by Googlebot, which is queued, and it's the only one of the four that creates
a real indexing risk.

That shifts the question from "which is faster?" to "what does the indexer
receive?", and it leads to an uncomfortable conclusion for anyone who reaches
for `useEffect` freely: a component that only exists after hydration is the
most common SEO mistake in Next.js. Not because Google doesn't run JavaScript
(it does), but because that rendering happens in a queue, and you don't control
your place in it.

The practical upshot is that you should be able to **prove** which strategy
each of your routes uses, rather than assuming. The route table from
`next build` shows it, with one symbol per route.

→ Full chapter: [SSR, SSG and ISR in Next.js: what Googlebot sees](/en/blog/nextjs-ssr-ssg-isr)

## LCP: diagnose before you optimize

The mistake that costs teams weeks on LCP is optimizing before knowing where
the time goes. LCP breaks down into four subparts (**TTFB**, **resource load
delay**, **resource load duration** and **element render delay**), and each
has different fixes. Optimizing the wrong subpart changes nothing.

Once you've found the bottleneck, a handful of moves solve most cases: make
sure the LCP element is in the initial HTML (a Server Component), use
`preload` on `next/image` for the LCP image only (Next.js 16 deprecated
`priority` in its favor), and load fonts with `next/font`.

Then there's the opposite case, which is more frustrating: an LCP that does
**not** improve after you've already switched everything to `next/image`. The
culprit there is usually a pattern that hides the resource from the preload
scanner (a CSS `background-image`, a hero behind `"use client"`), a render
delay you caused yourself with a fade-in animation or an A/B testing
anti-flicker snippet, or too many preloads competing for bandwidth with the
very element they were supposed to speed up.

Before diagnosing anything, it helps to know where you stand in the **field**:
the [Core Web Vitals checker](/en/tools/cwv-checker) queries your origin's
real p75 in CrUX. If your origin isn't in the dataset yet (which is the case
for most sites), that tells you something too: your only option is your own
RUM, which is what this site does.

## INP: the metric Lighthouse doesn't measure

INP (Interaction to Next Paint) measures the time between an interaction and
the next painted frame; good means ≤200 ms at the field p75. It replaced FID in
March 2024, and the difference is scope: FID only measured the initial delay
of the first interaction, while INP looks at every interaction and measures the
full cycle.

And here's the quirk that changes how you work: **Lighthouse has no INP**.
That's not a gap in the UI; it's conceptually impossible. INP requires a real
interaction from a real user, and there's nobody clicking in the lab. What the
lab audit gives you instead is TBT (Total Blocking Time), a proxy that
correlates with INP but can't replace it.

For a small site, that adds up to a double blind spot: with no interaction in
the lab, there's no INP in Lighthouse, and below the CrUX traffic threshold
there's no INP in PageSpeed Insights or Search Console either. The way out is
to collect your own field data with RUM: the `web-vitals` library's `onINP`
sending an event to GA4. That's what this site does, with attribution by
subpart.

→ Full chapter: [INP in Next.js: how to diagnose and fix it](/en/blog/nextjs-inp)

## Images: performance solved, indexing not

`next/image` gives you modern formats, a `srcset` per viewport, lazy loading
and dimensions reserved to prevent CLS. In this site's baseline, that shows up
as **CLS 0.000 across all 10 pages** measured: with explicit dimensions,
image-driven layout shift simply doesn't happen.

What it does **not** give you is indexing. Alt text, the surrounding text, the
file name and the sitemap entry are still your job, and the component is
completely blind to images declared in CSS. Search results treat "image SEO"
as a synonym for "image performance", but the other half is what decides
whether the image exists for the index at all.

Two things usually go unnoticed: the `sizes` attribute decides which file from
the `srcset` the user actually downloads (getting it wrong wipes out much of
the gain), and explanatory diagrams pay off more as **inline SVG** than as
raster images, because their `<text>` labels can be crawled and quoted. The
catch is that inline SVG doesn't show up in Google Images; if that channel
matters to you, export a raster copy and declare it in the image sitemap.

→ Full chapter: [next/image and SEO: what the component doesn't solve](/en/blog/next-image-seo)

## Measurement: GTM and GA4 in an SPA

Optimizing without measuring is guesswork, and measuring an SPA has a
specific trap: GTM's **All Pages** trigger only fires on the first load.
Subsequent navigations use `history.pushState` and don't reload the page, so
GA4 records the landing page and goes blind for the rest of the session.

The fix is the **History Change** trigger, and the mistake almost everyone
makes is turning it on in GTM **and** leaving GA4's Enhanced Measurement
listening for the same events, which counts every pageview twice. The hard
part was never getting the event to fire; it's getting it to fire exactly
once.

Add Consent Mode v2 with a denied default, a practical requirement under
Brazil's data protection law (LGPD), and you end up with an implementation you
have to validate against real requests, not just in GTM's preview mode.

→ Full chapter: [GTM in Next.js: SPA pageviews without double counting](/en/blog/nextjs-gtm)

## What this site measured

This guide isn't theoretical: every technique above is implemented on this
domain, and the numbers below come from it.

The most complete case is the home page. Its LCP element is a paragraph of
text, and diagnosing it by the four subparts pointed to **element render
delay**, not the image weight everyone assumes. Two changes fixed it: inlining
the CSS (~22 KB raw, ~5 KB compressed, and the site's only render-blocking
request) and switching the Inter font from `display: swap` to
`display: optional` with no preload, which took it off the critical path.

The result in PageSpeed Insights on mobile, in production, measured on July 18,
2026:

| Metric | Before | After |
|---|---|---|
| Performance | 78 | **100** |
| LCP | 4.9 s | **0.9 s** |
| Element render delay | 1,280 ms | **530 ms** |
| CLS | 0 | 0 |

Two days later, the full baseline of all 10 URLs came in at LCP 1.0–1.2 s,
CLS 0.000, TBT 80–148 ms, zero orphan pages and a maximum depth of 2 clicks.

What hasn't been measured yet matters just as much. The domain is below
CrUX's traffic threshold, so there's no public field data. The numbers above
come from the lab and from the site's own RUM. The field verdict is still
open, and it will appear here once it exists, not before.

## How this guide is maintained

All ten chapters are now implemented on this domain; hreflang was the last,
and it arrived by being built rather than described. Each chapter is an
article with real code and its own measurements, and this guide is the map
that ties them together. The chapter articles were first published in
Portuguese, this site's primary language; since October 2026, all ten also
have an English version, linked above.

What keeps the content from going stale is the same CI that protects the
code: a Playwright suite checks every route for a single `<h1>`, title and
description limits, a self-referencing canonical, JSON-LD that parses and,
since this page has existed, hreflang that's reciprocal in both directions.
Lighthouse budgets block the merge if LCP, CLS or TBT regress. When a
technique described here stops being true, the test breaks before any reader
notices.
