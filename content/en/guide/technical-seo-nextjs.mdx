**Technical SEO for Next.js** is the set of things you implement in code
(metadata, structured data, sitemaps, rendering, and performance) so Google
can crawl, index, and rank a site built with the App Router. Unlike content
SEO, you solve it in the repository, with the `Metadata API`, `sitemap.ts`,
`robots.ts`, JSON-LD, and Core Web Vitals. This guide takes each piece in the
order it shows up in a real project, with this site's own code and
measurements.

## What the App Router changed

Everything else follows from one change. In the App Router, a meta tag stopped
being JSX and became **data**. `next/head` isn't supported inside `app/`.
Instead, the framework builds the `<head>` from a `metadata` object that the
route exports, or from a `generateMetadata()` function when the value depends
on `params`. The sitemap and robots file went the same way. They're now code,
in `app/sitemap.ts` and `app/robots.ts`, not static files in `public/`.

That's good news and a trap at once. Since everything can be derived from
content, publishing one MDX file can be the only step a page needs to enter
the sitemap, get its JSON-LD, and be covered by tests. The trap is that these
objects don't pass from layout to page the way you'd expect, and that's where
the most expensive problems start.

## Metadata: canonicals, Open Graph and the merge that doesn't happen

Every page needs a unique `<title>`, a meta description, and a
self-referencing canonical. In the App Router, all three come from the
Metadata API.

What breaks sites in production is how pages inherit metadata from layouts,
through a **shallow merge**. If a page declares any field inside
`openGraph`, Next.js silently discards the parent layout's entire
`openGraph` object, including `og:image`, `og:site_name`, and `og:locale`.
`alternates` works the same way, so a canonical defined only in the layout
disappears on any route that customizes its alternates. That's exactly how
this site's Open Graph broke in July 2026.

Remembering to repeat fields on every page doesn't fix it. Removing the chance
to forget does. Route every page through a single metadata helper that builds
the complete `openGraph` every time and validates length limits at build
time. A title over 60 characters or a description over 155 then breaks the
build, not the SERP.

Two more things to check: `metadataBase`, which turns a relative path into an
absolute URL and is required for Open Graph, and `opengraph-image.tsx`, which
in Next.js 16.2.6 does **not** cascade to nested routes.

To audit an already-published route against these checks, use the
[meta tag validator](/en/tools/meta-tag-validator). It reads the HTML your
server responds with and grades the title, description, canonical, robots,
H1, and Open Graph, the same checks this site's CI enforces on every deploy.

## A sitemap and robots file derived from your content

`app/sitemap.ts` exports a function that returns an array of URLs. Write one
that **derives that array from the content** instead of listing routes by
hand. A manual list goes stale with the first article you publish.

Next.js accepts four fields per entry, and only two of them matter to Google:
`url` and `lastModified`. The official documentation says
`priority` and `changeFrequency` are ignored.

Google uses `lastmod` only when it's consistent and verifiable. A
`new Date()` on every build produces a date that never matches a real change,
which teaches Google to ignore the field. Emit `lastmod` only when you can
derive it from the content.

`app/robots.ts` is its counterpart, and the right default there is **not
indexing**. A preview environment that inherits production's robots file is a
common accident.

I fell into one trap here and measured it. `noindex` and `Disallow` do
**not** add up. A URL blocked in robots.txt is never crawled, so its `noindex`
is never read, and the two cancel each other out.

→ Full chapter: [Dynamic sitemap in Next.js with sitemap.ts and
robots.ts](/en/blog/nextjs-dynamic-sitemap)

## Redirects, canonicals and noindex: choosing the right tool

Before you choose between `redirects()` in `next.config` and middleware,
settle a question almost nobody asks first. Does the problem really call for
a redirect?

Three tools solve three different problems:

- A permanent redirect (301/308), when the old URL should stop existing.
- A canonical, when both URLs exist but one of them should consolidate the
  signals. A canonical is a strong hint, not an order.
- `noindex`, when the page exists for the user, not for the index.

If the two URLs have distinct content, there's no problem to solve.

Pick the wrong tool and nothing fails in the build. The symptom shows up
months later, in Search Console's indexing report.

Once you've made that choice, the implementation is simple. `redirects()` in
the config is static and evaluated before routing, with no per-request cost.
Middleware runs on **every** request, and it's the only one of the two that
can decide based on a cookie, a header, or geography. If you know the rule at
build time, it doesn't belong in middleware.

→ Full chapter: [Redirects and canonicals in Next.js: config or
middleware](/en/blog/nextjs-redirects-canonicals)

## JSON-LD in the App Router

You don't need a library for structured data in the App Router. A
`<script type="application/ld+json">` rendered in a Server Component is ready
in the initial HTML, exactly where Googlebot wants it.

What you have to decide is **where** each schema lives. As a practical rule,
render it at the level where the data that feeds it really exists. Per-route
schemas (`Article`, `BreadcrumbList`) go in `page.tsx`. Site-wide, stable
schemas (`WebSite`, `Organization`) can stay in the layout. A page can carry
multiple blocks without trouble. What it can't do is let the same type
contradict itself across blocks.

Where this really pays off is deriving the schema from the frontmatter
instead of writing it by hand. On this site, each article's `Article` comes
from the same fields that generate its `<title>` and its sitemap entry, so
they can never disagree.

As for `FAQPage`, Google stopped showing the rich result on May 7, 2026, and
removed its documentation on June 15, 2026. The type is still valid in
schema.org, and keeping it costs almost nothing when it comes from the same
source as the visible FAQ.

For a one-off schema, the [JSON-LD generator](/en/tools/json-ld-generator)
gets you there quickly. It returns both the object and a ready-to-use Next.js
component.

→ Full chapter: [How to implement JSON-LD in Next.js (App

## Hreflang and the bilingual site

This page is its own example. It's the English version of a Portuguese guide,
and the two declare each other as alternates.

Three rules carry almost all of hreflang:

- **Reciprocity.** If A declares B as an alternate, B has to declare A back,
  or Google discards the cluster. It fails silently, with no error anywhere.
- **Self-reference.** Each page lists itself among its alternates. That's
  what makes the same block of tags valid on both sides.
- **`x-default`.** It's the version served to anyone who matches no declared
  language. On a Portuguese-first site, it points to the Portuguese original,
  not the translation.

In the App Router, the tags come from `alternates.languages` in the Metadata
API. What matters is **where** you build that object. If you declare the pair
by hand on each page, the first refactor breaks reciprocity. Someone renames
a route, and only one side finds out. On this site, the pairs live in one
module, the same object generates both sides of each pair, and a test checks
reciprocity in the served HTML, not in the source code. That's the
difference between hreflang that works and hreflang that only exists.

I found a trap while writing that test, and it applies to anyone who audits
hreflang with a script. Next.js serializes the attribute as `hrefLang`, in
camelCase, in the HTML it serves. That's valid, because HTML attribute names
are case-insensitive. The browser reads `hreflang`, and so does Google. But if
you read the raw HTTP response with a case-sensitive regex, you find nothing
and conclude the site has no hreflang. That's exactly what happened here. The
DOM check passed, and the same check over HTTP came back empty.

Two decisions here aren't obvious. First, the English page's URL carries the
English query, `/en/guide/technical-seo-nextjs`, instead of mirroring the
Portuguese path, because the URL is part of what a page says it is. Second,
`<html lang>` follows each page's language, so it's `en` on this page and
`pt-BR` on the Portuguese original. Each language has its own root layout, in
route groups, so the English version has an English header, footer, and
cookie consent banner. In the first version, the English page lived inside
the Portuguese frame, and only the article carried `lang="en"`, since it was
the only part in English. Google treats both setups the same, because it
ignores the attribute and detects language from the content. Assistive
technology doesn't.

## Rendering: what Googlebot actually receives

The indexer doesn't care about the acronym. It cares about what arrives in the
HTML of the **first response**.

By that criterion, SSG and SSR are equivalent, since both deliver the complete
content in that HTML. ISR also delivers complete HTML, possibly stale between
revalidations. CSR delivers a skeleton and depends on Googlebot's second
rendering pass, which is queued. It's the only one of the four that creates a
real indexing risk.

That shifts the question from "which is fastest?" to "what does the indexer
receive?" If you reach for `useEffect` freely, the answer is uncomfortable. A
component that only exists after hydration is the most common SEO mistake in
Next.js. That's not because Google doesn't run JavaScript. It does. But
execution waits in a queue, and you don't control your place in it.

So you should be able to **prove** which strategy each of your routes uses,
instead of assuming it. `next build` shows it in its route table, with one
symbol per route.

→ Full chapter: [SSR, SSG and ISR in Next.js: what Googlebot
sees](/en/blog/nextjs-ssr-ssg-isr)

## LCP: diagnose before you optimize

Optimizing before you know where the time goes is the mistake that costs teams
weeks on LCP. LCP splits into four subparts: **TTFB**, **resource load
delay**, **resource load duration**, and **element render delay**. Each has
its own fixes, and optimizing the wrong one changes nothing.

Once you've found the bottleneck, a few moves solve most cases:

- Put the LCP element in the initial HTML, with a Server Component.
- Use `preload` on `next/image` only for the LCP image. Next.js 16 deprecated
  `priority` in its favor.
- Load fonts with `next/font`.

More frustrating is the opposite case, an LCP that does **not** improve after
you switch everything to `next/image`. The culprit is usually one of these:

- A pattern that hides the resource from the preload scanner, such as a CSS
  `background-image` or a hero behind `"use client"`.
- A render delay you created, with a fade-in animation or an A/B-test
  anti-flicker snippet.
- Too much preload, competing for bandwidth with the very element it should
  speed up.

Before any diagnosis, know your starting point in the **field**. The
[Core Web Vitals checker](/en/tools/cwv-checker) queries your origin's real
p75 in CrUX. If your origin isn't in the dataset yet, which is the case for
most sites, that's information too. It tells you to collect your own RUM,
which is what this site does.

→ Full chapters: [How to improve LCP in Next.js: a guide to the 4
subparts](/en/blog/improve-lcp-nextjs) · [High LCP in Next.js: the mistakes
that keep it high](/en/blog/nextjs-high-lcp)

## INP: the metric Lighthouse doesn't measure

INP (Interaction to Next Paint) is the time between an interaction and the
next painted frame. A good INP is 200 ms or less at the field p75.

It replaced FID in March 2024, and what changed is scope. FID measured only
the initial delay of the first interaction, while INP looks at every
interaction and measures the full cycle.

**Lighthouse has no INP**, and that changes how you work. It's not something
the interface left out. It's conceptually impossible, because INP requires a
real interaction by a real user, and nobody clicks in the lab. A lab audit
offers TBT (Total Blocking Time) instead, a proxy that correlates with INP but
doesn't replace it.

A small site is blind twice. With no interaction in the lab, Lighthouse has no
INP. Below the CrUX traffic threshold, neither PageSpeed Insights nor Search
Console has it either. The way out is to measure your own field data with
RUM, using the `web-vitals` library with `onINP` sending an event to GA4.
This site does, with attribution by subpart.

→ Full chapter: [INP in Next.js: how to diagnose and fix
it](/en/blog/nextjs-inp)

## Images: performance solved, indexing not

`next/image` gives you a modern format, a `srcset` per viewport, lazy loading,
and reserved dimensions against CLS. This site's baseline shows **CLS 0.000
across the 10 pages** measured. With explicit dimensions, image-driven layout
shift doesn't exist.

What it does **not** give you is indexing. `alt`, the text around the image,
the file name, and its presence in the sitemap are still on you. And
`next/image` is completely blind to images declared in CSS.

Across the whole SERP for this topic, pages treat "image SEO" as a synonym for
"image performance." Yet it's the other half, indexing, that decides whether
an image exists for the index.

Two points are easy to miss. First, the `sizes` attribute decides which
`srcset` file the user actually downloads, and getting it wrong cancels a
good part of the gain. Second, explanatory diagrams pay off more as **inline
SVG** than as raster images, because their `<text>` labels are crawlable and
citable. Inline SVG doesn't show up in Google Images, though. If that channel
matters to you, export a raster copy and declare it in the image sitemap.

→ Full chapter: [next/image and SEO: what the component doesn't
solve](/en/blog/next-image-seo)

## Measurement: GTM and GA4 in an SPA

Optimizing without measuring is guessing. In an SPA, GTM's **All Pages**
trigger is a trap, because it fires only on first load. Later navigations
use `history.pushState` and don't reload the page, so GA4 records the entry
and then goes blind until the session ends.

A **History Change** trigger fixes that. Then comes the decision almost
everyone gets wrong, which is enabling it in GTM **and** leaving GA4's
Enhanced Measurement listening to the same events. Every pageview then counts
twice. Getting the event to fire was never the problem. Getting it to fire
only once is.

Add Consent Mode v2 with a default of denied, a practical requirement under
LGPD (Brazil's data protection law), and you'll need to validate the setup in
real requests, not only in GTM's Preview mode.

→ Full chapter: [GTM in Next.js: SPA pageviews without double
counting](/en/blog/nextjs-gtm)

## What this site measured

None of this is theoretical. I've implemented every technique above on this
domain, and the numbers below come from it.

The home page is the most complete case. Its LCP element is a paragraph of
text, and the four-subpart diagnosis pointed to **element render delay**, not
the image weight everyone assumes.

Two changes solved it. First, I inlined the CSS (~22 KB raw, ~5 KB
compressed), which was the site's only render-blocking request. Second, I
moved the Inter font from `display: swap` to `display: optional`, without
preload, which took it off the critical path.

Here are the PageSpeed Insights results (mobile, in production) from
July 18, 2026:

| Metric | Before | After |
|---|---|---|
| Performance | 78 | **100** |
| LCP | 4.9 s | **0.9 s** |
| Element render delay | 1,280 ms | **530 ms** |
| CLS | 0 | 0 |

Two days later, a full baseline of the 10 URLs showed LCP of 1.0–1.2 s, CLS of
0.000, TBT of 80–148 ms, zero orphan pages, and a maximum depth of 2 clicks.

Some of it is **not** measured yet. This domain is below the CrUX traffic
threshold, so there's no public field data for it. The numbers above are lab
data and my own RUM. The field verdict is still open, and it'll appear here
when it exists, not before.

## How this guide is maintained

All ten chapters are published, each with real code and its own measurement,
and this guide maps how they connect. Hreflang was the last chapter to
arrive, and it came in the right order. I built the implementation first
and wrote the article from it, including the trap it revealed, the camelCase
`hrefLang`.

What keeps the content from going wrong as it ages is the same CI that
protects the code. On every route, a Playwright suite checks for a single
`<h1>`, title and description limits, a self-referencing canonical, JSON-LD
that parses, and, now that an English version exists, reciprocal hreflang in
both directions. Lighthouse budgets block a merge if LCP, CLS, or TBT regress.
When a technique described here stops being true, the test breaks before any
reader notices.
