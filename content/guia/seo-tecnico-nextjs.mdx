**SEO técnico para Next.js** é o conjunto de implementações no código —
metadados, dados estruturados, sitemaps, renderização e performance — que
permite ao Google rastrear, indexar e rankear um site feito com App Router.
Diferente do SEO de conteúdo, ele é resolvido no repositório: `Metadata API`,
`sitemap.ts`, `robots.ts`, JSON-LD e Core Web Vitals. Este guia percorre cada
peça na ordem em que ela aparece num projeto real, com o código e as medições
deste próprio site.

## O que o App Router mudou

A diferença que organiza todo o resto: no App Router, meta tag deixou de ser
JSX e virou **dado**. O `next/head` não é suportado dentro de `app/`; o
`<head>` é montado pelo framework a partir de um objeto `metadata` exportado
pela rota, ou de uma função `generateMetadata()` quando o valor depende de
`params`. Sitemap e robots seguiram o mesmo caminho — deixaram de ser arquivos
estáticos em `public/` e viraram código em `app/sitemap.ts` e `app/robots.ts`.

Isso é uma boa notícia e uma armadilha ao mesmo tempo. A boa notícia é que
tudo passa a ser derivável do conteúdo: publicar um arquivo MDX pode ser o
único passo necessário para a página entrar no sitemap, ganhar JSON-LD e ser
coberta por testes. A armadilha é que o comportamento de herança desses
objetos entre layout e página não é o que a intuição sugere — e é onde
começam os problemas mais caros.

## Metadados: canonical, Open Graph e o merge que não existe

Toda página precisa de `<title>` único, meta description, e canonical
auto-referente. No App Router isso sai da Metadata API. O detalhe que quebra
sites em produção é que a herança entre layout e página é um **merge raso**:
se a página declara qualquer campo dentro de `openGraph`, o objeto inteiro do
layout pai é descartado — silenciosamente, incluindo `og:image`,
`og:site_name` e `og:locale`. O mesmo vale para `alternates`, o que faz um
canonical definido só no layout desaparecer em qualquer rota que customize
alternates.

Foi exatamente assim que o Open Graph deste site quebrou, em julho de 2026. A
correção não é lembrar de repetir os campos em cada página — é remover a
possibilidade de esquecer: um helper único de metadados por onde toda rota
passa, que monta `openGraph` inteiro toda vez e valida os limites de tamanho
no build. Título acima de 60 caracteres ou description acima de 155 derrubam
o build, não a SERP.

Vale conferir também o `metadataBase` (é ele que transforma caminho relativo
em URL absoluta, obrigatório para Open Graph) e o comportamento do
`opengraph-image.tsx`, que no Next.js 16.2.6 **não cascateia** para rotas
aninhadas.

Para auditar uma rota já publicada pela régua desta seção, este site tem um
[validador de meta tags](/ferramentas/validador-meta-tags): ele lê o HTML que
o servidor responde e classifica title, description, canonical, robots, H1 e
Open Graph — as mesmas checagens que o CI daqui impõe a cada deploy.

→ [Metadata API do Next.js: canonical e o merge que não existe](/blog/metadata-api-nextjs)

## Sitemap e robots derivados do conteúdo

`app/sitemap.ts` exporta uma função que devolve um array de URLs — e a versão
que vale a pena escrever é a que **deriva esse array do conteúdo**, não a que
lista rotas à mão. Uma lista manual desatualiza no primeiro artigo publicado.

Dos quatro campos que o Next.js aceita por entrada, só dois interessam ao
Google: `url` e `lastModified`. A documentação oficial afirma que `priority` e
`changeFrequency` são ignorados. E `lastmod` só é usado quando for consistente
e verificável — um `new Date()` a cada build produz uma data que nunca
corresponde a uma mudança real, o que ensina o Google a ignorar o campo. A
regra que sobra: emita `lastmod` só quando ele for derivável do conteúdo.

`app/robots.ts` é o par disso, e o padrão certo dele é **não indexar**: um
ambiente de preview que herda o robots de produção é um acidente comum. Uma
última armadilha, que este site cometeu e mediu: `noindex` e `Disallow` **não
se somam**. Uma URL bloqueada no robots.txt nunca é rastreada, então o
`noindex` dela nunca é lido — os dois instrumentos se cancelam.

→ [Sitemap dinâmico no Next.js com sitemap.ts e robots.ts](/blog/sitemap-dinamico-nextjs)

## Redirects, canonicals e noindex: escolher o instrumento

Antes de decidir entre `redirects()` no `next.config` e middleware, existe uma
pergunta anterior que quase ninguém faz: esse problema pede mesmo um redirect?

São três instrumentos para três problemas diferentes. Redirect permanente
(301/308) quando a URL antiga deve deixar de existir. Canonical quando as duas
URLs existem mas uma consolida os sinais — e ele é uma dica forte, não uma
ordem. `noindex` quando a página existe para o usuário e não para o índice.
Quando são conteúdos distintos, não há problema a resolver. Errar essa escolha
não gera erro nenhum no build: gera sintoma meses depois, no relatório de
indexação do Search Console.

Resolvida a escolha, a implementação é simples: o `redirects()` do config é
estático, avaliado antes do roteamento e sem custo por request; o middleware
roda em **cada** request e é o único capaz de decidir com base em cookie,
header ou geografia. Se a regra já é conhecida no build, ela não tem o que
fazer no middleware.

→ [Redirects e canonicals no Next.js: config ou middleware](/blog/redirects-canonicals-nextjs)

## JSON-LD no App Router

Dados estruturados no App Router não precisam de biblioteca: um
`<script type="application/ld+json">` renderizado num Server Component sai
pronto no HTML inicial, que é exatamente onde o Googlebot quer encontrá-lo.

A decisão de arquitetura é **onde** cada schema vive, e a regra prática é
renderizá-lo no nível em que os dados que o alimentam realmente existem.
Schema que muda por rota — `Article`, `BreadcrumbList` — vai no `page.tsx`.
Schema estável para o site inteiro — `WebSite`, `Organization` — pode ficar no
layout. Vários blocos na mesma página são lidos sem problema; o que não pode é
o mesmo tipo se contradizer entre blocos.

O ganho real vem de derivar o schema do frontmatter em vez de escrevê-lo à
mão: o `Article` de cada artigo deste site nasce dos mesmos campos que geram o
`<title>` e o sitemap, então não existe estado em que os dois discordem. Sobre
`FAQPage`: o Google parou de exibir o rich result em 7 de maio de 2026 e
removeu a documentação em 15 de junho de 2026, mas o tipo continua válido no
schema.org — mantê-lo custa quase nada quando ele nasce da mesma fonte do FAQ
visível.

Para montar um schema avulso rapidamente, este site tem um
[gerador de JSON-LD](/ferramentas/gerador-json-ld) que devolve tanto o objeto
quanto o componente Next.js pronto.

→ [Como implementar JSON-LD no Next.js (App Router)](/blog/json-ld-nextjs)

## Hreflang e site bilíngue

Esta página tem uma [versão em inglês](/en/guide/technical-seo-nextjs), e as
duas se declaram uma à outra. É o próprio exemplo do capítulo.

Três regras carregam quase todo o hreflang. **Reciprocidade**: se A declara B
como alternativa, B tem que declarar A de volta, ou o Google descarta o
cluster — falha silenciosa, sem erro em lugar nenhum. **Auto-referência**: cada
página se lista entre as alternativas, o que é justamente o que torna o mesmo
bloco de tags válido dos dois lados. **`x-default`**: a versão servida a quem
não casa com nenhum idioma declarado; num site português-primeiro, ela aponta
para o original em português, não para a tradução.

No App Router as tags saem de `alternates.languages`, na Metadata API, e o
detalhe de implementação que importa é **onde** esse objeto é montado.
Declarar o par à mão em cada página é o que quebra a reciprocidade no primeiro
refactor — alguém renomeia uma rota e só um dos lados fica sabendo. Neste site
os pares vivem num módulo único, os dois lados de um par são gerados do mesmo
objeto, e um teste confere a reciprocidade no HTML servido, não no código
fonte. É a diferença entre hreflang que funciona e hreflang que só existe.

Uma pegadinha encontrada ao escrever esse teste, e que vale para qualquer um
que audite hreflang por script: o Next.js serializa o atributo como
`hrefLang`, em camelCase, no HTML que ele serve. É válido — nomes de atributo
em HTML são case-insensitive, o browser lê como `hreflang` e o Google também.
Mas quem lê a resposta HTTP crua com um regex sensível a maiúsculas não
encontra nada e conclui que o site não tem hreflang. Foi exatamente o que
aconteceu aqui: a checagem via DOM passava e a mesma checagem via HTTP
retornava vazio.

Duas decisões que valem ser ditas, porque não são óbvias. A URL da página em
inglês carrega a query em inglês — é `/en/guide/technical-seo-nextjs`, não um
espelho do caminho em português —, já que a URL faz parte do que a página diz
ser. E o `<html lang>` continua `pt-BR` nas duas: o header e o rodapé em volta
do artigo estão realmente em português, então virar o documento inteiro para
`en` rotularia errado essa moldura. Quem carrega `lang="en"` é a subárvore que
está de fato em inglês. Para o Google dá no mesmo — ele ignora o atributo e
detecta idioma pelo conteúdo —, mas não dá no mesmo para tecnologia assistiva.

## Renderização: o que o Googlebot realmente recebe

Para o indexador, a sigla não importa — importa o que vem no HTML da
**primeira resposta**.

Por esse critério, SSG e SSR são equivalentes: as duas entregam o conteúdo
completo já nesse HTML. ISR também entrega HTML completo, possivelmente
defasado entre revalidações. CSR entrega um esqueleto e depende de uma segunda
passada de renderização do Googlebot — que é enfileirada — e é a única das
quatro que cria risco real de indexação.

Isso desloca a pergunta de "qual é mais rápida" para "o que o indexador
recebe", e leva a uma conclusão desconfortável para quem usa `useEffect` com
liberdade: o componente que só existe depois da hidratação é o erro de SEO
mais comum em Next.js. Não porque o Google não execute JavaScript — ele
executa — mas porque essa execução é uma fila, e você não controla a posição
nela.

O corolário prático é que você deveria conseguir **provar** qual estratégia
cada rota sua usa, em vez de supor. A tabela de rotas do `next build` mostra
isso com um símbolo por rota.

## LCP: diagnosticar antes de otimizar

O erro que faz times perderem semanas em LCP é otimizar antes de saber onde o
tempo está. O LCP se divide em quatro subpartes — **TTFB**, **resource load
delay**, **resource load duration** e **element render delay** — e cada uma
tem correções diferentes. Otimizar a subparte errada não muda nada.

Descoberto o gargalo, os movimentos que resolvem a maioria dos casos são
poucos: garantir que o elemento LCP está no HTML inicial (Server Component),
usar `preload` no `next/image` apenas na imagem LCP — o Next.js 16 depreciou o
`priority` em favor dele — e carregar fontes com `next/font`.

Há também o caso oposto, mais frustrante: o LCP que **não melhora** depois de
você já ter trocado tudo por `next/image`. Aí o culpado costuma ser um padrão
que esconde o recurso do preload scanner (um `background-image` em CSS, um
hero atrás de `"use client"`), um render delay que você mesmo criou com uma
animação de fade-in ou um snippet anti-flicker de teste A/B, ou preload demais
competindo por banda com o próprio elemento que deveria acelerar.

→ [Como melhorar o LCP no Next.js pelas 4 subpartes](/blog/melhorar-lcp-nextjs)
→ [LCP alto no Next.js: os erros que impedem de melhorar](/blog/lcp-alto-next-js)

## INP: a métrica que o Lighthouse não mede

O INP (Interaction to Next Paint) mede o tempo entre uma interação e o próximo
frame pintado; bom é ≤200 ms no p75 de campo. Ele substituiu o FID em março de
2024, e a diferença é de escopo — o FID media só o atraso inicial da primeira
interação, o INP olha todas elas e mede o ciclo completo.

E aqui está a particularidade que muda a forma de trabalhar: **não existe INP
no Lighthouse**. Não é omissão de interface, é impossibilidade conceitual —
INP exige interação real de usuário real, e o lab não tem ninguém clicando. O
que a auditoria de lab oferece é o TBT (Total Blocking Time), um proxy que
correlaciona mas não substitui.

Para um site pequeno isso vira cegueira dupla: sem interação em lab não há INP
no Lighthouse, e abaixo do limiar de tráfego do CrUX também não há INP no
PageSpeed Insights nem no Search Console. A saída é medir o próprio campo com
RUM — a biblioteca `web-vitals` com `onINP` enviando evento ao GA4. É o que
este site faz, com atribuição por subparte.

→ [INP no Next.js: como diagnosticar e corrigir](/blog/inp-nextjs)

## Imagens: performance resolvida, indexação não

O `next/image` entrega formato moderno, `srcset` por viewport, lazy loading e
dimensões reservadas contra CLS. No baseline deste site isso aparece como
**CLS 0.000 nas 10 páginas** medidas — com dimensões explícitas, deslocamento
por imagem simplesmente não existe.

O que ele **não** entrega é indexação. `alt`, contexto textual em volta, nome
de arquivo e presença no sitemap continuam por sua conta, e o componente é
completamente cego para imagem declarada em CSS. A SERP inteira trata "SEO de
imagem" como sinônimo de "performance de imagem"; a outra metade é a que
decide se a imagem existe para o índice.

Dois pontos que costumam passar batido: o atributo `sizes` é quem decide qual
arquivo do `srcset` o usuário realmente baixa — errá-lo anula boa parte do
ganho —, e diagramas explicativos rendem mais como **SVG inline** do que como
raster, porque os rótulos em `<text>` são rastreáveis e citáveis. A ressalva é
que SVG inline não entra no Google Imagens; se esse canal importa, exporte uma
cópia raster e declare no sitemap de imagens.

→ [next/image e SEO: o que o componente não resolve](/blog/next-image-seo)

## Medição: GTM e GA4 numa SPA

Otimização sem medição é palpite, e medir SPA tem uma armadilha específica: o
gatilho **All Pages** do GTM só dispara no primeiro carregamento. As
navegações seguintes são `history.pushState` e não recarregam a página, então
o GA4 registra a entrada e fica cego para o resto da sessão.

A correção é o gatilho **History Change** — e a decisão que quase todo mundo
erra é ativá-lo no GTM **e** deixar o Enhanced Measurement do GA4 escutando os
mesmos eventos, contando cada pageview duas vezes. O problema nunca foi fazer
o evento disparar; é fazê-lo disparar uma vez só.

Some a isso o Consent Mode v2 com default negado, exigência prática para LGPD,
e o resultado é uma implementação que precisa ser validada nos requests reais
— não só no preview do GTM.

→ [GTM no Next.js: pageview de SPA sem contar duas vezes](/blog/gtm-nextjs)

## O que este site mediu

Este guia não é teórico: cada técnica acima está implementada neste domínio, e
os números abaixo saíram dele.

O caso mais completo é o da home. O elemento LCP dela é um parágrafo de texto,
e o diagnóstico pelas quatro subpartes apontou **element render delay** — não
o peso de imagem que todo mundo assume. Duas mudanças resolveram: inline do
CSS (~22 KB crus, ~5 KB comprimidos — era a única requisição render-blocking
do site) e a fonte Inter passando de `display: swap` para `display: optional`
sem preload, saindo do caminho crítico.

Resultado no PageSpeed Insights mobile, em produção, medido em 18/07/2026:

| Métrica | Antes | Depois |
|---|---|---|
| Performance | 78 | **100** |
| LCP | 4,9 s | **0,9 s** |
| Element render delay | 1.280 ms | **530 ms** |
| CLS | 0 | 0 |

Dois dias depois, o baseline completo das 10 URLs ficou em LCP 1,0–1,2 s, CLS
0,000, TBT 80–148 ms, zero páginas órfãs e profundidade máxima de 2 cliques.

Vale registrar o que ainda **não** está medido: o domínio está abaixo do
limiar de tráfego do CrUX, então não há dado de campo público. Os números
acima são de laboratório e de RUM próprio. O veredito de campo fica em aberto
— e aparecerá aqui quando existir, não antes.

## Como este guia é mantido

Os dez capítulos já têm implementação neste domínio; o de hreflang foi o
último a chegar, e chegou sendo construído, não descrito. Cada capítulo vira um
artigo com código real e medição própria — o de hreflang sai a partir da
implementação acima —, e este guia é o mapa que os conecta.

O que impede o conteúdo de envelhecer errado é o mesmo CI que protege o
código: uma suíte Playwright verifica, em toda rota, `<h1>` único, limites de
título e description, canonical auto-referente, JSON-LD que faz parse — e,
desde que a versão em inglês existe, hreflang recíproco nos dois sentidos. Os
orçamentos de Lighthouse bloqueiam o merge se LCP, CLS ou TBT regredirem.
Quando uma técnica descrita aqui deixa de valer, o teste quebra antes do
leitor perceber.
