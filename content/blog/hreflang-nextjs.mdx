No App Router, hreflang sai do campo `alternates.languages` da Metadata API, e
o framework converte esse objeto nas tags `<link rel="alternate" hreflang>` do
`<head>`. A sintaxe é a parte fácil. O que decide se aquilo funciona é a
**reciprocidade**: se a página A declara a B como alternativa e a B não
declara a A de volta, o Google descarta o cluster inteiro — sem erro de build,
sem aviso no HTML, sem sintoma visível. Este artigo mostra a implementação que
sobrevive a isso, com o código deste site: a versão em inglês do guia, o par
declarado numa fonte única, o teste que confere a volta no HTML servido, e uma
armadilha do Next.js que fez a auditoria daqui reportar hreflang ausente numa
página que estava perfeitamente correta.

## As três regras que decidem se o hreflang funciona

| Regra | O que ela exige | O que acontece se você errar |
| --- | --- | --- |
| Reciprocidade | Se A declara B, B declara A | O Google desconsidera a anotação — silenciosamente |
| Auto-referência | Cada página se lista entre as alternativas | O bloco deixa de ser idêntico nos dois lados e vira fonte de divergência |
| `x-default` | Uma versão para quem não casa com nenhum idioma | O Google escolhe sozinho qual servir |

A auto-referência é a que mais causa estranheza, então vale explicar: como
cada página lista **todas** as versões, inclusive ela mesma, o bloco de tags
fica **exatamente igual** nos dois lados do par. Isso não é redundância — é o
que torna a reciprocidade verificável. Dois blocos que deveriam ser idênticos
são fáceis de comparar; dois blocos que deveriam ser complementares, não.

| Cenário | O que existe no HTML | O que o Google faz |
| --- | --- | --- |
| Recíproco | As duas páginas listam as duas versões | Trata como cluster e serve a versão certa por idioma |

## Onde declarar: `alternates.languages`

O campo é este, e ele fica no mesmo objeto `alternates` que carrega o canonical:

```ts
// exemplo ilustrativo — a implementação real deste site vem na próxima seção
export const metadata: Metadata = {
  alternates: {
    canonical: "/guia/seo-tecnico-nextjs",
    languages: {
      "pt-BR": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
      en: "https://seotecnico.dev.br/en/guide/technical-seo-nextjs",
      "x-default": "https://seotecnico.dev.br/guia/seo-tecnico-nextjs",
    },
  },
};
```

Duas observações que a documentação não destaca. As URLs precisam ser
**absolutas** — hreflang relativo não conta, e é por isso que o exemplo acima
repete o domínio. E `alternates`, como `openGraph`, é **substituído e não
mesclado** entre layout e página: um bloco de idiomas definido só no layout
desaparece na primeira rota que declarar o próprio `alternates`. Esse é o
mesmo [merge raso da Metadata API](/blog/metadata-api-nextjs) que já quebrou o
Open Graph deste site.

Mas o problema de verdade do trecho acima não é nenhum dos dois. É que ele
está escrito **na página**.

## O par precisa nascer de uma fonte única

Declarar o par à mão em cada página funciona no dia em que você escreve, e
quebra no primeiro refactor: alguém renomeia uma rota, atualiza o hreflang do
lado que estava editando, e o outro lado continua apontando para uma URL que
não existe mais. Não há erro. Há um cluster que deixou de existir.

A correção é estrutural: os pares vivem num módulo, e os dois lados são
gerados do **mesmo objeto**. Este é o mapa de produção deste site, em
`src/lib/hreflang.ts`:

```ts
export const TRANSLATION_PAIRS: readonly TranslationPair[] = [
  {
    id: 'seo-tecnico-nextjs',
    paths: {
      'pt-BR': '/guia/seo-tecnico-nextjs',
      en: '/en/guide/technical-seo-nextjs',
    },
  },
] as const
```

E o helper único de metadados **deriva** o bloco de idiomas do caminho da
rota, em vez de recebê-lo como argumento — o trecho abaixo é o
`buildMetadata()` deste site:

```ts
const languagePaths = languageAlternatePaths(path)

return {
  alternates: {
    canonical: path,
    ...(languagePaths
      ? {
          languages: Object.fromEntries(
            Object.entries(languagePaths).map(([lang, target]) => [
              lang,
              absoluteUrl(target),
            ])
          ),
        }
      : {}),
    // …
  },
}
```

O ganho é que a página perde a capacidade de errar. Ela não declara o par:
ela informa o próprio caminho, e o par vem de quem sabe. Uma rota sem tradução
não emite nada, porque um cluster de um item só é ruído. E como os dois lados
consultam a mesma estrutura, o bloco sai idêntico nos dois — que é exatamente
o que a regra da auto-referência pedia.

## O atributo em camelCase que engana auditoria

Esta parte é original, e custou uma sessão de depuração aqui.

Ao ativar a verificação de reciprocidade no CI, ela acusou que a versão em
inglês **não tinha nenhuma tag hreflang** — numa página cujo `view-source`
mostrava as três tags, corretas. A causa: o Next.js serializa o atributo como
`hrefLang`, em camelCase, no HTML que entrega:

```html
<link rel="alternate" hrefLang="pt-BR" href="https://seotecnico.dev.br/guia/seo-tecnico-nextjs"/>
```

Isso é **válido**. Nomes de atributo em HTML são case-insensitive: o parser do
browser normaliza para `hreflang`, o DOM devolve minúsculo, e o Google lê sem
problema. Quem não lê é qualquer script que procure a string `hreflang=` numa
resposta HTTP crua com busca sensível a maiúsculas.

O detalhe que torna isso traiçoeiro é que a mesma checagem passa ou falha
dependendo de **onde** você lê a página. Lendo o DOM de uma página aberta no
browser, o atributo aparece minúsculo e tudo passa. Lendo a mesma página por
HTTP, ele aparece em camelCase e o resultado é zero. A auditoria daqui fazia
as duas coisas — DOM para a página atual, HTTP para a alternativa — e por isso
reportava justamente a falta do link de volta.

A correção é uma linha, e vale para qualquer auditoria de hreflang feita por
script:

```ts
// tests/seo/seo.spec.ts — as flags `i` são o conserto
return (html.match(/<link\b[^>]*>/gi) ?? [])
  .filter((tag) => /rel="alternate"/i.test(tag) && /\bhreflang=/i.test(tag))
```

Se você já rodou um crawler próprio num site Next.js e concluiu que ele não
tinha hreflang, vale reconferir com busca insensível a maiúsculas antes de
abrir um chamado. O [validador de meta tags](/ferramentas/validador-meta-tags)
deste site lê o HTML do servidor pelo mesmo motivo que este artigo defende —
ele normaliza os nomes de atributo, e ainda não checa hreflang; quando checar,
será por essa régua.

## `<html lang>`: o que o App Router não deixa você fazer

A pergunta que aparece logo depois de criar a rota em inglês: como mudar o
`lang` do `<html>` só nela?

No App Router, você **não muda** — não a partir de um layout aninhado. A tag
`<html>` pertence ao root layout, e um layout filho não a reescreve. As saídas
são duas, e nenhuma é gratuita:

1. **Dois root layouts, por route group** (`app/(pt)/layout.tsx` e
   `app/(en)/layout.tsx`, cada um com seu `<html lang>`). É a resposta
   canônica do framework. O custo é que navegar entre os dois grupos provoca
   um **carregamento completo de página**, não uma navegação client-side — e
   todas as rotas existentes precisam se mudar para dentro de um dos grupos.
2. **Marcar a subárvore**: `<article lang="en">` na página em inglês, com o
   `<html lang="pt-BR">` intacto.

Este site escolheu a segunda, e não por preguiça. O header, o rodapé e o
banner de consentimento em volta do artigo **estão em português de verdade**.
Virar o documento inteiro para `en` rotularia errado essa moldura; marcar como
inglês só o que é inglês é a descrição honesta de uma página cujo conteúdo e
cuja interface falam idiomas diferentes.

O impacto em SEO disso é nulo, e vale dizer com todas as letras: o Google
**ignora** o atributo `lang` para detectar idioma — ele lê o conteúdo. Quem
não ignora é a tecnologia assistiva, e é por ela que a marcação precisa estar
certa. Quando `/en` tiver moldura própria, a opção 1 passa a valer o preço.

## A URL da versão traduzida

Duas formas defensáveis: espelhar o caminho (`/en/guia/seo-tecnico-nextjs`) ou
traduzir o slug (`/en/guide/technical-seo-nextjs`). Este site escolheu a
segunda, porque a URL faz parte do que a página diz ser — uma página em inglês
com slug em português entrega uma pista errada logo no endereço.

O custo é real e vale registrar: com slugs diferentes, o caminho de um lado
não é derivável do outro por regex, e é justamente por isso que existe o mapa
da seção anterior. Espelhar o caminho dispensaria o mapa; foi a troca
aceita conscientemente.

## O link visível que contradiz o hreflang

Uma falha comum e chata de perceber: o hreflang correto no `<head>`, e o
seletor de idioma do menu apontando para a **home** do outro idioma. O leitor
que clica em "English" numa página de artigo cai numa home genérica e vai
embora — e os dois sinais que o site emite sobre a mesma relação discordam.

A prevenção é a mesma da seção do mapa: o seletor lê a **mesma fonte** que
gera as tags. Aqui ele resolve o caminho da contraparte pelo par, então o link
visível e a declaração de máquina não conseguem divergir. O rótulo, por sinal,
vai escrito no idioma de destino ("English" na página em português): quem
procura a outra versão lê o idioma que procura, não o que já está vendo.

## Como travar isso no CI

Nada acima resiste a seis meses de manutenção sem um teste. E o teste certo
não lê o código-fonte — lê o **HTML servido**, busca a alternativa declarada e
confere se ela declara a volta:

```ts
// tests/seo/seo.spec.ts — roda em toda rota do sitemap
const alternateResponse = await page.request.get(alternatePath)
expect(alternateResponse.status()).toBe(200)

const reciprocal = extractHreflangLinks(await alternateResponse.text())
expect(
  reciprocal.map((l) => new URL(l.href).pathname),
  `${alternatePath} must link back to ${route} via hreflang`
).toContain(route)
```

Repare no que ele cobre e que uma inspeção de código não cobriria: a
alternativa **responde 200** (hreflang para URL quebrada é erro comum em
migração) e a volta **existe no HTML entregue**, não na intenção do
desenvolvedor.

Um detalhe de processo que vale mais que o código: esse teste foi escrito
**antes** de existir qualquer página em inglês, com uma guarda que o deixava
inerte enquanto nenhuma rota emitisse hreflang. Ele ficou dormente por
semanas e passou a rodar sozinho no dia em que a rota `/en` entrou no sitemap
— e a primeira coisa que fez foi encontrar o problema do camelCase. Escrever a
asserção junto com a regra, mesmo sem ter o que asserir ainda, é barato; e
quem paga é a versão futura do site, não a atual.

## Como saber se funcionou

Markup correto não é resultado. O sinal que decide fica no Search Console, na
**Inspeção de URL** de cada versão: compare o canônico declarado pelo usuário
com o **canônico escolhido pelo Google**. Se o Google escolher a URL de um
idioma como canônica do outro, ele juntou as duas páginas numa só — o cluster
foi rejeitado, e nenhuma quantidade de tag correta no código muda isso.
Enquanto os dois idiomas mantiverem canônicos próprios e cada um aparecer nas
buscas do respectivo idioma, está funcionando.

O relatório de páginas do Search Console tem uma seção de idiomas alternativos
que ajuda, mas a inspeção URL a URL é o que responde a pergunta de verdade.

E a transparência que este site deve: a versão em inglês do guia entrou no ar
em 26/07/2026, junto com esta implementação. **O veredito ainda não existe** —
uma janela de 28 dias precisa fechar antes que qualquer número aqui signifique
alguma coisa, e a hipótese registrada é a de que a versão em inglês ganhe
impressões próprias **sem** derrubar as da versão em português. Se derrubar, o
par está sendo lido como duplicação e a implementação falhou. O resultado
aparece aqui quando existir, não antes.
