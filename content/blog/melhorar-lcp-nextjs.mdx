Para melhorar o LCP no Next.js, descubra primeiro em qual das quatro
subpartes o tempo está sendo gasto: **TTFB**, **resource load delay**,
**resource load duration** ou **element render delay**. Cada uma tem fixes
diferentes, e otimizar a subparte errada não muda nada. Depois, quatro
passos: garantir que o
elemento LCP está no HTML inicial (Server Component), usar
`fetchPriority="high"` no `next/image` apenas na imagem LCP (o Next.js 16
depreciou `priority`), carregar fontes com `next/font` e confirmar o
resultado nas subpartes do PageSpeed Insights.

```tsx
// app/page.tsx — o essencial num único exemplo
import Image from 'next/image'

export default function Page() {
  return (
    <section className="relative aspect-[16/9]">
      {/* Server Component: a <img> existe no HTML inicial,
          visível ao preload scanner do navegador */}
      <Image
        src="/hero.webp"
        alt="Descrição real da imagem"
        fill
        sizes="100vw"
        fetchPriority="high" // prioridade alta só na imagem LCP
      />
    </section>
  )
}
```

A partir do Next.js 16, a
[documentação do `next/image`](https://nextjs.org/docs/app/api-reference/components/image#qualities)
trata o config `images.qualities` como obrigatório. Sem ele, só a
qualidade 75 é aceita. O exemplo completo está na seção de
[resource load duration](#resource-load-duration-agora-sim-o-arquivo).

O resto deste guia explica **por que** cada um desses passos funciona,
mecanismo por mecanismo, e, principalmente, como descobrir de qual deles o
seu caso precisa.

## O que o LCP mede (e o que não mede)

LCP (Largest Contentful Paint) é o tempo até o maior elemento de conteúdo
visível no viewport terminar de renderizar. O threshold oficial é
**2,5 segundos ou menos no percentil 75 de dados de campo**. Ele não mudou em
2026, apesar de haver artigos que afirmam o contrário (detalhe no
[FAQ](#faq-titulo)). A referência é a
[documentação do web.dev](https://web.dev/articles/lcp), e as
[notas de versão do CrUX](https://developer.chrome.com/docs/crux/release-notes)
de 2026 não falam em mudança de threshold.

Dois detalhes que mudam decisões:

**Lab não é campo.** O número do Lighthouse rodando na sua máquina é um
teste sintético. O
[relatório de Core Web Vitals do Search Console](https://support.google.com/webmasters/answer/9205520?hl=pt-BR)
mostra outra coisa: o p75 dos usuários reais, com dados do CrUX dos
últimos 28 dias. Um fix pode melhorar o lab hoje e só aparecer
no campo semanas depois. Para ver em que pé está o campo do seu domínio
agora, o [checador de Core Web Vitals](/ferramentas/checador-cwv) consulta
esse mesmo p75 do CrUX, inclusive a distribuição das visitas em cada faixa,
que o número sozinho esconde.

Essa diferença tem uma consequência prática que quase ninguém explicita: **o
seu budget de laboratório precisa ser mais rígido que o threshold de campo.**
O lab roda em um aparelho emulado, numa rede emulada, geralmente com cache
frio e sempre no mesmo cenário. O p75 de campo inclui a cauda lenta (o
aparelho velho, o 4G ruim, a aba restaurada). Uma página que marca 2,4 s no lab
não está "quase passando": ela não tem margem nenhuma, e no campo tem tudo
para estourar os 2,5 s. Por isso o CI deste site reprova o build acima de
**2,0 s no lab**, e não em 2,5 s. Não é discordância do threshold do Google. É
a folga que separa um número sintético de um número real.

**O elemento LCP não é necessariamente uma imagem.** Pode ser um headline,
um bloco de texto ou um card renderizado a partir de dados. Isso importa
porque muito conteúdo sobre LCP assume imagem — e se o seu elemento
LCP é texto, otimizar imagem é esforço sem retorno.

Este artigo cobre só o LCP e faz parte do
[guia de SEO técnico para Next.js](/guia/seo-tecnico-nextjs) deste site,
que contextualiza as três métricas de Core Web Vitals.

## Antes de otimizar: descubra qual é o seu elemento LCP

O primeiro passo é identificar o elemento. No Chrome
DevTools, abra a aba **Performance**, grave um carregamento e clique no
marcador **LCP**: ele destaca o elemento exato na página. O PageSpeed
Insights também mostra o elemento no insight "Detalhamento da LCP".

Duas pegadinhas que eu sempre confiro:

- **Mobile e desktop podem ter elementos LCP diferentes.** Um layout que
  esconde o hero no mobile pode fazer o headline virar o LCP lá. O p75 é
  medido separado em mobile e desktop ([web.dev](https://web.dev/articles/lcp)),
  e o Search Console mostra os dois em relatórios separados.
- **O elemento pode mudar durante o carregamento.** Se algo re-renderiza
  maior depois (hidratação, slider), o LCP é remarcado para esse momento.
  Esse tipo de armadilha tem artigo próprio no cluster, sobre os
  [erros que impedem o LCP de melhorar](/blog/lcp-alto-next-js).

Com o elemento identificado, falta saber onde o tempo está indo.

| Subparte | O que é | Fix principal | Onde ver |
|---|---|---|---|
| **TTFB** | Tempo até o primeiro byte do HTML | Cache, streaming, CDN | PSI, `web-vitals` |
| **Resource load delay** | Do TTFB até o navegador *começar* a baixar o recurso LCP | Recurso no HTML inicial + `fetchPriority` | Waterfall |
| **Resource load duration** | O download em si | Formato, `sizes`, compressão | Waterfall |
| **Element render delay** | Do fim do download até a pintura | CSS render-blocking, fontes | Trace |

**Nos dados de campo do Chrome, o download quase nunca é o gargalo**, e
isso muda a estratégia. Num
[estudo do web.dev](https://web.dev/blog/common-misconceptions-lcp) sobre
as origens do CrUX com LCP ruim, a origem mediana esperou cerca de quatro
vezes mais para *começar* a baixar a imagem do que levou baixando, e o
TTFB e o load delay eram as subpartes mais longas. O arquivo da imagem — a
única coisa que muitos guias otimizam — é uma das quatro fases, e
frequentemente a mais curta. É por isso que comprimir a imagem pela
terceira vez não move o número.

As quatro seções a seguir atacam uma subparte cada.

## TTFB: o piso do seu LCP

Nada renderiza antes do primeiro byte do HTML chegar. O TTFB é um piso
que se soma a todo o resto. Se o seu TTFB é 1,8 s, sobram 0,7 s para
descobrir, baixar e pintar o elemento antes dos 2,5 s, e nenhum ajuste de
imagem recupera o que o servidor gastou. No estudo do web.dev citado acima,
o TTFB sozinho já deixava os 2,5 s quase fora de alcance para muitas das
origens com LCP ruim.

No Next.js, três alavancas:

**Renderização estática sempre que possível.** Página estática servida de
CDN elimina o tempo de servidor da equação. No App Router, isso significa
não usar APIs dinâmicas (`cookies()`, `headers()`) em páginas que não
precisam delas.

**Streaming quando há data fetching lento.** Se a página depende de dados,
não segure o HTML inteiro atrás do fetch. Envie o shell imediatamente e
faça o bloco lento chegar via `Suspense`:

```tsx
// app/produtos/page.tsx
import { Suspense } from 'react'
import { ListaProdutos } from './lista-produtos'

export default function Page() {
  return (
    <main>
      {/* Shell estático: chega no primeiro byte.
          O candidato a LCP deve estar AQUI, fora do Suspense. */}
      <h1>Produtos</h1>
      <Suspense fallback={<SkeletonLista />}>
        {/* Bloco que depende de fetch: chega via streaming */}
        <ListaProdutos />
      </Suspense>
    </main>
  )
}
```

Isso melhora o TTFB com certeza, porque o servidor responde antes de o fetch
terminar. O quanto melhora o *LCP* depende de onde está o
elemento LCP: se ele estiver dentro do `Suspense`, o streaming não resolve
(esse caso tem seção própria [mais abaixo](#quando-o-elemento-lcp-não-é-imagem)).

**Infraestrutura.** Região do deploy perto do público (para site brasileiro,
edge/região em SA), cache de dados do Next e CDN na frente. No Next.js 16,
o modelo de cache mudou para Cache Components. Se você vinha do PPR
experimental, vale reler a doc antes de supor como o cache se comporta.

No PHP em hospedagem compartilhada, essa era a subparte dominante por
definição: o servidor renderizava tudo a cada request e o TTFB engolia o
budget inteiro. No Next.js com estático/streaming, o gargalo tipicamente
migra para as duas próximas subpartes. Isso é bom, porque elas estão sob
controle do código, não da infraestrutura.

## Resource load delay: o navegador precisa descobrir a imagem cedo

O load delay mede quanto tempo o navegador levou para *começar* a baixar o
recurso LCP depois do TTFB. Delay alto quase sempre significa **descoberta
tardia**: o navegador não sabia que o recurso existia.

O navegador tem um preload scanner, um parser
secundário que varre o HTML bruto e antecipa downloads antes mesmo do parse
principal terminar. Ele lê **markup, não CSS nem JavaScript**
([web.dev](https://web.dev/learn/performance/optimize-resource-loading)).
Uma `<img>` no HTML da resposta é descoberta imediatamente. Uma imagem que
só existe dentro de um CSS ou depois de um script executar, não. Os padrões
invisíveis ao scanner (background-image, hero atrás de `"use client"`,
cadeias de `@import`) estão catalogados no artigo
[por que o LCP não melhora mesmo depois de otimizar](/blog/lcp-alto-next-js).

Garantida a descoberta, o segundo passo é **prioridade**. No Next.js 16:

```tsx
// components/hero.tsx
import Image from 'next/image'

// ❌ Next.js ≤15 — `priority` está depreciada no v16:
// <Image src="/hero.webp" alt="..." fill sizes="100vw" priority />

// ✅ Next.js 16:
export function Hero() {
  return (
    <div className="relative aspect-[16/9]">
      <Image src="/hero.webp" alt="..." fill sizes="100vw" fetchPriority="high" />
    </div>
  )
}
```

No Next.js 16, `priority` foi depreciada em favor de `preload`. Mas as duas
coisas não são a mesma. A prop `preload` só insere um `<link rel="preload">`
no `<head>`, e a
[documentação do `next/image`](https://nextjs.org/docs/app/api-reference/components/image#preload)
recomenda, na maioria dos casos, `fetchPriority="high"` ou `loading="eager"`
no lugar dela. Se a `<img>` já está no HTML inicial, o preload scanner já a
descobre. O que falta é prioridade. A mesma documentação desaconselha
`preload` junto com `fetchPriority` e quando mais de uma imagem pode ser o
LCP, conforme o viewport.

Use `fetchPriority="high"` em **uma imagem por página**, a que é de fato o
elemento LCP. Prioridade alta em várias imagens faz elas competirem por
banda entre si e com o CSS crítico, o que pode *piorar* o LCP.

Se o hero precisa mesmo ser background CSS (decisão de design legítima em
alguns layouts), avise o navegador manualmente:

```tsx
// app/layout.tsx (ou no componente da página)
import { preload } from 'react-dom'

export default function Layout({ children }: { children: React.ReactNode }) {
  preload('/hero.webp', { as: 'image', fetchPriority: 'high' })
  return <>{children}</>
}
```

Isso com certeza restaura a descoberta antecipada que o background-image
perde. O tamanho do ganho depende de quão tarde a imagem era
descoberta antes.

## Resource load duration: agora sim, o arquivo

O load duration é o download em si, a única subparte que a compressão de
imagem afeta. Três alavancas no Next.js:

**Formato: deixe o `next/image` negociar.** Por padrão, o componente serve
WebP ao navegador que aceita. AVIF só entra se você listar o formato em
[`images.formats`](https://nextjs.org/docs/app/api-reference/components/image#formats),
como o `next.config` deste site faz. Você não precisa converter
manualmente. Precisa apenas não desligar a otimização (`unoptimized`)
sem motivo.

**`sizes` correto.** Com `fill`, se você omitir `sizes`, o navegador assume
`100vw`. Num grid de 3 colunas, isso significa baixar uma imagem 3x maior
que o necessário. Para o hero full-width, `sizes="100vw"` está certo. Para
qualquer outro layout, descreva a realidade:

```tsx
// components/card-produto.tsx
<Image
  src={produto.imagem}
  alt={produto.nome}
  fill
  sizes="(max-width: 768px) 100vw, 33vw"
/>
```

**`qualities` no config (obrigatório no v16, pela documentação).** Sem ele,
só a qualidade 75 é aceita, e o Next avisa em desenvolvimento quando uma
imagem pede outra:

```ts
// next.config.ts
import type { NextConfig } from 'next'

const config: NextConfig = {
  images: {
    qualities: [50, 75], // 75 para heros, 50 para thumbnails
  },
}

export default config
```

Reduzir quality de 75 para 50 num thumbnail corta bytes sem diferença
visual perceptível naquele tamanho. Mas o ganho de LCP só existe se o
gargalo era duration. Confira no waterfall antes de gastar tempo aqui.

## Element render delay: a imagem chegou, falta pintar

O render delay é a subparte menos compreendida: o recurso já baixou, mas a
pintura não acontece. **O navegador não constrói a render tree
até o CSSOM estar completo.** CSS é render-blocking por padrão, a menos que
o atributo `media` do `<link>` diga o contrário
([web.dev](https://web.dev/learn/performance/understanding-the-critical-path)).
Uma imagem que baixou em 400 ms pode esperar 2 s parada na memória enquanto
um stylesheet lento segura a renderização da página inteira.

No Next.js, uma causa de render delay que o código controla são as
**fontes**:

```tsx
// app/layout.tsx
import { Inter } from 'next/font/google'

const inter = Inter({ subsets: ['latin'], display: 'swap' }) // 'swap' já é o padrão do next/font

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="pt-BR" className={inter.className}>
      <body>{children}</body>
    </html>
  )
}
```

O `next/font` baixa a fonte no build e serve do próprio domínio. Isso elimina o
request externo render-blocking do Google Fonts e a cadeia de descoberta
que ele cria. Isso melhora o render delay porque remove um recurso bloqueante
de outra origem do caminho crítico. O tamanho do ganho depende da latência até o
servidor de terceiros e do cache do usuário.

Quando o elemento LCP é **texto**, o `display` da fonte importa em dobro.
Texto com fonte web durante o período de block não conta como renderizado
para o LCP ([web.dev](https://web.dev/articles/lcp)). O `next/font` já usa
`display: 'swap'` por padrão, que deixa o texto aparecer na fonte de reserva
sem esperar.

Neste próprio site as três fontes carregam via `next/font`, mas com
`display: 'optional'` e sem preload. Medido aqui, `swap` dava o mesmo LCP e
somava CLS de 0,053 nos artigos, e o preload punha a fonte no caminho
crítico, com 140 a 290 ms a mais
([registro da medição](https://github.com/Alf4kill/seotecnico.dev.br/blob/main/docs/design-system.md#8-performance-cost-measured-accepted)).
O site ainda não aparece no CrUX, que exige um volume mínimo de tráfego
(consulta de 18/11/2026). Por isso há um RUM próprio: o `web-vitals` reporta
o LCP real de cada visita, com as 4 subpartes como parâmetros, direto para o
GA4 (o código está na [seção de verificação](#como-verificar-se-funcionou)).

Outras causas de render delay (fade-in no hero, anti-flicker de A/B
testing, cadeias de `@import`) são anti-patterns e estão catalogadas no
artigo do cluster sobre os [erros que seguram o LCP](/blog/lcp-alto-next-js).

## Quando o elemento LCP não é imagem

Se o seu elemento LCP é um headline, o caminho é a seção anterior: fonte
via `next/font`, `display: 'swap'`, e garantir que o texto está no HTML
inicial. Não existe "otimizar imagem" aqui, e é por isso que identificar
o elemento vem antes de tudo. (É o caso da home deste próprio site: o
elemento LCP é o parágrafo de abertura. A decomposição real está na
[seção de verificação](#como-verificar-se-funcionou).)

O caso mais difícil é o **LCP data-driven**: uma lista de produtos, o card
principal de um dashboard, o resultado de uma busca. O elemento LCP só
existe depois do fetch, então o LCP fica refém do banco de dados.

A decisão se resume a três caminhos: LCP imagem → descoberta e prioridade
(load delay) + arquivo (duration); LCP texto → fonte e CSS (render delay);
LCP data-driven → arquitetura de streaming, descrita a seguir.

As opções, da melhor para a de emergência:

1. **Tirar o candidato LCP do caminho dos dados.** Se a página tem um
   headline ou banner estático que pode ser o maior elemento acima da
   dobra, deixe-o fora do `Suspense`. Ele chega no primeiro flush e vira
   um LCP rápido, enquanto os dados fazem streaming abaixo.
2. **Cachear o dado que define o LCP.** Se o card principal muda pouco,
   cache de dados do Next (revalidação periódica) transforma o fetch lento
   em leitura de cache.
3. **Skeleton não resolve o LCP data-driven.** Um skeleton feito só de
   blocos de cor não é candidato a LCP, então o LCP espera o conteúdo real
   de qualquer jeito. Se o skeleton tem texto ou imagem e é *maior* que o
   conteúdo final, o problema é o oposto: o LCP só é remarcado por um
   elemento maior, e um elemento removido continua sendo o LCP
   ([web.dev](https://web.dev/articles/lcp)). O número passa a medir o
   skeleton e esconde a espera pelo dado.

Esse cenário quase não aparece em guias de LCP porque não tem fix de uma
linha — é decisão de arquitetura. Mas é o caso real de qualquer app
Next.js que renderiza dados acima da dobra.

## Como verificar se funcionou

Otimização sem verificação é palpite. O roteiro que eu uso, na ordem:

1. **PSI → subpartes.** Rode o PageSpeed Insights e olhe a decomposição do
   LCP: qual subparte domina? Ela aponta qual seção deste guia reler.
2. **DevTools Performance local.** Grave um trace com throttling de rede
   (Fast 4G) e CPU (4x): o marcador LCP mostra o elemento e o waterfall
   mostra quando o recurso foi descoberto e quando terminou.
3. **View-source, não o DOM.** Confirme que a `<img>` do LCP, com
   `fetchpriority="high"`, está no HTML da resposta do servidor. O DOM do DevTools mostra o estado *depois* de
   JS/CSS, que não é o que o preload scanner viu.
4. **RUM próprio.** O pacote `web-vitals` (build de attribution) reporta o
   LCP real dos usuários com a subparte dominante. É o que este site faz.
   O evento vai para o GA4 via GTM, sem backend nenhum (o consentimento é
   tratado pelo Consent Mode, como qualquer outra tag):

```ts
// lib/rum.ts — o código real deste site (simplificado)
import { onLCP } from 'web-vitals/attribution'

onLCP(({ value, rating, attribution }) => {
  window.dataLayer?.push({
    event: 'web_vitals',
    metric_name: 'LCP',
    metric_value: Math.round(value),
    metric_rating: rating,
    lcp_element: attribution.target, // v5: era `element` até a v4
    lcp_ttfb: Math.round(attribution.timeToFirstByte),
    lcp_load_delay: Math.round(attribution.resourceLoadDelay),
    lcp_load_duration: Math.round(attribution.resourceLoadDuration),
    lcp_render_delay: Math.round(attribution.elementRenderDelay),
  })
})
```

   No GTM, um trigger de Custom Event `web_vitals` alimenta uma tag GA4 com
   esses parâmetros, e as subpartes viram colunas numa exploração. Duas
   notas de implementação. Primeiro, na **v5** do `web-vitals` o seletor do elemento
   mudou de `attribution.element` para `attribution.target` (em JS puro, o
   campo antigo devolve `undefined` sem reclamar). Segundo, o callback só dispara
   quando a métrica *finaliza* (quando a página fica oculta ou na primeira
   interação), então não espere o evento no load. Se você tem backend com
   armazenamento, `navigator.sendBeacon` para um endpoint próprio também
   funciona. Num deploy serverless sem banco, o GA4 é o sink que sobra.

5. **Campo, com paciência.** CrUX/GSC usam janela móvel de 28 dias no p75.
   Não julgue um fix pelo dia seguinte. E se o site é novo, o CrUX pode
   não reportar ainda (exige volume mínimo de tráfego). O RUM
   próprio do passo 4 cobre esse vazio.

Entre as [ferramentas gratuitas de SEO técnico](/ferramentas) deste site
está um [checador de Core Web Vitals](/ferramentas/checador-cwv) via CrUX,
feito para o passo 5 desse roteiro.
