Não existe como provar que a IA **não** usa seu conteúdo. O que existe são três
coisas mensuráveis com os logs do próprio servidor: **quais agentes buscam
suas páginas**, **se a identidade que eles alegam é verdadeira** e **se
respeitam o robots.txt**. Este site mede as três em produção desde julho de
2026, com um honeypot no robots.txt, verificação de identidade por faixa de
IP, DNS reverso e assinatura criptográfica, e uma telemetria que separa
navegador de cliente automatizado. Este artigo mostra o método, o código, os
primeiros 28 dias de números — e três defeitos que a primeira leitura
encontrou no próprio instrumento.

## O que dá para medir e o que não dá

A pergunta "a IA usa meu conteúdo?" são quatro perguntas diferentes, e só
parte delas tem resposta num servidor web:

| Pergunta | Tem resposta? | Com o quê |
|---|---|---|
| Esta requisição veio de um cliente automatizado? | **Sim**, com boa confiança | Formato dos cabeçalhos e a comparação com as visitas que executam JavaScript |
| Qual agente fez a requisição? | **Em parte** | Faixas de IP publicadas, DNS reverso e assinatura Web Bot Auth — e só para fornecedores que publicam alguma dessas três |
| Foi para treinar um modelo? | **Não** | Só o fornecedor sabe. O máximo é citar a documentação dele sobre o propósito do agente |
| O robots.txt autorizava? | **Sim**, exatamente | O que o arquivo dizia para aquele agente no momento da requisição |

A assimetria organiza todo o resto. **Autorização é um fato** que o site
controla. **Propósito é uma citação**, nunca uma inferência. E **ausência não
se prova**: um crawler que não se identifica, uma cópia do seu artigo em outro
domínio ou uma base de dados já publicada ficam fora do alcance de qualquer
servidor. Qualquer texto que prometa "descobrir se a IA treinou com o seu
site" está vendendo a quarta resposta, que não existe.

## User agent é alegação, não identidade

O cabeçalho `User-Agent` é texto que o cliente escolhe. Um `curl` com
`-A "GPTBot"` envia exatamente o mesmo cabeçalho que o GPTBot de verdade. Por isso a
telemetria deste site trata o user agent como **alegação** e só fala em
identidade quando a requisição passa numa fonte publicada pelo próprio
fornecedor. São três, da mais forte para a mais fraca:

1. **Assinatura Web Bot Auth** (HTTP Message Signatures, RFC 9421). O cliente
   assina a requisição com uma chave Ed25519 publicada no domínio que ele
   declara no cabeçalho `Signature-Agent`. É criptografia, e não depende do
   user agent. O que ela prova é precisamente isto: **quem controla aquele
   domínio assinou** — qualquer um pode publicar chaves no próprio domínio, então
   o domínio *é* a identidade. O Google assina parte das requisições do
   `Google-Agent` desse jeito, em caráter experimental (documentação de
   2026-05-04), e a especificação ainda é um Internet-Draft.
2. **Faixas de IP publicadas.** OpenAI, Perplexity, Microsoft, Apple,
   Anthropic e Common Crawl publicam listas em JSON dos endereços dos seus
   crawlers. O IP da requisição dentro de uma faixa é identidade verificada.
3. **DNS reverso confirmado.** O nome reverso do IP termina no domínio
   documentado pelo fornecedor (`.search.msn.com` para o Bingbot,
   `.crawl.commoncrawl.org` para o CCBot) **e** esse nome resolve de volta para
   o mesmo IP. Sem a volta, o nome reverso é controlado por quem é dono do IP.

Desse processo saem os vereditos que a telemetria registra. O tipo é este,
copiado do código em produção:

```ts
// src/lib/crawler-verification.ts
export type Verdict =
  | 'verified-ip'
  | 'verified-signature'
  | 'verified-rdns'
  | 'impersonated'
  | 'unverifiable'
  | 'unknown-agent'

export interface VerificationResult {
  agent: string | null
  verdict: Verdict
  /** Which published source produced the verdict, for the log record. */
  evidence: string | null
}
```

Dois desses vereditos são achados, não falhas, e confundi-los seria o pior
erro possível neste tipo de medição:

- **`impersonated`** só existe quando havia uma fonte para conferir e a
  requisição falhou nela. Um IP fora das faixas da OpenAI alegando ser GPTBot
  é uma requisição **que alega ser GPTBot e não veio da OpenAI** — nunca "o
  GPTBot fez tal coisa".
- **`unverifiable`** é o fornecedor que não publica nada. Bytespider
  (ByteDance) e meta-externalagent (Meta) estão nesse grupo. Chamar esse
  tráfego de falso seria inventar uma prova que não existe.

Há ainda um atalho elegante: `Google-Extended` e `Applebot-Extended` são
**tokens de robots.txt**, não crawlers — os fornecedores documentam que nenhuma
requisição carrega esses nomes. Um user agent que alega ser um deles é falso
por construção.

A lista de quem publica o quê muda, e isso também é dado. A Anthropic publica
as faixas dos seus três agentes numa lista única, linkada de uma página de
2026-04-07; a Common Crawl publica faixas e DNS reverso. **Este site só
incorporou as duas em 2026-09-13** — até lá, as requisições que alegavam ser
desses agentes saíram como `unverifiable`. Uma lista de verificação envelhece
em silêncio; conferir as fontes antes de publicar qualquer número faz parte do
método.

## O honeypot: uma URL que só existe no robots.txt

O robots.txt deste site tem uma linha `Disallow` para uma rota de laboratório
com um nome aleatório. Essa URL não está no sitemap, não aparece na busca
interna, não tem link em página nenhuma — e não aparece neste artigo, pelo
mesmo motivo. O único jeito de chegar nela é **ler o robots.txt e escolher
buscar o que ele proíbe**. A lista de caminhos bloqueados é declarada assim:

```ts
// src/app/robots.ts
// O trap de robots (docs/detection-experiment.md §4) existe APENAS nesta
// linha de Disallow: fora do sitemap, fora do llms.txt, sem link de lugar
// nenhum. Quem chega lá parseou este arquivo e escolheu buscar o que ele
// proíbe. O trap de llms.txt (TRAP_LLMS_PATH) fica fora daqui de propósito —
// listá-lo contaminaria a atribuição de canal.
const DISALLOWED_PATHS = ['/api/', TRAP_ROBOTS_PATH]
```

Três limites precisam ser ditos junto:

- **O honeypot só pega quem lê o robots.txt.** Um cliente que nunca abre o
  arquivo nunca descobre a URL. Ele detecta desrespeito deliberado, não
  ignorância — uma afirmação mais estreita e mais forte.
- **Ele não identifica ninguém.** O robots.txt é o mesmo arquivo para todo
  mundo, então criar uma URL por agente não provaria nada. A atribuição vem da
  verificação de identidade do próprio acesso.
- **Não é uma armadilha punitiva.** Não gera lixo, não prende o cliente num
  labirinto de links, não tenta envenenar nada. A página explica o que é para
  quem cair nela, e envia `noindex` no cabeçalho. É a combinação que o
  [artigo sobre redirects e canonicals](/blog/redirects-canonicals-nextjs)
  desaconselha em página real — `Disallow` mais `noindex` —, usada aqui de
  propósito: quem obedece ao robots.txt nunca chega, e quem desobedece não
  consegue indexar.

Um segundo honeypot segue a mesma lógica para outro canal: uma URL que só
existe como link dentro do `llms.txt`. Um acesso a ela prova que o cliente lê
o `llms.txt` **e segue** os links do arquivo — a forma forte da pergunta "algum
agente usa llms.txt?".

## O delta dos dois pipelines

Crawler não executa JavaScript. Então a pergunta "esta requisição é de um
navegador?" tem uma resposta que não depende de cabeçalho nenhum: **houve uma
visita com JavaScript correspondente?**

O servidor registra toda requisição de página numa propriedade de analytics
separada. A propriedade das visitas humanas só recebe um evento quando o
JavaScript roda no navegador. Uma requisição de documento sem visita
correspondente é um cliente que não executa JavaScript. A confusão óbvia —
o visitante que recusa cookies — já estava eliminada por uma decisão anterior:
o Consent Mode deste site é do tipo avançado, então quem recusa o banner ainda
gera uma medição sem cookies.

Por requisição, a classificação usa o que o navegador sempre manda e um
cliente HTTP cru quase nunca manda:

```ts
// src/proxy.ts
function classifyUa(request: NextRequest, crawler: AiCrawler | undefined): UaClass {
  if (crawler) return 'declared-ai'
  const hasSecFetch = request.headers.has('sec-fetch-mode')
  const acceptsHtml = request.headers.get('accept')?.includes('text/html') ?? false
  return hasSecFetch && acceptsHtml ? 'browser-like' : 'unknown'
}
```

Nenhum endereço IP, cabeçalho bruto ou user agent completo sai do servidor.
Para correlacionar requisições da mesma rede sem identificar ninguém, a
telemetria registra um hash truncado da sub-rede, com um sal que muda todo
mês.

## Por que a maior parte do tráfego automatizado não se identifica

Se identificar só compensa para quem **quer ser reconhecido**. Buscadores
querem ser liberados no robots.txt. Os robôs que montam a prévia de um link no
WhatsApp ou no LinkedIn se declaram para receber as tags Open Graph.
Ferramentas de SEO publicam como verificar os próprios crawlers para não serem
bloqueadas. Do outro lado, quem teme bloqueio, limite de requisições ou
cobrança tem todo incentivo para parecer um navegador comum: scrapers que
passam por proxies residenciais, navegadores sem interface controlados por
script, varredores de vulnerabilidade — e agentes de IA que abrem páginas a
pedido de um usuário com um user agent de navegador.

O tamanho do fenômeno é grande e difícil de medir de fora. O relatório de bots
da Imperva publicado em 2026-04-29 estima o tráfego automatizado em 53% do tráfego
web de 2025, contra 47% humano — números de uma empresa que
vende proteção contra bots, com as definições dela. A Cloudflare só considera
"bot verificado" quem passa por Web Bot Auth ou validação de IP: todo o resto é,
por definição, não verificado, diga o user agent o que disser.

O caso público mais citado mostra por que é preciso cuidado ao atribuir. Em
2025-08-04 a Cloudflare acusou a Perplexity de usar crawlers não declarados,
com user agent de Chrome e rede trocada, para contornar bloqueios. A
Perplexity respondeu publicamente logo depois que a Cloudflare havia confundido
o tráfego dela com o de um serviço de navegador em nuvem de terceiros. As duas
versões seguem em disputa, e nenhuma delas é um fato estabelecido — que é
exatamente o ponto: sem identidade verificada, tráfego parecido com navegador
não tem dono.

## 28 dias em números

A primeira leitura cobre **16/08 a 12/09 de 2026** (28 dias). Estão excluídas
todas as requisições da rede do próprio autor em setembro — **687 eventos**,
entre eles os testes que o laboratório fez em produção (mais sobre isso na
próxima seção). Agosto não pôde ser filtrado do mesmo jeito, porque o
identificador de rede muda todo mês; a navegação do autor em agosto, se houve,
está nos números de navegador.

## O que a primeira leitura revelou: três defeitos no próprio instrumento

Um laboratório que só publica o que deu certo não é laboratório. A leitura
intermediária existia justamente para achar erro de coleta a tempo, e achou.

**1. Navegação humana contada como tráfego não identificado.** Toda visita num
navegador faz o Next.js pré-carregar os links visíveis da página com
requisições RSC, que levam o cabeçalho `rsc: 1` e não pedem HTML. A
classificação acima as marcava como `unknown`. A pista estava nos dados: as
seis páginas mais "acessadas" por clientes sem identificação a partir da rede
do autor eram exatamente os links do cabeçalho e do rodapé. Numa build local de
produção, uma única visita a um artigo pré-carregou essas mesmas seis rotas. A
correção tira essas requisições do proxy antes de qualquer contagem:

```ts
// src/proxy.ts
  matcher: [
    {
      source:
        '/((?!api/|_next/static|_next/image|images/|favicon.ico|icon.svg|opengraph-image|.*\\.(?:png|jpg|jpeg|webp|avif|svg|ico|woff2?)$).*)',
      missing: [
        { type: 'header', key: 'rsc' },
        { type: 'header', key: 'next-router-prefetch' },
      ],
    },
  ],
```

Para os dados anteriores à correção, a regra ficou registrada antes de
qualquer nova leitura: o grupo "não navegador" é o das requisições **sem**
cabeçalhos `Sec-Fetch-*`, que o navegador envia inclusive nas requisições RSC.

**2. Assinatura verificada sem o nome de quem assinou.** Como uma assinatura
Web Bot Auth prova apenas que o dono de um domínio assinou, o domínio é a
identidade inteira. O veredito era registrado; o domínio, não. As 64
requisições assinadas do período dizem "alguém assinou" e nada mais. Desde
13/09 o domínio do assinante é registrado junto.

**3. O formato atual do Web Bot Auth era recusado.** A versão de março de 2026
da especificação passou o cabeçalho `Signature-Agent` para um dicionário
(`agent1="https://…"`), que é o formato usado pelo Google. O verificador só
aceitava o formato anterior, então uma assinatura válida no formato novo nunca
seria verificada aqui. Corrigido também em 13/09.

**E um erro de processo.** O único acesso ao honeypot do robots.txt no período
foi um `curl` enviado pelo próprio laboratório durante uma auditoria de
indexação, em 2026-09-11. Nenhum crawler caiu na armadilha: fomos nós. O
acesso foi identificado, excluído junto com todo o tráfego da rede do autor, e
virou regra: qualquer requisição de teste enviada à produção é registrada no
plano de medição, com horário, antes do fim da sessão de trabalho.

## O que este site se proíbe de publicar

As regras vieram antes dos dados, e valem para este artigo e para o de
resultados:

1. Um agente só é **nomeado** como autor de um comportamento com três provas
   juntas: identidade verificada, observação datada neste domínio e o
   propósito declarado pelo próprio fornecedor.
2. Tráfego que **alega** ser um agente e falha na verificação é reportado como
   alegação — nunca sob o nome do fornecedor.
3. Contagens, datas e definições. Não adjetivos.
4. Toda classificação inferida é chamada de inferida, no texto e não em nota de
   rodapé.
5. Quando o fornecedor tem posição pública sobre o comportamento observado, ela
   aparece ao lado da observação.
6. Hipóteses que falharem são publicadas também.
7. Antes de publicar qualquer caso de falsificação, a verificação é refeita
   contra a lista do fornecedor baixada no dia, e a frase diz "fora das faixas
   publicadas em tal data".

Ignorar o robots.txt não é crime: o arquivo é um pedido voluntário. Este site
mede quem atende ao pedido, e não faz afirmação jurídica nenhuma.

## O que vem depois

As hipóteses do experimento foram registradas antes dos dados, com janelas de
90 dias que fecham por volta de 2026-10-23: se algum crawler cai no honeypot,
se algum agente de treino verificado busca página proibida, se o tráfego sem
identificação supera o declarado, se algum agente segue o `llms.txt`. O artigo
de resultados publica todas — inclusive as que não se confirmarem, e com os
números medidos pelo instrumento já corrigido.

O instrumento descrito aqui ganhou um controle positivo em setembro: visitas
de ChatGPT e Claude provocadas de propósito, com hora marcada, para conferir
que cada uma aparece no registro. Todas apareceram, e o teste mostrou também
[o que esses assistentes leem de uma página Next.js](/blog/chatgpt-le-javascript).

Para o lado técnico de como `robots.ts` e `sitemap.ts` são gerados neste site,
veja o [artigo sobre sitemap e robots dinâmicos](/blog/sitemap-dinamico-nextjs);
para o panorama completo de SEO técnico no App Router, o [guia de SEO técnico
para Next.js](/guia/seo-tecnico-nextjs). E para conferir o que o seu próprio
servidor responde a um crawler — robots, canonical, title e Open Graph lidos
direto do HTML —, use o [validador de meta tags](/ferramentas/validador-meta-tags).
